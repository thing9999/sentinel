## 1. 정보 우선순위 (3D 보기 탭 안)

1. **지금 보는 것이 언제·무엇인가** — 보기 머리 정보 줄(블록 수·관계 수·드리프트 계산 시각·MOCK·stale). 3D는 "지금 클러스터"가 아니라 **과거 기록**이라 이 줄을 항상 보인다.
2. **어디가 달라졌나** — 드리프트 표식(변경·삭제·추가·비교 불가)과 스캔 오류 표식. 표식이 있는 블록은 라벨 밀도와 무관하게 라벨을 항상 보인다.
3. **무엇이 무엇에 연결됐나** — 층·판·연결선, 선택 시 이웃 강조.
4. 개별 리소스 정보 — 선택 패널(종류·이름·경로·표식·관계 목록).
5. 이동 — [파일에서 보기] / [드리프트에서 보기].

- 1이 2보다 앞선다: 계산 시각을 모르면 표식을 현재 상태로 오해한다. 그래서 정보 줄은 캔버스 위에 상시 떠 있고 스크롤·회전으로 사라지지 않는다.
- 3D의 **입체감보다 표식의 가독성이 우선**이다. 표식·라벨은 3D 원근을 따르지 않는 2D 오버레이로 그려 거리와 무관하게 같은 크기(14px 아이콘, micro 11/14)를 유지한다.

## 2. 탭 · URL · 보기 기억

### 2.1 상세 탭에 3D 보기 추가 (K8S-D 4.5 표를 바꾼다)

| 순서 | id (`?view=`) | 라벨 | 아이콘·숫자 |
|---|---|---|---|
| 1 | `files` (기본) | `파일` | 기존 그대로 |
| 2 | `drift` | `드리프트` | 기존 그대로 |
| 3 | **`3d`** | **`3D 보기`** | **없음**(상태 아이콘·숫자 모두 없음) |
| 4 | `counts` | `리소스 수` | 기존 그대로 |
| 5 | `secrets` | `Secret 참조` | 기존 그대로 |
| 6 | `meta` | `메타데이터` | 기존 그대로 |

- 위치를 3번으로 두는 이유: 3D 보기는 새 데이터가 아니라 **파일 탭 + 드리프트 탭을 같이 보는 다른 방법**이다. 두 탭 바로 뒤에 두어 "같은 것을 다르게 보는 묶음"으로 읽히게 한다. 맨 뒤에 두면 참고 자료(리소스 수·Secret·메타) 뒤로 밀려 잘 발견되지 않는다.
- **숫자·상태 아이콘을 두지 않는 이유**: 3D 탭이 보여 줄 숫자(차이 N건, 발견 N건)는 이미 `드리프트`·`파일` 탭에 있다. 같은 숫자를 두 탭에 두면 어느 쪽을 눌러야 하는지 모호해지고, 상태 아이콘은 파일 상태 전용이라는 규칙(`status.md` 10.1)과 충돌한다.
- 탭 6개 폭 합계: `파일`(패딩 32 + 글자 28 = 60) + `드리프트`(32+56+숫자 26 = 114) + `3D 보기`(32+52 = 84) + `리소스 수`(32+62 = 94) + `Secret 참조`(32+82+26 = 140) + `메타데이터`(32+72 = 104) ≈ 596px. 1024px 뷰포트의 본문 976px 안에 들어가므로 가로 스크롤이 생기지 않는다.
- 파일 탭에 저장하지 않은 변경이 있는 채로 3D 보기로 가도 **편집 상태를 유지**한다(K8S-D 4.5와 같음). 3D 보기는 페이지를 떠나지 않는다.

### 2.2 URL

| 쿼리 | 값 | 기본값 | 설명 |
|---|---|---|---|
| `view` | `3d` | `files` | 상세 탭. 기존 값(`files`·`drift`·`counts`·`secrets`·`meta`)은 그대로 동작한다 |
| `gview` | `3d` \| `table` | 브라우저 저장소 값, 없으면 `3d` | 3D / 관계 표 전환. WebGL을 쓸 수 없으면 값과 무관하게 표(9.3) |
| `res` | 블록 ID(= `resourceKey` 형식 `<group\|core>/<Kind>/<ns\|_cluster>/<name>`) | 없음 | 선택한 블록. **드리프트 탭과 같은 쿼리 이름을 쓴다** |
| `gns` | 네임스페이스 이름 쉼표 목록 | 없음(전체) | 필터 |
| `gkind` | 종류 이름 쉼표 목록(`Deployment,Service`) | 없음(전체) | 필터 |
| `grel` | 관계 규칙 ID 쉼표 목록(`K1,K2,…`) | 없음 = 기본 켬 집합 `K1~K7` | 켠 관계 |
| `gmark` | `drift` \| `scan` \| `ghost` 쉼표 목록 | 없음 | 표식 필터. `drift,scan` = "문제 있는 것만" |
| `gq` | 검색어 | 없음 | 이름 부분 일치 |
| `glabels` | `all` \| `selected` \| `off` | 자동(4.7) | 라벨 밀도 |
| `gfocus` | `1` | 없음 | 주변만 보기(선택 블록 기준 한 단계) |
| `gdrift` | `0` | 없음(= 켬) | 드리프트 겹쳐 보기 끄기 |

- `res=`를 드리프트 탭과 **같은 이름으로 재사용**한다: 값의 뜻이 같고(리소스 키), 3D에서 블록을 고른 뒤 [드리프트에서 보기]를 누르면 `view`만 바뀌어 같은 리소스가 그대로 선택된다. 반대 방향(드리프트 → 3D)도 같다.
- 3D 전용 쿼리에는 모두 `g` 접두사를 붙인다. 기존 상세 쿼리(`file`, `line`, `res`, `kind`, `hidden`)와 **이름이 겹치지 않게** 하기 위해서다. 특히 드리프트 탭의 `kind=changed|deleted|added`와 3D의 종류 필터가 겹치면 탭을 오갈 때 값이 서로를 덮어쓴다.
- 3D 보기를 떠날 때 `g*` 쿼리는 **지우지 않는다**(돌아오면 같은 필터·선택). 스냅샷 ID가 바뀌면 `g*`와 `res`를 모두 비운다.
- 최종 쿼리 이름은 프론트가 정한다. 지켜야 할 것: ① 기존 5개 이름과 겹치지 않을 것 ② 선택은 `res` ③ 필터·검색·선택이 새로고침·링크 공유로 복원될 것(AC-3D10·12).

### 2.3 보기 기억 (AC-3D08)

- 사용자가 [3D | 표]를 바꾸면 `localStorage` `sentinel.snapshots.k8s.view3d` = `"3d"` \| `"table"`에 저장한다. 서버 요청 없음.
- 우선순위: `gview` 쿼리 > 저장소 > `"3d"`. **WebGL 없음·청크 실패·컨텍스트 손실은 저장소 값을 바꾸지 않는다**(환경 문제로 사용자의 선택을 덮어쓰지 않는다).
- 조작 도움말을 한 번이라도 열었는지는 `sentinel.snapshots.k8s.help3d`에 둔다.
- **범례 저장 키가 바뀐다(2026-09-20)**: 범례가 캔버스 밖 Popover가 되면서(6.5) 접힘 상태를 저장하지 않는다. 대신 **한 번이라도 열어 봤는지**만 `sentinel.snapshots.k8s.legendSeen` = `"1"`에 둔다(안 봤으면 버튼에 8px 점). 이전 키 `sentinel.snapshots.k8s.legend`는 **쓰지 않는다**(값이 boolean이라 뜻이 달라졌다. 남아 있어도 읽지 않는다).

## 4. 3D 장면 구성

### 4.0 단위와 좌표계

- 오른손 좌표계, **y 축이 위**. 판은 xz 평면.
- 이 문서의 모든 3D 치수는 u, 2D 오버레이(라벨·표식·도구)는 px다.
- **1u의 화면 크기는 카메라 거리에 따라 달라진다**: `px_per_u = 캔버스 높이 / (2 × 거리 × tan(17.5°))`.
- **기준 장면 (2026-09-20 (7) 확정 — 전부 frontend 실측값이다. 이 표가 이 문서의 모든 px 환산의 단일 출처다)**

| 항목 | 값 | 출처 |
|---|---|---|
| 스냅샷 | mock K-1 `20260919-061000` = 판 5장 · 블록 27개 · 관계 15개 | 그대로 |
| 뷰포트 · 테마 · 카메라 · 라벨 밀도 | 1440 × 900 · 라이트 · 기본 시점 · `전체` | 그대로 |
| **캔버스** | **766 × 616px** | 실측 (설계 636px − `SceneToolbar` 결과 수 줄바꿈 20px) |
| 안전 영역 (4.9-1) | **638 × 560px**, 중심 = 캔버스 좌상단 기준 **(331, 324)** | 계산 |
| 맞춤 영역 (4.9-1-1) | **586 × 508px**, 중심 동일 | 계산 |
| 기본 거리 `d0` | **≈ 179u** | 4.9-2 |
| **`px_per_u`** | **≈ 5.45** | `616 / (2 × 179 × tan17.5°)` |
| 블록 한 변 (4u) | **22px** | |
| 격자 셀 6u — 가로 / 깊이 | **28.4px / 23.1px** | 아래 투영 상수 |
| **층 한 칸 16u** (화면 세로) | **76px** | `16 × 0.866 × 5.45` (4.2 — 12u → 16u) |

| `d_read` 상한 (`s_min` 16px, h ≥ 600px) | **≈ 244u** — `d0`가 걸리지 않는다(`일부가 화면 밖` 칩 없음) | 4.9-2 |
| 맞춤 실측 | `fit` **1.00005** · `fillX` **0.9185** · `fillY` **0.8660** · `dx` **−0.013px** · `dy` **−0.002px** | frontend 2026-09-20 (6) |
| 라벨 실측 | 이름이 보이는 블록 **7 / 27** · `라벨 숨김` **20** · **`표식 숨김` 0** · 라벨이 블록을 덮지 않음 | 〃 |

- **캔버스 높이 이력**: 문서값 636px → 실측 576px((5) 시점, 도구 막대가 더 접혀 있었다) → **616px**(현재). 차이 20px은 `SceneToolbar`의 결과 수 줄바꿈(퍼블리셔 영역)이다. 3절의 작업 영역 식 `clamp(480px, calc(100vh − 176px), 960px)`은 **맞다** — (6)에서 적었던 "60px 어긋남"은 해소됐다.
- **`px_per_u`는 캔버스 높이가 바뀌어도 5.45로 거의 같다.** 기준 장면은 **가로가 먼저 차는 장면**(`fillX` 0.9185 = 맞춤 영역 폭 / 안전 영역 폭의 상한)이라, 거리가 캔버스 **폭**으로 정해지고 높이는 `d0`만 비례해서 움직인다. 캔버스 높이가 라벨 여유를 늘리는 방식은 `px_per_u`가 아니라 **`fillY`**(0.786 → 0.866)다.
- **이전 판들이 틀린 이유(기록)**: ① `px_per_u = 8`(판 4장·블록 150개)은 어떤 계산으로도 나오지 않는 값이었다 ② (5)의 `5.74`는 캔버스 636px + `d_fit × 1.06`을 전제로 한 값이다. (6)에서 `× 1.06`을 맞춤 영역으로 바꿔 실측 5.0 → **5.45**가 됐다.
- 기본 거리에서 **블록 한 변(4u)은 항상 `읽기 하한 s_min` 이상**이다(4.9). 캔버스 높이 600px 이상이면 16px, 480~599px이면 13px. 즉 `px_per_u ≥ 4.0`(큰 캔버스) / `≥ 3.25`(좁은 캔버스).

**투영 상수 (기본 시점 방위 −35°·고도 30°에서 고정)** — 4.7.1·4.9가 이 값을 쓴다.

| 세계 축 방향 1u | 화면 오른쪽 성분 | 화면 위 성분 | **화면 거리** |
|---|---|---|---|
| x (판 가로) | 0.819 | 0.287 | **0.868u** |
| z (판 깊이) | 0.574 | −0.410 | **0.705u** |
| y (위) | 0 | 0.866 | **0.866u** |

- 화면 right = `(0.819, 0, 0.574)`, 화면 up = `(0.287, 0.866, −0.410)`, 카메라 방향(대상 → 카메라) = `(−0.497, 0.5, 0.709)`.
- **여기서 나오는 결론이 4.7.1을 다시 쓰게 만들었다**: 격자 셀 6u가 화면에서 48px(= 6 × 8)이 되는 일은 없다. 깊이 방향 한 칸은 `6 × 0.705 = 4.23u`, 가로 방향 한 칸은 `6 × 0.868 = 5.21u`, 층 한 칸(16u)은 `13.86u`다. 기준 장면(`px_per_u = 5.45`)이면 각각 **23.1px · 28.4px · 75.5px**이다.
- **4.7.1이 쓰는 값** (기준 장면 `px_per_u = 5.45`, 위 상수에서 바로 나온다). `g`는 두 앵커의 화면 거리, `Δx`·`Δy`는 그 성분이다 — **라벨이 들어가느냐를 정하는 것은 `g`가 아니라 `Δx`다.**

| 이웃 | `Δx` (화면 가로) | `Δy` (화면 세로) | `g` |
|---|---|---|---|
| 같은 층 가로 이웃 (6u x) | **26.8px** | 9.4px | 28.4px |
| 같은 층 깊이 이웃 (6u z) | **18.8px** | 13.4px | 23.1px |
| 위 층 (16u y) | 0px | **75.5px** | 75.5px |

- **층 사이는 넉넉하고 층 안은 빡빡하다.** 이것이 이 장면의 성질이고 바뀌지 않는다. 층 간격은 3D 좌표라 늘릴 수 있지만(4.2에서 16u로 늘렸다) **층 안 이웃 간격 `Δx` 18.8~26.8px은 격자 셀·판 크기·카메라가 서로 상쇄해 늘릴 수 없다**(4.1). 그래서 층 안에 블록이 몰린 자리에서는 이름이 구조적으로 들어가지 않는다 — 4.7.1의 목표가 비율이 아니라 **불변**인 이유다.
- 원근 투영, 화각(수직 FOV) 35°. 원근이 강하면 뒤쪽 판의 블록 높이 비교가 어긋나므로 좁게 잡는다.

| 판 종류 | 모양 | 라벨 |
|---|---|---|
| 네임스페이스 판 | 두께 0.5u, 모서리 radius 1u, 면 `viz.plate.fill`, 윤곽 1px `viz.plate.edge` | `prod` captionStrong 12/16 `text.primary` + 4px + caption `text.tertiary` `리소스 42` |

| 클러스터 범위 판 (`_cluster/`) | 면 `viz.plate.fillAlt`, 판 맨 뒤 줄에 배치 | `클러스터 범위`(아이콘 `globe` 14px) |

**판 크기·배치 (2026-09-20 (5) 수치 조정)**

| 항목 | 이전 | **확정** |
|---|---|---|
| 판 여백(격자 바깥 좌우·앞뒤) | 3u | **2u** |
| 곁 띠 | 항상 3u | **곁(aux) 리소스가 있는 판만 3u, 없으면 0u** |
| 한 줄 판 수 | 최대 4장 | **최대 3장** |
| 판 간격 · 줄 간격 | 10u · 10u | **8u · 8u** |
| 최소 판 크기 | 18u × 18u | **14u × 14u** |

- 판 크기 = 각 층 격자의 폭·깊이 중 최댓값 + 여백 2u × 2 + 곁 띠(해당 판에 곁 리소스가 있으면 3u × 2), 최소 14u × 14u.
- 판 배치: 이름 오름차순으로 **왼 → 오**, 한 줄 최대 **3장**, 판 간격 8u, 줄 간격 8u. 클러스터 범위 → 해석 실패 순으로 맨 뒤 줄. 유령 판은 같은 줄 맨 끝.
- **왜 4장 → 3장인가**(위쪽 여백의 주원인): 방위 −35°·고도 30°에서 판을 가로로 늘어놓으면 화면 가로가 세로보다 훨씬 빨리 찬다. 판 5장을 4+1로 놓으면 장면의 투영 사각형이 **가로:세로 ≈ 1.54**가 되는데 안전 영역(4.9)은 **1.17**이라, 가로가 먼저 차고 **세로의 약 38%가 남는다**. 그 절반이 캔버스 위쪽 여백으로 보인다. 3+2로 놓으면 투영 비가 **1.32**로 내려가 남는 세로가 11%가 된다.
- 판 간격·여백을 줄인 이유는 같다. 기준 장면(판 5장·블록 27개)에서 위 수치를 적용한 뒤 frontend가 실측한 값은 **판 22u · `px_per_u` 5.0 · 이웃 간격 `g` 21~59px**이었다(적용 전 4.07 · 17~35px). 4.9-2의 여유 계산과 4.2의 층 16u까지 적용한 최종 실측은 **`px_per_u` 5.45 · `g` 23~76px**이다(4.0). **장면이 커지는 것이 라벨 문제의 절반을 푼다.**
- **격자 셀 6u는 바꾸지 않는다.** 셀을 키우면 판도 같은 비율로 커져 카메라가 그만큼 멀어지므로 화면상 이웃 간격 `g`는 거의 그대로다(장면 전체를 화면에 맞추는 한, `g`는 3D 단위가 아니라 `캔버스 크기 ÷ 가장 넓은 축의 블록 수`로 정해진다). 셀을 줄이면 블록 사이 틈(1u)이 사라져 윤곽이 붙는다.
- 배치는 여전히 결정적이다(AC-3D11). 위 값은 모두 상수다.
- 판은 선택할 수 없다(블록만 선택). 판 라벨을 누르면 그 판만 남기는 필터가 걸린다(`gns`에 추가).

**판 라벨 이름 앞 아이콘 (2026-09-20 (4) 확정 — 퍼블리셔 확인 3번)**

| 판 종류 | 이름 앞 아이콘 |
|---|---|
| 네임스페이스(보통·시스템) | **없음** |
| 클러스터 범위 | `globe` 14px |
| 해석 실패 | `file-warning` 14px `status.warn.fg` |
| 유령 판 | `circle-dashed` 12px `text.tertiary` |

- **보통 네임스페이스에 `folder`를 넣지 않는 이유**: ① 아이콘은 **다름을 알릴 때만** 쓴다. 판 대부분이 네임스페이스라 모든 라벨에 같은 글리프가 붙으면 뜻 없는 잡음이 된다 ② P0 이름 폭 200px에서 18px(아이콘 14 + 간격 4)을 먹고, P2·P3에서는 이름이 84·64px이라 아이콘이 이름을 밀어낸다 ③ 3D에서는 **판이라는 것이 모양(슬래브)으로 이미 보인다**.
- 관계 표 판 그룹 행(8.3)에는 `folder`를 **넣는다**. 거기서는 모양 단서가 없어 판 행인지 층 행인지 아이콘으로 갈리기 때문이다(같은 정보라도 자리에 따라 필요가 다르다).
- 유령 판은 P2·P3에서 caption `스냅샷에 없음`이 사라지므로 **단계와 무관하게** `circle-dashed`를 남긴다.

### 4.1.1 판 표식과 표시 문구 (계약 `plates[].markers` · `plates[].notes`)

판은 `<ns>/namespace.yaml` **문서 그 자체**다(4.2, 계약 16절 3). 그 문서의 스캔·드리프트·파일 문제·Helm은 블록이 아니라 **판**에 붙는다. 블록 표식(4.8)과 **뜻·순서·문구는 같고 모양만 다르다.**

| | 블록 표식 (4.8) | 판 표식 (여기) |
|---|---|---|
| 모양 | 18px **원** | 높이 20px **모서리 radius 4px 알약** |
| 위치(요약) | 블록 라벨 상자 맨 윗줄(4.8, 2026-09-20 변경) | 판 라벨 상자 세 번째 줄 |
| 배경·테두리 | `viz.label.bg` + 1px `border.default` | 같음 |
| 내용 | 아이콘 12px만(문구는 툴팁) | 아이콘 12px + 4px + 문구 micro 11/14 |
| 패딩 | 0 | 0 6px |
| 위치(상세) | 라벨 상자 맨 윗줄, 블록 중심에 가운데 정렬 | 판 라벨 **세 번째 줄**(아래 축소 사다리) |
| 최대 | 3개 + `+N`, 간격 4px | 3개 + `+N`, 간격 4px |

- 원 / 알약으로 **"이 표식이 블록 것인가 판 것인가"**를 구분한다. 색이나 아이콘으로 구분할 수 없다(축이 이미 종류·상태·드리프트 3개, `status.md` 11.1). 크기 차이만으로는 원근을 따르지 않는 2D 오버레이에서 읽히지 않는다.
- 판 표식에 문구를 붙이는 이유: 판은 **선택할 수 없어** 선택 패널로 상세를 볼 수 없다. 아이콘만 두면 마우스를 올리기 전에는 뜻을 알 수 없다.

**판 표식 목록** (순서 고정 — 블록과 같은 ① 스캔 → ② 드리프트 → ③ 파일 문제 → ④ Helm → ⑤ 정보)

| 순서 | 표식 | 아이콘 12px | 색 | 알약 문구 | 서버 값 |
|---|---|---|---|---|---|
| ① | 스캔 오류 | `octagon-x` | `status.crit.fg` | `오류 1` | `markers.scan.errors > 0` |
| ① | 스캔 경고 | `triangle-alert` | `status.warn.fg` | `경고 2` | `markers.scan.warnings > 0` |
| ② | 드리프트 변경 | `square-dot` | `text.secondary` | `변경 · 필드 1건` | `markers.drift.change = "changed"` |
| ② | 드리프트 삭제 | `square-minus` | `text.secondary` | `삭제됨` | `"deleted"` |
| ② | 비교 불가 | `eye-off` | `text.tertiary` | `비교 불가`(사유는 툴팁) | `"uncomparable"` + `reasonText` |

| ③ | 파일 문제 | `file-warning` | `status.warn.fg` | `markers.fileIssue.text`(`경로 불일치` 등) | `markers.fileIssue` |

| ⑤ | namespace.yaml 없음 | `file-question` | `text.tertiary` | `namespace.yaml 없음` | `notes[]`에 `namespace_file_missing` |

- 드리프트 `added`는 판에 오지 않는다. 스냅샷에 없던 네임스페이스는 **유령 판**(4.1)이고 라벨에 이미 `스냅샷에 없음`이 있다.
- `same`은 표식 없음(블록과 같다).
- 판 표식은 `summary.driftMarkers`·`summary.scanMarkers`에 **이미 들어 있다**(계약 10.1). 화면은 더하거나 빼지 않는다. 정보 줄의 `차이 3건`은 판 표식 + 블록 표식 합계다(AC-3D27).
- 판 표식은 **필터로 사라지지 않는다.** `gmark`·`gns`·`gkind`·`gq`는 블록만 거른다(9.2에서 판을 지우지 않는 것과 같은 이유 — 공간 기억 유지).

**클릭·툴팁**

| 알약 | 누르면 |
|---|---|
| 스캔 오류·경고, 파일 문제 | `?view=files&file=<plates[].navigate.file>&line=<markers.scan.firstLine ?? plates[].fileLine>` |

- 알약은 캔버스 안에서 **탭 정지점이 아니다**(캔버스는 정지점 1개, 11.1). 키보드·스크린리더 경로는 둘이다: ① `PageDown`/`PageUp`으로 그 판에 들어갈 때 `aria-live`가 읽는다 — `prod 판, 리소스 11개, 변경됨 필드 1건, 스캔 경고 2건` ② 관계 표 그룹 행(8.3)에 같은 알약이 **버튼**으로 있다.

**판이 많아도 겹치지 않게 — 라벨 축소 사다리**

판 라벨 상자는 판 앞 모서리 **왼쪽 끝**에 아래쪽을 맞추고(판 상면 위 8px) 위로 쌓는다(아래로 쌓으면 판을 가린다). 가용 폭 `A` = 같은 줄에서 **다음 판 라벨 앵커까지의 화면 거리 − 8px**(줄의 마지막 판은 200px).

| 단계 | 조건 | 판 라벨 |
|---|---|---|
| **P0** | `A ≥ 200px` | 3줄. ① 이름 captionStrong 12/16(최대 200px) + 시스템 Chip / 클러스터 아이콘 ② caption 11/14 `리소스 11 · 유령 5` ③ 알약 최대 3개 + `+N` |
| **P1** | `132 ≤ A < 200px` | 2줄. ① 이름(최대 `A`) ② 알약 최대 2개 + `+N`. 리소스 수는 툴팁으로 내린다 |
| **P2** | `84 ≤ A < 132px` | 2줄. ① 이름 가운데 말줄임 84px ② 알약 **1개로 합침** = 순위 1위 아이콘 + 총계 숫자(`▣ 4`), 툴팁에 전부 |
| **P3** | `A < 84px` | 1줄. 이름 가운데 말줄임 64px + 4px + 합침 알약(아이콘만, 폭 20px) |

- 줄 간 4px. 단계는 **판마다** 따로 정한다(줄 끝 판은 넓게 쓸 수 있다).
- **표식이 있는 판의 알약은 어느 단계에서도 지우지 않는다**(정보 우선순위 2, 1절). 사라지는 순서는 ① 리소스 수 → ② 이름 길이 → ③ 알약 문구 → ④ 알약 개수(합침)다. 표식이 없는 판은 P2·P3에서 이름만 남는다.
- 판 라벨끼리는 위에서 정리되므로 **줄을 바꿔 피하지 않는다**(4.1의 배치를 흔들면 "같은 입력 같은 배치"가 깨진다).
- 블록 라벨은 판 라벨과 겹치면 **블록 라벨을 숨긴다**(4.7의 "먼 라벨 숨김"과 같은 규칙, 판 라벨이 항상 이긴다).

### 4.2 층 (판 위 높이)

| 층 | 판 상면 기준 바닥 높이 | 무엇 | 색(5.2) |
|---|---|---|---|
| 저장·설정 | 0u | PersistentVolumeClaim, ConfigMap, Secret 참조(유령) | `viz.kind.storage` |
| 워크로드 | **16u** | Deployment, StatefulSet, DaemonSet, CronJob, Job | `viz.kind.workload` |
| 서비스 | **32u** | Service | `viz.kind.service` |
| 진입 | **48u** | Ingress | `viz.kind.ingress` |
| 곁 (판 가장자리 띠) | 0u | HPA, PDB, NetworkPolicy, ServiceAccount, Role, RoleBinding, ResourceQuota, LimitRange, 사용자 지정 리소스 | `viz.kind.aux` |

- **층 바닥 간격 9u → 10u → 12u → 16u (2026-09-20 (7) 확정 — frontend A·B·C·D 실측 비교에서 C안 채택)**
  - **왜 12u로는 모자랐나**: 블록 하나의 2D 오버레이 상자는 최대 **56px**(표식 18 + 4 + 이름 줄 16 + 2 + 보조 줄 16)인데 층 한 칸 12u는 화면에서 **57px**이라 여유가 1px뿐이었다. 라벨이 조금만 밀려 올라가도 위 층 블록·상자와 부딪혀 자리가 떨어졌다.
  - **16u = 76px**이면 여유가 **20px**이다. 오버레이 상자(56px)와 밀어 올리기 한 칸(8px)을 쓰고도 남는다.
  - **실측 근거**(frontend 2026-09-20 (6), 같은 장면·같은 규칙에서 네 안 비교): 층 16u만 바꾼 C안이 이름 5 → **7 / 27**, 19자리가 모두 막힌 블록 18 → **12**, 밀어 올려 구제된 블록 5 → **10**, **`fillY` 0.786 → 0.866**이 되면서 **유일하게 라벨이 블록을 덮지 않았다.** 다른 안(몸체 점유 축소·위쪽 절반만 금지)은 이름이 같거나 적으면서 라벨이 블록 몸통에 얹혔다.
  - **`px_per_u`는 거의 그대로다**(5.45). 기준 장면은 가로가 먼저 차는 장면이라 층을 높여도 거리가 바뀌지 않고, 늘어난 세로가 `fillY`를 채운다(4.0).
- **층을 더 높이지 않는 이유**: 20u 이상이면 세로가 먼저 차는 장면이 되어 이번엔 `fillX`가 내려가고 `px_per_u`가 같이 떨어진다(블록·글자가 작아진다). 16u는 **세로를 거의 다 쓰면서 가로 제약을 넘지 않는 값**이다.
- 프론트는 `graph/layout.ts`의 층 간격 상수 한 곳(`U.layerGap`)만 16으로 두면 된다(카메라·오버레이는 따라온다).
- 비어 있는 층은 자리를 차지하지 않는다(위 층이 내려온다). 판마다 층 높이가 다르면 판끼리 비교가 어려우므로 **한 스냅샷의 모든 판이 같은 층 높이**를 쓴다(그 스냅샷에 하나라도 있는 층만 남긴다).
- `namespace.yaml`은 블록으로 그리지 않는다. 판 자체가 그 리소스다. 판 라벨을 두 번 누르면 `namespace.yaml`로 이동한다.

| 면 | 층 색 `fill`, **밝기 3단 100 / 82 / 64%**(4.11의 양자화 규칙). **그림자 없음**(1,000 블록에서 비용이 크고, 그림자가 표식과 겹친다) |
| 윤곽 | 1px `viz.kind.*.edge` (화면 고정 굵기). 모양별 모서리 집합은 4.11 |

| 윗면 아이콘 | **없다** (2026-09-20 (5) 변경 — 아래) |

- **모서리 radius 0.25u 폐지 (2026-09-20 (8))**: 원래 목적은 "완전한 각을 피해 윤곽선이 읽히게"였는데, 기준 장면에서 0.25u는 **1.4px**이라 보이지 않는다(윤곽은 1px 선이 맡는다). 실제 구현에도 들어가 있지 않았고, 면취를 살리면 모양 8종의 삼각형 예산(4.11)을 먹는다.

- **같은 입력이면 같은 배치**(AC-3D11): 배치는 오직 ① 서버가 준 판·층·블록 순서 ② 위 규칙으로 정해진다. 난수·물리 시뮬레이션·force layout을 쓰지 않는다. 필터는 블록을 **숨기기만** 하고 자리를 다시 계산하지 않는다(빈 자리가 생긴다).
- 여러 문서(`---`)가 든 파일은 문서마다 블록 1개. 두 블록 모두 같은 파일로 이동하고, 블록 라벨 뒤에 caption `text.tertiary` `(문서 1/2)`를 붙인다.

**윗면 종류 아이콘 폐지 → 오버레이 12px 아이콘 (2026-09-20 (5) 확정 · 프론트 요청 ③ 승인)**

블록 윗면에 종류 아이콘을 **그리지 않는다.** 윗면은 층 색 `fill` + 1px 윤곽만이다. 종류 아이콘은 **블록 오버레이 상자의 이름 줄 맨 앞에 12px**로 둔다(색 `text.secondary`, 이름과 간격 4px). 4.7.1의 모든 단계에 들어가며, 이름이 사라지는 단계에서도 **아이콘은 마지막까지 남는다**.

- **왜 승인하는가**
  1. 원래 조건이 스스로 무너졌다. 4.3은 "블록 윗면 한 변이 16px 미만이면 그리지 않는다"였는데, 기준 장면의 블록 한 변이 **16~23px**이다. 16px 아이콘을 16~23px 면에 얹으면 아이콘이 면을 거의 다 덮어 **층 색(= 층 구분)이 사라진다.** 예외가 아니라 상시 상태였다.
  2. 기본 시점 고도가 30°라 윗면은 항상 `sin 30° = 0.5`로 눌려 보인다. 25° 조건을 겨우 넘는 자리에서 그리는 아이콘은 찌그러진 글리프다.
  3. 아이콘 아틀라스 텍스처는 3D 청크를 키우고(AC-3D02 예산), 색이 `--color-viz-*`에서 오므로 **테마 전환마다 다시 구워야** 한다.
  4. 오버레이 아이콘은 원근을 따르지 않아 거리와 무관하게 같은 크기다 — 1절("입체감보다 표식·라벨의 가독성이 우선")과 오히려 더 맞는다.
- `viz.kind.*.onFill` 토큰은 **지우지 않는다**(범례·2단계 묶음 블록용으로 남긴다). 1단계에서 쓰는 자리는 없다.
- 묶음 블록(9.7)도 같다 — 윗면 아이콘 대신 묶음 라벨(`ConfigMap 412`) 앞에 12px 아이콘.

### 4.4 유령 블록

면을 그리지 않고 **1.5px dashed `viz.ghost.edge` 윤곽선만** 그린다(면 `viz.ghost.fill`, 불투명도 `opacity.vizGhost` 0.35). 상태색(`unknown` 포함)을 쓰지 않는다.

- **모양은 그 종류의 모양 그대로다**(4.11). 유령이라고 모양을 바꾸지 않는다 — 유령도 "무엇이 없는가"를 말해야 하고, 그 답의 절반이 종류다. 유령 Secret은 `chamfer` 윤곽, 유령 ServiceAccount는 곁 타일 윤곽이다.

| 경우 | 라벨 뒤 사유 문구 | 표식 |
|---|---|---|
| 참조 대상이 스냅샷에 없음 | `스냅샷에 없음` | `circle-dashed` |
| Secret 참조 | `Secret — 이름만, 값 없음` | `circle-dashed`만 (**2026-09-20 변경**: `key-round`는 Secret의 **종류 아이콘**이 되어 윗면·패널·표에 이미 있다. 표식으로 한 번 더 두면 같은 아이콘이 한 블록에 두 번 나온다 — 4.10) |
| ServiceAccount `default` 등 | `자동 생성 또는 스냅샷에 없음` | `circle-dashed` |
| RoleBinding이 가리키는 ClusterRole | `클러스터 범위, 스냅샷에 없을 수 있음` | `circle-dashed` |
| 드리프트 `added`(클러스터에만 있음) | `추가됨` | `square-plus` + `circle-dashed` |

- 유령 블록은 자기 층의 격자에 **정상 블록 뒤에** 놓는다(같은 층 마지막 줄부터).
- 유령 블록은 선택할 수 있고 패널도 열린다. 이동 버튼만 다르다(10.4).

**언제 보이나 (계약 `ghostFromRules`, 계약 16절 4)**

서버는 유령 블록을 **항상** 응답에 담는다(표·개수에서 빠지지 않게). 숨기는 것은 화면이다.

| 유령 | 보임 조건 |
|---|---|
| 관계가 만든 유령(`ghostFromRules`에 규칙 있음) | `ghostFromRules`의 규칙이 **하나라도 켜져 있으면** 보인다. 전부 꺼지면 그 블록과 들어오는 선을 함께 숨긴다 |
| 드리프트 `drift_added`(`ghostFromRules` 빈 배열) | 관계 필터와 무관하게 보인다. **드리프트 겹쳐 보기를 끄면(`gdrift=0`) 숨긴다** |

- 적용 순서: ① 관계 필터(`grel`)로 유령 숨김 → ② 드리프트 겹쳐 보기 → ③ `gns`·`gkind`·`gq`·`gmark`. `gmark=ghost`는 ①에서 숨은 유령을 **되살리지 않는다**(켜지 않은 관계의 상대를 표식 필터로 끌어오면 두 필터가 서로를 덮는다).
- 기본 켬 집합(K1~K7)에서는 K9가 만든 ServiceAccount 유령이 숨는다. 이것은 **"필터를 건 상태"로 세지 않는다**: 정보 줄은 `블록 27 · 관계 15`처럼 **그린 수**만 적고 툴팁에 `전체 블록 33(유령 9) · 전체 관계 26`을 붙인다. 사용자가 기본 집합에서 무엇이든 바꾸면 그때부터 `블록 33개 중 12개` 형식으로 바뀐다(6.1).
- 관계 표도 **같은 규칙으로 행을 숨긴다**(필터는 두 보기에 똑같이 걸린다, 6.1·AC-3D04). 표 위 요약 문구도 같은 수치를 쓴다.

### 4.5 연결선

| 항목 | 값 |
|---|---|
| 모양 | 2차 베지어. 출발 = 근원 블록 밑면 중심, 도착 = 대상 블록 윗면 중심(같은 층이면 옆면 중심). 제어점 = 두 점 중점 + 위로 (두 점 거리 × 0.18) |
| 확정 | 실선 1.5px `viz.edge.confirmed` |
| 추정 | **dashed 6 3**, 1.5px `viz.edge.estimated` |
| 방향 | 대상 쪽 끝에 삼각형 머리 8px(선과 같은 색) |
| 강조(선택·hover) | 3px, 색 `viz.edge.highlight`, 머리 10px. 나머지 선은 `opacity.vizDimmed` 0.25 |
| 흐림(주변만 보기 꺼짐 + 선택 있음) | 1px, `viz.edge.dimmed` |
| `optional: true` 참조 | 추정과 같은 대시에 불투명도 0.6, 선택 패널·표에 `선택 참조` 칩 |

- 선 색은 **중립 한 가지**다. 관계 종류는 색이 아니라 ① 두 블록의 층(어디서 어디로 가는지) ② 선택 패널·관계 표의 근거 문구로 구분한다. 관계 11종에 색 11개를 쓰면 종류 팔레트와 충돌하고 색맹 환경에서 무너진다.
- **확정 / 추정만 선 모양으로 구분**한다(실선 / 대시). 이 구분은 "이 선을 믿어도 되나"라는 판단에 바로 쓰이므로 색 없이도 읽혀야 한다.
- 선을 못 그리는 경우는 **선을 지어내지 않는다**. 대신 블록에 표시 문구를 붙인다: `대상 없음`, `셀렉터 없음(수동 Endpoints·ExternalName)`, `PVC 템플릿 2개(스냅샷에 PVC 없음)`. 표시 문구는 블록 라벨 아래 줄 micro 11/14 `text.tertiary`, 선택 패널·관계 표에도 같은 말로.
- 해석 실패 구역의 블록에는 선을 그리지 않는다.
- 보기 안 상시 안내(정보 줄 옆 `circle-help` 14px, 툴팁): `선이 없다고 관계가 없는 것은 아닙니다. 이 보기는 규칙 11가지(K1~K11)로 찾은 관계만 그립니다.`

- 라벨 밀도(도구 막대 B): `전체` / `선택·검색 결과만` / `끄기`.

### 4.7.1 블록 라벨 겹침 규칙 (2026-09-20 신설 — 판 라벨의 P0~P3에 대응)

판 라벨에는 축소 사다리가 있는데 블록 라벨에는 없어서, 블록이 한 판에 몰리면 이름이 서로 겹쳐 읽히지 않는다(프론트 1단계 스크린샷 확인). 블록 라벨도 **① 우선순위 → ② 축소 단계 → ③ 격자 점유 → ④ 숨김** 네 단계로 정리한다.

**① 우선순위 점수** (높을수록 살아남는다. 동점이면 8.2 기본 정렬이 앞선 블록)

| 점수 | 대상 |
|---|---|
| 1000 | 선택한 블록(`res=`) |
| 900 | 지금 가리키는(hover) 블록 |
| 800 | 검색 결과 블록 |
| 700 | 스캔 **오류** 표식이 있는 블록 |
| 600 | 그 밖 표식(스캔 경고·드리프트·파일 문제·유령)이 있는 블록 |
| 500 | 선택한 블록과 선으로 이어진 이웃 |
| 0~400 | 나머지. `400 × (1 − 카메라 거리 / 최대 거리)` — 가까울수록 높다 |

**수용 기준 (2026-09-20 (7) 확정 — 비율 목표를 없애고 불변만 남긴다)**

> **기본 시점에서 이름이 보이는 블록 수는 장면 규모에 따라 달라진다. 목표로 두지 않는다.**
> 기준 장면(4.0 = mock K-1 · 블록 27개 · 캔버스 766 × 616px · 라벨 밀도 `전체`)의 **관측치는 7 / 27**이다. 이 수를 올리는 것이 이 절의 목적이 아니다.

**불변 — 어떤 장면·어떤 카메라에서도 지킨다(깨지면 규칙 위반이므로 고치거나 보고한다)**

| # | 불변 | 어떻게 지키나 | 확인 방법 |
|---|---|---|---|
| 1 | **표식은 지우지 않는다** | B4에서 자리가 없어도 표식 줄은 **겹쳐서라도** 그린다(④) | 정보 줄 `표식 N개 숨김` = **0** (칩이 뜨지 않는다) |
| 2 | **표식이 있는 블록은 이름도 보인다** | ②-1의 **최소 B2 보장**. 자리를 다투면 점수가 낮은 라벨을 먼저 치운다 | 표식 블록 수 = 그중 이름이 보이는 수 |
| 3 | **라벨이 블록을 덮지 않는다** | ③의 **블록 몸체 점유**(한 변 `4u × px_per_u`) | 몸체 침범 0 (스크린샷 확인) |
| 4 | **숨긴 것은 반드시 고지한다** | `라벨 N개 숨김` 칩 + 누르면 관계 표(④) | 칩의 N = 이름 글자가 하나도 없는 블록 수 |
| 5 | **카메라 맞춤** | 4.9 | `fit` 0.98~1.02 · `max(fillX, fillY) ≥ 0.90` · `\|dx\|·\|dy\| ≤ 4px` |
| 6 | **결정적** | 난수·물리 시뮬레이션 없음, 후보 자리 고정 순서 | 같은 입력·같은 카메라면 같은 결과 (AC-3D11) |

- "이름이 보인다" = 오버레이 상자에 이름 글자가 **4자 이상** 그려진다(B3 이상). 말줄임이 붙어도 보이는 것으로 센다.
- **왜 비율 목표를 버리는가.** 80%(22개) → 74%(20개) → 실측 7개로 세 번 빗나갔다. 원인은 조정 부족이 아니라 **장면의 성질**이다: 층 **사이**는 76px로 넉넉하지만 층 **안** 이웃은 `Δx` 18.8~26.8px이고(4.0), 이 값은 격자 셀·판 크기·카메라가 서로 상쇄해 **늘릴 수 없다**(4.1). 이름 한 줄의 최소 폭이 52px(B3)이므로 **층 안에 블록이 몰린 자리에서는 이름이 물리적으로 들어가지 않는다.** 도달할 수 없는 수를 수용 기준에 남겨 두면 매 판마다 "미달"만 반복되고, 더 나쁘게는 **불변(표식·겹침 금지)을 깎아서 비율을 올리려는 압력**이 생긴다.
- 실제로 그 압력이 한 번 확인됐다: 블록 몸체 점유를 `4u → 2u`로 줄이면(A안) 이름이 7 → 9개가 되지만 **라벨이 블록 몸통 위 절반을 덮는다.** 이름 2개와 불변 3번을 맞바꾸는 것이라 **불채택**했다(2026-09-20 (7) PM 결정).
- **이름 전수 확인은 3D의 일이 아니다** — 아래 「이름을 읽는 경로」.

**이름을 읽는 경로 (2026-09-20 (7) 신설 — 원칙)**

**3D 보기는 구조를 파악하는 화면이고, 이름을 하나하나 확인하는 일은 관계 표가 맡는다.** 기본 시점에 모든 이름이 동시에 떠 있어야 할 이유가 없다.

| 경로 | 무엇을 준다 | 어디 |
|---|---|---|
| **① 확대(줌)** | 가까이 갈수록 `g`가 커져 단계가 올라간다. `+` 키·휠로 2~3단만 당기면 그 구역의 이름이 다 뜬다 | 4.9 확대·축소 |
| **② 가리키기(hover)** | 가리킨 블록**과 이어진 이웃까지** B0(②-1) + 툴팁 `Deployment · api` | 4.7.1 ②-1 |
| **③ 고르기 → 선택 패널** | 종류·이름 전체·네임스페이스·파일 경로·표식·관계 목록. **이름이 잘리지 않는다** | 7절 |
| **④ 관계 표(`gview=table`)** | **모든 블록의 전체 이름**이 잘리지 않고 한 화면에. 3D와 **수치가 같다**(AC-3D04) | 8절 |
| ⑤ 검색(`gq`) | 이름 부분 일치 → 결과 블록은 점수 800이라 **단계와 무관하게 B0** | 6.2 |

- `라벨 N개 숨김` 칩을 누르면 **④로 간다**(④ 숨김과 알림). 이 칩이 그 원칙을 사용자에게 말하는 자리다.
- 그래서 라벨 밀도 기본값이 `전체`여도 **모든 이름이 보이지 않는 것이 정상**이고, 화면은 그 사실을 칩으로 고지한다. 감춰진 것이 있다는 사실을 말하지 않는 것만이 잘못이다(불변 4).
- 기록: 1단계 `라벨 17개 숨김` → (5) 19 → (7) **20**. 그동안 함께 고친 것들은 헛되지 않았다 — **표식 숨김 6 → 0**, 장면 크기 `px_per_u` 4.07 → **5.45**, `fillX` 0.79 → **0.92**, `fillY` 0.786 → **0.866**, 라벨이 블록을 덮는 일 **없음**. **불변 쪽이 전부 좋아졌고, 비율만 제자리다.** 그것이 이 절의 결론이다.

**② 축소 사다리 B0~B4 (임계값·폭 전면 조정)** — 기준은 **이웃 간격 `g`**: 이 블록의 앵커(윗면 중심의 화면 좌표)에서 **가장 가까운 다른 블록 앵커까지의 화면 거리(px)**.

**왜 이전 값(96 / 64 / 40px)이 틀렸나.** 이전 판은 "격자 셀 6u = 48px"을 전제로 했는데, 6u는 화면에서 48px이 되지 않는다. 기본 시점(방위 −35°·고도 30°)에서 셀 한 칸의 화면 거리는 깊이 방향 `6 × 0.705 = 4.23u`, 가로 방향 `6 × 0.868 = 5.21u`다(4.0 투영 상수). `px_per_u = 5.45`이면 **23px · 28px**이고, 층 한 칸(16u)은 76px이다. 즉 **`g`는 어떤 장면에서도 거의 늘 23~76px 구간에 있고**, 40px 미만을 전부 B3(표식만)로 내리면 대부분의 이름이 사라진다. 임계값을 실제 도달 구간에 맞춘다.

**임계값과 상자 폭은 (6)·(7)에서도 바꾸지 않는다.** frontend 실측 `g`(21 · 39 · 59px @ `px_per_u` 5.0 → 23 · 43 · 76px @ 5.45)가 아래 B3~B0 구간에 그대로 들어맞았다. **못 맞춘 원인은 단계가 아니라 자리였고**, 자리는 층 간격 16u(4.2)와 후보 19개(③)로 넓힐 수 있는 만큼 넓혔다. **이 표를 더 건드리지 않는다** — 이름 폭 36px(B3)이 "4자 + 말줄임"의 하한이라 더 줄이면 읽을 수 없는 글자를 세게 된다.

| 단계 | 조건 | 오버레이 상자 (폭 = 아이콘 12 + 4 + 이름) | 이름 |
|---|---|---|---|
| **B0** | `g ≥ 72px` | 136px. 표식 줄 + [아이콘 + 이름] + 보조 줄 | 최대 **120px**, 가운데 말줄임 뒤 8자 보존 |
| **B1** | `48 ≤ g < 72` | 104px. 표식 줄 + [아이콘 + 이름]. **보조 줄은 툴팁·선택 패널로 내린다** | 최대 **88px**, 뒤 8자 보존 |
| **B2** | `28 ≤ g < 48` | 76px. 표식 줄 + [아이콘 + 이름] | **60px**, 가운데 말줄임 뒤 **6자** 보존 |
| **B3** | `18 ≤ g < 28` | 52px. 표식 줄 + [아이콘 + 이름] | **36px**, 가운데 말줄임 뒤 **4자** 보존 |
| **B4** | `g < 18` | 20px. 표식 줄 + [아이콘]만 | 없음 |

- 글자 크기는 **모든 단계에서 micro 11/14 그대로**다. 작은 글자 단계를 새로 만들지 않는다(11px 미만은 `typography`에 없고, 새 값을 넣을 근거가 "겹쳐서"뿐이라 약하다). 줄이는 것은 **폭**이지 크기가 아니다.
- **이름 줄은 언제나 한 줄**이다(두 줄 이름은 만들지 않는다). 두 줄로 나누면 상자 높이가 14px 늘어 위 층 라벨을 밀어낸다 — 세로는 가로보다 훨씬 귀하다(층 간격 76px 안에 상자 56px + 밀어 올림이 들어가야 한다).
- **상자 높이**(③이 쓰는 값): 표식이 없는 블록 = 이름 줄 하나 → **16px**(글자 14 + halo 위아래 1px). 표식이 있으면 18 + 4 + 16 = **38px**. B0에서 보조 줄까지 있으면 16 + 2 + 38 = **56px**. 8px 격자에서는 각각 **2칸 · 5칸 · 7칸**을 먹는다.
- 버리는 순서는 항상 **① 보조 줄 → ② 이름 글자 수 → ③ 이름 전체 → ④ 표식**이다. 표식은 마지막까지 남는다(정보 우선순위 2, 1절).
- **B4에서도 종류는 알 수 있다**: 종류 아이콘 12px과 층 색이 남고, 가리키면 툴팁 `Deployment · api`가 뜬다. 윗면 아이콘을 폐지(4.3)하면서 이 역할이 오버레이 아이콘으로 옮겨 왔다.
- 기준 장면에서 단계가 잡히는 모양: 층에 블록이 1개뿐인 자리는 `g ≈ 76px`(층 한 칸) → **B0**, 같은 층에 가로로 2~3개면 `g ≈ 28px` → **B2**, 깊이 방향으로 붙으면 `g ≈ 23px` → **B3**.
- **실측 단계 분포**(그려진 22개, 2026-09-20 (7)): B0 1 · B1 3 · B2 2 · B3 1 · **B4 12**. B4 12개는 `g`가 18px 미만이어서가 아니라 **19자리가 모두 막혀 단계를 끝까지 내린 결과**다(③). 즉 이 장면에서 한계는 `g`(단계)가 아니라 **자리**다.

**②-1 우선순위에 따른 하한 (선택·호버 예외 확대)**

| 점수 | 보장 |
|---|---|
| 1000 (선택) · 900 (hover) · 800 (검색 결과) | **단계와 무관하게 B0**, z-order 맨 위 |
| **900 (hover) — 추가** | 가리킨 블록과 **선으로 이어진 이웃 블록들도 함께 B0**로 올린다. 27블록 화면에서 이름을 읽는 주된 수단이 "마우스를 올려 그 주변을 읽는 것"이 되게 한다 |
| 700 (스캔 오류) · 600 (그 밖 표식) | **최소 B2**(이름이 반드시 보인다). 자리가 없으면 ③의 밀어 올리기를 먼저 쓰고, 그래도 없으면 **주변의 점수가 낮은 라벨을 먼저 숨긴다** |
| 500 (선택 블록의 이웃) | 최소 **B3** |
| 0~400 | 사다리 그대로 |

- 이전 규칙 "겹치면 **카메라에서 먼 쪽**을 숨긴다"를 **"점수가 낮은 쪽을 숨긴다"**로 바꾼다. 카메라 거리는 이미 0~400점에 들어 있어(가까울수록 높다) 같은 뜻을 두 번 적용하고 있었고, 그 때문에 **표식이 있는 먼 블록이 표식 없는 가까운 블록에 졌다.**

**③ 격자 점유 + 자리 후보 19개 (2026-09-20 (6) 전면 개정 — frontend 실측 원인 해소)**

**무엇이 틀렸나.** (5)의 규칙은 상자를 **블록 가로 중심에 고정**하고 세로로만 32px 옮겼다. 그런데 기준 장면에서 같은 층 가로 이웃의 화면 x 거리는 `Δx = 26.8px`, 깊이 이웃은 `18.8px`인데 B2 상자는 **76px**이다. 상자가 이웃 간격의 2~4배라 **가로로는 어떤 경우에도 겹치고**, 세로 32px은 상자 높이(16~38px)의 한두 칸뿐이라 한 층에 3개만 모여도 자리가 떨어졌다. 그 결과가 `이름 9/27`이다. 고칠 것은 임계값이 아니라 **자리 후보의 수와 모양**이다.

**이 규칙은 2026-09-20 (7)에서 확정이다.** 층 간격 16u(4.2)까지 합쳐 실측 이름 7 / 27, `표식 숨김` 0, 몸체 침범 0. **더 올리려면 불변을 깎아야 하므로 여기서 멈춘다**(위 「수용 기준」).

**점유하는 것** — 화면을 **8 × 8px 격자**로 나눈다. 라벨을 놓기 전에 아래 둘을 **미리 점유**한다.

| 미리 점유 | 사각형 |
|---|---|
| 판 라벨 상자 (4.1.1) | 그 단계(P0~P3)의 상자 그대로. 블록 라벨이 언제나 진다 |
| **모든 블록의 몸체 (2026-09-20 (6) 신설, (7) 유지 확정)** | 앵커(윗면 중심)를 중심으로 한 변 `4u × px_per_u`인 정사각형(기준 장면 **22px**). **자기 블록은 제외한다** |

- **블록 몸체를 점유에 넣는 이유는 두 가지다.** ① 라벨이 다른 블록을 덮으면 그 블록은 층 색도 표식도 읽을 수 없다 ② 이것이 **소유 관계를 보장하는 장치**다 — 상자가 다른 블록의 앵커를 덮을 수 없으므로 "이 이름이 어느 블록 것인가"가 애매해지지 않는다. 그래서 아래 가로 비킴을 안심하고 쓸 수 있다.
- **사각형을 `4u`에서 줄이지 않는다 (2026-09-20 (7) PM 결정).** `2u`(≈11px)로 줄이거나 "몸체 위쪽 절반만 금지"로 바꾸면 기준 장면에서 이름이 7 → **9개**로 늘지만, 실측에서 **라벨이 블록 몸통 위 절반을 덮었다**(frontend A·B·D안). 이름 2개와 「불변 3. 라벨이 블록을 덮지 않는다」를 맞바꾸는 거래라 **하지 않는다.** 라벨은 블록을 가리키는 것이지 블록을 대신하는 것이 아니다.

**자리 후보 19개** — 상자는 `(세로 밀어 올림 n, 가로 비킴 o)`로 놓는다. 상자 바닥 = 블록 윗면 중심 위 `6 + n` px, 상자 가로 중심 = 블록 앵커 x + `o`.

```
n ∈ { 0, 8, 16, 24, 32, 40, 48 }                  // 7단계, 8px 격자에 맞춘다
o_max = max(0, 상자 폭 ÷ 2 − 12px)                 // B0 56 · B1 40 · B2 26 · B3 14 · B4 0
o ∈ { 0, −o_max, +o_max }                          // n = 0 에서는 o = 0 하나뿐
후보 수 = 1(n=0) + 6 × 3 = 19
시도 순서 = n 오름차순 → 각 n 안에서 0 → −o_max → +o_max
```

- **`o_max = 상자 폭/2 − 12px`인 이유**: 이 범위 안에서는 **블록 앵커가 늘 상자의 가로 범위 안에 있고, 상자 가장자리에서 12px 이상 안쪽**이다. 그래서 ① 지시선이 여전히 **수직 한 줄**이고(꺾인 선·대각선을 만들지 않는다) ② 상자가 자기 앵커 위에 걸쳐 있어 소유가 눈에 보인다.
- **이 한 가지가 문제를 푼다**: 가로로 이웃한 두 블록이 서로 반대쪽으로 비키면 상자 중심 거리가 `Δx + 2 × o_max = Δx + 상자 폭 − 24px`가 된다. 겹치지 않을 조건은 `Δx + 상자 폭 − 24 ≥ 상자 폭`, 즉 **`Δx ≥ 24px`** — **상자 폭과 무관하다.** 기준 장면의 같은 층 가로 이웃은 `Δx = 26.8px`이라 **어느 단계에서든 짝이 나란히 들어간다.** (깊이 이웃은 `Δx = 18.8px`로 미달이지만 `Δy = 13.4px`가 있어 밀어 올림 한 칸이면 풀린다.)
- **밀어 올림 한도는 48px로 고정한다**(32px에서 올렸다). 근거 둘: ① 표식 없는 상자(16px)를 기준으로 겹치지 않는 세로 칸이 `0 · 16 · 32 · 48` **4칸**이 되어, 한 층에 가로로 몰린 블록 **4개**까지 이름이 들어간다(32px이면 3칸·3개였다) ② 층 한 칸의 화면 세로 거리 **76px**(4.0, 층 16u)보다 작아 라벨이 위 층 **앵커**를 넘어가지 않는다.
  - **층이 16u가 됐다고 이 값을 더 올리지 않는다.** 76px 안에서 48px을 쓰면 상자 56px과 합쳐 위 층 앵커까지 20px이 남는다. 이 여유가 없어지면 밀어 올린 라벨이 위 층 블록에 붙어 **어느 층 것인지** 읽히지 않는다(층 색은 라벨이 아니라 블록에 있다). 실측에서도 48px로 구제된 블록이 5 → **10개**로 늘어 한도가 병목이 아님이 확인됐다.
  - (5)의 "32px은 위 층 블록을 넘어가지 않는다"는 근거는 **블록 몸체 점유로 대체된다.** 상자 윗부분이 위 층 블록의 높이에 닿더라도 그 블록의 22px 사각형이 이미 점유돼 있어 **덮을 수 없고** 비킴 후보로 넘어간다.
- **지시선**: `n ≥ 8`이면 블록 윗면 중심에서 상자 바닥까지 **1px 세로 지시선**(`border.default`). 상자와 같은 z-order, 화살표·꺾임 없음. `n = 0`이면 지시선 없음(6px이라 보이지 않는다). **가로로 비킨 상자는 `n ≥ 8`이므로 언제나 지시선이 있다** — 이것이 가로 비킴의 소유 단서다.
- 후보 순서가 `n` 우선인 이유: 세로로 멀어지면 **어느 층 것인지**가 흐려지고, 가로로 비끼는 것은 층을 바꾸지 않는다. 그래서 같은 `n` 안에서 가로를 먼저 다 쓰고 다음 `n`으로 간다.

**놓는 순서**

1. 점수(①) 내림차순으로 한 번 훑는다. 동점이면 8.2 기본 정렬.
2. 그 블록의 단계(②)에서 후보 19자리를 순서대로 본다. 비어 있는 첫 자리에 놓고 그 칸들을 점유한다.
3. 19자리가 모두 막히면 **한 단계 내리고**(B0→B1→…→B4) 2번부터 다시 한다. 단계가 내려가면 상자 폭이 줄어 `o_max`도 줄지만, 폭이 줄어든 만큼 필요한 자리도 작아진다.
4. B4(아이콘만)에서도 19자리가 모두 막히면 **④ 숨김**.

- ②-1의 하한(표식 있는 블록 최소 B2 등)은 3번의 **바닥**으로 동작한다. 바닥에서 19자리가 모두 막히면 단계를 더 내리지 않고, **그 자리를 막고 있는 라벨 중 점수가 가장 낮은 것을 먼저 치운다**(④).
- 난수·반복 최적화·물리 시뮬레이션을 쓰지 않는다. **점수 정렬 → 한 번 훑기(greedy) → 후보 19자리 고정 순서**라 같은 카메라면 결과가 같다. 블록당 최대 19 × 5단계 = 95회 사각형 검사이고, 1,000 블록에서도 250ms 주기 안에 끝난다.

**④ 숨김과 알림** — B4(아이콘만)에서도 겹치면 **점수가 낮은 쪽을 숨긴다.** 숨긴 것이 있으면 정보 줄에 칩을 둔다(6.4-8 자리).

| 숨긴 것 | 칩 | 툴팁 |
|---|---|---|
| 이름 라벨 | `라벨 N개 숨김` (`eye-off` 12px `text.tertiary`) | `겹쳐서 이름을 숨겼습니다. 확대하거나 표 보기에서 전부 볼 수 있습니다.` + 누르면 `gview=table` |
| 표식 | `표식 N개 숨김` (`triangle-alert` 12px `status.warn.fg`) | `표식이 겹쳐 일부를 숨겼습니다. 표 보기에는 전부 있습니다.` + 누르면 `gview=table` |

- **칩이 세는 것 (2026-09-20 (5) 정의 고정)**: `라벨 N개 숨김`의 N = **이름 글자가 하나도 그려지지 않은 블록 수**(B4 + 완전히 숨긴 것). B3까지는 이름이 있으므로 세지 않는다. `표식 N개 숨김`의 N = 표식이 있는데 그리지 못한 블록 수.
- **표식 줄은 어떤 경우에도 지우지 않는다 (2026-09-20 (6) 확정 — frontend 구현 수용)**. B4까지 내려가 19자리가 모두 막혀도 표식 줄만은 **겹쳐서라도 그린다**(잃는 것은 이름뿐이다). 1절 정보 우선순위 2를 규칙으로 못 박는 것이고, 그래서 **`표식 N개 숨김` 칩은 1단계 K8s 구성도에서는 뜨지 않는다.** 칩 정의는 남긴다 — 9.7 묶어 보기에서 묶음 블록이 자식 표식을 합칠 때 쓴다.
- 숨겼다는 사실은 반드시 위 칩으로 말한다(숨긴 채 조용히 넘어가면 "문제 없음"으로 읽힌다). 관계 표에는 언제나 전부 있다(AC-3D04).
- 다시 계산하는 때: 카메라 조작이 멈춘 뒤 1회 + 조작 중에는 **250ms마다**(판 라벨 밀도와 같은 주기). 프레임마다 계산하지 않는다.
- 이 규칙은 **카메라 상태에 따라 달라지는 표시**일 뿐, 블록 배치(AC-3D11)와는 무관하다. 같은 입력·같은 카메라면 결과도 같다(난수 없음).
- 라벨 밀도가 `선택·검색 결과만`이면 ①의 800점 이상과 표식이 있는 블록만 후보가 되고, 그 후보들에 같은 사다리를 적용한다. `끄기`면 표식만 남기고 사다리를 적용한다.
- **프론트 회귀 점검 (2026-09-20 (7) — 「목표 대조」가 아니라 「불변 확인」이다)**: 이 절이나 4.2·4.9를 고쳤을 때 기준 장면에서 위 **불변 1~6**만 확인한다. 이름 수는 **참고 기록**으로 적는다(현재 7 / 27). **이름 수가 줄지 않았는지**를 보되, 줄었어도 불변이 지켜지면 실패가 아니다.
- **임계값·상자 폭·몸체 사각형을 이름 수를 올리려고 건드리지 않는다.** 이름 폭 36px(B3)이 "4자 + 말줄임"의 하한이고, 몸체 사각형을 줄이면 라벨이 블록을 덮는다(③). 둘 다 이미 실측으로 확인했다. 이름을 더 봐야 하면 규칙이 아니라 **사용자의 경로**(확대·hover·선택 패널·관계 표)로 간다.

### 4.8 표식 (블록 위 2D 배지)

- **위치 (2026-09-20 변경 — 프론트 구현 수용)**: 블록 **라벨 상자의 맨 윗줄**. 블록 하나의 2D 오버레이는 아래에서 위로 **[보조 줄] [종류 아이콘 12px + 4px + 이름] [표식 줄]** 한 덩어리이고, 상자 **바닥이 블록 윗면 중심 위 `6 + n` px**, 상자 가로 중심이 **블록 앵커 x + `o`**다(`n` · `o`는 4.7.1 ③의 자리 후보 — `n ∈ 0…48`, `o ∈ {0, ±(상자 폭/2 − 12)}`). **기본 자리는 `n = 0, o = 0`, 즉 블록 중심에 가로 가운데 정렬**이고, 붐빌 때만 비킨다. 어느 자리든 **블록 앵커는 상자 가로 범위 안 12px 이상 안쪽**에 있다. 줄 간격은 보조↔이름 2px, 이름↔표식 4px. 표식 줄 안에서 가로 간격 4px, 최대 3개 + `+N`(micro 11/14 `text.tertiary`).
- 모양: 18px 원, 배경 `viz.label.bg`, 1px `border.default`, 안에 아이콘 12px.
- 바꾼 이유: ① 원래의 "윗면 오른쪽 위 모서리"는 블록 크기에 따라 앵커가 움직여 먼 블록에서 라벨과 표식이 따로 놀았다 ② 오버레이가 한 덩어리여야 겹침 계산(4.7.1 ③)·툴팁·z-order를 한 번에 다룰 수 있다 ③ 표식이 있는 블록은 라벨도 항상 보이므로(4.7) 둘이 떨어질 이유가 없다.
- 대신 층 바닥 간격을 9u → 10u → 12u → **16u**로 넓혔다(4.2). 오버레이 상자가 위로 최대 56px 자라는데 층 한 칸 12u는 화면에서 57px(여유 1px)이었다. 16u = **76px**이라 밀어 올리기까지 쓰고도 20px이 남는다.
- 라벨이 줄어도 표식 줄은 **B4까지 남는다**(4.7.1 ②). 즉 표식은 이름보다 늦게 사라진다. 반대로 **표식이 있는 블록은 최소 B2**가 보장되어 이름도 함께 보인다(4.7.1 ②-1).
- **순서 고정** (파일 탭 트리 5.2와 같은 순서): ① 스캔 → ② 드리프트 → ③ 파일 문제 → ④ Helm → ⑤ 유령·정보.

| 표식 | 아이콘 | 색 | 뜻 |
|---|---|---|---|
| 스캔 오류 | `octagon-x` | `status.crit.fg` | `오류 N` (툴팁 `스캔 오류 1건 · k8s-env-literal`) |
| 스캔 경고 | `triangle-alert` | `status.warn.fg` | `경고 N` |
| 드리프트 변경 | `square-dot` | `text.secondary` | `변경됨 · 필드 2건` |
| 드리프트 삭제 | `square-minus` | `text.secondary` | `삭제됨` |
| 드리프트 추가 | `square-plus` | `text.secondary` | `추가됨`(유령 블록) |
| 비교 불가 | `eye-off` | `text.tertiary` | `비교 불가 (대시보드 권한 밖)` 등 사유(K8S-D 5.2 문구) |
| 파일 문제 | `file-warning` | `status.warn.fg` | `경로 불일치` / `중복 정의` / `런타임 필드 남음` |

- 표식 색은 위 표가 전부다. **블록 면 색은 상태를 뜻하지 않는다**(면 색 = 층). 범례에 이 문장을 그대로 적는다.
- 표식 아이콘에는 모두 툴팁이 붙고, 같은 문구가 선택 패널·관계 표에도 텍스트로 있다(색만으로 구분하지 않음).
- 판(네임스페이스)의 표식은 **같은 아이콘·순서·문구**를 쓰되 모양이 알약이다(4.1.1). 원 = 블록, 알약 = 판.
- `notes[]` 중 `custom_resource`는 **표식 원을 만들지 않는다**(문제가 아니라 성질이다). 자리는 7.4 표 참고.

| 초기화 | 도구 `⤢` 버튼, `0` 키 → 기본 시점으로 |
| 시점 바로가기 | `1` 위에서(고도 90°, 방위 0°) / `2` 비스듬히(기본) / `3` 앞에서(고도 12°, 방위 0°) |
| 이동 시간 | 300ms(`motion.duration.slow`, easing `standard`). **`prefers-reduced-motion: reduce`이면 0ms(즉시 전환)** |
| 자동 회전 | **없음**(어느 설정에서도) |

- 위에서 시점(고도 70° 이상)에서는 아래층이 가려지므로, **가장 위 층부터 아래로 가면서 위쪽 층의 면 불투명도를 0.35로 낮추고 윤곽은 그대로** 둔다. 라벨·표식은 그대로 보인다.
- 검색 결과·선택으로 카메라를 옮길 때: 대상 블록이 **안전 영역 가운데**에 오고, 거리는 `min(36u, 기본 거리)`까지만 당긴다(주변 맥락을 잃지 않게).
- 카메라 상태는 URL에 넣지 않는다(링크 공유의 기준은 선택·필터다. 좌표까지 넣으면 주소가 길어지고 같은 입력 같은 배치 규칙과 중복된다).

#### 기본 거리 맞춤 (2026-09-20 신설 — "대각선 × 1.25"를 대신한다)

프론트 보고대로 `대각선 × 1.25`만으로는 768px 캔버스에서 장면이 잘리거나 가운데 작게 남았고, 실제 화면에서는 **장면이 아래로 몰리고 위쪽 절반이 비는** 문제도 확인됐다. 거리는 **화면에 맞춰 계산하고**, 중심은 **안전 영역 가운데에 맞춘다**.

**1) 안전 영역 (캔버스 안에서 장면이 실제로 쓸 수 있는 사각형)**

| 변 | 여백 | 근거 |
|---|---|---|
| 위 | **44px 고정** (2026-09-20 (5) 변경 — 이전 `44~88px`) | 12 + 정보 줄 한 줄 20 + 12. **정보 줄은 한 줄을 넘지 않는다**(6.4에서 그렇게 만든다). 칩이 늘었다고 안전 영역이 바뀌면 같은 스냅샷을 열 때마다 첫 화면이 달라지고, 2줄(76px)이 되는 순간 안전 영역 중심이 캔버스 중심보다 **32px 아래**로 내려가 위쪽이 더 빈다 — 이번에 본 증상의 일부다 |
| 오른쪽 | **116px** | 카메라 오버레이(6.3) 폭 96px + 여백 12px + 여유 8px |
| 왼쪽 | **12px** | 범례가 캔버스 밖으로 나가(6.5) 더 뺄 것이 없다 |
| 아래 | **12px** | |

- 기준 장면(캔버스 **766 × 616px**)이면 안전 영역 = **638 × 560px**, 중심은 캔버스 좌상단 기준 **(331, 324)**, 즉 캔버스 중심보다 **왼쪽 52px · 아래 16px**.
- **알림(9.5·9.8·9.9)과 툴팁·팝오버는 안전 영역 계산에 넣지 않는다.** 잠깐 떴다 사라지는 것에 카메라가 반응하면 화면이 출렁인다.

**1-1) 맞춤 영역 (2026-09-20 (6) 신설 — `d_fit × 1.06`을 대신한다)**

- **맞춤 영역 = 안전 영역의 네 변에서 각각 26px 안쪽**. 기준 장면이면 **586 × 508px**, 중심은 안전 영역과 같다.
- 장면 바운딩 박스를 맞추는 대상은 **안전 영역이 아니라 맞춤 영역**이다. 26px 테두리는 **블록 가장자리에 붙는 2D 오버레이 몫**이다.
- **왜 26px인가**: 최소 단계 상자(B3) 폭이 52px이고, 가로 가운데로 놓이면 앵커에서 좌우로 26px씩 뻗는다. 즉 **안전 영역 가장자리에 놓인 블록에 최소 단계 라벨이 붙어도 안전 영역을 넘지 않는 최소값**이다. (B0 136px 상자까지 감당하려면 68px이 필요한데, 그러면 장면이 다시 20% 작아진다. 가장자리 블록이 B0를 받는 일은 드물고, 넘치더라도 캔버스 안(안전 영역 밖 12~116px 여백)에 그려진다.)
- **왜 비율(`× 1.06`)이 아니라 px인가**: 오버레이는 카메라 거리와 무관한 **고정 px**이다(1절). 비율로 잡으면 장면이 클수록 여유가 커져(잘못) 작은 장면에서는 모자란다. 실제로 `× 1.06`은 기준 장면에서 `fillX`를 0.844로 떨어뜨렸다(frontend 실측).

**2) 거리 (2026-09-20 (5) — `d_fit` 식을 모서리별 계산으로 바꾼다)**

```
FOV_v = 35°,  w·h = 캔버스 폭·높이,  W_f·H_f = 맞춤 영역 폭·높이 (1-1)
tanY = tan(17.5°) × (H_f / h)
tanX = tan(17.5°) × (W_f / h)          // (w/h) × (W_f/w) 를 정리한 것

장면 바운딩 박스 = 판 + 블록 기하 (2D 라벨은 넣지 않는다)
대상 c0 = bbox 3D 중심,  모서리 8개 p_i (c0 기준 상대 좌표)
right = (0.819, 0, 0.574),  up = (0.287, 0.866, −0.410),  toCam = (−0.497, 0.5, 0.709)   // 4.0

sx_i = p_i·right,  sy_i = p_i·up,  sz_i = p_i·toCam
d_fit = max over i of  max( |sx_i| / tanX + sz_i ,  |sy_i| / tanY + sz_i )

s_min  = (h ≥ 600px) ? 16px : 13px                  // 블록 한 변(4u)의 읽기 하한, 12절
d_read = 4h / (2 × s_min × tan(17.5°))              // 블록 한 변이 s_min이 되는 거리
기본 거리 d0 = clamp( min(d_fit, d_read), 36u, 대각선 × 3 )      // ★ × 1.06 을 쓰지 않는다
```

- **`× 1.06` 삭제 (2026-09-20 (6))**. 라벨 여유는 이제 **맞춤 영역의 26px 테두리**가 맡는다(1-1). 두 군데에서 같은 여유를 잡고 있었고, 그 합이 `fillX` 0.844의 절반이었다.
- `d_fit`을 **안전 영역이 아니라 맞춤 영역**에 맞춘다. 나머지 식(모서리별 계산)은 (5)와 같다.

- **왜 모서리별로 바꾸나**: 이전 식 `max(r_x/tanX, r_y/tanY) + r_z`는 "화면에서 가장 옆으로 벌어진 모서리"와 "카메라에 가장 가까운 모서리"가 **같은 모서리라고 가정**한다. 직육면체에서 그 둘은 대개 다른 모서리라 거리가 필요 이상으로 멀어졌다 — 기준 장면에서 **18% 과다**(275u vs 234u)였고, 그만큼 장면이 작아지고 안전 영역에 여백이 남았다. 모서리별 식은 "8개 모서리가 모두 맞춤 영역 안"을 정확히 만족하는 **최소** 거리다.
- 모서리별 식도 여전히 조금 보수적이다(**모서리 8개의 경계 상자**와 **투영 사각형**이 정확히 같지는 않다). 남는 몫은 아래 3)의 **크기 조이기 반복**이 없앤다.
- **`d_read` 상한**: 장면이 커도 블록 한 변이 `s_min` 밑으로 내려가지 않는다. 기준 장면(766 × 616px → `h ≥ 600px`이므로 `s_min` 16px)이면 `d_read = 4 × 616 / (2 × 16 × tan17.5°) ≈ **244u**`이고 `d0 ≈ 179u`라 걸리지 않는다. 캔버스 높이가 480~599px이면 `s_min` 13px → `d_read ≈ 4h / 8.20`이다.
  - **`s_min`의 근거가 바뀌었다**: 이전 근거는 "윗면 종류 아이콘 16px을 그릴 수 있는 최소"였는데 윗면 아이콘을 폐지했다(4.3). 새 근거는 **① 블록이 마우스로 집히는 크기 ② 윗면·옆면·아랫면 3단 밝기가 구분되는 크기**이고, 그 하한이 12px이라 여유 1px을 더해 13px이다. 큰 캔버스에서는 오버레이 상자(최대 136px)가 블록보다 지나치게 커 보이지 않게 16px을 유지한다.
- `d_fit > d_read`여서 상한에 걸리면 장면 일부가 화면 밖으로 나간다. 이때 정보 줄(6.4-8 자리)에 Chip neutral sm **`일부가 화면 밖`**(아이콘 `maximize` 12px `text.tertiary`, 툴팁 `블록을 읽을 수 있는 크기를 지켰습니다. 전체를 보려면 축소(−)하거나 네임스페이스 필터로 좁히세요.`). **누르면 `d_fit`(= 3)의 반복까지 마친 맞춤 거리)으로 한 번 축소한다** — 이 동작 때문에 `SceneInfoItem`에 `onClick`을 넣는다(6.4).
- 바닥 36u는 판 한 장짜리 스냅샷에서 카메라가 블록에 코를 박지 않게 하는 값이다.
- **기준 장면 실측**(4.0): `d0 ≈ 179u`(`d_read 244u` 상한에 걸리지 않는다) → **`px_per_u ≈ 5.45`**, 블록 한 변 **22px**, 이웃 간격 `g` **23~76px**. 이력: 1단계 `d0 = 248u` · `px_per_u = 4.07` · 블록 16px · `fillX 0.79` → (5) `px_per_u 5.0` · `fillX 0.844` → **(7) `px_per_u 5.45` · 블록 22px · `fillX 0.9185` · `fillY 0.8660` · `fit 1.00005`** ✅.

**3) 가운데 맞추기 (2026-09-20 (5) — "세로 가운데"가 실제로 보장되는 계산식)**

1단계 구현은 대상을 bbox 3D 중심으로 고쳤는데도 위쪽이 비었다. 남은 원인이 셋이고, 셋 다 아래에서 닫는다.

| 원인 | 어디서 닫나 |
|---|---|
| ① 장면 투영 사각형이 안전 영역보다 훨씬 **납작**(가로:세로 1.54 vs 1.17)해서 세로 38%가 남았다 | **4.1** 판 3열 배치 + **4.2** 층 간격 12u → **16u**. 실측 `fillY` 0.786 → **0.866**으로 세로 여백이 거의 사라졌다 |
| ② `d_fit` 과다(18%)로 장면이 안전 영역 안에서 더 작아졌다 | **4.9-2** 모서리별 `d_fit` |
| ③ 정보 줄이 2줄이 되면 위 여백이 44 → 76px이 되어 안전 영역 중심이 32px 아래로 내려갔다 | **4.9-1** 위 여백 44px 고정 + **6.4** 정보 줄 한 줄 제한 |

**계산 순서 (이 순서를 그대로 구현한다)**

```
1. c = bbox 3D 중심 (판 바닥이 아니라 블록 높이를 포함한 중심),  d = 4.9-2 의 d0
2. 아래 3~6 을 **3회 반복**한다:
3.   실제 화면 좌표를 구한다 — 평행 투영 근사를 쓰지 말 것:
        px_per_u = h / (2 × d × tan17.5°)
        모서리 8개에 대해  scale_i = d / (d − sz_i)
        X_i = cx + sx_i × scale_i × px_per_u
        Y_i = cy − sy_i × scale_i × px_per_u
     투영 사각형 R = [min X, max X] × [min Y, max Y], 중심 r = R의 중심
4.   **크기 조이기 (2026-09-20 (6) 신설)**
        k = max( R.width / W_f , R.height / H_f )       // 1 이면 맞춤 영역에 꼭 맞는다
        d = clamp( d × k , 36u , min(d_read, 대각선 × 3) )
5.   안전 영역 중심 s = ( left + W_s/2 , top + H_s/2 )   // 기준 장면이면 (331, 324)
6.   Δ = s − r (px) 를 카메라 대상에 더한다:
        target += right × (Δx / px_per_u) − up × (Δy / px_per_u)
```

**3-1) 유효 모서리 — 카메라 뒤로 간 모서리는 계산에서 뺀다 (2026-09-20 (8-2) 신설, PM 결정)**

대규모 장면(frontend `large` mock **3,264 블록**)에서 **첫 화면이 비는 버그**가 나왔다. 원인은 3번의 `scale_i = d / (d − sz_i)`다. `d_read` 상한(4.9-2)에 걸리면 거리가 장면을 다 담을 만큼 멀어지지 못해 **카메라가 장면 안으로 들어가고**, 그때 일부 bbox 모서리는 `sz_i ≥ d`(카메라 뒤)가 된다. 그러면 `scale_i`가 **0으로 나누거나 부호가 뒤집혀** 투영 사각형 `R`의 중심 `r`이 폭주하고, 6번의 팬이 장면을 화면 밖으로 밀어낸다.

```
near = 카메라 근평면(프론트 값)
유효 모서리 조건:  d − sz_i ≥ max(near, 0.05 × d)      // 카메라 뒤·근평면 앞의 모서리는 제외
유효 모서리 개수 m:
  m ≥ 3  → 유효 모서리만으로 R · r 을 구하고 4~6 을 평소대로 한다
  m < 3  → 이번 회차의 4·5·6 을 모두 건너뛴다 (d 와 target 을 직전 값 그대로 둔다)
```

- **`m < 3`이면 크기 조이기도 중심 맞추기도 하지 않는다.** 사각형을 2점 이하로 정의할 수 없는데 억지로 계산하면 지금의 버그가 된다. 이때는 **직전 값(= `d0`와 bbox 중심)이 최선의 추정**이다.
- 이 상태에서 `inside`가 거짓이면(장면이 안전 영역을 넘으면) 정보 줄에 **`일부가 화면 밖` 칩**(6.4-8)을 그대로 띄운다. 칩을 누르면 `d_read` 상한을 풀고 맞춤 거리로 한 번 축소하는 기존 동작도 그대로다 — **사용자가 빠져나올 길이 이미 있다.**
- **`0.05 × d` 여유를 두는 이유**: `d − sz_i`가 0에 아주 가까우면 `scale_i`가 수백 배가 되어 사각형이 사실상 무한대가 된다. 모서리를 "뒤에 있다"로만 거르면 이 경우를 놓친다.
- **결정적이다**(불변 6): 제외 조건이 상수이고 난수가 없다. 같은 입력·같은 카메라면 제외되는 모서리도 같다.
- `fitCheck()`는 이 경우 **`skipped: true`와 `m`을 함께 낸다.** `skipped`이면 `fit`·`fillX`·`fillY`·`dx`·`dy` **기준을 적용하지 않는다**(측정 자체가 성립하지 않는다). 불변 5(카메라 맞춤)는 `skipped: false`인 장면에서만 판정한다.
- 이 규칙은 **대규모 장면의 안전 장치**이고 기준 장면(블록 27개)에서는 모든 모서리가 유효하므로 **실측값이 바뀌지 않는다**(frontend (8-2) 확인: `fit` 1.0000472 · `fillX` 0.9185386 · `fillY` 0.8659683).

- **4번(크기 조이기)이 이번에 더해진 것이다.** `d_fit`은 "모서리 8개가 모두 들어가는 거리"라 **경계 상자 기준**인데, 실제로 화면을 채우는 것은 **투영 사각형**이다. 둘의 차이만큼 장면이 작게 남았다(실측 `fillX` 0.844). `k`를 곱하면 사각형이 맞춤 영역에 정확히 붙는다. `d_read` 상한에 걸릴 때는 `clamp`가 막고 `일부가 화면 밖` 칩이 뜬다.
- **2번(3회 반복)이 핵심이다.** 원근이라 거리를 바꾸거나 대상을 밀면 어느 모서리가 극단인지 달라져 한 번으로는 맞지 않는다((5)에서 중심 맞추기만 2회였고 잔차 ±4px이었다). 크기 조이기가 들어가 변수가 하나 늘었으므로 **2회 → 3회**로 올린다. 3회면 `|dx|·|dy| ≤ 4px`, `k` 잔차 ≤ 0.02다. 4회 이상은 눈에 띄지 않는다. **횟수는 상수로 못 박는다**(수렴 판정을 쓰면 부동소수 차이로 기기마다 결과가 달라진다).
- 3번에서 `scale_i`를 빼고 평행 투영으로 계산하면 **가까운 모서리가 실제보다 작게 잡혀** 사각형이 위로 치우치고, 그 결과가 정확히 "위가 빈다"로 나타난다.
- 크기 조이기는 **`d`만** 바꾸고 대상 `c`는 바꾸지 않는다. 순서를 4 → 5·6으로 두는 이유: 거리를 먼저 정해야 `px_per_u`가 정해지고, `Δ`를 3D 단위로 되돌릴 수 있다.

**확인식 (프론트 자가 점검 — `fitCheck()`가 내야 하는 값)**

| 값 | 기준 |
|---|---|
| `dx` = `r.x − s.x` | **\|dx\| ≤ 4px** |
| `dy` = `r.y − s.y` | **\|dy\| ≤ 4px** |
| `fillX` = `R.width / W_s` | `max(fillX, fillY) ≥ 0.90` — 한 축은 반드시 안전 영역을 거의 채운다. 아니면 거리 계산이 틀린 것 |
| `fillY` = `R.height / H_s` | **`fillY ≥ 0.70`** — 세로가 이보다 비면 장면 모양이 너무 납작한 것이므로 4.1 판 배치(3열·간격 8u)가 제대로 적용됐는지 본다 |
| **`fit` = `max(R.width / W_f, R.height / H_f)`** | **`0.98 ≤ fit ≤ 1.02`** (2026-09-20 (6) 신설). 3)의 크기 조이기가 도는지 보는 값이고, **`fillX`·`fillY`보다 이것이 1차 지표**다 |
| `inside` | `d_read` 상한에 걸리지 않았다면 `R ⊆ 안전 영역` |
| **`skipped` · `m`** | **2026-09-20 (8-2) 신설.** 유효 모서리 `m < 3`이라 보정을 건너뛰었는지(3-1). **`skipped: true`면 위 다섯 값의 기준을 적용하지 않는다** — 대신 `일부가 화면 밖` 칩이 떠 있어야 한다 |

- **기준 장면 실측**(766 × 616px, 2026-09-20 (7)): `fit` **1.00005**, **`fillX` 0.9185**, `fillY` **0.8660**, `dx` −0.013px, `dy` −0.002px. **다섯 값 모두 기준 안** ✅
  - 왜 `fillX`가 1.00이 아닌가: 안전 영역(638px) 안에 26px 테두리 두 개(52px)를 뺀 맞춤 영역(586px)에 맞추므로 **최대 `fillX`는 `586 / 638 = 0.9185`**다. 실측이 정확히 그 값이라는 것은 **가로가 먼저 차고 맞춤이 끝까지 조여졌다**는 뜻이다.
  - 세로가 먼저 차는 장면이면 반대로 `fillY = 508 / 560 = 0.907`, `fillX`가 더 작아진다. 어느 쪽이든 `max(fillX, fillY) ≥ 0.90`을 만족한다.
  - `fillY` 0.866은 **층 간격 16u**(4.2)가 만든 값이다(12u일 때 0.786). 세로 여백이 줄어 장면이 캔버스를 고르게 쓴다.
- (5)가 적었던 기대치 `fillX ≈ 0.99` · `fillY ≈ 0.95`는 **잘못이다.** 두 축이 동시에 1에 가까워지려면 장면 투영 사각형과 안전 영역의 가로세로 비가 정확히 같아야 하는데 그런 일은 없고, 여유 테두리를 빼면 어느 축도 1.00에 닿지 않는다.

### 4.10 종류 → 아이콘 (2026-09-20 신설)

5.2에서 색은 **층 5가지**뿐이라 같은 층 안의 종류는 **아이콘으로만** 구분된다. 1단계 구현에서 이 표가 없어 블록 오버레이·선택 패널·관계 표의 아이콘 자리가 비어 있었다. 여기서 확정한다. (2026-09-20 (5): 블록 **윗면**에는 그리지 않고 오버레이 이름 줄에 12px로 그린다 — 4.3)

**정하는 원칙**

1. **등록된 아이콘을 먼저 쓴다**(`components.md` 13절). 새로 등록하는 것은 등록 목록에 뜻이 맞는 것이 없을 때만.
2. **한 화면(3D 보기 탭) 안에서 한 아이콘은 한 뜻**이다. 다른 기능·다른 탭과 겹치는 것은 허용한다(비유가 그대로 통할 때만).
3. **표식 아이콘 집합과 겹치지 않는다**(`octagon-x`·`triangle-alert`·`square-dot`/`-minus`/`-plus`·`eye-off`·`file-warning`·`ship-wheel`·`circle-dashed`·`file-question`). 종류와 상태가 같은 글리프로 보이면 안 된다(`status.md` 11.1 세 축 분리).
4. 아이콘은 **혼자 뜻을 지지 않는다**: 선택 패널·관계 표에서는 항상 종류 이름과 나란히 있고, 3D에서는 hover 툴팁(`Deployment · api`)이 있다. 그래서 범례에 종류 15줄을 만들지 않는다.

### 4.11 블록 모양 (종류별 실루엣) — 2026-09-20 (8) 신설

사용자 요청: "3D 블록 모양을 각 서비스 특징에 맞게". 지금까지 블록은 **모두 같은 상자**였고 종류는 오버레이 아이콘 12px으로만 갈렸다. 라벨이 줄거나 숨는 장면(4.7.1 — 기준 장면에서 이름이 보이는 블록 7~14 / 27)에서는 **몸체만 보이는 블록이 절반 이상**이라, 그 블록들은 층 색밖에 말하지 못했다. 몸체에 종류를 실어 **라벨이 없어도 무엇인지 읽히게** 한다.

#### 4.11.0 지켜야 할 것 (이 절이 깨면 안 되는 규칙)

| # | 제약 | 이 절이 지키는 방법 |
|---|---|---|
| 1 | **발자국 4u × 4u 고정** | 모든 모양이 4u × 4u 발자국 안에 들어간다. 격자 점유·판 크기·`o_max` 계산이 그대로다 |
| 2 | **앵커(라벨·표식 기준점) 불변** | 앵커 = **층 바닥 + 3u 평면의 중심** 고정. 모양이 달라져도 값이 같다. 그래서 **모든 모양은 (0, 3u, 0)에서 솔리드**여야 한다(상단 중심이 비면 라벨이 허공에 뜬다) |
| 3 | **높이는 층 두께 안** | 모든 모양의 **상단 평면이 정확히 3u**다. 3u를 넘는 모양은 없다. 층 한 칸 16u(76px) 근처에도 가지 않는다 |
| 4 | **카메라·라벨 실측값 유지** | 장면 바운딩 박스가 판 + 블록 기하인데(4.9-2), 발자국과 높이가 그대로라 **bbox가 한 치도 바뀌지 않는다**. `d0` 179u · `px_per_u` 5.45 · 블록 한 변 22px · `g` 23~76px · `fit`/`fillX`/`fillY`/`dx`/`dy` 실측값이 모두 유효하다 |
| 5 | **22px에서 윤곽만으로 갈린다** | 아래 모든 모양 차이는 **윤곽선 위치가 3.5px 이상**(전체 폭으로는 7px 이상) 달라진다(4.11.2 환산표). 그보다 미세한 차이는 쓰지 않았다 |
| 6 | **색은 여전히 층, 모양은 종류** | 모양은 **상태를 뜻하지 않는다.** 드리프트·스캔·유령은 지금처럼 표식과 윤곽선 모양(dashed)으로만 말한다(`status.md` 11.1) |
| 7 | **성능** | 모양 **8종 + 곁 타일 1종 = 9종**. 인스턴싱 단위가 `층 × 모양`으로 늘지만 실제 장면에서 8~14 조합이고, 모양 하나의 삼각형 상한이 64개다(4.11.5) |

#### 4.11.1 모양 8종 (+ 곁 타일)

봉투는 모두 **4u(x) × 3u(y) × 4u(z)**, 셀 중앙, 상단 평면 3u. 방향은 **세계 좌표 고정**(카메라를 돌려도 모양이 따라 돌지 않는다 — 배치가 결정적이어야 하므로, AC-3D11).

| 2 | `stack` | 겹 상자 | 아래 단 4 × 4, y 0 → 0.9 · 위 단 **2.4 × 2.4**(중앙), y 0.9 → 3.0 | 2.4 × 2.4 평면 | 밑에 **낮고 넓은 턱**(높이 4.2px), 위는 폭 11.3px. 턱이 **수직으로** 꺾인다 |
| 3 | `cylinder` | 원통 | 지름 4(16각 근사) 수직, y 0 → 3 | 지름 4 원판 | **둥근 윤곽**. 세로 모서리선이 없어 매끈하다 |
| 4 | `panel` | 얇은 판 | x 4 × z **1.2**, y 0 → 3, 셀 중앙. **판 면은 x축과 나란히 고정** | 4 × 1.2 평면 | 깊이가 4.6px뿐인 **얇은 벽**(상자는 15.4px). 윗면이 가느다란 띠로 보인다 |
| 5 | `roof` | 박공 지붕 | 밑면 4 × 4. **용마루 = `x = 0` 선, `z` 방향으로 `z = −2 … +2` 전 구간, 높이 3.0u**. **처마 = `x = ±2` 두 선**(z축과 나란함), 높이 1.0u. 따라서 **사면 2장은 ±x를 향하고(45°), 박공(삼각) 벽 2장은 ±z를 향한다**(2026-09-20 (8-1) 확정 · (8-2) 문구 확인) | 면이 아니라 **능선**(`x = 0` 선이 3u) | 윗머리가 **삼각형**(지붕 높이 9.4px = 전체 높이의 2/3). 유일하게 뾰족하다 |
| 6 | `chamfer` | 머리 깎은 상자 | 수직 4 × 4, y 0 → 1.6 · 사면 y 1.6 → 3.0에서 4 × 4 → **1.6 × 1.6** | 1.6 × 1.6 평면 | 위쪽이 **사선으로** 좁아져 상단 폭 7.6px. 꺾임이 **대각선**이고 높은 자리(7.6px 지점)에서 시작한다 |
| 7 | `gate` | 아치 문 | 다리 4개(각 1.2 × 1.2, 발자국 네 모서리) y 0 → 1.6 · 상단 보 4 × 4 × 1.4, y 1.6 → 3.0 | 4 × 4 평면 | 아래에 **뚫린 구멍**(가로 7.6px × 높이 7.6px). 어느 방위에서도 구멍이 보인다 |
| 8 | `diamond` | 다이아몬드 | 밑면 2.0 × 2.0 → y 1.4에서 **4.0 × 4.0**(최대 폭) → y 3.0에서 1.6 × 1.6 | 1.6 × 1.6 평면 | **가운데가 불룩**하고 위아래가 좁다(밑면 9.5px). 유일하게 밑면이 작다 |
| — | `tile` | 곁 타일 | 6 × 3 × 0.75 (판 가장자리 띠, **기존 그대로**) | 6 × 3 평면 | 납작한 타일. 위치(띠)와 중립색으로 이미 갈린다 |

- **`gate`의 다리를 네 모서리에 두는 이유**: 다리 2개(터널형)면 카메라를 돌렸을 때 구멍이 옆으로 숨는다. 네 모서리 기둥이면 어느 방위에서도 다리 사이 구멍이 보인다. 구멍의 천장(보의 밑면)은 밝기 64%라 안쪽이 어둡게 읽힌다.
- **`roof`의 용마루를 `z` 방향(`x = 0` 선)으로 고정한다 — 2026-09-20 (8-1) 확정.** (8)에서 이 항목의 서술("용마루 방향을 x축으로")과 4.11.3 밝기 표(+z / −z 사면)가 표와 어긋나 있었다. **치수표(4.11.1)가 맞고, 서술과 밝기 표를 여기에 맞춘다.**
  - **고른 기준은 기본 시점(방위 −35°·고도 30°)에서 밝기 3단이 읽히는가**다. 사면이 ±x를 향하면 `t`가 **0.96 / 0.27**(→ 100% / 82%)로 임계값에서 멀고, 카메라가 보는 −x 사면이 **100%**라 그 아래 −x 벽(82%)과 확실히 갈린다. 사면이 ±z를 향하면 `t`가 **0.69 / 0.54**로 둘 다 경계(0.65) 근처라, 지붕 기울기를 조금만 바꿔도 보이는 사면이 82%로 떨어져 **아래 벽과 같은 밝기로 뭉갠다**(그러면 지붕이 사라진다).
  - 대가: 용마루의 화면 기울기가 x 방향일 때(19°)보다 가파르다(35°). 그래도 **삼각 박공 벽이 카메라 쪽(+z)을 향해 정면으로 보이므로** 뾰족한 실루엣은 그대로 읽힌다.
  - 방향을 종류마다 바꾸지 않는다("모양이 뜻을 갖는다"는 규칙이 흔들린다). `panel`의 판 면(x축)과도 축이 달라 두 모양이 섞이지 않는다.
- **`panel`의 판 면도 x축 고정**이다. 카메라를 약 90° 돌리면 얇은 쪽을 보게 되어 폭 4.6px의 기둥으로 보이는데, **그래도 다른 일곱 모양과 갈린다**(가장 가는 모양). 기본 시점·`1`·`2`·`3` 시점 바로가기에서는 모두 넓은 면이 보인다.
- **`cylinder`의 세로 모서리선**: 윤곽선은 인접 면 법선각 **25° 이상**인 모서리만 그린다. 16각 원통의 세로 모서리는 22.5°라 그려지지 않아 위·아래 링만 남고 매끈한 원통이 된다. 다른 모양은 모든 모서리가 25°를 넘어 전부 그려진다.

#### 4.11.2 모양 ↔ 종류 (4.10의 종류 전부)

**모양의 1차 목적은 같은 층 안에서 갈리는 것이고, 비유는 2차다.** 아래 배정은 먼저 층별로 서로 다른 윤곽을 주고, 그다음 뜻이 통하는 쪽을 골랐다.

| 층 | 종류(`blocks[].kind`) | 모양 | 고른 이유 |
|---|---|---|---|
| 워크로드 | `Deployment` | **`stack`** | 같은 파드 **여러 벌을 겹쳐 둔 것**. 이 층에서 가장 흔하므로 한눈에 세어지는 모양을 준다 |
| 워크로드 | `StatefulSet` | **`cylinder`** | 순서와 **고정 저장소**를 가진 워크로드. 저장 층의 PVC와 같은 원통이라 "저장에 묶인 것"이 층을 건너 읽힌다 |
| 워크로드 | `DaemonSet` | **`panel`** | 노드마다 한 벌씩 **얇게 깔리는 판**. 발자국을 줄일 수 없으므로 "낮고 넓은 판" 대신 **얇은 판**으로 옮겼다(높이를 낮추면 앵커가 허공에 뜬다 — 4.11.0-2) |
| 워크로드 | `CronJob` | **`roof`** | 주기적으로 **오르내리는 톱니**(반복 파형). 이 층에서 유일하게 뾰족하다 |
| 워크로드 | `Job` | **`chamfer`** | **끝이 있는 일감** — 모서리를 잘라 낸 육면체. `stack`(수직 턱)과 꺾임 방향이 다르다(대각선) |
| 워크로드 | `Pod` · `ReplicaSet` · 그 밖 | **`box`** | 기본형. 아래 "기본형이 여럿을 받는 이유" |
| 서비스 | `Service` | **`diamond`** | 한 점에서 **여러 갈래로 퍼지는 분배 지점**(팔면체 느낌) |
| 서비스 | 그 밖(`Endpoints` 등) | `box` | 기본형 |
| 진입 | `Ingress` | **`gate`** | 밖에서 안으로 들어오는 **문** |
| 진입 | 그 밖 | `box` | 기본형 |
| 저장·설정 | `PersistentVolumeClaim` · `PersistentVolume` | **`cylinder`** | **드럼**. 둘이 같은 모양인 것은 4.10의 아이콘(`hard-drive` 공유)과 같은 근거 — 언제나 다른 판(네임스페이스 / 클러스터 범위)에 있다 |
| 저장·설정 | `ConfigMap` | **`panel`** | 설정 값을 적은 **얇은 판**(문서) |
| 저장·설정 | `Secret` | **`chamfer`** | **모서리를 봉한 상자** — 스냅샷에는 이름만 있고 안을 열어 볼 수 없다. 저장 층에서 원통·얇은 판과 확실히 갈리는 남은 윤곽이다 |
| 저장·설정 | 그 밖 | `box` | 기본형 |
| 곁 | `HorizontalPodAutoscaler` · `PodDisruptionBudget` · `NetworkPolicy` · `ServiceAccount` · `Role` · `ClusterRole` · `RoleBinding` · `ClusterRoleBinding` · `ResourceQuota` · `LimitRange` · `CustomResourceDefinition` · 사용자 지정 | **`tile`**(모양 나누지 않음) | 곁 타일은 높이 0.75u = 화면 **3.5px**이라 윤곽으로 나눌 여지가 없다. 곁 층은 **위치(판 가장자리 띠) + 중립색**으로 이미 갈리고, 종류는 아이콘·이름이 맡는다 |
| 아무 층 | `custom: true`가 곁이 아닌 층에 오면 | `box` | 기본형 + `shapes` 아이콘 |
| (판·곁 띠·묶음) | — | 4.1 · 9.7 | 판은 모양을 바꾸지 않는다 |

**기본형(`box`)이 여러 종류를 받는 이유.** `box`는 "이 다섯(또는 하나)이 아닌 것"이라는 **뜻을 가진 자리**다. 워크로드 층에서 모양이 따로 있는 것은 사람이 매니페스트로 쓰는 다섯(`Deployment`·`StatefulSet`·`DaemonSet`·`CronJob`·`Job`)이고, `Pod`·`ReplicaSet`은 보통 컨트롤러가 만드는 런타임 산물이라 스냅샷 파일로 존재하는 일이 드물다. 이 셋을 억지로 갈라 모양을 3개 더 만들면 **22px에서 갈리지 않는 차이**가 생긴다(4.11.0-5). 구분은 아이콘(`box` / `copy`)·이름·선택 패널이 맡는다. 같은 예외를 4.10이 이미 쓴다(PVC·PV의 `hard-drive`).

**같은 층 안에서 갈리는지 확인** (이 표가 이 절의 수용 기준이다)

| 층 | 쓰는 모양 | 가장 가까운 쌍 | 윤곽 차이 |
|---|---|---|---|
| 워크로드 | `stack` · `cylinder` · `panel` · `roof` · `chamfer` · `box` | **`stack` ↔ `chamfer`** | 좁아지는 자리가 **아래(4.2px 지점) / 위(7.6px 지점)**, 꺾임이 **수직 / 대각선**, 상단 폭 **11.3 / 7.6px** |
| 서비스 | `diamond` · `box` | `diamond` ↔ `box` | 밑면 9.5 / 18.9px, 중간 불룩 |
| 진입 | `gate` · `box` | `gate` ↔ `box` | 구멍 7.6 × 7.6px |
| 저장·설정 | `cylinder` · `panel` · `chamfer` · `box` | `chamfer` ↔ `box` | 상단 폭 7.6 / 18.9px |
| 곁 | `tile` 하나 | — | 모양으로 나누지 않는다 |

- **`stack` ↔ `chamfer`가 이 설계에서 가장 가까운 쌍**이다. 둘 다 워크로드(같은 파랑)에 있으므로 **프론트 회귀 점검에 "한 판에 `Deployment`와 `Job`이 함께 있는 장면" 스크린샷을 넣는다**(4.11.6). 여기서 갈리지 않으면 **`stack`의 아래 단 높이를 0.9 → 0.6u로 낮추고 위 단을 2.4 → 2.8u로 넓혀**(= 턱을 더 낮고 얕게) `chamfer`와 반대 방향으로 벌린다. 그래도 갈리지 않으면 **둘 중 하나(`Job`)를 `box`로 내리고** 종류 구분을 아이콘·이름에 넘긴다. 어느 경우에도 발자국 4u·상단 평면 3u는 건드리지 않는다.

**화면 크기 환산** (기준 장면 `px_per_u` 5.45, 투영 상수 x 0.868 · z 0.705 · y 0.866 — 4.0)

**두 가지 px을 섞지 않는다.** 4.0·4.7.1이 쓰는 **명목 22px**은 `4u × px_per_u`(투영 성분을 빼고 넉넉히 잡은 값)이고 **점유 사각형 전용**이다. 아래는 실제로 눈에 보이는 **투영 크기**로, 1u당 가로 `0.868 × 5.45 = 4.73px` · 깊이 `0.705 × 5.45 = 3.84px` · 세로 `0.866 × 5.45 = 4.72px`이다(4.0 투영 상수).

| 3D 값 | 화면(투영) |
|---|---|
| 발자국 한 변 4u | 가로 **18.9px** · 깊이 **15.4px** (명목 22px) |
| 블록 높이 3u | **14.2px** |
| `stack` 턱 높이 0.9u / 위 단 폭 2.4u | 4.2px / **11.3px** |
| `chamfer` 사면 시작 높이 1.6u / 상단 폭 1.6u | 7.6px / **7.6px** |
| `panel` 깊이 1.2u | **4.6px** |
| `gate` 구멍 1.6u(가로 / 깊이 / 높이) | **7.6 / 6.1 / 7.6px** |
| `roof` 지붕 높이 2.0u | **9.4px** |
| `diamond` 밑면 2.0u / 최대 폭 4.0u / 상단 1.6u | 9.5 / 18.9 / 7.6px |

- **좁은 캔버스(블록 한 변 13px, 12절)에서는** 둥근 / 각진 / 구멍 / 얇음 네 가지(`cylinder` · `box`류 · `gate` · `panel`)까지 갈리고, `stack`·`chamfer`·`roof`의 상단 차이는 흐려진다. **읽기 하한 `s_min`을 바꾸지 않는다** — 13px은 원래 "집히는 크기 · 밝기 3단이 갈리는 크기"로 정한 값이고, 모양이 완전히 갈리는 것은 22px 기준 장면의 목표다(4.9 · 12절).

#### 4.11.3 면 밝기 3단 — 모양이 늘어도 값은 세 개뿐

밝기 값은 지금과 같은 **100% / 82% / 64%** 세 개다(새 값·새 토큰 없음). 정하는 법만 바꾼다: 면마다 고정 광원 방향과의 내적 `t = n · l`을 구해 **세 값 중 하나로 양자화**한다.

```
고정 광원 방향 l = (−0.49, 0.87, 0.10)      // 정규화됨. 방위 −78° · 고도 60°
t ≥ 0.65            → 100%   (윗면·빛 쪽 사면)
0.20 ≤ t < 0.65     → 82%    (빛 쪽 옆면·반대쪽 사면)
t < 0.20            → 64%    (빛 반대쪽 옆면·아랫면·구멍 천장)
```

| 면 | `t` | 밝기 |
|---|---|---|
| 윗면 (0, 1, 0) | 0.87 | 100% |
| −x 옆면 | 0.49 | 82% |
| +z 옆면 | 0.10 | 64% |
| +x · −z 옆면 | −0.49 / −0.10 | 64% |
| `roof` **−x 사면**(카메라가 보는 쪽) | 0.96 | 100% |
| `roof` **+x 사면** | 0.27 | 82% |
| `roof` 박공(삼각) 벽 ±z | 0.10 / −0.10 | 64% |
| `gate` 보의 밑면(구멍 천장) | −0.87 | 64% |

- 위 표의 `roof` 행은 **용마루가 z 방향(사면이 ±x)**이라는 4.11.1 치수표를 전제로 한다(2026-09-20 (8-1) 일치 작업). 기준 장면에서 보이는 사면이 100%, 그 아래 −x 벽이 82%, 카메라 쪽 박공 벽이 64%라 **한 블록에 3단이 모두 보인다.**
- **광원 방위를 −45°에서 −78°로 옮긴 이유**: 이전 값에서는 기본 시점에서 보이는 두 옆면(−x, +z)이 **둘 다 82%**로 나와, 몸체의 꺾임(모서리)이 밝기로는 전혀 읽히지 않았다. 모양을 나누는 이 변경에서는 **윗면 100 · 왼쪽 옆면 82 · 오른쪽 옆면 64**로 세 단이 한 블록에 동시에 보이는 것이 중요하다. 값 세 개는 그대로이므로 대비 검증(5.3)도 그대로다.
- 양자화이므로 **원통·사면도 매끄러운 그라데이션을 만들지 않는다.** 원통 옆면은 82% 띠와 64% 띠 두 덩어리로 나뉘고, 윤곽(위·아래 링)이 둥글기를 말한다. 그라데이션을 쓰면 층 색이 흐려져 "면 색 = 층"(`status.md` 11.1)이 약해진다.
- 구현은 지금과 같다: **밝기를 지오메트리 정점 색으로 구워** 빛·그림자 계산 없이 인스턴싱한다(frontend 2026-09-20 보고).

| **비교 불가 · 비교 못 함** | **아무 것도 바꾸지 않는다.** `eye-off` / `file-warning` 표식만 | 모양으로 상태를 말하지 않는다(4.11.0-6) |
| 드리프트(변경·삭제·추가) | 표식만(`square-dot`/`-minus`/`-plus`). `added`는 유령 모양 | 모양·색 그대로 |
| **선택** | 같은 모서리 집합에 2px `viz.select.outline` | 두꺼운 윤곽이 모양을 따라간다 |
| **hover** | 같은 모서리 집합에 **1.5px `viz.select.outline` 원색**(2026-09-20 (8-2)) + 툴팁 | 〃 |
| 검색 결과 | 2px dashed 4 3 `viz.search.outline` | 〃 |
| 흐림(선택 중 나머지 · 주변만 보기) | `opacity.vizDimmed` 0.25, 윤곽도 같이 흐려진다 | 모양 유지 |
| 위에서 시점(고도 70° 이상) | 위층 면 불투명도 0.35, **윤곽은 그대로** | 면이 투명해져도 **윤곽으로 종류가 남는다** — 이 설계의 덤 |
| 저사양 간소화(9.5) | 모양을 단순화하지 **않는다**(줄이는 것은 라벨·안개다) | 삼각형 예산이 이미 작다(4.11.5) |
| 묶어 보기(9.7) | 묶음 블록은 **그 종류의 모양을 가로·세로 1.5배(6u × 6u), 높이 3u 그대로** | 묶음은 종류별이므로 모양이 그대로 뜻을 갖는다 |
| 히트 영역 | **모양과 무관하게 봉투 4u × 3u × 4u** | 얇은 `panel`도 상자와 같은 크기로 집힌다 |

- 윤곽선 집합은 모양마다 한 번만 만들고(정적) 상태에 따라 **굵기·색·대시만** 바꾼다. 상태별로 다른 선을 만들지 않는다.

#### 4.11.5 성능 — 인스턴싱과 삼각형 상한

| 모양 | 삼각형 상한 | 비고 |
|---|---|---|
| `box` | **12** | |
| `stack` | **20** | 두 상자 합침 |
| `cylinder` | **64** | 16각 근사(옆 32 + 위·아래 28) |
| `panel` | **12** | |
| `roof` | **20** | |
| `chamfer` | **28** | 기둥 + 사면 4장 |
| `gate` | **60** | 다리 4 + 보 |
| `diamond` | **28** | |
| `tile` | **12** | 기존 그대로 |
| 합계(고유 지오메트리) | **≤ 256** | 장면 전체에서 한 번만 만든다 |

- **인스턴싱 단위가 `층` → `층 × 모양`으로 바뀐다.** 최악 5 × 8 = 40이지만 실제 장면은 **8~14 조합**이다(층마다 쓰는 모양이 1~6종). 윤곽선도 같은 단위로 합친 `LineSegments` 1개씩 → 드로콜 최대 80, 보통 16~28.
- 블록 3,000개 장면에서 삼각형 합계는 **평균 30 × 3,000 ≈ 9만**이다(지금은 12 × 3,000 = 3.6만). 모바일이 아닌 데스크톱 WebGL에서 문제가 되는 규모가 아니고, 그림자·후처리가 없다는 조건도 그대로다.
- **기준 장면 구현 실측 (frontend 2026-09-20 (8-2))**: 층 × 모양 조합 **10**, 블록 드로콜 **20**(장면 전체 **30**), 모양별 삼각형 합계 **224** ≤ 256. 예상(8~14 조합·드로콜 16~28)과 맞는다.
- **모양을 더 늘리지 않는다.** 9종은 ① 한 층의 최대 종류 수(워크로드 5 + 기본형) ② 22px에서 갈리는 윤곽의 가짓수 ③ 인스턴싱 조합 수를 함께 만족하는 상한이다. 종류를 더 나눠야 하면 모양이 아니라 **아이콘·이름·선택 패널**로 간다.

#### 4.11.6 4.7.1 불변 6개 점검 (이 변경이 건드리지 않음을 확인한다)

| 불변 | 영향 | 근거 |
|---|---|---|
| 1. 표식은 지우지 않는다 | **없음** | 표식은 2D 오버레이이고 앵커만 쓴다 |
| 2. 표식 있는 블록은 이름도 보인다(최소 B2) | **없음** | 단계·자리 계산에 모양이 들어가지 않는다 |
| 3. 라벨이 블록을 덮지 않는다 | **없음(오히려 안전해진다)** | 몸체 점유 사각형은 앵커 중심 `4u × px_per_u` = **22px 고정**이다. `panel`·`diamond`처럼 실루엣이 그보다 작은 모양은 점유가 보수적으로 크다 |
| 4. 숨긴 것은 고지한다 | **없음** | 칩 규칙 그대로 |
| 5. 카메라 맞춤 | **없음** | bbox = 판 + 블록 기하인데 발자국 4u·높이 3u가 그대로라 bbox가 같다. `fit` 1.00005 · `fillX` 0.9185 · `fillY` 0.8660 · `dx` −0.013 · `dy` −0.002 **재측정 없이 유효** |
| 6. 결정적 | **없음** | 모양 = `kind`(+`custom`·`layer`)의 함수. 난수 없음, 카메라·필터와 무관 |

- 즉 **4.7.1을 한 글자도 고치지 않는다.** 4.0 기준 장면 표의 수치도 그대로다. 프론트는 모양 적용 후 `fitCheck()`가 같은 값을 내는지만 확인하면 된다(값이 달라지면 봉투를 벗어난 모양이 있다는 뜻이다 — 회귀 신호로 쓴다).
  - **모양 구현 후 실측으로 확인됨 (frontend 2026-09-20 (8-2))**: `fit` **1.0000472** · `fillX` **0.9185386** · `fillY` **0.8659683**(모양 적용 전과 같다) · 이름 **14 / 27** · `라벨 숨김` **13** · **`표식 숨김` 0**. **불변 1~6 모두 유지** ✅
  - 4.9에는 (8-2)에서 **대규모 장면 안전 규칙(3-1 유효 모서리)**이 더해졌다. 이것은 모양과 무관한 별개 버그 수정이고, 기준 장면에서는 모든 모서리가 유효해 위 실측값에 영향을 주지 않는다.
- **회귀 점검에 한 줄 추가**: 기준 장면 스크린샷에 ① 한 판에 `Deployment`(stack)와 `Job`(chamfer)이 함께 있는 자리 ② 유령 `Secret`(chamfer dashed) ③ `Ingress`(gate) 구멍이 보이는지 확인한다.

#### 4.11.7 모양이 영향을 주지 **않는** 자리 (확인)

| 자리 | 지금 | 바뀌나 |
|---|---|---|
| 선택 패널 ① 식별 줄(7.2) | 층 색 사각 12px + 종류 아이콘 14px + 종류 이름 | **안 바뀐다** |
| `RelationItem`(7.3) | 층 색 사각 10px + 종류 이름 | **안 바뀐다** |
| 관계 표 리소스 행·그룹 행(8.2·8.3) | 층 색 사각 10px + 종류 아이콘 14px | **안 바뀐다** |
| 블록 오버레이 이름 줄(4.7) | 종류 아이콘 12px + 이름 | **안 바뀐다** |
| 표식·판 알약(4.8·4.1.1) | 원 / 알약 | **안 바뀐다** |

## 5. 색 · 토큰

### 5.1 새 토큰이 필요한 이유 (기존 토큰 검토 결과)

| 후보 | 왜 안 되나 |
|---|---|
| `status.*`(ok/warn/crit/unknown/stale) | 3D 3.5가 **종류 구분에 상태색을 금지**한다. 블록 면을 상태색으로 칠하면 표식(4.8)과 뜻이 충돌한다 |
| `chart.series[8]` | ① 1.5~2px 선용으로 고른 색이라 큰 면을 칠하면 채도가 과하고 옆면·윗면 명암 차이가 뭉갠다 ② 배열 5번째 `#B07A2A`가 `status.warn.solid` `#BF8C00`과, 8번째 `#7A8595`가 `status.unknown.solid` `#8C95A1`과 거의 같아 블록이 "주의·알 수 없음"으로 읽힌다 ③ 시리즈 색은 차트마다 순서로 배정되는 **서수**여서 "이 색 = 워크로드"라는 고정 의미를 걸 수 없다 |
| `advisor.category.*` | 어드바이저 제안 분류(비용·안정성·성능·보안·DB) 전용 의미가 이미 붙어 있다. 같은 색이 다른 뜻으로 두 곳에 있으면 안 된다 |
| `bg.*`·`border.*` | 판·격자·라벨 halo는 이것으로 되지만, 3D 장면 배경·안개·연결선·유령 윤곽은 2D UI 표면과 밝기 기준이 달라야 한다(블록이 배경과 분리돼 보여야 함) |

→ **새 그룹 `color.<theme>.viz`를 만든다.** 3D 장면에서만 쓰고, 2D UI에는 쓰지 않는다.

### 5.2 종류 구분 팔레트 = **층 팔레트**

개별 종류(17가지 이상)마다 색을 주지 않고 **층 5가지**에만 색을 준다. 개별 종류는 ① 오버레이 이름 줄의 종류 아이콘 12px(4.3) ② 라벨 ③ 선택 패널·관계 표의 종류 이름으로 구분한다.

- 이유 1: 색 17개는 라이트·다크·색맹 세 조건을 동시에 만족시킬 수 없다. 색 5개는 가능하다.
- 이유 2: 색이 층(= 높이)과 같은 것을 가리키면 위에서 본 시점에서 높이 정보를 잃어도 층을 알 수 있다(중복 부호화).
- 이유 3: 필터·범례가 5줄로 끝난다.

| 토큰 | 층 | 라이트 fill / edge / onFill | 다크 fill / edge / onFill | 색상(H) | 밝기 순서 |
|---|---|---|---|---|---|
| `viz.kind.workload` | 워크로드 | #5B8BEF / #2A5FC9 / #0B1A33 | #4E79D8 / #7AA3F2 / #F0F4FF | 파랑 220° | 4 (어두움) |
| `viz.kind.service` | 서비스 | #9B7AE0 / #6B45B8 / #170B2E | #8A6BD0 / #B392F0 / #F6F0FF | 보라 265° | 3 |
| `viz.kind.ingress` | 진입 | #E08FB8 / #B85586 / #2E0F22 | #C97BA6 / #F0A8CE / #FFF0F7 | 자홍 330° | 2 |
| `viz.kind.storage` | 저장·설정 | #62C5BB / #14867E / #052A27 | #2E9F97 / #3DD1C7 / #E6FFFC | 청록 175° | 1 (밝음) |
| `viz.kind.aux` | 곁 | #B4BECF / #7A8592 / #1B1F24 | #59626F / #8A93A0 / #E6E9ED | 중립 215° | — |

- **색맹**: 파랑·보라·자홍·청록은 적록색약(1형·2형)에서 서로 다른 명도·채도로 남는다. 빨강·초록·노랑을 아예 쓰지 않아 가장 흔한 혼동 축을 피했다. 위 표의 "밝기 순서"대로 회색조에서도 4단계가 남는다(인접 단계 상대 휘도 비 1.25 이상).
- `aux`는 유일한 중립색이지만 **곁 타일은 높이 0.75u의 납작한 타일**이라 다른 층의 3u 블록과 모양이 다르고, 판 가장자리 띠라는 위치도 다르다. 상태 `unknown`(#8C95A1)과 가까워 보일 수 있어 라이트에서 한 단계 밝게(#B4BECF), 다크에서 한 단계 어둡게(#59626F) 잡았다.
- 드리프트 색 규칙(`status.md` 10.3 중립·빨강/초록 금지)은 **그대로**다. 드리프트는 면 색이 아니라 표식 아이콘으로만 나타난다.

### 5.4 이 기능이 **만들지 않는** 색

- diff 색(추가 초록 / 삭제 빨강): 금지 유지(`status.md` 10.3).
- 관계 종류별 색: 만들지 않는다(4.5).
- 네임스페이스별 색: 만들지 않는다. 네임스페이스는 판(위치)으로 구분한다. 네임스페이스 수는 스냅샷마다 달라 고정 팔레트를 만들 수 없고, 색을 돌려 쓰면 스냅샷마다 같은 이름이 다른 색이 된다.

- 2번 개수 칩의 툴팁에는 **항상** 전체 수를 붙인다: `전체 블록 33(유령 9) · 전체 관계 26`(4.4의 유령 숨김 때문에 그린 수와 전체 수가 다를 수 있다).
- **줄바꿈 금지 (2026-09-20 (5) 변경)**: 정보 줄은 **높이 20px 한 줄**을 넘지 않는다. 칩 폭 합계가 480px을 넘으면 뒤에서부터 **8번 → 7번 → 6번** 순으로 `+N` Chip 하나(아이콘 없음)로 합쳐 480px 안에 넣는다. 1~5번과 9번은 합치지 않는다(우선순위 1·2).

  - 툴팁 내용: 합쳐진 칩의 **문구를 순서대로 ` · `로 이은 한 덩어리**. 예 `묶어 보기 · 라벨 19개 숨김 · 일부가 화면 밖`. 아이콘·줄바꿈 없이 글자만 쓴다.

  - 그래서 `+N`은 **탭 정지점이 아니다**(11.1). 합쳐져 동작이 사라진 정보는 ① 관계 표(`gview=table`)와 ② 선택 패널에 모두 남아 있다.

  - 이전 규칙(줄바꿈 허용 + 6개 초과 시 합침)을 버리는 이유: 정보 줄이 2줄이 되면 카메라 안전 영역의 위 여백이 44 → 76px로 커지고(4.9-1), 안전 영역 중심이 캔버스 중심보다 32px 아래로 내려가 **장면이 아래로 몰린다.** 실제로 1440px 기준 장면에서 칩이 7개(mock·개수·드리프트·`라벨 N개 숨김`·`표식 N개 숨김`·`일부가 화면 밖`·안내)가 되어 2줄이 됐다. **정보 줄 높이를 상수로 만들어야 카메라 규칙이 상수가 된다.**
- **누르면 동작하는 칩 (`onClick`, 2026-09-20 (5) 신설 — publisher 요청 ① 수용)**: 정보 줄 칩은 `href`(링크) 또는 `onClick`(동작) 중 **하나만** 갖는다. 둘 다 없으면 툴팁만 있는 글자다.

|---|---|---|
| 5번 `리소스 밖 발견 N건` | `href` | 파일 탭 스캔 발견 보기 |

### 6.5 범례 (2026-09-20 변경 — **캔버스 밖 Popover**)

프론트 보고: 캔버스 768 × 636px에서 범례(200 × 약 380px)가 왼쪽 아래 1/4을 덮어 **왼쪽 뒤 판이 완전히 가렸다.** 두 안(① 기본 접힘 ② 캔버스 밖) 중 **② 캔버스 밖**을 고른다.

- **왜 ①(기본 접힘)이 아닌가**: 접힘은 문제를 미루기만 한다. 범례는 "블록 색 = 층, 상태 아님"을 배우는 곳이라 사용자가 한 번은 편다. 펴는 순간 같은 자리가 다시 가려지고, 그때 카메라를 다시 맞추면 장면이 출렁이고 안 맞추면 판이 가려진 채로 남는다. 또 카메라 안전 영역(4.9)이 범례 상태에 따라 200px씩 달라지면 **같은 스냅샷을 열 때마다 처음 화면이 달라진다.**

## 7. 선택 정보 패널 (4열 376px)

- **이 패널이 "이름을 정확히 읽는 자리"다 (2026-09-20 (7) 원칙).** 3D 장면의 블록 라벨은 붐비면 줄어들고 숨는다(4.7.1). **3D는 구조를 파악하는 화면이고, 이름·경로·관계를 글자로 확인하는 일은 이 패널과 관계 표(8절)가 맡는다.** 그래서 이 패널의 이름·파일 경로는 **어떤 경우에도 줄이지 않는다**(7.2의 말줄임은 패널 폭 376px을 넘을 때만이고, 전체 값은 툴팁·복사 버튼으로 항상 얻을 수 있다).
- **모든 블록의 이름을 한꺼번에 보려면 관계 표**(`gview=table`, 8절)다. 정보 줄의 `라벨 N개 숨김` 칩이 그리로 데려간다(4.7.1 ④).

- `custom_resource`에 **표식 원을 만들지 않는 이유**: 표식 원 5종(스캔·드리프트·파일 문제·Helm·유령)은 모두 "봐야 할 것"인데, 사용자 지정 리소스는 그 자체로 할 일이 없다. 대신 곁 층(`aux`)에 놓이는 위치와 정보 줄 칩으로 전체 개수를 알린다.
- 모든 문구는 **서버 `text` 그대로**다. 화면은 길이를 줄일 때만 짧은 문구를 쓰고 **전문은 툴팁·선택 패널 ④**에 남긴다. 짧은 문구를 쓰는 곳은 두 군데뿐이다:

|---|---|---|
| `pvc_template_unmatched` | `PVC 템플릿 2개 — 스냅샷에 맞는 PVC가 없습니다.` | `맞는 PVC 없음 (템플릿 2)` — `count`가 없으면 `맞는 PVC 없음` |

- 짧은 문구는 **표 표식 열(200px)과 3D 보조 줄(최대 120px)에서만** 쓴다. 두 자리 모두 한 줄이라 전문이 잘려 뜻이 끊긴다(`PVC 템플릿 2개 — 스냅샷에…`). 선택 패널 ④와 툴팁에는 언제나 전문이 있다.

## 8. 관계 표 (대체 보기, 3D 3.7 Q2 = A안)

- **2D 평면도는 만들지 않는다**(사용자 확정). 대체 보기는 관계 표 하나다.
- 관계 표는 "3D를 못 쓸 때의 차선"이 아니라 **항상 쓸 수 있는 같은 급의 보기**다. 도구 막대 A의 [3D | 표]로 언제든 바꾼다(필터·검색·선택 유지).
- **이름 전수 확인은 이 표가 맡는다 (2026-09-20 (7) 원칙).** 3D 장면은 층 안에 블록이 몰리면 이름을 줄이거나 숨긴다(4.7.1 — 기준 장면에서 27개 중 7개만 보인다). 그것은 결함이 아니라 **역할 분담**이다: **3D = 구조(무엇이 어디에, 무엇과 이어졌나), 표 = 목록(모든 이름·경로·관계를 잘림 없이)**. 두 보기의 수치는 언제나 같다(AC-3D04).
- 그래서 표는 **이름 열을 줄이지 않는다.** 정보 줄의 `라벨 N개 숨김` 칩을 누르면 바로 이 표로 온다.

| 위치 | 136px | 네임스페이스 mono 12. 클러스터 범위 `클러스터 범위`, 해석 실패 `해석 실패` |
| 표식 | 200px | 4.8 아이콘 12px + 문구(`변경 2`, `오류 1`, `유령`, `Helm`, `비교 불가`). 줄바꿈 허용, 최대 2줄 |
| 들어옴 | 72px, 오른쪽 | tabular 숫자. 0이면 `text.tertiary` |
| 나감 | 72px, 오른쪽 | 같음 |
| 동작 | 176px, 가운데 | `Button` ghost sm `파일`(아이콘 `file-text`) + 4px + ghost sm `드리프트`(`git-compare`). 10.4 규칙으로 표시·비활성 |

- 열 합계: 320 + 136 + 200 + 72 + 72 + 176 = 976px, 남는 폭은 이름 열이 먹는다(최대 504px).
- 행을 누르면 **펼쳐져** 관계 목록(7.3 `RelationItem`을 가로 2열로 배치, 들어옴/나감 제목 포함)이 나온다. 펼침 영역 배경 `bg.surfaceSunken`, 패딩 12px 16px.
- 기본 정렬: **3D의 배치 순서와 같다** — 네임스페이스 이름순 → 층(저장·설정 → 워크로드 → 서비스 → 진입 → 곁) → 종류(서버 순서) → 이름순. 마지막에 클러스터 범위 → 해석 실패 → 유령 판. `status.md` 5.2의 k8s 트리 정렬과 같은 계열이다. **열 정렬 버튼은 표식 열에만** 둔다(표식 있는 것 먼저 → 기본). 이유: 다른 열로 정렬하면 3D와 순서가 달라져 "같은 데이터"라는 약속이 흔들린다.
- 기본 펼침: 리소스 150개 이하면 그룹 모두 펼침, 초과면 네임스페이스만 펼치고 층은 접음. 200행을 넘으면 가상 스크롤(`status.md` 5.4).
- 표 위 왼쪽 caption `text.secondary`: `블록 128개(유령 6) · 관계 164개 · 드리프트 표식 3 · 스캔 표식 2` — **3D 정보 줄과 같은 수치**(AC-3D04). 필터 중이면 `블록 128개 중 12개 …`.
- 선택(`res=`)된 행은 `bg.selected` + 왼쪽 3px `accent.default`, 열린 상태로 스크롤해 보인다. 3D에서 고른 블록이 표로 바꿔도 그대로 선택돼 있다.
- 빈 결과: `EmptyState` sm `조건에 맞는 리소스가 없습니다` + ghost sm `필터 초기화`.

### 8.3 그룹 행 (판 · 층)

그룹 행은 두 가지다. **판(네임스페이스) 행만 표식·동작을 가진다** — 판이 곧 `namespace.yaml` 문서이기 때문이다. 층 행은 리소스가 아니라 묶음일 뿐이라 표식 열·동작 열을 비운다.

| 열 | 판 그룹 행(depth 0) | 층 그룹 행(depth 1) |
|---|---|---|
| 종류 · 이름 | `chevron-right`/`chevron-down` 12px + **판 아이콘 14px**(네임스페이스 `folder` / 클러스터 범위 `globe` / 해석 실패 `file-warning` / 유령 판 `circle-dashed`, 4.10) + 이름 captionStrong 13/20 + caption `text.tertiary` 개수 + 시스템·클러스터 범위·해석 실패 Chip | 들여쓰기 16px + `layers` 12px + 층 이름 caption `text.secondary` + `(3)` |
| 위치 | mono 12/20 `prod/namespace.yaml`(가운데 말줄임, 파일 이름 보존, 툴팁 전체). 없으면 `text.tertiary` `파일 없음` | 비움 |
| 표식 | **`BlockMarkers` inline** — 판 표식(4.1.1)을 아이콘 12px + 문구로. 3D 알약과 **같은 순서·같은 문구**, 최대 2줄 | 비움 |
| 들어옴 / 나감 | `—` `text.tertiary`(판은 관계를 갖지 않는다, `aria-label="해당 없음"`) | 비움 |
| 동작 | `Button` ghost sm `파일`(`file-text`) / `드리프트`(`git-compare`) — 4.1.1 클릭 표와 같은 주소. 조건에 맞지 않으면 그리지 않는다 | 비움 |

- 행 높이는 리소스 행과 같은 40px. 판 행 배경 `bg.surfaceSunken`, 층 행은 배경 없음 + 위 1px `border.subtle`.
- **클릭 영역 분리**: `chevron` + 이름 = 펼침/접힘 토글, 표식·동작 버튼 = 각자 동작(클릭 전파 막음). 판 행은 `res=`로 **선택되지 않는다**(판은 선택 대상이 아니다, 7.1).
- 행 `aria-level`(판 1 / 층 2) + `aria-expanded`. 스크린리더 문장: `prod, 리소스 11개, 변경됨 필드 1건, 스캔 경고 2건, 펼침`.
- **그룹 행 개수 표기 (2026-09-20 확정)**: 필터·검색이 하나도 없으면 `(11)` **전체 수**, 필터 중이면 `(3 / 11)` = **보이는 수 / 전체 수**. 자식이 0인 판은 `(0 / 11)`. 두 수를 함께 적는 이유는 정보 줄이 같은 형식(`블록 33개 중 12개`, 6.1)을 쓰기 때문이고, `(3)`만 두면 "이 판에 리소스가 3개뿐"으로 읽히기 때문이다. 층 그룹 행도 같은 규칙. `title`은 `보이는 리소스 3개, 전체 11개`.
- **표식이 있는 판은 자식 행이 0개여도 남긴다**(필터로 리소스가 다 걸러진 경우). 이름 뒤 caption `text.tertiary` `표시할 리소스 없음`을 붙이고 펼침 화살표를 비활성으로 둔다. 표식이 없고 자식이 0이면 행을 숨긴다. — 판 표식은 필터로 사라지지 않는다는 4.1.1 규칙을 표에서도 지키기 위해서다.
- 정렬(`표식` 열)을 켜면 **판 순서는 그대로 두고 판 안에서만** 다시 정렬한다. 표식이 있는 판을 위로 올리지 않는다(판 순서는 3D 배치와 같아야 한다, `status.md` 11.4).

### 9.3 WebGL 없음 (AC-3D03)

- 탭을 열면 **관계 표로 열린다**(오류·빈 화면 없이). 표 위에 `InlineAlert` neutral(아이콘 `info`, 닫을 수 없음):
  - 제목 `이 브라우저에서 3D를 쓸 수 없어 표로 보여 줍니다`
  - 설명 `WebGL을 쓸 수 없는 환경입니다(원격 데스크톱·그래픽 가속 꺼짐 등). 표에는 3D와 같은 블록·관계가 모두 있습니다.`
- 도구 막대 A의 `3D` 칸은 `aria-disabled` + 툴팁 `이 브라우저에서 3D를 쓸 수 없습니다`. 저장소의 보기 선택은 바꾸지 않는다(2.3).

### 9.4 3D 청크 로딩 실패 · 컨텍스트 손실

| 경우 | 모습 |
|---|---|
| 청크 로딩 실패 | 관계 표로 전환 + `InlineAlert` **warn**: 제목 `3D 보기를 불러오지 못했습니다`, 설명 `네트워크 문제일 수 있습니다. 표는 그대로 쓸 수 있습니다.`, 액션 `Button` secondary sm `다시 시도` |
| WebGL 컨텍스트 손실 | 관계 표로 전환 + `InlineAlert` neutral: 제목 `3D를 잠시 멈췄습니다`, 설명 `그래픽 장치 연결이 끊겨(컨텍스트 손실) 3D를 껐습니다. 선택·필터는 그대로입니다.`, 액션 secondary sm `3D 다시 켜기` |

- **이 표의 세 알림에는 모두 `live`를 준다 (2026-09-20 (5) 확정 — publisher 요청 ② 수용).** `live`를 주는 기준은 "사용자가 누르지 않았는데 나타나는 알림"이고(`components.md` 6.2), 청크 실패·컨텍스트 손실·조회 실패는 모두 그렇다. 따라서 **`live`를 주는 알림은 9.4 · 9.5 · 9.8 세 곳**이다. 9.3(WebGL 없음)·9.9(잘림)는 **탭을 여는 순간부터 있는 사실**이라 주지 않는다(진입 시 낭독이 두 번 겹친다).
- 9.4의 알림은 `Scene3DFrame`이 상태(`chunkFailed`·`contextLost`·`error`)에 따라 **컴포넌트 안에서** 그리므로, `live`는 프론트가 넘기는 값이 아니라 **컴포넌트가 고정으로 켠다**(`components.md` 16.1).

### 9.5 저사양 (AC-3D07)

- 조건: 조작 중 5초 동안 중앙값 20fps 미만(프론트 측정).
- **강제 전환하지 않는다.** 다음을 자동으로 적용하고 정보 줄에 Chip neutral sm `간소화 켬`(툴팁 `라벨을 줄이고 먼 블록을 단순하게 그립니다`)을 보인다:
  1. 라벨 밀도 `선택·검색 결과만`으로 내림(사용자가 다시 올릴 수 있음, 올리면 자동 간소화는 그 뒤로 라벨을 건드리지 않는다)
  2. 기본 끔 관계를 켜 두었으면 끔을 권하는 문구를 알림에 포함
  3. 안개 끝 거리 축소(`카메라 거리 + 대각선 × 0.7`, 5.3)
- 동시에 캔버스 아래쪽 가운데에 `InlineAlert` neutral compact(**`closable`**, 한 번 닫으면 이 스냅샷을 보는 동안 다시 뜨지 않음 — `components.md` 6.2): `3D가 느립니다. 표로 보기를 권합니다.` + `Button` ghost sm `표로 보기`.

### 9.7 큰 규모 (AC-3D22)

- **기준은 서버 값이다**: 화면이 3,000을 직접 세지 않고 `summary.grouped`가 참일 때 묶어 보기로 연다. 안내 문구의 숫자는 `summary.groupThreshold`·`summary.blocks`를 그대로 쓴다(운영에서 `K8S_GRAPH_GROUP_THRESHOLD`가 바뀌어도 화면 문구가 어긋나지 않게).
- 묶음은 `groups[]`(판 × 층 × 종류)를 그대로 쓴다. 묶음 블록의 표식 합계는 `groups[].drift`·`groups[].scan`이고, 화면이 블록을 세어 다시 만들지 않는다.
- 블록 3,000개 초과면 **묶어 보기**로 연다.
  - 판 위 각 층에 **묶음 블록**: 밑면 6u × 6u, 높이 3u, 면은 층 색 fill(불투명도 0.9) + 윤곽 1.5px, **윗면 아이콘 없음**(4.3). 오버레이 라벨 `ConfigMap 412`(micro, 숫자 필수) 앞에 종류 아이콘 12px.
  - **묶음 블록의 모양은 그 종류의 모양**(4.11)을 가로·세로 **1.5배**(6u × 6u)로, 높이는 3u 그대로 늘린 것이다. 묶음 기준이 종류(판 × 층 × 종류)라 모양이 그대로 뜻을 갖는다. 앵커는 지금처럼 6u 봉투의 상단 중심이다.
  - 묶음 기준: 네임스페이스 × 종류.
  - 묶음 블록을 한 번 클릭 = 선택(패널에 종류·개수·드리프트 표식 합계·스캔 합계), 두 번 클릭 = **그 묶음만 펼침**(그 자리에 개별 블록 격자로 교체, 다른 묶음은 그대로). 펼친 묶음은 정보 줄에 Chip `prod / ConfigMap 펼침` + `x`로 접기.
  - 관계선은 펼친 묶음에 속한 블록에만 그린다. 묶음끼리는 선을 그리지 않는다(묶음 간 선 수가 관계 수와 달라 오해를 부른다). 대신 묶음 블록 선택 시 패널에 `이 묶음의 관계 1,204개 — 펼치면 선을 그립니다`.
- 정보 줄 Chip neutral sm `묶어 보기`(툴팁 `리소스가 3,000개를 넘어 종류별로 묶어 보입니다. 표 보기에는 전체가 있습니다.`).
- **관계 표는 언제나 전체 행**을 보인다(묶지 않는다).

### 9.8 구성이 바뀜 (AC-3D16)

- 표식·라벨만 바뀌는 변경(드리프트 결과, 스캔, Helm 등): **말없이 갱신**한다. 카메라·선택 그대로.
- 블록·판·관계가 생기거나 없어지는 변경: 장면은 **그대로 두고** 캔버스 위쪽 가운데에 `InlineAlert` info compact(그림자 sm, 폭 최대 420px): `구성이 바뀌었습니다 (블록 +2 · −1)` + `Button` primary sm `다시 배치`. 누르면 새 배치로 다시 그린다(카메라 유지).
- 선택한 블록이 없어졌으면: 선택 해제 + 위 알림 설명에 한 줄 추가 `고른 블록(Deployment api)이 더 이상 없습니다.` `res=`를 지운다.
- 알림 등장에 애니메이션을 쓰지 않는다(reduced-motion과 무관).

### 9.9 일부만 표시 (`summary.truncated`)

서버 안전 장치(계약 10.1: 블록 20,000 · 관계 40,000 상한)에 걸리면 응답 자체가 잘린 채 온다. **3D와 관계 표가 같은 배열을 쓰므로 표도 같은 범위**다. 이 사실을 숨기면 "없는 리소스"로 읽히므로 두 곳에 남긴다.

| 자리 | 모습 |
|---|---|
| 정보 줄 | Chip neutral sm `일부만 표시`(아이콘 `triangle-alert` 12px `status.warn.fg`, 6.4-6). 툴팁 `블록 20,000개 · 관계 40,000개까지만 그립니다. 블록 1,204개 · 관계 2,300개를 뺐습니다.` |
| 캔버스 위쪽 가운데 | `InlineAlert` **warn** compact(폭 최대 420px, shadow sm, **`closable`** — 한 번 닫으면 이 스냅샷을 보는 동안 다시 뜨지 않는다): 제목 `구성이 너무 커서 일부만 그립니다`, 설명 `표시하지 못한 블록 1,204개 · 관계 2,300개. 표 보기도 같은 범위입니다. 네임스페이스 필터로 범위를 좁혀 보세요.` |
| 관계 표 | 표 위 같은 `InlineAlert`(닫기 없음 — 표에는 정보 줄이 없어 다른 단서가 없다). 설명 가운데 한 마디만 바꾼다: `… 표시하지 못한 블록 1,204개 · 관계 2,300개. **3D 보기도 같은 범위입니다.** 네임스페이스 필터로 범위를 좁혀 보세요.` 표 위 요약 문구 뒤에 `(1,204개 제외)` |

- **문구 두 벌 확정 (2026-09-20 (5) — 프론트 확인 요청)**: 3D 쪽은 `표 보기도 같은 범위입니다.`, 표 쪽은 `3D 보기도 같은 범위입니다.` 나머지 문장은 글자 하나까지 같다. 보고 있는 쪽을 가리켜 "저기 가면 더 있다"고 오해하게 만들지 않는 것이 목적이다.
- 숫자는 `truncated.droppedBlocks`·`droppedEdges`를 그대로 쓴다. `reason`이 `BLOCK_LIMIT`이든 `EDGE_LIMIT`이든 문구는 같다(사용자가 할 일이 같다).
- 정보 줄 2번 개수 칩은 **잘린 뒤 실제로 그린 수**(`summary.blocks`·`summary.edges`)를 보인다. 잘리기 전 전체 수를 모르므로 `N개 중 M개` 형식을 쓰지 않는다.
- 잘림 알림은 "구성이 바뀌었습니다"(9.8)·저사양(9.5) 알림과 **같은 자리**를 쓴다. 동시에 생기면 세로로 쌓고(간격 8px) **최대 2개**까지만 보인다. 우선순위: ① 잘림 ② 구성 변경 ③ 저사양.
- 잘림은 오류가 아니다. `graph.state`는 여전히 `ok`이고 장면·표는 정상으로 조작할 수 있다.

## 10. 드리프트 · 스캔 겹쳐 보기

### 10.1 겹쳐 보기 규칙

- 기본 **켬**. 쓰는 결과: `DriftBadge.mode`가 `auto`/`on_demand`이거나, `last_result`이면서 `resultAvailable: true`(K8S-D 3.5 판단과 같음).
- 표식 → 블록 매핑은 `resources[].change`(리소스 단위)와 `files[].drift`(파일 단위)를 쓴다. **3D가 드리프트를 새로 계산하지 않는다.**

| 서버 값 | 블록 |
|---|---|
| `changed` | `square-dot` 표식 + 선택 패널 `변경됨 · 필드 N건` |
| `deleted` | `square-minus` 표식(블록은 그대로 — 스냅샷에는 있다) |
| `added` | **유령 블록** + `square-plus`(해당 네임스페이스 판 위, 판이 없으면 유령 판) |
| `same` | 표식 없음(숨긴 차이만 있는 것도 없음) |
| `uncomparable` | `eye-off` 표식 + 사유 문구 |
| `skipped` | `file-warning` 표식 + `비교 못 함 (해석 실패·중복)` |

- 계산 시각은 도구 막대 B와 정보 줄 양쪽에 **항상** 보인다. `last_result`면 `지난 결과 · 9월 18일 14:02`, stale이면 stale 배지.
- 드리프트 표식 수는 드리프트 응답의 건수와 같아야 한다(AC-3D27). 숨긴 차이만 있는 리소스는 세지 않는다.

### 10.2 드리프트 결과가 없을 때 (AC-3D28)

- 구성도는 **정상으로 그린다**. 도구 막대 B:
  - 스위치 `aria-disabled` + 툴팁 = 사유(`actions.computeDrift.reasonText`, 없으면 K8S-D 3.5.1 대체 문구)
  - 뒤에 caption `text.tertiary` `계산 안 함`
  - `actions.computeDrift.allowed`이면 `Button` ghost sm `드리프트 계산`(아이콘 `git-compare`). 누르면 **기존 `POST …/drift`** 를 그대로 쓴다. 계산 중에는 버튼 loading `계산 중`, 끝나면 표식이 그려지고 스위치가 켜진다.
  - 계산 불가(다른 클러스터·연결 없음 등)면 버튼 대신 사유 문구만.
- 3D 보기를 열어 둔 동안 요청 계산의 **임대를 갱신**한다(K8S-API 10.8, 드리프트 탭과 같은 동작). 탭을 떠나면 갱신을 멈춘다.
- 다른 클러스터 스냅샷(K-9): 구성도는 보이고 사유는 `다른 클러스터`.

### 10.3 스캔 겹쳐 보기

- 파일에 현재 스캔 발견이 있으면 그 파일의 블록(여러 문서면 모두)에 등급 표식(4.8).
- 블록이 없는 발견(`metadata.json`, `secret-refs.json`)은 정보 줄 칩 `리소스 밖 발견 N건`으로만(6.4-5).
- 스캔은 **끄고 켜는 스위치를 두지 않는다**: 파일 상태(커밋 금지)는 이 기능의 최우선 정보라 숨길 수 있게 하지 않는다(1절, K8S-D 1절).

### 10.4 이동 규칙 (AC-3D30·32)

| 블록 | [파일에서 보기] | [드리프트에서 보기] | 기본 이동(두 번 클릭 / `Enter`) |
|---|---|---|---|
| 보통 리소스 | `?view=files&file=<경로>` | 드리프트 표식이 있을 때만 `?view=drift&res=<resourceKey>` | 드리프트 표식 있으면 드리프트, 없으면 파일 |
| 스캔 발견이 있는 리소스 | `?view=files&file=<경로>&line=<첫 발견 줄>` | 위와 같음 | **파일 + 발견 줄**(스캔 오류가 드리프트보다 급하다, 1절) |
| 유령 — 드리프트 `added` | 없음(비활성 + 툴팁 `이 리소스는 스냅샷에 파일이 없습니다`) | `?view=drift&res=<key>` | 드리프트 |
| 유령 — Secret 참조 | 없음 | 없음 | **`?view=secrets`**(Secret 참조 탭). 버튼 라벨 `Secret 참조에서 보기`(아이콘 `key-round`) |
| 유령 — 그 밖(ConfigMap 없음, SA 없음 등) | 없음 | 없음 | 이동 없음. 버튼 자리에 caption `text.tertiary` `스냅샷에 파일이 없어 이동할 곳이 없습니다` |
| 해석 실패 파일 블록 | `?view=files&file=<경로>` | 없음 | 파일 |
| 묶음 블록(9.7) | — | — | 묶음 펼침 |

- 여러 문서가 든 파일의 블록은 **모두 같은 파일**로 간다. 문서 위치로 줄을 이동하지 않는다(서버가 문서 시작 줄을 주면 그 줄로 — 14절 요청).
- 이동은 **같은 페이지의 탭 전환**이라 편집 중 이탈 확인을 띄우지 않고 파일 탭의 편집 내용을 유지한다(K8S-D 4.5).

## 11. 접근성

### 11.1 키보드 (AC-3D06)

캔버스는 **하나의 탭 정지점**(`tabindex="0"`)이다. 탭 순서: 도구 막대 A → 도구 막대 B(**범례 버튼 포함**) → **캔버스** → 카메라 오버레이 → 선택 패널. (2026-09-20: 범례가 캔버스 밖 팝오버가 되면서 캔버스 뒤의 `범례` 정지점이 없어졌다. 팝오버를 열면 포커스가 팝오버 안으로 들어가고 닫으면 버튼으로 돌아온다 — `Popover` 기본 동작.)

| 키 | 동작 (캔버스에 포커스가 있을 때) |
|---|---|
| `↑` `↓` `←` `→` | 카메라 회전 (1회 5°) |
| `Shift` + 방향키 | 카메라 이동(팬, 1회 화면 40px) |
| `+` / `-` | 확대 / 축소 (1회 12%) |
| `0` | 카메라 초기화 |
| `1` / `2` / `3` | 시점: 위에서 / 비스듬히 / 앞에서 |
| `]` / `[` | **다음 / 이전 블록 선택**(배치 순서 = 8.2 표 정렬과 같음). 선택하면 카메라가 그 블록을 비춘다 |
| `Home` / `End` | 첫 / 마지막 블록 |
| `PageDown` / `PageUp` | 다음 / 이전 네임스페이스 판의 첫 블록 |
| `Enter` | 선택한 블록의 기본 이동(10.4) |
| `Esc` | 선택 해제. 선택이 없으면 캔버스 포커스 해제 |
| `f` | 주변만 보기 켜고 끄기(선택 있을 때) |
| `t` | 표 보기로 전환 |
| `?` | 조작 도움말 Popover |
| `Tab` | 캔버스를 벗어나 **정보 줄의 동작 칩 → 카메라 오버레이** 순으로 (블록을 순회하지 않는다 — 블록이 1,000개면 표에 도달할 수 없다) |

- **관계를 따라 이동**하려면 선택 패널의 관계 목록(7.3)을 쓴다. 각 항목이 버튼이라 `Tab`·`Enter`로 상대 블록을 선택할 수 있다.
- **정보 줄 칩의 탭 정지점 (2026-09-20 (5) · (6) 보탬)**: `href`·`onClick`이 있는 칩만 정지점이다(6.4 표의 5·6·7·8번 일부). 툴팁만 있는 칩(`블록 27 · 관계 15`, `묶어 보기`, **`+N` 합침 칩**, 안내 `circle-help`)은 정지점이 아니다 — 같은 내용이 캔버스 `aria-label`(11.2)에 이미 문장으로 있다.
- 캔버스 바로 앞에 **건너뛰기 링크** `표로 보기`(`Button` ghost sm, 평소 시각적으로 숨김 `sr-only`, 포커스를 받으면 캔버스 왼쪽 위에 나타남)를 둔다. 누르면 `gview=table`.
- 도구 막대·오버레이·패널의 모든 컨트롤은 마우스 없이 쓸 수 있고, 최소 클릭 영역 32×32px(`status.md` 7절).
- 조작 도움말 Popover(320px)에 위 표를 그대로 싣고, 처음 3D 보기를 연 사용자에게는 도움말 버튼 옆에 8px 점(`accent.default`)을 한 번 보인다(`sentinel.snapshots.k8s.help3d`).

### 11.2 스크린리더

- 캔버스: `role="application"` + `aria-roledescription="3D 구성도"` + `aria-label` 요약 —
  `Kubernetes 구성도, 네임스페이스 5개, 리소스 128개, 관계 164개, 드리프트 차이 3건, 스캔 오류 1건`
  (필터 중이면 `… 중 12개 표시`). 값이 바뀌면 이 라벨도 갱신한다.
- `aria-describedby`로 조작 안내 한 줄: `방향키로 회전, 대괄호 키로 블록 이동, 엔터로 이동, 표로 보려면 T.`
- 선택 결과는 캔버스 옆 보이지 않는 `aria-live="polite"` 영역에 문장으로 (7.1). 카메라 회전·확대는 읽지 않는다(소음).
- **3D는 보조 수단이고 구조적 정보의 기준은 관계 표**다: 표는 `<table>` + `aria-level`/`aria-expanded`를 가진 행 그룹으로 읽히고, 모든 블록·관계·표식이 문장으로 있다.
- 표식·확실성은 아이콘만 두지 않고 `title`/`aria-label`에 문구를 넣는다(`변경됨, 필드 2건`, `추정, 셀렉터`).
- 사용자 입력·리소스 이름·서버 문구는 모두 텍스트 노드로만 렌더한다(HTML·마크다운 해석 금지, ASM-D 11절).

### 11.3 `prefers-reduced-motion: reduce` (AC-3D05)

- 카메라 이동(초기화·시점·검색 결과 이동·블록 이동) **0ms 즉시 전환**.
- 자동 회전 없음(원래 없음), 깜박임·맥동 강조 없음, 알림 등장 페이드 없음, 로딩 스피너는 `Spinner` 기존 규칙을 따른다.
- 3D 자체는 **끄지 않는다**. 사용자가 원하면 계속 3D를 쓴다.
- 호버·선택 강조는 애니메이션 없이 즉시 켜고 끈다.

## 12. 반응형

| 뷰포트 | 3D 보기 탭 |
|---|---|
| ≥ 1440px (본문 1160px) | 캔버스 8열 768px + 선택 패널 4열 376px |
| 1280~1439px (본문 1168~1327px) | 같은 8:4. 늘어난 폭은 캔버스가 먹는다 |
| 1024~1279px (본문 976~1231px) | 캔버스 8열(최소 640px) + 패널 4열(최소 320px) 유지. 도구 막대 A에서 **관계·표식 필터를 `필터 ▾` 팝오버 하나로 접고**, 검색 폭 200 → 160px. 도구 막대 B에서 라벨 밀도 Select 라벨을 `라벨: 전체` → `전체`로 줄인다. 관계 표는 `위치` 열을 숨긴다(이름 열 그룹에서 읽힌다) |
| < 1024px | 지원 대상 아님(1024px 기준 가로 스크롤, 3D 명세 6절) |

- 캔버스 크기가 바뀌어도 **카메라 대상과 거리를 유지**한다(화각만 재계산). 창을 줄였다 늘였을 때 시점이 초기화되지 않는다.
- 기기 배율 1~1.5를 지원한다. 렌더 해상도는 `min(devicePixelRatio, 2)`(프론트).

**좁은 캔버스 완화 (2026-09-20 (5) 신설 — 프론트 요청 ② 수용)**

1024px 뷰포트에서는 캔버스가 640 × 504px까지 줄어드는데, `d_read`(블록 한 변 16px 하한)가 걸려 판 일부가 캔버스 밖으로 나갔다. **읽기 하한을 캔버스 높이에 따라 두 단계로 둔다.**

| 캔버스 높이 `h` | 블록 한 변 읽기 하한 `s_min` | 768×636 / 640×504에서 `d_read` |
|---|---|---|
| **600px 이상** | **16px** | 252u |
| **480 ~ 599px** | **13px** | 246u (h = 504px 기준) |

- 480px 미만은 생기지 않는다(3절 작업 영역 높이 하한 480px − 88px = 392px … **주의**: 실제로는 작업 영역 480px일 때 캔버스가 392px이 된다. 이때는 `s_min = 13px`을 그대로 쓰고, 그래도 걸리면 `일부가 화면 밖` 칩으로 알린다. 하한을 12px 밑으로 더 내리지 않는다).
- **왜 13px인가**: 이전 16px의 근거는 "윗면 종류 아이콘 16px을 그릴 수 있는 최소"였는데 윗면 아이콘을 폐지했다(4.3). 남은 근거는 ① 마우스로 집히는 최소 크기 ② 밝기 3단(100 / 82 / 64%)이 구분되는 최소 크기이고, 둘 다 **12px**이 하한이다. 여기에 1px을 더했다.
- **모양(4.11) 때문에 하한을 올리지 않는다**: 13px에서도 둥근 / 각진 / 구멍 / 얇음 네 갈래는 갈리고, 상단 차이(`stack`·`chamfer`·`roof`)만 흐려진다. 하한을 16px로 통일하면 좁은 창에서 판이 잘린다 — 그 대가가 더 크다(4.11.2).
- **왜 큰 캔버스까지 13px로 내리지 않는가**: 오버레이 상자가 최대 136px(4.7.1 B0)인데 블록이 13px이면 라벨이 블록의 10배가 되어 "블록 위의 라벨"이 아니라 "라벨 사이의 점"으로 읽힌다. 좁은 캔버스에서는 그 대가를 치르더라도 **판이 잘리지 않는 것**이 더 낫다.
- 1024px에서도 안전 영역 여백은 같다(위 44 / 오른 116 / 왼·아래 12px)이고, **맞춤 영역은 거기서 다시 26px 안쪽**이다(4.9-1-1).
- 4.1의 새 판 배치(3열·간격 8u)를 적용하면 기준 장면 규모(판 5장)에서는 1024px에서도 `d_fit < d_read`라 **애초에 상한에 걸리지 않는다**(frontend 실측: `일부가 화면 밖` 칩이 1024px에서도 뜨지 않았다). 완화는 그보다 큰 스냅샷을 위한 것이다.
- **위 표의 `d_read` 예시가 쓰는 캔버스 크기는 뷰포트 폭이 아니라 창 높이가 정한다.** 4.0의 실측대로 1440 × 900 창의 캔버스가 766 × **616px**이므로, 같은 창 높이라면 1024px 폭에서도 캔버스 높이는 616px이고 `s_min`은 **16px**이다. 창이 더 낮아 캔버스가 600px 밑으로 내려갈 때만 13px로 갈린다 — `s_min`은 **캔버스 높이**로만 갈린다.

## 14. 화면이 필요로 하는 값 (백엔드 계약 요청)

`docs/api/snapshot-3d.md`(또는 K8S-API 확장)에 아래가 있어야 이 설계를 그릴 수 있다. **서버가 판단하고 화면은 그린다**(`docs/api/common.md` 2.2). 화면은 관계·드리프트·표식을 다시 계산하지 않는다.

| 화면 개념 | 필요한 값 | 비고 |
|---|---|---|
| 판 | `plates[]`: `id`, `kind`(`namespace`\|`cluster`\|`unparsed`\|`ghost`), `name`, `system`(bool), `resourceCount` | 순서 = 화면 배치 순서(이름순). 4.1 |
| 블록 | `blocks[]`: `id`(= `resourceKey` 형식), `plateId`, `layer`(`storage`\|`workload`\|`service`\|`ingress`\|`aux`), `kind`, `apiVersion`, `name`, `namespace`, `file`(경로, 없으면 null), `fileLine`(문서 시작 줄, 여러 문서 파일용), `documentIndex`/`documentCount` | `layer`를 **서버가 준다**(화면이 종류→층 표를 따로 갖지 않게). 4.2·4.3 |
| 블록 순서 | `blocks[]` 배열 순서 그대로 배치 | 같은 입력 같은 배치(AC-3D11)의 근거 |
| 유령 | `blocks[].ghost`: `{ reason: "not_in_snapshot"\|"secret"\|"autocreated"\|"cluster_scope"\|"drift_added", text }` | 4.4 |
| 표식 | `blocks[].markers`: `scan{level,count}`, `drift{kind,fieldCount}`, `fileIssue{code,text}`, `helm`, `notComparable{reason,text}` | 4.8. 값은 기존 계약 값과 같은 코드 |

| 관계 | `edges[]`: `id`, `from`(blockId), `to`(blockId), `rule`(`K1`~`K11`), `certainty`(`confirmed`\|`estimated`), `evidence`(문구), `optional`(bool) | 4.5·4.6·7.3 |
| 요약 | `summary`: `blocks`, `ghosts`, `edges`, `driftMarkers`, `scanMarkers`, `outsideFindings`, `grouped`(bool), `truncated` | 6.4·8.2 수치가 3D와 표에서 같아야 한다(AC-3D04) |

| 계산 버튼 | 기존 `actions.computeDrift` 그대로 | 10.2 |
| mock | `MOCK 데이터` 배지 조건은 기존 규칙 | 9.6 |

- **응답에 들어오면 안 되는 것**(AC-3D14): env 값, command/args, 어노테이션 값, 레이블·셀렉터 원문, ConfigMap 내용, Secret 값. `evidence`는 `셀렉터`처럼 **어디서 뽑았는지**만 말하고 값을 담지 않는다.

- `blocks[].fileLine`이 없으면 여러 문서 파일의 이동은 파일 첫 줄로 간다(10.4 각주).

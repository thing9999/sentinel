# snapshot-3d · designer 작업 보고

> 파일 위치: `docs/reports/snapshot-3d/designer.md`
> 같은 기능에서 같은 역할이 다시 작업하면 새 파일을 만들지 말고 아래에 `## YYYY-MM-DD HH:mm · <작업 이름>` 섹션을 **추가**한다 (이전 섹션은 지우지 않는다).

## 2026-09-20 · 1단계(공통 기반 + K8s 구성도·드리프트) 화면 설계

### 1. 요청 내용

PM이 기능 `snapshot-3d`의 **1단계만** 설계하라고 지시했다.

- 범위: 공통 기반(3D 틀·관계 표 대체 보기·지연 로딩·접근성·성능) + K8s 구성도·드리프트 = **AC-3D01~33**.
- 2~4단계(AWS 구성도·시간축·통합 장면, AC-3D34~56)는 **보류**. 화면 구조만 열어 두고 설계하지 말 것.
- 사용자 확정 사항(그대로 따름)
  - 대체 보기는 **관계 표만**(2D 평면도 없음, 명세 Q2 = A).
  - 블록 **한 번 클릭 = 선택·정보 패널(이동 버튼 포함)**, **두 번 클릭·`Enter` = 파일/드리프트 탭의 해당 리소스로 이동**(Q3 = A).
  - 조회 전용(쓰기·적용 버튼 없음).
- planner의 designer 요청 중 1단계 해당분
  - k8s 상세에 "3D 보기" 탭 추가(기존 주소·기본 화면 유지, `?view=` 규칙을 기존과 일관되게)
  - 종류 구분 팔레트: 새 토큰이 필요한지 판단(기존 토큰 우선), 라이트·다크 모두에서 구분되고 색맹 고려, 드리프트 규칙과 충돌 금지
  - 3D 장면 구성(네임스페이스 바닥 판·리소스 블록·연결선·라벨), 도구 막대, 선택 정보 패널, 관계 표, 빈·로딩·WebGL 없음·저사양·오류 상태
  - 접근성: 키보드만으로 리소스 이동·선택·이동, 스크린리더 구조, `prefers-reduced-motion`
- 산출물: `docs/design/snapshot-3d.md` + 공통 문서 갱신. **코드 작성 금지**.

### 3. 작업 내용

1. **명세·기존 설계 대조.** 1단계 수용 기준(AC-3D01~33)을 하나씩 훑어 "화면이 책임지는 항목"을 뽑고, 기존 k8s 상세 화면(탭·작업 영역 높이·트리 마커·드리프트 규칙)과 충돌하지 않는 선을 정했다.
2. **`docs/design/snapshot-3d.md` 신규 작성** (16절 구성)
   - 0·1절: 화면 목록, 정보 우선순위(① 언제·무엇 → ② 어디가 달라졌나 → ③ 연결 → ④ 개별 → ⑤ 이동).
   - 2절: 상세 탭 6개(3번째에 `3D 보기`), URL 규칙(`view=3d`, 선택은 기존 `res=` 재사용, 3D 전용 필터는 `g` 접두사), 보기 기억(localStorage).
   - 3절: 레이아웃(캔버스 8열 768px + 선택 패널 4열 376px, 작업 영역 높이는 파일·드리프트 탭과 같은 `clamp(480px, calc(100vh - 176px), 960px)`).
   - 4절: 3D 장면 — 단위(1u = 8px), 판 5종, 층 5개와 높이(0 / 9 / 18 / 27u), 블록 치수(4u×4u×3u, 셀 6u), 유령 블록, 연결선(확정 실선 1.5px / 추정 dashed 6 3), 관계 K1~K11 필터 라벨·근거 문구, 라벨(밀도 3단계·겹침 규칙), 표식 9종(순서 고정), 카메라(기본 −35°/30°, 거리·고도 제한, 시점 3개, 300ms/0ms).
   - 5절: 색 — 새 토큰 필요성 판단표, **층 팔레트 5색**, 장면 색 16종, 만들지 않는 색(diff 색·관계별 색·네임스페이스별 색).
   - 6절: 도구 막대 A(48px)·B(40px), 카메라 오버레이, 정보 줄, 범례.
   - 7절: 상호작용(한 번/두 번 클릭·`Esc`·판 라벨), 선택 패널 6영역, `RelationItem` 44px.
   - 8절: 관계 표(12열, 열 6개, 트리 들여쓰기, 정렬은 3D 배치 순서와 동일, 표식 열만 정렬 가능, 수치 일치 규칙).

### 5. 주요 결정과 이유

| 결정 | 검토한 대안 | 고른 이유 |
|---|---|---|
| **종류 구분을 "층 팔레트 5색"으로** (종류 17+개에 색을 주지 않음) | ⓐ 종류마다 색 ⓑ 색 없이 아이콘만 | 색 17개는 라이트·다크·색맹 세 조건을 동시에 만족시킬 수 없다. 층(높이)과 색이 같은 것을 가리키면 위에서 본 시점에서 높이를 잃어도 층을 안다(중복 부호화). 개별 종류는 윗면 아이콘 + 라벨 + 패널·표의 종류 이름으로 구분한다. 색을 아예 안 쓰면 1,000 블록에서 덩어리 구분이 불가능하다 |
| **새 토큰 그룹 `color.*.viz` 신설** | `chart.series` 재사용, `advisor.category.*` 재사용, `status.*` 재사용 | `status.*`는 명세 3.5가 금지. `chart.series`는 ① 1.5~2px 선용 색이라 큰 면에서 과하고 ② 5번째 `#B07A2A`가 `status.warn.solid` `#BF8C00`, 8번째 `#7A8595`가 `status.unknown.solid` `#8C95A1`과 거의 같아 블록이 "주의·알 수 없음"으로 읽히며 ③ 서수라 고정 의미를 걸 수 없다. `advisor.category.*`는 다른 뜻이 이미 있다. 장면 전용 요소(배경·안개·판·격자·연결선·유령·라벨 halo)는 대응 토큰이 아예 없다 |
| 팔레트에 **빨강·초록·노랑을 쓰지 않음**(파랑·보라·자홍·청록 + 중립) | 무지개 팔레트 | 상태색(초록 ok·노랑 warn·빨강 crit)과 겹치지 않고, 적록색약의 가장 흔한 혼동 축을 피한다. 회색조에서도 4단계 명도가 남게 밝기 순서를 잡았다 |
| **관계선 색은 중립 한 가지**, 확정/추정만 실선·대시로 구분 | 관계 11종에 색 11개 | 색을 더 쓰면 층 팔레트와 충돌하고 색맹 환경에서 무너진다. "이 선을 믿어도 되나"가 실제 판단이므로 그 축만 모양으로 부호화했다 |
| **3D 보기 탭을 3번째**(파일·드리프트 뒤)에 두고 **숫자·상태 아이콘 없음** | 맨 뒤, 또는 드리프트 건수 표시 | 3D는 새 데이터가 아니라 파일+드리프트를 같이 보는 다른 방법이라 두 탭 옆이 맞다. 같은 숫자를 두 탭에 두면 어디를 눌러야 할지 모호해지고, 상태 아이콘은 파일 상태 전용 규칙(`status.md` 10.1)과 충돌한다. 탭 6개 폭 합계 약 596px로 1024px 뷰포트에서도 가로 스크롤이 없다 |
| **선택 쿼리는 기존 `res=` 재사용**, 3D 전용 쿼리는 `g` 접두사 | 모두 새 이름, 또는 모두 기존 이름 | `res=`는 값의 뜻이 같아(리소스 키) 3D ↔ 드리프트 탭 이동 시 선택이 그대로 이어진다. 반대로 종류 필터를 `kind=`로 두면 드리프트 탭의 `kind=changed|deleted|added`와 충돌해 탭을 오갈 때 서로를 덮어쓴다 |
| 캔버스 **왼쪽 8열**, 선택 패널 오른쪽 4열 (파일 탭과 반대) | 파일 탭처럼 4+8 | 3D는 "먼저 장면에서 찾고 그다음 읽는" 순서라 큰 영역이 왼쪽이다. 명세 시나리오 S1의 "오른쪽 패널"과도 맞는다. 작업 영역 높이는 파일·드리프트 탭과 같은 값을 써서 탭을 오갈 때 카드 높이가 튀지 않게 했다 |
| **배치 좌표는 서버가 주지 않고 화면이 규칙으로 계산** | 서버가 x/y/z 제공 | 규칙(판 이름순 → 층 → 서버 순서 → 격자 채움)이 결정적이라 같은 입력이면 같은 배치가 보장된다(AC-3D11). 좌표를 실으면 응답이 커지고 뷰포트·묶어 보기에 따라 다시 계산해야 한다. 대신 `layer`(층)는 **서버가 준다** — 화면이 종류→층 표를 따로 들고 있으면 서버와 어긋난다 |
| 키보드: **`Tab`은 캔버스를 벗어나고 블록 이동은 `]`/`[`** | `Tab`으로 블록 순회 | 블록이 1,000개면 `Tab`으로 순회할 때 표·다음 영역에 영영 도달하지 못한다. 관계를 따라가는 이동은 선택 패널의 관계 목록(버튼)으로 한다 — 3D에서 "다음 선"의 순서는 사용자가 예측할 수 없다 |
| 저사양은 **강제 전환하지 않고 자동 간소화 + 권유** | 자동으로 표로 전환 | 명세 3.7이 "강제 전환하지 않음"을 요구한다. 라벨 밀도 낮춤·안개 축소만 자동으로 하고 `표로 보기` 버튼을 권유로 둔다 |
| WebGL 없음·청크 실패·컨텍스트 손실은 **저장소의 보기 선택을 덮어쓰지 않음** | 저장소에 `table` 기록 | 환경 문제로 사용자의 선택을 바꾸면 정상 환경으로 돌아와도 계속 표가 열린다 |
| 스캔 겹쳐 보기에는 **끄는 스위치를 두지 않음**(드리프트만 끌 수 있음) | 둘 다 스위치 | 파일 상태(커밋 금지)는 이 기능의 최우선 정보라 숨길 수 있게 하지 않는다(`k8s-snapshot.md` 1절 우선순위) |
| 대체 보기는 **관계 표만** | 2D 평면도 추가 | 사용자 확정(Q2 = A). 표가 스크린리더·저사양·WebGL 없음을 한 번에 해결하고, 수치 일치(AC-3D04) 검증이 단순하다 |

### 7. 남은 이슈·한계

- **3D 조명 후 대비**: 블록 옆면(82%)·아랫면(64%) 밝기를 곱한 뒤에도 판·서로 간 3:1이 유지되는지는 실제 렌더에서 확인해야 한다. 안 되면 옆면 계수를 0.88로 올리는 것이 먼저이고 팔레트는 마지막에 손댄다.
- **라벨 겹침 알고리즘**: "화면 24px 반경 안에서 먼 라벨 숨김"의 비용이 1,000 블록에서 프레임 목표(중앙값 50fps)를 깎을 수 있다. 프론트가 측정 후 간격 값을 조정해도 된다(규칙은 유지, 숫자는 협의).
- **묶어 보기의 관계선**: 묶음끼리 선을 그리지 않기로 했다. 실제로 써 보면 "묶음 사이 연결이 하나도 안 보인다"는 불만이 나올 수 있다. 1단계 사용 후 재검토 대상.
- **`aria-roledescription="3D 구성도"`** 는 스크린리더별 지원이 고르지 않다. 표가 기준 구조라는 설계로 위험을 낮췄지만, NVDA·VoiceOver 실제 확인이 필요하다.
- 성능 목표(AC-3D19~21)는 설계로 보장할 수 없다. 측정은 프론트·백엔드 몫이다.
- 2~4단계(AWS·시간축·통합)는 **설계하지 않았다**. 15절에 자리만 적어 두었다.

### 5. 주요 결정과 이유

| 결정 | 대안 | 이유 |
|---|---|---|
| 판 표식 = **알약**, 블록 표식 = **원** | ① 같은 원에 크기만 키움 ② 판 전용 색 ③ 판 라벨 앞에 아이콘만 | 색·아이콘 축은 이미 종류·상태·드리프트 3개로 꽉 찼다(`status.md` 11.1). 크기 차이는 원근 없는 2D 오버레이에서 비교 대상이 없어 읽히지 않는다. 모양은 색맹·회색조에서도 남는다 |

### 7. 남은 이슈·한계

1. **축소 사다리 경계값은 계산값이다.** 기본 카메라(거리 = 대각선 × 1.25, FOV 35°)에서 판 앵커 간격을 추정해 200/132/84px을 잡았다. 판 20장 이상에서 P2·P3가 얼마나 자주 나오는지는 구현 뒤 확인이 필요하다. 조정하더라도 **"표식 알약은 마지막까지 남긴다"** 규칙은 바뀌지 않는다.
2. **판 라벨 앵커 거리 계산 주체**는 프론트다(투영 좌표). 디자인은 "무엇을 기준으로 어떤 단계를 쓰는가"만 정했다.
3. `groups[]`(묶어 보기)에는 **판 표식 합계가 없다**. 묶어 보기에서도 판 표식은 `plates[].markers`를 그대로 쓴다 — 계약에 부족한 값은 없다고 판단했지만, 묶어 보기 + 판 표식 조합은 mock `large`(3,200개)에서 실제로 확인해야 한다.
4. **2단계(AWS)**에서 판 개념이 그대로 쓰일지는 미정이다. `PlateLabel`의 `kind`를 enum으로 열어 뒀다.
5. `evidenceItems[]`를 관계 표 펼침에서만 쓰기로 했는데, 근거 5건 초과(`evidenceTruncated`)일 때 펼침 영역 높이가 커지는 문제는 구현에서 확인이 필요하다(현재 규칙: 서버가 붙인 `외 N건`을 그대로 둔다).
6. publisher가 **이미 만든 컴포넌트**에 이번 요청(판 알약·그룹 행 확장·`PlateLabel`)이 들어가야 한다. 구현 순서상 추가 작업이 생긴다 — PM이 판단할 몫이다.

### 8. 다른 담당 요청

**publisher 요청** — 모두 기존 컴포넌트 prop 확장이고, 새 컴포넌트는 1개다.

1. `BlockMarkers`(components.md 16.9) — **변형 추가**
   - `variant`에 `"plate"` 추가: 높이 20px, radius 4px, 패딩 0 6px, 배경 `viz.label.bg`, 1px `border.default`, 아이콘 12px + 4px + micro 11/14 문구, 알약 간 4px, 최대 3 + `+N`.
   - `notes?: { code; text; count? }[]` — 표식 뒤(⑤ 정보)에 그린다. `custom_resource` → `shapes` + `사용자 지정 리소스`, `namespace_file_missing` → `file-question` + `namespace.yaml 없음`.
   - `hrefs?: { scan?: string; drift?: string }` — 있으면 그 표식만 `<a>`로(판 표식 클릭 이동), 없으면 `<span>` + 툴팁.
   - `density?: 0|1|2|3` — `plate` 전용. 0 아이콘+문구 / 1 아이콘만 / 2 순위 1위 아이콘 + 총계 숫자 1개 / 3 순위 1위 아이콘만(폭 20px). **어느 단계에서도 최소 1개는 남는다.**
   - `inline` 변형 문구에 `사용자 지정` 추가.
2. `RelationTable`(16.8) — **그룹 행 확장**
   - 행에 `groupKind: "plate" | "layer"`, `markers?`, `notes?`, `location?`, `actions?: { file?: {href}; drift?: {href} }`, `emptyHint?: string` 추가.
   - `layer` 행은 위치·표식·들어옴·나감·동작 열을 **비운다**. `plate` 행만 채운다.
   - 그룹 행 클릭 영역 분리(chevron+이름만 토글, 표식·버튼은 전파 막음). 판 행은 `selectedId` 대상이 아니다.
   - `emptyHint`가 있으면 자식 0개여도 행을 남기고 펼침 화살표 비활성.

**(1) 카메라 — 4.9 「기본 거리 맞춤」 신설 (요청 1)**

"대각선 × 1.25"를 버리고 네 조각으로 나눠 수치로 적었다.

- **안전 영역**: 캔버스에서 상시 오버레이를 뺀 사각형. 위 `12 + 정보 줄 높이 + 12`(최소 44 · 최대 88px), 오른쪽 **116px**(카메라 오버레이 96 + 여백 12 + 여유 8), 왼쪽 **12px**(범례가 나갔다), 아래 **12px**. 768 × 636px → **640 × 580px**. 알림·툴팁은 계산에 넣지 않는다(떴다 사라질 때 카메라가 출렁인다).
- **거리**: `tanY = tan17.5° × (H_s/h)`, `tanX = tan17.5° × (w/h) × (W_s/w)`, bbox를 기본 시점 카메라 축에 투영한 `r_x·r_y·r_z`로 `d_fit = max(r_x/tanX, r_y/tanY) + r_z`. 최종 `d0 = clamp(min(d_fit × 1.06, d_read), 36u, 대각선 × 3)`.
- **`d_read` = 블록 한 변(4u)이 16px이 되는 거리** (`h / (2 × tan17.5° × 4.0)`, 768 × 636에서 ≈ 252u). 장면이 아무리 커도 블록이 16px 밑으로 내려가지 않는다 → PM이 지적한 "블록이 너무 작아 아이콘·상태를 못 읽음"에 대한 답. 이 상한에 걸리면 정보 줄에 칩 `일부가 화면 밖`(눌러 축소).
- **가운데 맞추기**: 대상 = bbox의 **3D 중심**(바닥면 중심이 아니다 — 바닥을 대상으로 잡아 블록이 위로만 자란 것이 "아래쪽에 몰림"의 원인), 그다음 장면 중심의 투영점이 **안전 영역 중심**에 오도록 화면 축으로 평행 이동(`1px = 2 × d0 × tan17.5° / h`). 768 × 636 예시는 왼쪽 52px · 아래 16px.
- **자가 점검식**: 투영 사각형의 중심이 안전 영역 중심과 ±4px, 사각형이 안전 영역 안(`d_read` 상한 제외).
- **다시 맞추는 때 / 아닌 때** 표를 넣었다(필터·검색·선택·창 크기 변경은 다시 맞추지 않는다).
- 딸린 수정: 4.0 단위 설명(1u = 8px은 **기준 장면**의 값), 거리 상한 `max(대각선 × 3, 기본 거리 × 2)`, 검색·선택 이동 거리 `min(36u, 기본 거리)`, **5.3 안개를 카메라 기준으로**(`거리 + 대각선 × 0.25 ~ 거리 + 대각선 × 1.1`) — 고정값 `대각선 × 1.2`는 기본 거리가 멀어지면 장면 전체를 안개에 잠기게 한다(설계 버그였다). 9.5 저사양의 안개 끝도 같은 형식으로 고쳤다.

### 7. 남은 이슈·한계

1. **사다리 경계(96/64/40px)와 안전 영역 여백은 계산값이다.** 기준 장면(`px_per_u = 8`, 격자 6u = 48px)에서 꽉 찬 층이 B2가 되도록 잡았다. 실장비에서 "이름이 너무 자주 48px로 줄어든다"면 B1·B2 경계를 각각 −8px씩 내리는 것이 1차 조정안이다. **버리는 순서(보조 줄 → 이름 → 표식)는 조정 대상이 아니다.**
2. **`d_read`(블록 16px) 하한에 걸리는 장면의 첫 인상은 확인하지 못했다.** 판 10장 이상에서 장면 일부가 화면 밖으로 나가고 `일부가 화면 밖` 칩이 뜬다. 실제로 답답하면 하한을 14px로 내리는 것이 1차 조정안이다(그 이하는 윗면 아이콘 16px을 못 그린다).
3. **층 간격 10u는 기준 장면 기준 계산값**이다. 보조 줄이 없는 스냅샷에서는 2u가 남는다(문제 없음). 장면이 세로로 길어지는 만큼 기본 거리가 늘지만, 층이 4개여도 30u라 영향은 작다.
4. **새 아이콘 8개의 lucide 존재 여부는 퍼블리셔가 확인해야 한다.** `user-round`·`grid-2x2`는 버전에 따라 이름이 다를 수 있어 대체안(`user`, `layout-grid`)을 적어 두었다.
5. **`Banner` 사용처 정리(deprecated 제거)는 미뤘다.** 언제 제거할지는 정하지 않았다 — 별도 작업으로 PM이 잡아야 한다.
6. 관계 표 보기에서 범례 팝오버가 **표 위 어느 위치에 뜨는지**는 도구 막대 B가 표 보기에서도 그대로 있다는 전제다(8.1). 표 보기 도구 막대 B에서 라벨 밀도·주변만 보기를 뺀다는 기존 규칙은 그대로다.
7. 9.2 "필터 결과 0개" 안내 카드는 여전히 **캔버스 가운데**다(안전 영역 가운데로 옮기지 않았다). 오버레이가 둘뿐이라 실제로 가리는 일이 드물다고 봤다.

### 8. 다른 담당 요청

**publisher 요청**

1. **`KindIcon` 신규**(`components.md` 16.12 · 표는 `snapshot-3d.md` 4.10) — props `kind`, `custom?`, `plate?`, `size(12|14|16)`, `color?`. 매핑을 **이 컴포넌트에만** 둔다. 모르는 종류는 `box`, `custom: true`는 `shapes`, 항상 `aria-hidden="true"`.
2. **아이콘 8개 등록**(lucide): `hard-drive` · `network` · `door-open` · `grid-2x2` · `briefcase` · `user-round` · `scroll-text` · `link`. 버전에 없으면 `user-round` → `user`, `grid-2x2` → `layout-grid`.
3. **`InlineAlert`에 `closable` / `onClose` / `closeLabel`**(6.2) — `action` 다음 8px, `IconButton` sm `x`(클릭 영역 32 × 32px). 닫기를 **주면 안 되는 알림 3종**은 6.2에 적었다.
4. **`Banner` 이름 하위 호환**(6.1·17.6) — `closable`/`onClose`/`closeLabel`을 표준으로 받고, `dismissible`/`onDismiss`도 당분간 함께 받는다(`closable ?? dismissible`). 기존 사용처는 **이번에 고치지 않는다.**
5. **`SceneLegend`를 팝오버용으로**(16.5) — `collapsed`/`onCollapsedChange` 제거, 폭 200 → **280px**, 머리 오른쪽은 `x` 닫기, 층 줄에 대표 종류 아이콘 12px(`exampleKind`), `onClose` 추가. 종류 아이콘 해설 줄은 **넣지 않는다.**
6. **`Scene3DFrame`에서 `legend` 슬롯 제거**(16.1) — 캔버스 오버레이는 `infoBar`(왼쪽 위)·`cameraControls`(오른쪽 아래) 둘뿐.
7. **`RelationTable` 그룹 행에 `count`·`totalCount`·`plateKind`**(16.8) — 표기 `(11)` / `(3 / 11)` / `(0 / 11)`, `title` `보이는 리소스 3개, 전체 11개`. 판 행 아이콘은 `plateKind`로 고른다(`folder`/`globe`/`file-warning`/`circle-dashed`, 기존 `box` 대체).
8. **`Popover`에 `align?: "start" | "end"`·`maxHeight?`**(17.7) — 범례가 오른쪽 정렬 + 내부 스크롤이다.

### 3. 작업 내용

**① 증상의 원인을 수치로 특정했다 (가장 중요한 부분)**

이번 두 증상은 취향 문제가 아니라 **문서의 전제가 틀린 것**이었다. 기본 시점(방위 −35°·고도 30°)의 투영 상수를 직접 계산해 넣었다.

- 화면 right = `(0.819, 0, 0.574)`, up = `(0.287, 0.866, −0.410)`, 카메라 방향 = `(−0.497, 0.5, 0.709)`
- 따라서 세계 1u의 **화면 거리**는 축마다 다르다: x = **0.868u**, z = **0.705u**, y = **0.866u**

여기서 두 가지가 무너진다.

1. **4.7.1의 임계값은 도달 불가능한 값이었다.** 문서는 "기준 장면 `px_per_u = 8`이라 격자 셀 6u = 48px, 꽉 찬 층은 B2"라고 적었는데, 6u는 화면에서 48px이 되지 않는다. 깊이 방향 한 칸은 `6 × 0.705 = 4.23u`, 가로 한 칸은 `6 × 0.868 = 5.21u`다. 게다가 `px_per_u = 8`도 나오지 않는다 — 4.9의 규칙대로 계산하면 기준 장면의 `d0 = 248u`, **`px_per_u = 4.07`**이다. 즉 실제 `g`는 **17~35px**이고, B2 하한이 40px이면 **정의상 거의 전부 B3**가 된다. frontend가 관측한 24~30px과 일치한다.
2. **장면의 투영 사각형이 안전 영역보다 훨씬 납작하다.** 판을 한 줄 4장으로 놓으면 기준 장면 bbox가 126u × 58u가 되고, 투영 사각형의 가로:세로가 **1.54**다. 안전 영역은 640 × 548 = **1.17**이라 가로가 먼저 차고 **세로의 38%가 남는다.** 그 절반이 위쪽 여백으로 보인다. 여기에 정보 줄이 2줄(칩 7개)이 되어 위 여백이 44 → 76px이 되면서 안전 영역 중심이 **32px 더 아래**로 내려갔다.

그리고 `d_fit` 식 자체도 과했다: `max(r_x/tanX, r_y/tanY) + r_z`는 "가장 옆으로 벌어진 모서리"와 "가장 가까운 모서리"가 같은 모서리라고 가정하는데 직육면체에서는 대개 다르다. 기준 장면에서 **275u vs 234u, 18% 과다**였다.

**② 장면을 키웠다 (4.1 판 배치 · 4.2 층 간격)**

| 항목 | 이전 | 확정 |
|---|---|---|
| 한 줄 판 수 | 4장 | **3장** |
| 판 간격 · 줄 간격 | 10u · 10u | **8u · 8u** |
| 판 여백 | 3u | **2u** |
| 곁 띠 | 항상 3u | **곁 리소스가 있는 판만 3u** |
| 최소 판 | 18u × 18u | **14u × 14u** |
| 층 바닥 간격 | 10u | **12u** |
| 격자 셀 | 6u | **6u 유지** |

- 계산 결과(기준 장면): `d_fit ≈ 165.8u` → `d0 ≈ 175.7u`, **`px_per_u` 4.07 → 5.74**, 블록 한 변 16 → **23px**, 이웃 간격 `g` 17~35 → **24~60px**, `d_read` 상한에 **걸리지 않음**(`일부가 화면 밖` 칩이 사라진다).
- 3열 배치 + 층 간격 12u를 함께 쓰면 가로 제약 `164.6u`와 세로 제약 `165.8u`가 거의 같아져 **두 축이 동시에 안전 영역을 채운다** → 위쪽 빈 띠가 구조적으로 사라진다.
- **격자 셀은 일부러 키우지 않았다.** 장면 전체를 화면에 맞추는 한 셀을 키우면 판도 같은 비율로 커져 카메라가 그만큼 멀어지므로 화면상 `g`는 거의 그대로다. 이 사실을 4.1에 근거로 적어 두었다(나중에 "셀을 키우자"가 다시 나오지 않게).

**③ B 사다리를 다시 썼다 (4.7.1 전면 개정)**

- **수용 기준을 표로 신설**: 기준 장면에서 **이름이 보이는 블록 80% 이상(27개 중 22개)**, 표식 있는 블록은 **100%**, `라벨 N개 숨김` **N ≤ 5**, `표식 N개 숨김` **0**. "이름이 보인다"는 **글자 4자 이상**으로 정의했다.
- 사다리를 **B0~B4 5단계**로 늘리고 임계값을 실제 도달 구간(24~60px)에 맞췄다.

| 단계 | 조건 | 상자 폭 | 이름 폭 | 보존 |
|---|---|---|---|---|
| B0 | `g ≥ 72px` | 136px | 120px | 뒤 8자 + 보조 줄 |
| B1 | `48 ≤ g < 72` | 104px | 88px | 뒤 8자 |
| B2 | `28 ≤ g < 48` | 76px | 60px | 뒤 6자 |
| B3 | `18 ≤ g < 28` | 52px | 36px | 뒤 4자 |
| B4 | `g < 18` | 20px | 없음 | 종류 아이콘만 |

- **폰트는 건드리지 않았다**(micro 11/14 고정). 줄이는 것은 폭뿐이다. **이름은 언제나 한 줄**(두 줄 금지 — 상자가 14px 높아지면 층 간격 60px 안에서 위 층을 밀어낸다).
- **격자 점유에 「위로 밀어 올리기」를 추가**했다: 겹치면 단계를 내리기 **전에** 상자를 8px씩 최대 4칸(32px) 올려 다시 시도하고, 올린 상자에는 블록 윗면 중심까지 1px 세로 지시선(`border.default`)을 그린다. 이름을 지우는 것보다 20~30px 올리는 쪽이 정보 손실이 없다. 32px은 층 간격 60px보다 작아 위 층을 넘지 않는다.
- **선택·호버 예외를 넓혔다**: hover는 그 블록**과 이어진 이웃까지** B0, 표식이 있는 블록(600·700점)은 **최소 B2 보장**, 선택 블록의 이웃(500점)은 최소 B3.
- 겹칠 때 버리는 기준을 **"카메라에서 먼 쪽" → "점수가 낮은 쪽"**으로 바꿨다. 카메라 거리는 이미 0~400점에 들어 있어 같은 뜻을 두 번 적용했고, 그 때문에 **표식이 있는 먼 블록이 표식 없는 가까운 블록에 졌다.**
- `라벨 N개 숨김`이 세는 대상을 **"이름 글자가 하나도 안 그려진 블록(B4 + 완전 숨김)"**으로 고정했다(B3까지는 세지 않는다).

**④ 카메라를 다시 썼다 (4.9)**

- 안전 영역 위 여백 `44~88px` → **44px 고정**. 대신 **6.4 정보 줄을 한 줄로 못 박았다**(줄바꿈 금지, 480px을 넘으면 8→7→6번 순으로 `+N` 합침). 정보 줄 높이가 상수여야 카메라 규칙이 상수가 된다.
- `d_fit`을 **모서리별 계산**으로 교체: `d_fit = max over 8 corners of max(|sx|/tanX + sz, |sy|/tanY + sz)`.
- `d_read`의 블록 읽기 하한 `s_min`을 **캔버스 높이별 2단계**로: h ≥ 600px면 16px, 480~599px면 **13px**.
- **가운데 맞추기 계산식을 실행 순서로 명시**: ① bbox 3D 중심 ② `d0` ③ **원근 보정한 실제 화면 좌표**로 투영 사각형 `R` ④ 안전 영역 중심 `s` ⑤ `Δ = s − R중심`만큼 대상 이동 ⑥ **③~⑤를 2회 반복**. 평행 투영 근사를 쓰면 가까운 모서리가 작게 잡혀 사각형이 위로 치우치고, 그게 정확히 "위가 빈다"로 나타난다. 1회로는 최대 12px 잔차가 남는다.
- 자가 점검을 `dx`·`dy` ±4px에 **`fillX`·`fillY`**를 더했다: `max(fillX, fillY) ≥ 0.90`(맞춤이 걸렸나) + **`fillY ≥ 0.70`**(세로가 비지 않나). 기준 장면 기대치 `fillX ≈ 0.99` · `fillY ≈ 0.95`.

**⑤ 윗면 종류 아이콘 폐지를 승인했다 (4.3 · 4.10 · 9.7 · status.md 11.6 · components.md 16.12)**

- 블록 윗면에 아이콘을 **그리지 않는다.** 종류 아이콘은 **오버레이 이름 줄 맨 앞 12px**(`text.secondary`, 이름과 4px)로 옮긴다. B4에서도 이 아이콘만은 남는다.
- `viz.kind.*.onFill` 토큰은 지우지 않고 남긴다(1단계에서 쓰는 자리는 없다 — 문서에 명시).

**⑥ 1024px 완화안 (12절)**

- 좁은 캔버스 완화 표를 신설: `h ≥ 600px → s_min 16px` / `480 ≤ h < 600px → s_min 13px`. 근거를 "윗면 아이콘 16px"에서 **"마우스로 집히는 크기 + 3단 밝기가 구분되는 크기 = 12px, 여유 1px"**로 바꿨다.
- 다만 4.1의 새 판 배치를 적용하면 기준 장면 규모에서는 1024px에서도 `d_fit × 1.06 ≈ 171u < d_read 246u`라 **애초에 상한에 걸리지 않는다.** 완화는 더 큰 스냅샷용 안전장치다.

**⑦ publisher 요청 2건 — 둘 다 수용**

- `SceneInfoItem.onClick` **신설**(6.4 + components.md 16.4). `href`와 `onClick`은 동시에 주지 않는다(동시에 오면 `href` 무시 + 개발 모드 경고). `actionLabel`로 접근 이름을 `"<text> — <actionLabel>"`로 만든다. 칩별 `href`/`onClick` 표를 6.4에 넣었다. 11.1에 탭 정지점 규칙도 추가(동작이 있는 칩만 정지점).
- 9.4 알림 **`live` 수용**(components.md 16.1 + snapshot-3d 9.4). `Scene3DFrame`이 안에서 그리는 알림이라 **컴포넌트가 고정으로 켠다**. `live`를 켜는 알림은 **9.4 · 9.5 · 9.8** 세 곳으로 고정(9.3·9.9 제외)임을 두 문서에 같이 적었다.

**⑧ 덤으로 정리한 것**

- frontend (2) 섹션이 물었던 9.9 문구 두 벌을 확정: 3D 쪽 `표 보기도 같은 범위입니다.` / 표 쪽 `3D 보기도 같은 범위입니다.` 나머지는 글자까지 동일.
- 13절 컴포넌트 표에서 `Scene3DFrame` 슬롯 목록의 `범례`를 지웠다(6.5에서 이미 캔버스 밖으로 나갔는데 표만 남아 있었다).

### 5. 주요 결정과 이유

| 결정 | 검토한 대안 | 이유 |
|---|---|---|
| **① 장면 키우기 + ② 임계값 완화 + ③ 라벨 폭 축소를 함께** 쓴다 | frontend가 준 3안 중 하나만 고르기 | 어느 하나만으로는 목표에 못 간다. `px_per_u`가 4.07이면 임계값을 아무리 내려도 `g = 17px`에 이름을 그릴 수 없고, 반대로 장면만 키워도 40px 임계값에 막혀 여전히 B3다. 원인이 둘이라 답도 둘이다 |
| 판 한 줄 **4장 → 3장** | 판 크기만 줄이기 / 카메라만 당기기 | 투영 사각형의 **모양**이 문제다. 3열이면 가로:세로 1.54 → 1.32, 층 12u까지 더하면 가로·세로 제약이 `164.6 : 165.8`로 거의 같아진다. 판을 줄이면 이름이 안 들어가고, 카메라를 당기면 판이 잘린다 |
| 층 간격 **10u → 12u** | 오버레이 상자를 52 → 44px로 줄이기 | 상자를 줄이려면 표식 줄이나 이름 줄을 지워야 하는데 둘 다 정보 우선순위 2다. 12u는 오버레이 자리(60px)도 주고 세로 여백도 없앤다. 대가는 `px_per_u` 5.83 → 5.74뿐 |
| **밀어 올리기(8px × 4칸 + 지시선)**를 격자 점유에 추가 | 단계만 내리기 / 지그재그 배치 / 라벨 회피 물리 시뮬레이션 | 단계 내리기는 글자를 지운다. 지그재그는 규칙이 자의적으로 보인다. 물리 시뮬레이션은 AC-3D11("같은 입력 같은 배치")의 정신과 어긋나고 비용이 크다. 밀어 올리기는 **점수 정렬 → 한 번 훑기**라 결정적이고, 성긴 층에서는 거의 항상 빈 자리를 찾는다 |
| 겹칠 때 **"점수 낮은 쪽"**을 숨김 | "카메라에서 먼 쪽" 유지 | 카메라 거리는 이미 0~400점 안에 있다. 두 번 적용하면 **표식이 있는 먼 블록이 표식 없는 가까운 블록에 진다** — 정보 우선순위 2를 정면으로 깬다 |
| 글자 크기는 **11px 유지** | 9~10px 단계 추가 | `tokens.json`에 11px 미만이 없고, 추가 근거가 "겹쳐서"뿐이라 약하다. 10px 한글은 1440px 화면에서 읽기 어렵고, 3D 캔버스에서 안티에일리어싱까지 겹치면 더 나빠진다. **폭을 줄이는 것이 크기를 줄이는 것보다 손실이 적다**(뒤 4~8자를 살리면 리소스 이름의 식별 부분이 남는다) |
| 이름 **한 줄 고정**(두 줄 금지) | 붐비면 두 줄로 접기 | 세로가 가로보다 훨씬 귀하다. 층 간격 60px 안에 표식 18 + 이름 14 + 보조 14가 이미 들어 있어 14px만 늘어도 위 층을 침범한다 |
| `d_fit`을 **모서리별**로 | `× 0.85` 같은 보정 계수 | 계수는 장면 모양에 따라 맞기도 틀리기도 한다. 모서리별 식은 "8개 모서리가 모두 안전 영역 안"을 정확히 만족하는 최소 거리라 **모든 장면에서 맞는다** |
| 가운데 맞추기 **2회 반복** | 1회 / 수렴할 때까지 | 원근이라 밀면 극단 모서리가 바뀌어 1회로는 최대 12px 잔차가 남는다(실제로 남았다). 2회면 ±4px 안에 들고, 3회 이상은 눈에 안 보인다. 반복 횟수를 상수로 못 박아야 결과가 결정적이다 |
| 위 여백 **44px 고정 + 정보 줄 한 줄** | 정보 줄 높이를 계속 반영 | 칩 개수에 따라 안전 영역이 바뀌면 **같은 스냅샷을 열 때마다 첫 화면이 달라진다.** 실제로 칩 7개 → 2줄 → 안전 영역 중심 32px 하강이 이번 증상의 일부였다 |
| 윗면 아이콘 **폐지 승인** | 아틀라스 텍스처를 만들라고 요구 | 조건("한 변 16px 미만이면 그리지 않는다")이 **상시 참**인 상태였다(블록이 16~23px). 아이콘이 층 색을 덮어 `status.md` 11.1(면 색 = 층)을 읽을 단서가 사라진다. 텍스처는 3D 청크를 키우고 테마 전환마다 다시 구워야 한다 |
| `s_min`을 **16 / 13px 2단계** | 전 구간 13px / 1024px 전용 예외 | 큰 캔버스에서 13px이면 오버레이 상자(최대 136px)가 블록의 10배라 "블록 위의 라벨"이 아니라 "라벨 사이의 점"으로 읽힌다. 좁은 캔버스에서는 그 대가보다 **판이 잘리지 않는 것**이 낫다. 기준을 뷰포트가 아니라 **캔버스 높이**로 잡아 작업 영역 높이 변화에도 맞게 했다 |

### 7. 남은 이슈·한계

1. **수치는 전부 계산값이다.** mock K-1의 판 크기를 "층 격자 최댓값 12u + 여백 + 곁 띠 = 22u"로 가정했다. 실제 판이 이보다 크면 `px_per_u`가 5.74보다 낮아지고 `g`도 함께 내려간다. **frontend 실측으로 확인해야 한다.**
2. **80% 목표를 못 맞출 가능성**이 남아 있다. 한 층에 블록이 6개 이상 몰리면 가로 이웃이 30px 밑으로 내려가 B3·B4가 나온다. 그때는 임계값을 더 내리지 말고(24px 이하에서 이름을 그리면 이웃과 글자가 겹쳐 **둘 다** 못 읽는다) 있는 그대로 보고하도록 4.7.1에 적었다.

4. **AC-3D22 묶어 보기(3D)**는 여전히 미구현이고 이번 변경과 무관하다. 9.7의 묶음 블록도 윗면 아이콘 폐지를 따라가도록만 고쳤다.

### 9. 다음 담당이 알아야 할 점

- **`px_per_u`는 상수가 아니다.** 4.0의 기준 장면(≈ 5.74)은 "이 스냅샷에서 이 정도"라는 뜻이고, 판 수·블록 수가 달라지면 바뀐다. px로 적힌 모든 값(4.7.1 임계값, 4.2 근거)은 그 기준 장면에서의 환산값이다.
- **화면상 이웃 간격 `g`는 3D 단위로 조절할 수 없다.** 장면 전체를 화면에 맞추는 한 `g ≈ 캔버스 크기 ÷ 가장 넓은 축의 블록 수`다. 격자 셀이나 층 간격을 키워도 카메라가 그만큼 멀어진다. `g`를 키우는 유일한 방법은 **장면의 투영 모양을 안전 영역 모양에 맞추는 것**(4.1 판 배치)뿐이다.
- **카메라 계산에서 평행 투영 근사를 쓰지 말 것.** 가까운 모서리가 실제보다 작게 잡혀 투영 사각형이 위로 치우치고, 그 결과가 "위쪽이 빈다"로 나타난다. 4.9-3의 `scale_i = d0 / (d0 − sz_i)`를 반드시 넣는다.
- **가운데 맞추기는 2회 반복이 규칙이다.** 1회로 끝내면 ±4px 자가 점검을 통과하지 못한다. "수렴할 때까지"로 바꾸지 말 것(횟수가 장면마다 달라지면 결정적이지 않다).
- **정보 줄 높이는 카메라 규칙의 입력이다.** 칩을 늘리거나 줄바꿈을 되살리면 안전 영역이 흔들려 첫 화면이 스냅샷마다 달라진다. 칩을 더 넣어야 하면 `+N` 합침 규칙(6.4)에 넣는다.
- **표식은 이름보다 늦게 사라지고, 표식이 있는 블록은 이름도 보인다.** 이 두 문장이 4.7.1의 핵심이다. 성능·겹침 때문에 어느 쪽을 깨야 할 상황이면 깨지 말고 보고한다(칩으로 알리는 것이 그다음 수단이다).
- 블록 윗면에는 이제 아무것도 그리지 않는다. 종류는 **오버레이 12px 아이콘 + 층 색 + 툴팁**으로만 읽힌다.

### 3. 작업 내용

**① 원인을 다시 특정했다 — "상자 폭"이 아니라 "자리 후보"가 문제였다**

frontend가 지목한 "상자 폭 76px > `g` 39px"은 맞지만, **폭을 줄여도 풀리지 않는다.** 투영 상수(4.0)로 두 이웃의 **화면 가로 성분**을 분리해 보면 이렇다.

| 이웃 | 화면 `Δx` | 화면 `Δy` | `g` |
|---|---|---|---|
| 같은 층 가로 이웃 (6u x) | **26.8px** | 9.4px | 28.4px |
| 같은 층 깊이 이웃 (6u z) | **18.8px** | 13.4px | 23.1px |
| 위 층 (12u y) | 0px | 56.6px | 56.6px |

상자가 블록 가로 중심에 **고정**되어 있으면 두 상자가 겹치지 않을 조건은 `Δx ≥ 상자 폭`이다. 가로 이웃 26.8px에 이 조건을 맞추려면 상자를 **26px 이하**로 줄여야 하는데, 그러면 이름 폭이 10px(2자 미만)이라 "이름이 보인다"(4자 이상)를 스스로 깬다. **폭을 줄이는 길은 막혀 있다.**

그래서 고정을 푼다. 상자를 좌우로 `±o` 비킬 수 있게 하면 조건이 `Δx + 2o ≥ 상자 폭`이 되고, `o = 상자 폭/2 − 12`로 두면 **`Δx ≥ 24px`** — **상자 폭과 무관한 조건**이 된다. 기준 장면의 가로 이웃은 26.8px이라 **어느 단계에서든 짝이 나란히 들어간다.**

**② 자리 후보를 19개로 정의했다 (4.7.1 ③ 전면 개정)**

```
n(세로 밀어 올림) ∈ {0, 8, 16, 24, 32, 40, 48}
o_max = max(0, 상자 폭 ÷ 2 − 12px)     → B0 56 · B1 40 · B2 26 · B3 14 · B4 0
o ∈ {0, −o_max, +o_max}                → n = 0 에서는 o = 0 하나
후보 19개, 시도 순서 = n 오름차순 → 각 n 안에서 0 → −o_max → +o_max
```

- `o_max = 폭/2 − 12`인 이유: **블록 앵커가 언제나 상자 가로 범위 안 12px 이상 안쪽**에 있다 → 지시선이 여전히 **수직 한 줄**이고(꺾인 선을 만들지 않는다) 소유가 눈에 보인다.
- **밀어 올리기 32 → 48px**. 근거 둘: ① 표식 없는 상자(16px) 기준 겹치지 않는 세로 칸이 `0·16·32·48` **4칸** → 한 층에 몰린 블록 4개까지 수용(32px이면 3칸·3개) ② 층 한 칸 화면 거리 **57px**보다 작아 위 층 **앵커**를 넘지 않는다. 8px 배수 중 57 미만의 최댓값이 48이다.
- **점유에 「모든 블록의 몸체 사각형」을 추가**했다(앵커 중심, 한 변 `4u × px_per_u` = 기준 장면 22px, 자기 블록 제외). 두 가지를 한 번에 한다: 라벨이 블록을 덮지 않고, **상자가 남의 앵커를 덮을 수 없으므로 소유가 애매해지지 않는다** — 가로 비킴을 안심하고 쓸 수 있게 하는 장치다.
- `n = 0`에는 지시선이 없고(6px이라 안 보인다), **가로로 비킨 상자는 언제나 `n ≥ 8`이라 지시선이 있다**.

**③ frontend 3안과 그 밖 선택지를 하나씩 판정했다**

| 안 | 판정 | 이유 |
|---|---|---|
| ① 상자 폭 `min(76, g − 4)` | **불채택** | `g = 39`면 상자 35px → 이름 19px(3자)이라 "이름이 보인다" 정의를 깬다. **지표는 안 오르고 글자만 짧아진다.** 폭을 줄여도 필요 간격이 같은 비율로 줄지 않는다(①의 표) |
| ② 이름을 좌·우 **번갈아** 배치 | **변형 채택** | 순서 기반 "번갈아"는 이웃이 3개 이상이면 규칙이 무너지고 앵커가 상자 밖으로 나가면 소유를 못 읽는다. **후보 자리(`±o_max`, 앵커가 상자 안)**로 바꿔 채택 |
| ③ 밀어 올리기 32 → 48px | **채택** | 위 ②의 근거 두 가지 |
| 이름 축약(앞 N글자 + …) | **불채택** | 4.7이 이미 **가운데 말줄임 + 뒤 N자 보존**을 쓴다. k8s 이름은 접두사가 겹치고(`api`, `api-config`, `api-db-credentials`) 식별 부분이 뒤에 있어 앞 N글자는 더 나쁘다 |
| 세로 쌓기(층 옆에 라벨을 모아 범례처럼) | **불채택** | 블록과 라벨의 공간 연결이 끊긴다(1절 "3D의 입체감보다 표식의 가독성"은 **그 블록의** 표식을 읽는다는 뜻이다). 지시선 다발이 장면을 덮고, 판이 5장이면 라벨 기둥도 5개가 된다 |
| 선택·호버 예외 확대 | **이미 최대** | (5)에서 hover를 이웃까지 B0로 넓혔다. 더 넓히면 "가리키지 않으면 안 보인다"가 되어 **첫 화면**(정지 상태) 지표는 그대로다 |
| 글자 크기 10px 이하 | **불채택** | (5)와 같다. `tokens.json`에 11px 미만이 없고 근거가 "겹쳐서"뿐이다 |

**④ 목표를 80% → 74%로 내리고, 근거를 `g` 구간별 표로 적었다**

기준 장면 `g`(4.0 보정 뒤 23 / 43 / 64px) 구간별로 세면 **20~24개**가 나온다. 22~24는 "한 층에 4개 이하로 모여 있다"는 가정에 기대므로, **가정이 깨져도 지켜지는 바닥인 20개(74%)**를 수용 기준으로 삼았다. `라벨 숨김`도 `≤ 5` → **`≤ 7`**로 맞췄다(27 − 20 = 7). **표식 100% · `표식 숨김` 0은 그대로** — 이미 달성됐고 정보 우선순위 2라 양보 대상이 아니다.

- 부수 효과 하나: 보정 뒤 최소 `g`가 23px이라 **기준 장면에서 B4가 아예 나오지 않는다**(B4 조건은 `g < 18`). 즉 모든 블록이 "이름을 가질 자격"은 갖고, 남는 실패는 **자리 부족뿐**이다.
- **표식 줄은 자리가 없으면 겹쳐서라도 그린다**를 규칙으로 못 박았다(frontend 구현 수용). 그래서 `표식 N개 숨김` 칩은 1단계에서는 뜨지 않는다 — 칩 정의는 9.7 묶어 보기용으로 남겼다.

**⑤ `fillX` 0.844 → 0.92: `× 1.06`을 버리고 「맞춤 영역」 + 「크기 조이기 반복」으로 바꿨다 (4.9)**

- **`d_fit × 1.06` 폐지.** 여유를 **비율**로 잡은 것이 틀렸다 — 오버레이는 카메라 거리와 무관한 **고정 px**이다(1절). 대신 **맞춤 영역 = 안전 영역에서 네 변 각 26px 안쪽**을 신설하고 거기에 맞춘다. **26px = B3 상자 폭 52px의 절반** = "가장자리 블록에 최소 단계 라벨이 붙어도 안전 영역을 넘지 않는 최소값".
- **크기 조이기 반복 추가.** `d_fit`은 **모서리 8개의 경계 상자** 기준인데 화면을 채우는 것은 **투영 사각형**이라 늘 조금 보수적이다(실측 잔차 ≈ 9%). 중심 맞추기 반복 안에 `k = max(R.w/W_f, R.h/H_f)` → `d ← d × k`를 넣어 사각형이 맞춤 영역에 붙게 했다. 변수가 하나 늘었으므로 반복을 **2회 → 3회**로 올렸다(횟수는 여전히 상수 — 수렴 판정을 쓰면 기기마다 결과가 달라진다).
- 자가 점검에 **`fit = max(R.w/W_f, R.h/H_f)` = 0.98~1.02**를 1차 지표로 추가했다. `fillX`·`fillY`는 파생값이다.
- **(5)가 적었던 기대치 `fillX ≈ 0.99` · `fillY ≈ 0.95`는 도달 불가였다**고 문서에 적었다. 26px 테두리를 빼면 `fillX`의 상한이 `586/638 = 0.919`다. 목표 0.90은 그 아래라 만족한다.

**⑥ 4.0 기준 장면을 캔버스 576px 기준으로 보정했다 (표로 못 박음)**

| 항목 | (5) 문서값 | **(6) 확정** |
|---|---|---|
| 캔버스 | 768 × 636 | **766 × 576px** |
| 안전 영역 | 640 × 580 | **638 × 520px**, 중심 **(331, 304)** |
| 맞춤 영역 | — | **586 × 468px** (신설) |
| `d0` | 175.7u | **≈ 168u** |
| `px_per_u` | 5.74 | **5.45** (실측 5.0 × 크기 조이기 1.09) |
| 블록 한 변 4u | 23px | **22px** |
| 격자 셀 6u 가로 / 깊이 | 30 / 24px | **28.4 / 23.1px** |
| 층 한 칸 12u | 60px | **57px** |
| `g` | 25~60px | **23~64px, 중앙값 43px** |
| `d_read`(`s_min` 13px) | — | **≈ 281u**, 걸리지 않음 |

- **3절과 60px이 어긋나는 것은 풀지 않고 드러냈다.** 3절은 작업 영역을 `clamp(480, 100vh − 176, 960)`로 잡아 1440 × 900에서 724px → 캔버스 636px을 기대하는데, 실제 작업 영역은 **664px**(= 100vh − 236px)이었다. **설계는 나쁜 쪽(576px)을 기준으로 쓰고**, `176px`이 맞는지는 frontend가 확인해 보고하도록 3절·4.0에 적었다. 캔버스가 636px이 되면 `px_per_u`가 6.02로 올라 모든 목표가 더 쉬워진다(작아지는 경우는 없다).

**⑦ PM 결정 반영 — `+N`은 툴팁만 (6.4 · components.md 16.4)**

- `+N` Chip은 **툴팁 하나**만 갖는다. 내용 = 합쳐진 칩 `text`를 ` · `로 이은 **한 줄 문자열**(`묶어 보기 · 라벨 19개 숨김 · 일부가 화면 밖`).
- **`href`·`onClick`을 주지 않는다** → `<span>`, **탭 정지점 아님**(11.1에 명시). 합쳐지기 전 동작(`라벨 N개 숨김` → `gview=table` 등)은 `+N`으로 옮기지 않는다.
- `components.md` 16.4의 (5) 마지막 줄("나머지는 그 칩의 `Popover`에 담는다")을 **철회**하고 그 자리에 (6) 블록을 적었다. **publisher가 `Popover`를 아직 만들지 않았으면 만들지 말 것**(8절 요청).

### 5. 주요 결정과 이유

| 결정 | 검토한 대안 | 이유 |
|---|---|---|
| **상자 폭은 그대로 두고 자리 후보를 늘린다** | frontend ① `min(76, g−4)` | 폭을 줄여도 필요 간격이 같이 줄지 않는다. `±o` 비킴을 쓰면 조건이 **`Δx ≥ 24px`로 폭과 무관**해지고, 기준 장면 가로 이웃은 26.8px이라 만족한다. 폭을 줄이면 이름만 짧아진다 |
| `o_max = 상자 폭/2 − 12px` | 고정 ±16px / `g`에 비례 | 고정값은 넓은 상자에서 모자라고 좁은 상자에서 넘친다. `g` 비례는 B2 구간에서 `o` 17px이 나와 **필요한 24px에 못 미친다**. `폭/2 − 12`는 "앵커가 상자 안 12px"이라는 **읽기 조건에서 바로 나온 값**이고, 그 결과가 폭 무관 조건이다 |
| **블록 몸체를 점유에 넣는다** | 라벨끼리만 점유 | ① 라벨이 블록을 덮으면 층 색·표식을 못 읽는다 ② **상자가 남의 앵커를 못 덮으므로 소유가 애매해지지 않는다** — 가로 비킴을 허용하는 전제 조건이다 ③ 밀어 올림 48px이 위 층으로 올라가도 위 층 블록을 가리지 않는 것이 이걸로 보장된다 |
| 밀어 올림 **48px**(6칸) | 32px 유지 / 64px 이상 | 32px은 16px 상자 기준 3칸이라 한 층 3개가 한계였다(실측이 그랬다). 48px은 4칸이고 **층 한 칸 57px보다 작아** 라벨이 위 층 앵커를 넘지 않는다. 64px은 그 선을 넘어 "어느 층 것인지"가 흐려진다 |
| 후보 순서를 **`n` 우선, 같은 `n` 안에서 가로** | 가로 우선 | 세로로 멀어지면 **층**이 흐려지고, 가로로 비끼는 것은 층을 바꾸지 않는다… 지만 **비킴에는 지시선이 따라붙어야 읽힌다**(6px 지시선은 안 보인다). 그래서 `n = 0`은 가운데 하나만, `n ≥ 8`부터 가로 3자리를 다 쓴다 |
| 목표 **80% → 74%(20개)** | 80% 유지 / 60%로 더 내리기 | 계산 기대치는 22~24개지만 "한 층 4개 이하" 가정에 기댄다. **가정이 깨져도 지켜지는 바닥**을 기준으로 삼아야 세 번째 미달 보고가 나오지 않는다. 60%는 지금 규칙으로 쉽게 넘으므로 아무것도 검증하지 못한다 |
| `× 1.06` → **맞춤 영역 26px** | `× 1.02`로 줄이기 | 여유의 정체가 **고정 px 오버레이**인데 비율로 잡으면 장면 크기에 따라 과하거나 모자란다. 26px은 B3 상자 절반이라 **왜 그 값인지 말할 수 있다** |
| **크기 조이기를 반복 안에** | `d_fit`에 보정 계수 곱하기 | 계수는 장면 모양에 따라 맞기도 틀리기도 한다. 투영 사각형을 직접 재서 곱하면 **모든 장면에서** `fit ≈ 1.00`이 된다. 중심 맞추기가 이미 사각형을 계산하고 있어 추가 비용이 없다 |
| 반복 **2회 → 3회** | 2회 유지 / 수렴 판정 | 거리와 대상을 함께 움직이므로 변수가 하나 늘었다. 수렴 판정은 부동소수 차이로 기기마다 결과가 달라져 AC-3D11의 정신(같은 입력 같은 결과)과 어긋난다 |
| 기준 장면을 **실측 576px**로 | 3절 식(636px)을 믿기 | 목표 수치는 **실제 화면에서 검증**돼야 한다. 둘 중 나쁜 쪽을 쓰면 636px일 때는 저절로 더 나아진다. 60px 불일치는 숨기지 않고 frontend 확인 항목으로 남겼다 |
| `+N`을 **툴팁만** | `Popover` 유지 | PM 결정. 정보 줄은 읽는 자리지 조작 자리가 아니고(1절 우선순위 1), 캔버스 위에 여는 면을 하나 더 만들면 범례를 캔버스 밖으로 뺀 결정(6.5)과 어긋난다. 합쳐진 칩의 동작은 관계 표·선택 패널에 그대로 있다 |

### 7. 남은 이슈·한계

1. **20개(74%)도 계산값이다.** `g` 구간별 블록 수를 실측 요약값(최소 21 · 중앙값 39 · 최대 59)에서 추정했다. 실제 분포가 아래쪽에 몰려 있으면(예: `g < 28`이 10개 이상) 바닥이 20개 밑으로 갈 수 있다. **그때는 임계값을 내리지 말고 4.7.1 자가 점검의 ①~③(자리 분포·단계 내림 수·숨긴 블록의 `g`)을 받아 다시 조정한다.**

- **상자 폭을 줄여서 라벨 문제를 풀려는 시도는 이미 계산으로 기각됐다**(4.7.1 ③ 머리말). 겹치지 않을 조건이 `Δx ≥ 24px`로 **폭과 무관**하기 때문이다. 다음에 같은 제안이 나오면 이 문단을 먼저 보라.

- **블록 몸체 점유는 장식이 아니라 소유 보장 장치다.** 성능 때문에 빼면 상자가 남의 블록 위에 앉아 라벨이 엉뚱한 블록의 것으로 읽힌다.
- **카메라는 이제 세 가지를 반복 안에서 함께 푼다**: 투영 사각형 → 크기 조이기 → 중심 맞추기, **3회**. 하나만 떼어 고치면 다른 둘이 어긋난다. 평행 투영 근사는 여전히 금지다(`scale_i = d / (d − sz_i)`).
- **정보 줄 높이는 카메라 규칙의 입력이다.** 한 줄 20px·위 여백 44px 고정이 깨지면 안전 영역 중심이 움직여 첫 화면이 스냅샷마다 달라진다. 칩을 더 넣어야 하면 `+N` 합침(6.4)에 넣고, `+N`에 동작을 달지 않는다.
- **목표 수치(20개 / `fit` 1.00 / `fillX` 0.92)는 실화면에서 확인되기 전까지 계산값이다.** 세 번째 미달이면 규칙이 아니라 **장면 규모**를 의심할 차례다(8절 PM 요청 참고).

| 2 | 표식이 있는 블록은 이름도 보인다 | ②-1 최소 B2 보장, 다투면 점수 낮은 쪽을 치운다 | 표식 블록 수 = 그중 이름 보이는 수 |
| 3 | 라벨이 블록을 덮지 않는다 | ③ 블록 몸체 점유(한 변 `4u × px_per_u`) | 몸체 침범 0 |
| 4 | 숨긴 것은 반드시 고지한다 | `라벨 N개 숨김` 칩 + 누르면 관계 표 | 칩 N = 이름 글자 0인 블록 수 |
| 5 | 카메라 맞춤 | 4.9 | `fit` 0.98~1.02 · `max(fillX,fillY) ≥ 0.90` · `dx,dy ≤ 4px` |
| 6 | 결정적 | 난수 없음·후보 고정 순서 | 같은 입력·카메라 → 같은 결과 |

- **왜 비율을 버리는지**를 장면의 성질로 적었다: 층 **사이**는 76px로 넉넉한데 층 **안** 이웃은 `Δx` 18.8~26.8px이고 이 값은 격자 셀·판 크기·카메라가 서로 상쇄해 **늘릴 수 없다**(4.1). 이름 한 줄의 최소 폭이 52px(B3)이므로 **층 안에 몰린 자리에서는 이름이 물리적으로 안 들어간다.**
- **도달 못 할 목표를 남기면 불변을 깎는 압력이 생긴다**는 것을 실례로 적었다 — C+A안이 정확히 "이름 2개 ↔ 불변 3번"의 거래였다.
- 4.7.1 ④의 「프론트 자가 점검(목표 대조)」을 **「불변 회귀 점검」**으로 바꿨다: 이름 수는 **참고 기록**(줄지 않았는지만 본다), 합격·불합격은 불변 1~6으로만 가른다.
- 실측 단계 분포(B0 1 · B1 3 · B2 2 · B3 1 · **B4 12**)를 ②에 넣고, **B4 12개는 `g < 18`이어서가 아니라 19자리가 모두 막혀 끝까지 내려간 결과**라고 적었다(한계는 단계가 아니라 자리라는 결론).

**④ 「이름을 읽는 경로」를 원칙으로 신설 — 4.7.1 · 7절 · 8절 세 곳**

4.7.1에 표로:

| 경로 | 무엇을 준다 |

- **7절 머리**: "이 패널이 이름을 정확히 읽는 자리다. 3D는 구조를 파악하는 화면이고, 이름·경로·관계를 글자로 확인하는 일은 이 패널과 관계 표가 맡는다."
- **8절 머리**: "이름 전수 확인은 이 표가 맡는다. **3D = 구조, 표 = 목록.** 3D에서 이름이 줄거나 숨는 것은 결함이 아니라 역할 분담이다."
- `라벨 N개 숨김` 칩이 관계 표로 데려가는 동작이 **그 원칙을 사용자에게 말하는 자리**임을 명시했다.

**⑤ (6)에서 열어 둔 질문 두 개를 닫았다**

- **C + A(몸체 2u) 허용?** → **불허.** 4.7.1 ③의 몸체 점유 항목에 "사각형을 `4u`에서 줄이지 않는다 (PM 결정)"과 거래 내용(이름 +2 ↔ 블록을 덮음)을 적었다.
- **`fillY` 유지?** → **닫힘.** 층 16u로 `fillY`가 0.866이 되어 4.9 자가 점검의 `fillY ≥ 0.70`을 여유 있게 넘는다. 4.9 확인식의 기대치를 계산값에서 **실측값으로 교체**했다.

### 6. 검증 결과

| 검증 | 결과 | 비고 |

### 7. 남은 이슈·한계

1. **불변 2(표식 있는 블록은 이름도 보인다)가 기준 장면에서 실제로 지켜지는지 숫자로 확인되지 않았다.** 실측은 `표식 숨김 0`(= 표식이 그려짐)만 보고됐고, **표식 블록의 이름**이 몇 개 보이는지는 따로 세지 않았다. B4가 12개나 되므로 표식 블록이 그 안에 섞였을 수 있다 → frontend 요청 ②.
2. 캔버스 **616px**은 `SceneToolbar` 줄바꿈 때문이다. 퍼블리셔가 한 줄로 고치면 636px이 되고 `fillY`가 더 올라간다(좋아지는 방향). 그때 4.0 표의 캔버스·안전 영역·`d0`를 다시 적어야 한다.
3. **AC-3D22 묶어 보기(3D)** 미구현 — 이번 변경과 무관하게 남아 있다. 묶음 블록은 라벨 수가 줄어 이 절의 부담도 함께 준다.
4. 판 라벨 사다리 P0~P3(4.1.1)은 이번에도 **다시 재지 않았다.** 층 16u는 판 배치를 바꾸지 않으므로 가용 폭 `A`도 그대로다.
5. **비율을 버린 대가**: "이름이 몇 개 보이나"로 회귀를 잡을 수 없게 됐다. 대신 불변 1~6이 그 역할을 한다. 이름 수는 기록만 하고, **줄었을 때 원인을 확인**하는 용도로 쓴다.

### 9. 다음 담당이 알아야 할 점

- **4.7.1에는 이제 비율 목표가 없다.** 합격·불합격은 **불변 6개**로만 가린다. "이름 7/27"은 기준 장면의 **관측 기록**이지 목표가 아니다.
- **「라벨이 블록을 덮지 않는다」가 불변 3번이다.** 블록 몸체 점유 사각형(`4u × px_per_u`)을 줄이면 이름이 2개 늘지만 라벨이 블록 위 절반을 덮는다 — 실측으로 확인됐고 PM이 불채택했다. 성능·이름 수를 이유로 되돌리지 말 것.
- **층 간격은 `layout.ts`의 `U.layerGap` 한 곳(16u)이다.** 올리면 세로가 먼저 차서 `px_per_u`가 떨어지고(블록·글자가 작아진다), 내리면 오버레이 상자가 위 층에 부딪힌다. **16u가 두 제약이 맞바뀌는 지점**이라 임의로 움직이지 말 것.
- **`px_per_u`는 캔버스 폭이 정한다**(기준 장면이 가로 우선 장면이라서). 캔버스 높이를 늘리면 `fillY`가 올라가지 장면이 커지지는 않는다. 이 성질을 모르면 "높이를 늘렸는데 왜 안 커지나"에서 막힌다.
- **3D = 구조, 표 = 목록.** 이 한 줄이 4.7.1 · 7절 · 8절 세 곳에 있다. 셋 중 하나만 바꾸면 약속이 깨진다.
- 다음에 라벨을 다시 건드려야 할 상황이면, 순서는 ① 9.7 묶어 보기(라벨 수 자체를 줄인다) ② `SceneToolbar` 한 줄화(캔버스 +20px) ③ 판 배치 재검토(3열 → 2열)다. **규칙 미세 조정은 이미 바닥까지 갔다.**

### 3. 작업 내용

**① 봉투(envelope)를 먼저 고정했다 — 이것이 모든 제약을 한 번에 푸는 결정이다**

모든 모양을 **4u(x) × 3u(y) × 4u(z)** 안에 넣고, **상단 평면을 정확히 3u**로 통일했으며, **(0, 3u, 0)에서 반드시 솔리드**일 것을 조건으로 걸었다. 결과:

- 발자국 4u 고정 ✅ → 격자 점유(22px 사각)·`o_max`·판 크기 계산이 그대로.
- 앵커(= 층 바닥 + 3u 평면의 중심) 불변 ✅ → 라벨·표식 자리 계산이 그대로.
- **장면 바운딩 박스가 전혀 바뀌지 않는다** ✅ → `d0` 179u · `px_per_u` 5.45 · `fit`·`fillX`·`fillY`·`dx`·`dy` 실측값이 **재측정 없이 유효**하다.

"모양마다 높이를 다르게"는 **쓰지 않았다**. 높이를 낮추면 앵커가 블록 위 허공에 뜨고(라벨이 붕 뜬다), 높이를 키우면 bbox가 바뀌어 카메라 실측값이 전부 무효가 된다. 대신 **3u 안의 윤곽(폭 프로파일·구멍·두께·상단 형태)**으로만 갈랐다.

**② 모양 8종 + 곁 타일 1종 = 9종 (4.11.1)**

`box`(기본 상자) · `stack`(겹 상자) · `cylinder`(원통) · `panel`(얇은 판) · `roof`(박공 지붕) · `chamfer`(머리 깎은 상자) · `gate`(아치 문) · `diamond`(다이아몬드) · `tile`(곁 타일, 기존 그대로).

각 모양에 치수(u), 상단 면, **기준 장면에서 보이는 것**을 표로 적었다. 예: `stack` 아래 단 4×4×0.9u + 위 단 2.4×2.4×2.1u(상단 폭 11.3px), `gate` 다리 4개(1.2×1.2×1.6u) + 보 4×4×1.4u(구멍 7.6 × 7.6px), `panel` 깊이 1.2u(화면 4.6px, 상자는 15.4px).

환산표에서 **명목 22px과 투영 크기를 분리**했다: 4.0·4.7.1의 `22px`은 `4u × px_per_u`로 점유 사각형 전용이고, 실제로 보이는 발자국 한 변은 **가로 18.9px · 깊이 15.4px**, 높이 3u는 **14.2px**이다(투영 상수 x 0.868 · z 0.705 · y 0.866). 모양 차이는 모두 이 투영 크기 기준으로 **윤곽선 위치 3.5px 이상**이다.

**③ 모양 ↔ 종류 배정 (4.11.2)**

| 층 | 배정 |
|---|---|
| 워크로드 | Deployment `stack` · StatefulSet `cylinder` · DaemonSet `panel` · CronJob `roof` · Job `chamfer` · Pod/ReplicaSet/그 밖 `box` |
| 서비스 | Service `diamond` · 그 밖 `box` |
| 진입 | Ingress `gate` · 그 밖 `box` |
| 저장·설정 | PVC·PV `cylinder` · ConfigMap `panel` · Secret `chamfer` · 그 밖 `box` |
| 곁 | 전부 `tile`(모양 나누지 않음) |

**같은 층 안에서 갈리는지**를 별도 표로 확인했고, 가장 가까운 쌍(`stack` ↔ `chamfer`, 둘 다 워크로드)의 차이를 수치로 적었다(좁아지는 자리 4.2px / 7.6px 지점, 꺾임 수직 / 대각선, 상단 폭 11.3 / 7.6px) + 그 쌍의 **스크린샷 회귀 점검 항목**을 남겼다.

**④ 밝기 3단 유지 방법 (4.11.3) — 값은 그대로, 광원만 옮김**

`t = n · l`을 **100 / 82 / 64% 세 값으로 양자화**한다(`t ≥ 0.65` / `0.20~0.65` / `< 0.20`). 광원 방향을 **방위 −45° → −78°**(`l = (−0.49, 0.87, 0.10)`)로 옮겼다 — 이전 값에서는 기본 시점에서 보이는 두 옆면이 **둘 다 82%**라 몸체의 꺾임이 밝기로 읽히지 않았다. 이제 한 블록에 윗면 100 · 왼쪽 옆면 82 · 오른쪽 옆면 64가 동시에 보인다. 원통·사면도 양자화라 그라데이션이 생기지 않는다(면 색 = 층이 흐려지지 않게).

**⑤ 상태별 모습 (4.11.4)** — 유령(모양 유지 + dashed 윤곽), 비교 불가(아무 것도 바꾸지 않음), 선택 2px / hover 1.5px 50% / 검색 dashed(모두 **같은 모서리 집합**에 굵기·색·대시만 변경), 흐림 0.25, 위에서 시점(면 0.35 + 윤곽 유지 → 오히려 모양이 남는다), 저사양(모양 단순화 안 함), 묶음 블록(종류 모양 1.5배), **히트 영역은 모양과 무관하게 봉투 고정**.

**⑥ 성능 (4.11.5)** — 인스턴싱 단위 `층` → `층 × 모양`(최악 40, 실제 8~14 조합, 드로콜 16~28), 모양별 삼각형 상한 표(합계 ≤ 256), 3,000 블록에서 약 9만 삼각형. **모양을 더 늘리지 않는 이유**도 적었다.

**⑦ 4.7.1 불변 6개 점검 (4.11.6)** — 항목별 "영향 없음" + 근거. 특히 불변 3(라벨이 블록을 덮지 않는다)은 몸체 점유가 22px 고정이라 **오히려 보수적으로 안전**해진다(`panel`·`diamond`는 실루엣이 점유보다 작다).

**⑧ 영향 없는 자리 확인 (4.11.7)** — 선택 패널 ①, `RelationItem`, 관계 표 리소스·그룹 행, 블록 오버레이 이름 줄, 표식·판 알약: **전부 그대로**(아이콘 유지). 이유(종류 이름이 글자로 함께 있는 자리 + 작은 실루엣은 층 색을 흐린다)를 명시했다.

**⑨ 범례·필터 갱신** — 6.5에 **「모양 = 종류」 절**(중립 실루엣 견본 16px × 9항목, 2열 5줄 110px, 팝오버 총 약 440px < 592px), 6.1 **종류 필터 옵션의 층 색 사각 10px → 모양 견본 14px(층 색으로 채움)**. 맨 아래 문장·정보 줄 `circle-help` 툴팁 둘째 줄을 `블록 색은 층, 모양은 종류를 뜻합니다. 상태가 아닙니다.`로 갱신(줄 수 유지).

**⑩ 부수 정리** — 4.3의 **모서리 radius 0.25u 폐지**(22px에서 1.4px이라 보이지 않고 삼각형 예산만 먹는다. 실제 구현에도 없었다), 히트 영역을 봉투로 못 박음, 12절 `s_min`(13/16px)은 **그대로 둔다**는 판단과 이유 추가.

### 2. 처리

**① `roof` 치수 줄 — 이미 (8-1)에서 고쳐져 있었고, 오해가 없게 문구를 더 명확히 했다**

**② 4.9-3에 「3-1) 유효 모서리」 신설 (PM 결정 그대로)**

원인을 문서에 적었다: `d_read` 상한에 걸려 거리가 더 멀어지지 못하면 카메라가 장면 안으로 들어가고, 그때 `sz_i ≥ d`인 모서리에서 `scale_i = d / (d − sz_i)`가 0으로 나누거나 부호가 뒤집혀 투영 사각형 중심이 폭주 → 6번 팬이 장면을 화면 밖으로 민다.

규칙:
```
유효 모서리 조건:  d − sz_i ≥ max(near, 0.05 × d)
m ≥ 3 → 유효 모서리만으로 R·r 계산, 4~6 평소대로
m < 3 → 그 회차의 4·5·6 건너뜀 (d·target 직전 값 유지)

```

### 6. 다음 담당이 알아야 할 점

- **`skipped: true`는 실패가 아니라 "측정 불가 + 사용자에게 고지됨" 상태**다. 이때 화면이 지켜야 할 것은 **① 장면이 그려질 것 ② `일부가 화면 밖` 칩이 떠 있을 것** 둘뿐이다.
- 카메라 계산에서 **원근 나눗셈(`scale_i`)이 들어가는 자리는 언제나 분모 부호·크기를 먼저 확인**해야 한다. 이번 버그는 (5)에서 평행 투영 근사를 버리고 원근 보정을 넣을 때 함께 생긴 위험이었다.
- hover가 **원색 1.5px**이 되면서 선택(2px)과 굵기 차이가 0.5px뿐이다. 선택의 주된 신호는 **나머지 흐림 + 선택 패널**이므로, 나중에 "흐림이 과하다"는 이유로 `opacity.vizDimmed`를 올리자는 요청이 오면 **hover와 선택이 구분되지 않게 된다**는 점을 함께 검토할 것.

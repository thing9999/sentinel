> 파일 위치: `docs/reports/logs/planner.md`
> 같은 기능에서 같은 역할이 다시 작업하면 새 파일을 만들지 말고 아래에 `## YYYY-MM-DD HH:mm · <작업 이름>` 섹션을 **추가**한다 (이전 섹션은 지우지 않는다).

## 2026-09-25 · logs 기능 명세 작성 (1단계 기획)

### 1. 요청 내용

PM이 새 기능 `logs`(로그 조회)의 기획을 요청했다. 산출물은 `docs/specs/logs.md`와 이 보고서.

배경: 지금 대시보드는 "무엇이 잘못됐다"는 신호만 보여주고 "왜"를 못 보여준다. 파드가 `CrashLoopBackOff`인 것은 보이는데 로그를 볼 수 없어 사용자가 터미널로 나가야 한다. 사용자가 직접 요청한 기능이다. 대상 환경은 kOps 클러스터(2026-09-24 전환 완료).

반드시 다루라고 지시받은 것:
1. **비밀값** — `pods/log`를 여는 것은 기존 원칙의 예외다. 완화 수단을 반드시 정하고, 이 항목 없이는 구현하지 않는다(PM 결정)
2. **두 출처의 차이를 화면이 정직하게 알릴 것** — 직접 조회는 지난 로그가 없다. "검색이 안 되네"가 아니라 "왜 안 되는지"
3. **컨트롤 플레인 로그**(kOps 특성) + apiserver 자기참조 한계
4. **화면·동선** — 진입점, 다중/init 컨테이너, 줄 수 상한·tail·연결 상한, 긴 줄·ANSI·바이너리, 빈 상태/권한 없음/출처 죽음
5. **설정과 mock** — 외부 스택 제품 선택 + 근거, mock에서 두 출처 모두 눈으로 동작
6. **수용 기준(`AC-LOG01~`)과 단계** — 직접 조회만으로도 쓸모가 있을 것

원칙(어기면 안 됨): 조회 전용 / RBAC 추가는 `pods/log` `get` 하나뿐 / 로그 본문을 어드바이저로 보내지 않는다.

사용자가 확정해 재논의 금지인 것: 출처 두 가지를 모두 지원하고 있는 쪽을 자동 선택. 외부 스택이 없으면 그 메뉴가 회색으로 빠지고 자동으로 직접 조회.

외부 확인(WebSearch/WebFetch) — 추측하지 않고 확인한 것:
- 쿠버네티스 Logging Architecture: **`kubectl logs`는 가장 최근 로그 파일만 준다**(기본 `containerLogMaxSize` 10Mi / `containerLogMaxFiles` 5)
- `--previous`는 **직전 1세대만**, 파드 객체가 삭제되면 조회 불가
- `pods/log` 서브리소스 RBAC 표기(`resources: ["pods/log"]`, `verbs: ["get"]`)와 쿼리 파라미터(`container`·`follow`·`previous`·`sinceSeconds`·`sinceTime`·`tailLines`·`limitBytes`·`timestamps`)
- **stdout/stderr는 섞여서 나온다.** 분리는 1.32+ 알파 기능 게이트 `PodLogsQuerySplitStreams` 필요 (kubernetes/kubernetes#28167, kubernetes/enhancements#3288)
- Loki HTTP API: `query_range`(`limit` 기본 100, `direction` 기본 `backward`), **`/loki/api/v1/tail`은 WebSocket**(`delay_for` 0~5), `labels`·`label/{name}/values`, 멀티테넌트 `X-Scope-OrgID`
- Promtail/Grafana Alloy가 올리는 관례 라벨: `namespace`·`pod`·`container`·`node_name`·`stream`·`app`·`job` — **다만 배포마다 다를 수 있음**

`docs/specs/logs.md` 한 개를 새로 썼다. 구성:

1. **0절 확정 전제와 사실 확인** — `kops-support.md`의 0절 구조를 따랐다. 0.1 재논의 금지 9개(D1~D9), 0.2 **확인한 사실 11개(F1~F11, 근거 명시)**, 0.3 **확인 필요 6개(U1~U6)와 각각의 처리 방법**. 확인 못 한 것을 명세가 단정하지 않도록 분리했다.
2. **1절 배경/목표** — 1.2에 "이 기능이 여는 위험"을 따로 뒀다. `pods/log`를 여는 순간 "비밀값을 조회하지 않는다"는 원칙에 처음 구멍이 생긴다는 것을 배경으로 명시.
3. **2절 시나리오 S1~S6** — S1 CrashLoop 원인 확인(핵심), S2 "검색이 안 되는 이유를 아는 순간", S3 **사라진 파드**(장애 조사에 가장 필요한 순간), S4 로그 스택이 생긴 뒤, S5 스택이 죽음(자동 전환 없음), S6 컨트롤 플레인.
4. **3절** — 이 명세의 본체.
   - 3.0 **로그 내용으로 상태를 판단하지 않는다**(다른 명세와 형식이 다른 이유를 명시)

   - 3.2 **능력 차이 표(capabilities)** + `direct`일 때 상단 고정 한계 4줄

### 5. 주요 결정과 이유

#### 5.1 비밀값 (PM이 "없으면 구현하지 않는다"고 한 항목)

| 결정 | 검토한 대안 | 선택 이유 |
|---|---|---|
| **가림은 서버에서** (P1) | 화면(프론트)에서 가리기 | 화면에서 가리면 원문이 이미 네트워크·브라우저 메모리·개발자 도구·HAR·프록시를 지나간 뒤다. "가린 척"이 된다 |
| **가림을 끄는 설정을 만들지 않는다** (P2) | `LOG_REDACTION=strict\|off` | 끌 수 있는 안전장치는 켜져 있지 않은 안전장치다. 대신 **추가만 가능한** `LOG_REDACT_EXTRA_PATTERNS`를 뒀다(회사 고유 패턴) |
| **원문 보기 기능 없음** (P3) | ① 줄별 "원문 보기" ② 전체 해제 토글 | 조사에 필요한 것은 대개 "여기에 토큰이 있었다"는 사실이지 값 자체가 아니다. 대신 **규칙 이름 + `앞 2글자****(N자)`**를 보여 "이 토큰이 문제구나"까지는 알 수 있게 했다. 표기는 `k8s-snapshot`의 기존 규칙과 맞췄다. **열린 질문 Q2로 남겼다** — 판단이 갈릴 수 있는 지점이라 임의 확정하지 않고 PM 확인을 요청 |
| **"마스킹은 완벽하지 않다"를 닫을 수 없는 문구로 상시 표시** (P4) | 첫 진입 시 1회 안내 | 완벽하지 않은 것을 완벽한 척하면 사용자가 화면을 그대로 캡처해 공유한다. 마스킹이 **없는 것보다 위험해지는 유일한 경우**가 이것이다 |
| **어디에도 저장하지 않는다** (P5) | 최근 로그 캐시(재조회 절약) | 저장하는 순간 백업·덤프·실수로 커밋될 경로가 생긴다. DB 테이블 없음 + 디스크 없음 + **API 자신의 로그에도 본문·검색어를 찍지 않음** + 브라우저 저장소 없음 + 내려받기 버튼 없음까지 묶어 원칙으로 못박았다 |
| **fail-closed** (P7) | 실패 시 원문 통과 | 가림 모듈이 예외를 던지면 그 줄을 통째로 `[가림 처리 실패 — 줄 생략]`으로 바꾼다 |
| **식별자는 가리지 않는다** (IP·인스턴스 ID·ARN) | 어드바이저처럼 전부 가명 처리 | 노드 이름이 인스턴스 ID인 kOps(F9)에서 그걸 가리면 "어느 노드인지"를 알 수 없어 조사가 불가능해진다. 로그는 **어드바이저로 나가지 않으므로**(P6) 가명 처리의 이유가 성립하지 않는다. 가림 대상은 "비밀값"이지 "식별자"가 아니라고 선을 그었다 |
| **접근 제한 4종** | RBAC만 믿기 | 인증 없는 대시보드(가정 A5)에서 로그는 지금까지 다룬 어떤 데이터보다 민감하다. `LOGS_ENABLED` / **클러스터 안 배포는 기본 `false`** / `LOG_DENY_NAMESPACES` / `Origin` 검사 + 127.0.0.1 바인딩 |

#### 5.2 두 출처

| 결정 | 이유 |
|---|---|
| **능력 목록(capabilities)을 서버가 준다.** 화면이 "직접 조회니까 검색은 없겠지"라고 추론하지 않는다 | 출처가 늘어날 때(Elasticsearch) 화면을 고치지 않아도 되고, 화면과 서버가 서로 다른 말을 할 여지가 없다 |
| **찾기/검색의 이름이 출처에 따라 바뀐다** — `direct`는 `화면 안에서 찾기` + `가져온 N줄 안에서만 찾습니다`, `stack`은 `검색` | 사용자 요구 2번("왜 안 되는지 알려라")의 핵심. 같은 이름을 쓰면 "검색이 고장났다"가 된다 |
| **직접 조회의 기간 선택은 "제한적으로 가능"** | `sinceSeconds`로 현재 파일 안에서 좁힐 수는 있다(F2). "아예 불가"라고 쓰면 그것도 거짓이다. 툴팁에 `현재 로그 파일 안에서만 좁힙니다` |
| **스택이 죽어도 자동으로 직접 조회로 내려가지 않는다** | 자동 전환하면 "검색했는데 결과 0건"을 "로그가 없다"로 오해한다. **초기 자동 선택은 자동, 실패 시 전환은 수동 클릭** |
| **직접 조회는 한 번에 컨테이너 1개** (여러 파드 합쳐보기 없음) | N개 파드에 팬아웃하면 apiserver 부하가 N배가 되고, 시각 정렬이 출처마다 어긋난다. 합쳐보기는 `stack`의 능력으로 남겨 차이를 분명히 했다 |

#### 5.3 제품 선택: Loki

| 후보 | 판단 |
|---|---|
| **Loki (선택)** | ① 자체 운영 클러스터(kOps처럼 직접 만든 환경)에서 가장 흔하고 자원 소모가 작다 ② **라벨 모델이 대시보드 식별자와 1:1**(namespace/pod/container/node) — 이미 아는 파드를 그대로 셀렉터로 옮기면 된다 ③ 범위 조회·실시간 tail이 모두 문서화된 HTTP API로 있다(F10) ④ 단일 바이너리로 떠서 검증이 쉽다 |
| Elasticsearch/OpenSearch | 회사가 쓸 가능성이 실재하지만 인덱스·매핑·쿼리 DSL이 조직마다 달라 "설정만 채우면 동작"이 성립하지 않는다. **L4 어댑터로** |
| CloudWatch Logs | `logs:*` IAM 확대가 필요. 지금 권한 목록은 읽기 전용 7개로 고정하기로 한 상태 |
| 자체 저장 | 3.3.4(저장 없음) 원칙과 정면 충돌 |

**나중에 다른 것을 붙일 자리**: API·화면 계약을 **출처 중립**으로 정의했다. 화면은 셀렉터+기간+텍스트+줄수+능력목록만 알고, LogQL은 서버 안쪽에만 존재한다(AC-LOG47). 어댑터 추가 시 바뀌는 것은 `LOG_BACKEND` 값과 서버 어댑터 1개뿐.

#### 5.4 부하·상한

- **로그 본문을 공용 SSE(`/api/stream`)에 싣지 않는다.** 공용 스트림은 방송이라 로그를 보지 않는 탭까지 받고, heartbeat가 로그 폭주에 밀린다. 전용 연결을 쓰되 **전송 방식은 backend가 정하도록** 남겼다(구현 결정이므로).
- **`LOG_MAX_STREAMS=3`을 `SSE_MAX_CLIENTS=20`과 따로 센다.** 로그 스트림 1개는 일반 구독자보다 훨씬 비싸다. 1인 운영자용이라 탭 2~3개면 충분.
- **250ms 배치**: 줄당 이벤트면 초당 2,000 이벤트가 되어 브라우저가 렌더에 갇힌다.
- **유휴 5분 자동 일시정지 + 30분 강제 종료**: 잊고 켜 둔 탭이 apiserver·Loki를 계속 때리는 것을 막는다. "일시정지"는 화면 상태가 아니라 **실제 연결 해제**로 정의했다.
- **초당 2,000줄 초과는 버리고 생략 표시**: 브라우저가 멈추는 것보다 정직한 생략이 낫다.

#### 5.5 그 밖

- **로그 내용으로 상태를 판단하지 않는다**: "ERROR N줄이면 장애" 같은 규칙을 만들지 않았다. 포맷이 앱마다 달라 오탐이 확실하고, 상태 판단은 이미 `cluster-status` 3절이 한다. 기준을 두 벌 두면 화면 두 곳이 서로 다른 말을 한다. 사이드바 상태 점도 넣지 않았다(`k8s-snapshot` 드리프트를 메뉴 상태에 넣지 않은 전례).
- **ANSI 색상은 제거하고 평문으로**(열린 질문으로 미루지 않고 결정): 색 렌더링은 조사에 필수가 아니고 성능·주입 비용이 있다. 반대로 제거하지 않으면 `[31m` 찌꺼기가 화면을 덮으므로 제거 자체는 필수다.
- **사이드바 `로그` 메뉴를 만들기로** 했다: 파드 상세에서만 들어가면 **사라진 파드**와 **기간 검색**에 도달할 길이 없다. 다만 `shell.md`에 "컨트롤 플레인 메뉴는 무게가 안 맞아 만들지 않는다"는 전례가 있어 **열린 질문 Q3**로 함께 올렸다.
- **단계 구분의 기준**을 "직접 조회만으로도 쓸모가 있어야 한다"로 잡았다. L1 끝나면 S1(CrashLoop 원인 확인)이 완결된다. L3(Loki)는 Q1 답에 따라 L4로 밀려도 기능이 성립한다.

### 7. 남은 이슈·한계

- **열린 질문 10개가 미해결**이다(명세 9절). 특히 **Q1(회사 로그 스택 존재·제품)**은 월요일 확인 전까지 L3 착수 판단을 막는다. L1·L2는 Q1과 무관하게 진행 가능하다.
- **Q2(가린 값 원문 보기)**는 이 기능의 성격을 바꾸는 질문이다. "볼 수 없음"으로 정해 뒀지만, 반대로 결정되면 3.3.1 P1·P3을 다시 써야 한다.
- **Q3(사이드바 메뉴 신설)**은 `shell.md`의 기존 판단 전례와 부딪힌다. 안 만들기로 하면 3.8.1과 L2의 AC-LOG28~29를 고쳐야 한다.
- 확인 못 한 4건(U2~U5)은 **명세가 단정하지 않고** 설정·안내 문구·오류 전달로 우회했다. 실클러스터를 받은 뒤 backend가 확인해 문서에 적어야 한다.
- **마스킹은 원리적으로 완벽할 수 없다.** 앱이 비밀값을 평범한 문장으로 찍으면(`the key is hunter2`) 잡히지 않는다. 명세 9절 "알려진 한계"에 사실로 적었다.
- **`stack` 모드의 서버 검색은 가려지지 않은 원본을 대상으로 한다.** 검색어를 바꿔 가며 결과 유무로 가린 값의 일부를 추론할 수 있다. 단일 운영자용이라는 전제에서 감수하기로 하고 "알려진 한계"에 적었다. 인증을 붙이면 다시 봐야 한다.
- DB 파드 로그에 **Postgres 쿼리 원문이 찍힐 수 있다**(`log_statement` 설정에 따라). `cluster-status` 가정 A7과 부딪히므로 DBA 확인 요청으로 남겼다.

### 9. 다음 담당이 알아야 할 점

- **명세의 무게 중심은 3.3(비밀값)이다.** PM이 "이 항목 없이는 구현하지 않는다"고 못박은 부분이라, 원칙 P1~P7 중 하나라도 빼려면 PM 확인이 필요하다. 특히 **P1(서버에서 가림)**과 **P2(끄는 설정 없음)**는 다른 결정의 전제다.
- **가림 표기는 `앞 2글자****(N자)`**로 `k8s-snapshot` 드리프트와 통일했다. 문서 전체에서 표기가 하나여야 한다.
- **능력 목록(capabilities)은 서버 값이다.** 프론트는 출처 이름으로 기능 유무를 추론하지 말고 서버가 준 목록을 그대로 쓴다(AC 여러 개가 이걸 검사한다).
- **자동 전환 금지 규칙에 주의**: 초기 출처 선택은 자동이지만, 스택이 **죽었을 때** 직접 조회로 내려가는 것은 사용자 클릭으로만이다(S5, AC-LOG42).
- **`direct`의 한계 4줄은 UI 장식이 아니라 수용 기준이다**(AC-LOG19). 접어도 한 줄 요약이 남아야 한다.
- **컨트롤 플레인 로그는 RBAC를 늘리지 않는다.** static pod가 `kube-system` 미러 파드로 보이기 때문이다(F8). `kops-support` D3("RBAC는 늘리지 않는다")와 충돌하지 않는다는 판단 근거를 명세 8절에 적어 뒀다.
- **mock이 이번 단계의 유일한 검증 수단이다**(실클러스터가 없다). `secrets` 시나리오는 **선택이 아니라 필수**이고, "가려서는 안 되는 긴 문자열"(커밋 해시·트레이스 ID)을 일부러 섞어 오탐도 눈으로 확인하게 설계했다.
- **AC 번호는 AC-LOG01~48**이고 단계는 L1(01~24) / L2(25~34) / L3(35~48)이다. L4는 번호를 쓰지 않았다.
- 확인 못 한 4건(U2~U5)은 `0.3` 표에 처리 방법까지 적어 뒀다. 실클러스터를 받으면 **backend가 확인해 `docs/api/logs.md`에 기록**하는 것이 명세의 요구다.

### 3. 작업 내용 (logs 관점)

**(1) `cluster-status.md` 6절 — 로그 두 줄 정리**

`logs` 8절이 지목한 두 줄은 이랬다.
```
- 파드 재시작, 스케일 조정, cordon/drain, 로그 스트리밍, exec 등 **모든 조작** (조회 전용 원칙)
- 컨테이너 로그 보기 (별도 명세 필요)
```
- 첫 줄에서 **"로그 스트리밍"만 뺐다.** `logs` L1의 **따라가기(tail)**가 바로 이 동작인데, `pods/log`의 `get`으로 읽는 **읽기**다(`logs` F1). 조작 목록에 두면 기능과 정면 충돌한다. 왜 뺐는지를 하위 항목으로 남기고 **`exec`·포트 포워딩은 계속 범위 밖**임을 같은 자리에 적었다(`logs` 6절·D4와 일치).
- 둘째 줄은 **"컨테이너 로그 보기·실시간 따라가기 → `docs/specs/logs.md`"**로 교체했다. "별도 명세 필요"가 채워졌다는 사실과 함께 ① 늘어나는 권한은 **`pods/log`의 `get` 하나뿐**(AC-LOG01), ② **로그를 근거로 한 조작·상태 판단은 하지 않는다**(`logs` 3.0)를 적었다. 두 문장이 없으면 "로그를 열었으니 exec도"나 "ERROR 세서 상태 매기기"가 다시 올라온다.

**(2) `cluster-status.md` — 8절이 "수정 불필요"로 본 곳 두 군데에 보충**

- **5절 AC "RBAC에 쓰기 동사와 secrets 접근이 없다"**: `logs` 8절 판단대로 **그대로 성립한다**(`pods/log`는 읽기). 다만 서브리소스가 들어온다는 사실을 적어 두지 않으면 검증하는 사람이 이 AC를 실패로 볼 수 있어, **AC 문구·체크박스는 건드리지 않고** 하위 보충 한 줄만 붙였다("`pods/exec`·`pods/portforward`·`secrets`는 여전히 없다"까지 명시).
- **가정 A7(쿼리 원문 미표시)**: `logs` 7절 DBA 항목이 지적한 **DB 파드 로그의 쿼리 원문** 문제를 **미결(PM 판단 대기)**로 적었다. DBA가 `log_statement`·`log_min_duration_statement`를 확인하기 전이라 **결론을 내지 않았다.** 가정 자체는 그대로 두고, "DB 세션 화면에 쿼리 원문을 보여주지 않는다"는 규칙이 변하지 않음을 명시했다.
- (덤) **가정 A5**에 로그 본문·웹훅 URL이 로그인 없는 화면에서 민감하다는 점과 `logs` 3.3.6(클러스터 배포 시 `LOGS_ENABLED=false`) 위치를 적었다.

**(3) `architecture-advisor.md` 3.4 — 로그 격리 (이번 작업의 핵심 중 하나)**

`logs` 3.3.5 P6 / D6 / 8절이 요구한 항목이다. 제외 목록에 다음을 추가했다.
- **"컨테이너 로그 본문 — 가림 처리한 것도 포함"**. 로그 줄뿐 아니라 **로그에서 뽑은 문장·오류 메시지·요약 통계("ERROR 줄 수" 같은 것)**까지 금지했고, 컨트롤 플레인(미러 파드) 로그도 같다고 적었다.
- 하위 항목 ①: 브리지 프롬프트·도구 목록에 **로그 조회 수단을 주지 않는다**(허용 도구는 `StructuredOutput` 하나 그대로).
- 하위 항목 ②: 이벤트는 기존대로 **message 원문 없이 reason별 개수만** 들어가는데, **로그가 그 우회로가 되면 안 된다**.
- 3.4 **검증** 문단에 로그 본문 혼입 검사(스냅샷 JSON 전체에서 mock 로그 픽스처 특징 문자열 **0건**)를 추가하되, **advisor 쪽 AC 번호는 만들지 않고 AC-LOG21을 참조**하게 했다.
- 머리말에 갱신 줄(2026-09-25): "`logs`가 `pods/log`를 열더라도 로그가 어드바이저로 새어 나가지 않는다"를 요약.

**(4) `kops-support.md` — "지표는 없지만 로그는 볼 수 있다"**

`logs` 8절이 제안한 항목이다. 3.2.2의 `etcd 내부 지표는 표시하지 않습니다(Prometheus 필요)` 줄 **아래에** 한 줄을 붙였다.
- 그 안내가 "컨트롤 플레인을 전혀 들여다볼 수 없다"로 읽히지 않게 **구성요소 매트릭스 칸의 `로그` 링크**(`logs` 3.7, AC-LOG30~33)를 가리킨다.
- 미러 파드라 **`pods/log`의 `get` 하나**로 읽으며, D3가 막은 **etcd 심층 지표와는 다른 것 — 충돌하지 않는다**.
- `kube-apiserver` 로그의 **자기참조 한계**(apiserver가 멈추면 그 로그도 못 본다)를 기존 "또 하나의 한계"와 같은 성격으로 연결했다.
- **AC-KOPS26의 안내 두 줄 문구는 그대로 둔다**고 못 박았다. 그 AC는 화면에 뜨는 두 줄을 검사하는데, 여기에 세 번째 줄을 끼워 넣으면 검증이 깨진다. 로그 링크는 `logs` 쪽 AC로 확인한다.
- **10.8 "RBAC·권한(변경 없음을 확인)"**에도 보충: `pods/log` 추가는 **`logs` 기능의 변경이지 kOps 전환의 변경이 아니다**. 그대로 두면 `logs`가 rbac를 여는 것과 모순으로 읽힌다.

**(5) 전체 훑기 (지시 4)**

`docs/specs/**`를 `로그` 키워드로 검색해 한 건씩 확인했다. "로그를 볼 수 없다"는 취지의 문장은 `cluster-status` 6절 두 줄이 유일했고(고침), 나머지는 성격이 다른 것들이었다 — `k8s-snapshot`·`aws-snapshot-manager`·`snapshot-3d`의 "**서버 로그**에 원문을 남기지 않는다", `architecture-advisor`의 "Claude Code **로그인**", `cluster-status` 가정 A5의 "앱 내 **로그인**". 이들은 `logs` 기능과 무관하거나 오히려 같은 방향(로그에 원문 금지)이라 건드리지 않았다.

### 7. 남은 이슈·한계

1. **`docs/specs/logs.md` 9절의 열린 질문 Q2·Q3·Q4·Q6·Q7은 PM이 이미 답했는데 명세에는 "열린 질문"으로 남아 있다.** 내가 고칠 수 없는 파일이라 8절에 요청으로 올렸다. 착수하는 사람이 "아직 미정"으로 읽을 위험이 있다.
2. **가정 A7(쿼리 원문) 충돌은 미결.** DBA의 `log_statement` 확인 결과에 따라 `logs` 3.3.2 가림 규칙에 줄이 하나 늘 수 있다.
3. `logs` 8절 충돌표의 나머지는 **내 쓰기 영역 밖**이라 그대로 남아 있다: `deploy/rbac.yaml` 첫 줄 주석(backend), `docs/api/common.md` 1.4·2.3·5.1·6.1(backend), `docs/design/shell.md` 3.1(designer).
4. `logs` 3.8.1의 진입점 8번(알림 항목 → 로그)은 **`alerts` 쪽 작업**이다. PM 결정대로 **링크만** 걸고 알림 본문에는 로그 줄을 넣지 않는데, **그 금지가 `alerts.md`에 아직 적혀 있지 않다**(8절 참조).

### 8. 다른 담당 요청

- **PM 요청 — `docs/specs/alerts.md`에 "알림 본문에 로그 줄을 넣지 않는다"가 없다.** PM이 logs planner 요청을 수용해 결정한 사항인데(`docs/reports/alerts/README.md`), `alerts.md` 3.3.2 "절대 넣지 않는 것" 목록에 **로그 줄(가린 줄 포함)**이 빠져 있다. `logs` 6절은 "`alerts`에도 같은 금지가 필요하다"고 적고 있다. 이 한 줄이 없으면 나중에 "로그 한 줄만 붙이면 친절하다"가 다시 올라오고, **디스코드는 밖으로 나가는 경로**라 되돌릴 수 없다. → `alerts.md` 담당(PM 지시가 오면 planner가 고치겠다).
- **PM 요청 — `docs/specs/logs.md` 9절의 답 나온 열린 질문에 "결정됨" 표시.** Q2(원문 보기 금지), Q3(사이드바 `로그` 메뉴), Q4(`LOGS_ENABLED=false` 기본), Q6(내려받기 없음), Q7(로그 기반 알림 범위 밖). **Q1(회사 로그 스택)·Q5·Q8·Q9·Q10은 계속 열려 있다.**
- **PM 요청 — `alerts.md`가 확정 결정과 어긋나는 곳 7군데**(상단바 벨 잔존 등). 상세 목록은 `docs/reports/alerts/planner.md` 2026-09-25 섹션 8번에 적었다.
- **`dba` 요청 (재확인)**: 모니터링 대상 Postgres의 `log_statement`·`log_min_duration_statement` 설정. 쿼리 원문이 로그로 나오면 `cluster-status` 가정 A7과 부딪힌다 — 그 자리에 **미결 표시**를 해 두었으니 결과를 `docs/db/`에 남겨 주면 PM이 판단한다.
- **`backend` 요청 (변동 없음)**: `deploy/rbac.yaml` 첫 줄 주석 갱신, `docs/api/common.md`의 `logBackend` `SourceId`·mock 그룹 `logs`·1.4 예외·로그 전용 연결 상한. 명세 쪽 근거는 이번에 정리했다.
- **`designer` 요청**: `docs/design/shell.md` 3.1에 `로그` 메뉴 추가(상태 점 **없음**). `알림`·`설정`과 **한 번에** 처리하면 된다(PM 조율). 상단바는 건드리지 않는다.

### 9. 다음 담당이 알아야 할 점

1. **`cluster-status.md` 6절은 이제 로그 기능을 가리킨다.** "컨테이너 로그 보기 (별도 명세 필요)"를 근거로 "로그는 범위 밖"이라고 말하면 안 된다. 반대로 **`exec`·포트 포워딩·파드 재시작은 여전히 범위 밖**이다.
2. **로그는 어드바이저로 나가지 않는다** — 이제 `architecture-advisor.md` 3.4에 **명시**돼 있다. 스냅샷 스키마에 로그 필드를 만들거나 "근거로 로그 몇 줄"을 넣는 변경은 명세 위반이다(AC-LOG21로 검증).
3. **컨트롤 플레인 로그는 RBAC를 늘리지 않는다**(미러 파드). `kops-support` 3.2.2·10.8에 "지표는 없지만 로그는 볼 수 있다 / `pods/log`는 `logs` 기능의 변경"이라고 적어 뒀으니, D3를 근거로 로그 링크를 지우지 마라.
4. **AC-KOPS26의 화면 안내 두 줄은 그대로다.** 컨트롤 플레인 섹션에 세 번째 안내 줄을 넣지 마라(검증이 깨진다). 로그 링크는 `logs` 쪽 AC로 확인한다.
5. **로그로 상태를 판단하지 않는다**(`logs` 3.0)는 문장을 `cluster-status` 6절에도 적어 두었다. 사이드바 `로그` 메뉴에 상태 점을 붙이지 마라.
6. **DB 파드 로그의 쿼리 원문은 미결**이다(`cluster-status` 가정 A7의 미결 표시). DBA 확인 전에 가림 규칙을 임의로 늘리거나 줄이지 마라.
7. 이번 수정은 **전부 보충·이동**이다. 기존 AC 번호·문구·체크박스는 하나도 바뀌지 않았다.

1. **퍼블리싱 구현 난이도**: 가상 스크롤 + 긴 줄 가로 스크롤 + `position: sticky` 조합은 브라우저에서 까다로운 편이다(가로 스크롤 컨테이너를 어디에 두느냐에 따라 sticky가 안 먹는다). 7절 퍼블리싱에 확인 항목으로 적어 뒀다.
2. **어드바이저 화면의 `가림 1건` 칩**(`docs/design/architecture-advisor.md`)은 **조회 단위 합계**라 이번 변경과 무관하다. 다만 `logs` 3.3.3이 "어드바이저와 같은 표현"이라고 적고 있으니, 나중에 어드바이저 쪽도 줄 단위 표식을 갖게 되면 같은 문제를 다시 검토해야 한다.

### 8. 다른 담당 요청

- **`publisher` 요청**: 가림 gutter는 **`position: sticky`로 가로 스크롤에 고정**돼야 한다(AC-LOG07). 가상 스크롤 구조와 함께 동작하는지 **실제로 긴 줄을 만들어 확인**해 달라 — 왼쪽에 두기만 하고 스크롤과 함께 밀리면 고친 의미가 없다.
- **`frontend` 요청**: `줄 바꿈` 토글을 끈 상태가 이 규칙이 깨지는 지점이다(3.8.3). 토글 구현 시 gutter 고정을 함께 확인해 달라.
- **`backend` 요청 (PM이 이미 전달)**: 계약은 왼쪽 gutter 기준. 응답에는 **줄별 가림 건수 + 규칙 ID·확신 등급**이 있으면 되고 **위치는 화면 몫**이다 — 계약에 좌/우 개념을 넣을 필요는 없다.
- **`designer`**: 요청 없음. **이번에는 designer 판단이 맞았고 명세가 그쪽에 맞춰졌다.**

### 9. 다음 담당이 알아야 할 점

1. **가림 표식은 줄 왼쪽 고정 gutter다. 오른쪽으로 되돌리지 마라.** 이유는 3.3.3에 4줄로 적혀 있다 — 요약하면 **줄 바꿈을 끄면 오른쪽은 사라진다.**
2. **핵심은 위치가 아니라 "사라지지 않는다"**이다(AC-LOG07). 왼쪽에 뒀어도 가로 스크롤과 함께 밀리면 **AC 불합격**이다.
3. 이 규칙은 `docs/design/status.md` 3.1과 **3.3.1 P4**(마스킹이 완벽하지 않다는 사실을 숨기지 않는다)에 걸려 있다. 배치 취향 문제가 아니다.
4. 구체적인 폭·배경·정렬은 **`docs/design/logs.md`가 정본**이다. 명세는 위치와 불변 조건만 요구한다.
5. **AC 번호는 그대로**다(AC-LOG07 문구만 수정). 검증 계획을 다시 짤 필요 없다.

### 7. 남은 이슈·한계

1. **`sql_statement`는 "SQL 문장"과 "그 밖의 줄"을 함께 다뤄야 한다.** `DETAIL: Key (email)=(a@b.com)`은 SQL 문장이 아니라 **Postgres가 붙이는 설명 줄**이라, `maskSqlLiterals()`가 그대로는 못 잡을 수 있다. 7절 DBA에 확인 항목으로 적었다 — **AC-LOG49가 이걸 검사한다.**
2. **오탐 위험**: 앱 로그에 SQL처럼 생긴 문자열(ORM 디버그 출력 등)이 있으면 같이 `?`로 바뀐다. 값이 사라지는 방향이라 **안전한 쪽 오탐**이지만, 규칙 이름이 표시되므로(3.3.3) 사용자가 판단할 수 있다.
3. `log_min_error_statement`는 **대상 DB의 기본값 확인 결과**다. 회사 클러스터에서 다르게 설정돼 있으면(더 낮으면) 평상시 쿼리도 로그에 남을 수 있다 — 그래도 **같은 규칙이 그대로 덮는다**(규칙이 설정을 전제하지 않는다).

### 8. 다른 담당 요청

- **`dba` 요청**: `maskSqlLiterals()` / `sanitizeQueryText()`가 ① `STATEMENT:` / `DETAIL:` / 여러 줄로 이어지는 Postgres 로그 형태를 처리하는지, ② **SQL 문장이 아닌 `DETAIL:` 줄의 값**도 잡는지 확인해 달라. 못 잡으면 그 함수 쪽을 보강하는 것이 맞다(로그 전용 규칙을 새로 만들지 않는다). `docs/db/health.md`는 **DBA가 직접** 갱신한다.
- **`backend` 요청**: `sql_statement`는 **새로 만들지 말고 재사용**. 치환이 다른 규칙과 다르다(`?`). 응답의 규칙 ID·건수 형식은 동일하게. **규칙 개수를 코드·테스트·응답에 숫자로 박지 말 것.** mock `secrets`에 7번 픽스처 추가.
- **`designer`**: 요청 없음. 화면에서 규칙 **개수를 고정하지 않기로 한 판단이 명세와 일치**한다(3.3.2에 같은 취지를 적어 뒀다).

### 9. 다음 담당이 알아야 할 점

1. **가정 A7은 살아 있다.** 다만 덮는 범위는 **모니터링 계정의 조회**까지다. DB 파드 로그에 실패 SQL이 보이는 것은 A7 위반이 아니라 **`sql_statement` 규칙이 맡는 별개 경로**다.
2. **대상 DB의 `log_min_error_statement`를 올리지 마라.** 관측 대상에 쓰기이고 DBA가 장애 원인을 못 보게 된다. 두 문서에 "되돌아오지 말 것"으로 적어 뒀다.
3. **`sql_statement`는 문장을 통째로 가리지 않는다.** 리터럴만 `?`다 — 안 그러면 "무엇이 실패했는지"가 사라져 로그를 보는 의미가 없다(AC-LOG49).
4. **가림 규칙 개수를 숫자로 박지 마라.** 앞으로 늘어난다. 목록이 정본이다.
5. **AC-LOG49는 L1 소속**이고 번호만 뒤에 있다. 01~48은 그대로다.

### 5. 주요 결정과 이유

| # | 결정 | 이유 |
|---|---|---|
| 1 | **AC-LOG13이 "섹션이 있다"가 아니라 "접힘 = 스트림 수 불변, 펼침 = +1, 접기·떠나기 = 원래대로"를 검사**하게 했다 | D1의 핵심은 모양이 아니라 **스트림 슬롯**이다. "섹션이 있다"만 보면 **항상 펼친 섹션**(D1이 막으려던 바로 그 구현)이 통과한다. AC-LOG07을 "왼쪽에 있다"가 아니라 "가로로 끝까지 밀어도 사라지지 않는다"로 바꾼 것과 같은 방식 — 위치·모양이 아니라 **불변 조건**을 검사한다 |
| 2 | "다시 접으면 연결을 닫는다"를 넣었다 | D1이 "**접힘 = 연결 없음**"이라는 상태 등식이라 초기 접힘뿐 아니라 다시 접은 상태에도 성립해야 한다. 새 결정이 아니라 등식의 적용이다. 단 **frontend 실측은 "떠나면 0"까지만 있고 "다시 접으면 0"은 확인되지 않았다**(7절) |
| 3 | **AC-LOG16에 "N이 계속 늘어난다"와 스트림 수**를 넣었다 | 스위치가 켜져 있는지만 보면 **"스위치는 켜진 채인데 연결은 끊긴" 구현**을 못 잡는다. N이 늘어나는 것은 연결이 살아 있다는 **화면에서 보이는 유일한 증거**이고, 스트림 수는 서버 쪽 증거다. 또 "스위치를 끄면 스트림 수가 준다"를 같은 AC에 두어 4절의 "끄면 닫는다"도 함께 확인한다 — 두 문장이 **한 AC 안에서 동시에 참**이어야 D2가 풀린 것이다 |
| 4 | 4절의 "끄면 연결을 닫는다"는 **지우지 않고 유지**, 그 아래에 D2 문단을 붙였다 | D2는 그 문장을 부정하지 않는다 — **스위치 = 연결**로 오히려 확정한다. 틀린 것은 AC-LOG16의 "스크롤 = 스위치 끄기"였다. 문단에 **처음 두 문장이 왜 충돌했는지 ①②**와 **"스크롤로 연결을 끊자"로 돌아오지 말 이유**(유휴·최대 지속이 이미 막는다)를 함께 적었다 — A7 때처럼 이유가 하나면 우회된다 |
| 5 | D3은 **AC-LOG30을 고치지 않고 AC-LOG50을 신설** | AC-LOG30("링크가 있고 누르면 미러 파드 로그가 열린다")은 D3와 **충돌하지 않는다.** 그리고 알림 쪽 기본값을 검사할 AC가 `logs`에 없었다. 경로별 기본값은 **서로 대비될 때 의미가 있으므로**(매트릭스 켬 ↔ 알림 끔 ↔ `/logs` 끔) 한 AC에 모았다. L2 소속, 번호는 뒤(AC-LOG49 선례) |
| 6 | AC-LOG50에 "**서버 `logHref` 그대로, 화면이 덧붙이지 않는다**"를 넣었다 | D3이 "링크 규칙은 한 곳"을 함께 결정했다. 기본값만 검사하면 화면이 `follow=1`을 덧붙여도 통과한다 — 그러면 규칙이 두 곳이 되고 `LOG_DENY_NAMESPACES`가 한쪽만 먹는 문제(README)가 되풀이된다 |
| 7 | 진입점 2·4·5·7의 기본값을 **채우지 않고 Q12**로 | D3는 매트릭스와 알림만 정했다. 이벤트 행은 알림처럼 "특정 시각", 파드 목록 행은 파드 상세처럼 "지금 상태"라 **어느 쪽으로 유추해도 그럴듯해서** 오히려 추측하면 안 된다. 그때까지의 처리는 새 결정이 아니라 "`follow=1`이 없으면 `/logs` 기본값"이라는 기존 규칙의 귀결이다 |
| 8 | `at`의 화면 동작을 **정하지 않고 Q11**로 | D3의 근거("그 시각을 보러 가는 링크")가 `at`이 무언가를 한다고 전제하는데, **명세·계약·디자인 어디에도 정의가 없다**(`docs/api/alerts.md` 예시 URL에만 있다). 따라가기를 끄면 "그 지점을 잃지 않을" 뿐 "그 지점으로 가지는" 않는다. 목적이 절반만 달성된다는 사실을 적어 두고 결정은 PM에게 넘긴다 |
| 9 | S1 4단계·3.8.3에 **`previous` + 따라가기 금지**를 적었다 | D1(펼치면 따라가기 켬) 때문에 핵심 시나리오 S1이 그대로는 재현되지 않게 됐다. 계약 13절이 이미 "명세에 없음 → 금지(400)"로 결정한 것이라 **새 결정이 아니다.** 핵심 시나리오를 틀린 채로 두면 검증하는 사람이 버그로 본다 |
| 10 | **`alerts.md`에도 D3을 적었다**(지시 범위는 "탭 서술 확인"이었다) | 알림 `logHref`는 **알림 쪽 계약에서 만드는 링크**다. `logs`에만 적으면 알림 쪽 문서를 보고 링크를 만드는 사람이 모른다 — "결정 기록과 작업 지시서가 갈라지면 안 된다"(PM, 벨 사건 교훈). 각 1줄씩, 판단 기준·AC는 건드리지 않았다 |
| 11 | design 쪽 **`탭` 서술 위치를 명세 7절에 목록으로** 남겼다(고치지는 않음) | PM 지시는 designer에게 "9절"을 맞추라고 했다. 검색해 보니 **9절 밖에도 9곳**이 남아 있다(9절에서 `Tabs` 컴포넌트를 쓴다는 14절 표까지). 9절만 고치면 나머지가 남아 다음 사람이 "탭"으로 되돌린다 |
| 12 | 0.1 D1~D9와 **번호 충돌**을 문서에 명시 | 같은 문서에 "D3"가 두 개다. 표시 없이 두면 AC 옆 "(PM 결정 D3로 수정)"을 0.1에서 찾게 된다 |

### 7. 남은 이슈·한계

1. **PM 확인 필요 3건**(9.2): **Q11**(`at`의 화면 동작), **Q12**(진입점 2·4·5·7 따라가기 기본값 — 진입점 2는 통합 2차에서 지금 만드는 중이라 **가장 급하다**), **Q13**(D2 + 링버퍼로 읽던 줄이 지워질 수 있음).
2. **AC-LOG50의 매트릭스 절반은 지금 검증할 수 없다.** SSE `logHref`가 항상 `null`이라 매트릭스 링크는 화면 `podKey` 폴백이 만든다. backend 수정(5b) + 폴백 제거(5d) 뒤에야 "서버 링크 그대로 + `follow=1`"을 확인할 수 있다.
3. **`LOG_STREAM_LIMIT_REACHED` 문구**(3.4) "다른 탭의 로그 화면을 닫아 주세요"는 D1 이후 **펼친 파드 상세 섹션도 슬롯을 쓴다**는 점을 담지 못한다. 문구는 서버·디자인이 확정한 것(`docs/design/logs.md` 8.5)이라 명세 제안 문구만 바꾸면 세 문서가 어긋나서 **바꾸지 않았다.** 고칠지는 PM 판단.
4. **"다시 접으면 연결을 닫는다"는 D1의 등식에서 도출**했다. frontend 실측은 "떠나면 0"까지다.
5. design 쪽 `탭` 서술이 9절 밖에 9곳 남아 있다(8절 designer 요청). designer가 9절만 고치면 AC-LOG13 검증 시 디자인 문서와 명세가 다르게 읽힌다.

### 9. 다음 담당이 알아야 할 점

1. **파드 상세의 로그는 섹션이다. 탭으로 되돌리지 마라.** 파드 상세에는 탭이 없다. 그리고 "기본 접힘"은 모양이 아니라 **스트림 슬롯을 지키는 장치**다 — 펼침 상태를 기억해 다음에 펼친 채로 열면 D1이 무너진다(AC-LOG13이 잡는다).
2. **`따라가기` 스위치 = 연결, 자동 스크롤 = 화면 동작.** 스크롤로 스위치를 끄지 마라 — `새 줄 N개`가 셀 줄이 없어진다. 연결을 오래 잡는 문제는 유휴 5분·최대 30분이 막는다(4절).
3. **따라가기 기본값은 링크가 정하고 링크는 서버가 만든다.** 화면에서 `follow=1`을 덧붙이지 마라(AC-LOG50).
4. 이 명세에는 **D1~D3가 두 벌**이다(0.1 확정 전제 / 9.1 통합 1차). AC 옆 "(2026-09-25 PM 결정 D□)"는 **9.1** 쪽이다.
5. **`이전 세대`와 `따라가기`는 함께 켤 수 없다**(계약). 파드 상세 섹션을 펼치면 따라가기가 켜지므로 이전 세대를 보려면 먼저 끈다(S1 4단계).

**남은 이슈(추가분)** — 위 7절의 1·3번은 **해소됐다**(PM 결정).
1. **`at`의 세부 동작은 계약이 나온 뒤**다. 명세는 참조만 두었으므로 계약이 나와도 명세 본문을 고칠 필요는 없다. PM이 요약 반영을 원하면 다시 요청할 수 있다.
2. **AC-LOG51을 재현할 수단이 약하다.** `noisy`는 초당 수천 줄이지만 frontend는 지금까지 `noisy`를 **정지 조회로만** 확인했다. 2만 줄을 채우는 따라가기 시나리오를 mock에서 확인할 수 있는지 frontend·backend가 봐야 한다.
3. `다시 시작`을 눌렀을 때 **읽던 자리를 어떻게 하는지**(맨 아래로? 그대로?)는 결정에 없다 — 디자인·프론트 몫으로 두고 명세에 적지 않았다.
4. 유휴 일시정지·최대 지속으로 연결이 닫힐 때 **스위치가 꺼지는지**도 명세에 없다(A6). 지금 결정 범위 밖이라 건드리지 않았다.

### 3. 작업 내용
1. HANDOFF 3절의 지표 목록을 영역(요약 띠, 노드, 워크로드, 파드, 이벤트, CPU·메모리, DB)으로 나눔.
2. 상태 체계를 정상/주의/장애 + "알 수 없음" + "데이터 오래됨"으로 정의. 출처 실패를 장애로 오인하지 않게 분리.
3. 영역별 수치 기준 표 작성 (예: 최근 1시간 재시작 1~2회 주의·3회 이상 장애, 노드 NotReady 60초 이상 장애, CPU 70/90%, 메모리 75/90%, DB 연결 70/90%, 긴 쿼리 5/30분, xid 나이 5억/10억, 복제 지연 10/60초).
4. 순간 튐 방지용 지속 조건(연속 3회), 집계 규칙(최악 상태), 판단 이유 한 줄 표시 규칙 추가.
5. 갱신 주기: Watch → SSE 3초 이내, 메트릭·DB 15초, 시간 경과 판단 15초 재평가.
6. Given/When/Then 수용 기준(mock 포함), 범위 밖, 역할별 전달 사항 작성.
7. HANDOFF의 열린 질문 3개를 가정 A3~A5로 대체.

### 5. 주요 결정과 이유
- **상태 판단은 서버에서 계산**하고 판단 이유를 같이 내린다 / 대안: 화면 계산 / 이유: 어드바이저 스냅샷·여러 탭에서 같은 판단을 재사용, 기준값 한곳 관리.
- **"알 수 없음"을 장애와 분리** / 이유: 연결 끊김·metrics-server 부재를 장애로 표시하면 오경보.
- **재시작은 누적이 아니라 최근 1시간 증가분** / 이유: 오래된 파드의 누적 재시작이 영구 장애로 보이는 문제 방지.
- **단일 레플리카는 이 화면에서 정상** / 이유: 현재 상태가 아니라 설계 위험이므로 어드바이저 사전 점검(R-SINGLE)으로 이관.
- **가정 A3** metrics-server 있음 / **A4** Prometheus 없음 → API가 최근 1시간 표본 유지 / **A5** 로컬 전용, 앱 내 인증 없음 / 이유: 현재 로컬 PC에 kubeconfig도 없는 상황이라 모두 합리적 기본값으로 진행 가능하고, 틀리면 해당 가정만 바꾸면 됨.
- 쿼리 원문 비표시 / 이유: 개인정보 포함 가능, 어드바이저 스냅샷 제외 규칙과 일관.

### 7. 남은 이슈·한계
- 열린 질문 없음. 가정 A1~A8이 사실과 다르면 명세 수정 필요.

## 2026-09-24 · alerts 기능 기획 (초안 작성)

### 1. 요청 내용

PM이 새 기능 `alerts`(알림)의 기획을 요청했다.

- **배경**: 대시보드가 상태를 보여주기만 하고 나빠졌을 때 알려주지 않는다. 화면을 안 보고 있으면 장애를 놓친다. 사용자가 직접 요청한 기능이다.
- **대상 환경**: kOps 클러스터(2026-09-24 전환 완료). 컨트롤 플레인(마스터·static pod)이 새 모니터링 대상이 된 점이 알림에도 영향을 준다.
- **사용자가 확정한 것 (재논의 금지)**
  1. 화면 안 알림 센터 — 상태 변화 이력 + 배지. 외부 연동 없이 바로 동작.
  2. 디스코드 웹훅 — 지금은 주소가 없고, 나중에 주소만 넣으면 동작해야 한다.
  3. 설정 화면 필요 — 웹훅 주소를 화면에서 입력.
  4. 지금은 실제 클러스터가 없다(월요일쯤 IAM·접속 정보 수령 예정). 그때까지 mock에서 전부 동작하고 눈으로 확인 가능해야 한다.
- **반드시 다룰 것 8가지**: ① 무엇을 알릴지(기존 판단 재사용, 새 기준 금지), ② 언제 알릴지(전이 기준, 중복 억제·해제·플래핑·`unknown` 구분·재시작 폭주 방지), ③ 어디로(화면 필수 + 디스코드 선택, 설정 없어도 안 죽음), ④ 설정 화면(웹훅 비밀값 취급 판단), ⑤ 테스트 발송(되돌릴 수 없는 외부 동작), ⑥ mock 동작(발송 금지, 명시 스위치), ⑦ 이력 보관(무엇을 저장할지만, 설계는 DBA), ⑧ `AC-ALERT01~` 수용 기준, ⑨ 단계 구분(화면 센터만으로도 쓸모).
- **원칙**: 조회 전용 유지(설정 저장 ≠ 알림 발송 ≠ 클러스터 쓰기 — 층 구분을 명세에 명시), 알림 내용에 비밀값·환경 변수·command/args 원문 금지, 노드 이름이 인스턴스 ID(`i-0…`)일 수 있음 고려, RBAC 증설 금지.
- **참고**: 설정 화면 틀에 나중에 예산 편집이 붙을 수 있으나 이번 범위 아님(자리만). `deploy/app.example.yaml`로 클러스터 안 배포 가능성 고려(port-forward 없음).
- **산출물**: `docs/specs/alerts.md`, `docs/reports/alerts/planner.md`. 코드는 건드리지 않는다.

### 3. 작업 내용

1. **기존 판단 기준 조사** — `cluster-status` 3.2~3.7, `kops-support` 3.2, `aws-cost` 3.5~3.7에 정의된 상태 기준과, 그것이 API에서 어떤 모양(`StatusInfo`·`areas.*`·`overview.cost.status`)으로 나오는지 확인했다. **새 기준을 만들 필요가 전혀 없음**을 확인하고, 명세 전체를 "기존 `StatusInfo`를 받아 전이만 감지한다"는 구조로 잡았다.
2. **알림 단위(알림 키) 설계** — 개별 리소스 단위 vs 영역 단위를 비교해 **영역 단위 8개**로 확정했다(3.1). 도배 가능성, 기존 화면 단위와의 일치, `problems` 재사용 가능성을 근거로 적었다. `area:metrics`·`overall`을 뺀 근거와 `source:kube`만 출처 키로 둔 근거를 각각 서술했다.
3. **트리거 규칙 설계**(3.2) — 전이 표(7가지), 중복 억제(15분·반복 N회·영향 객체 변화), 플래핑(30분 4회 → 묶음 1건 후 침묵), `unknown` 지속 5분 + **출처 억제**(kube 끊김 → 5건을 1건으로), 워밍업 120초 + 정지 구간 heartbeat를 정의했다. 각 규칙에 "왜 이 값인가"를 붙였다.
4. **채널 설계**(3.3) — 화면 센터는 끌 수 없음, 디스코드는 미설정이 정상 상태(오류 아님)로 확정. 배지 숫자·색 규칙, 발송 본문에 담을 정보 표, 절대 넣지 않는 것 목록, 실패·429·재시작 큐 처리를 정의했다.
5. **비밀값 취급 판단**(3.4.3) — 저장 위치(DB `settings` 별도 키 + env 우선·잠금), 원문 미노출, 끝 4자 힌트, 평문 저장의 근거와 한계, `redactSecrets`·스캐너 확장을 표로 정리하고 각 항목에 근거를 붙였다. 암호화 여부는 Q4로 남겼다.
6. **테스트 발송 설계**(3.5) — 8단계(저장된 주소만·버튼 활성 조건·확인 대화상자·`confirm: true` 422·60초 쿨다운 429·`[테스트]` 문구·이력 기록·mock 차단). 기존 `SNAPSHOT_CONFIRMATION_REQUIRED` 패턴을 재사용해 새 개념을 만들지 않았다.
7. **mock 동작 설계**(3.6) — `ALERTS_DISPATCH=mock|live`(`ADVISOR_BRIDGE` 패턴 복제), `[MOCK]` 접두어 강제, mock 시나리오 그룹 9개, 그리고 **가장 중요한 확인 경로**로 "`cluster`/`cost` 시나리오를 바꾸면 실제 전이가 일어나 알림이 생성된다"를 명시하고 AC로 박았다.
8. **이력 보관 요구사항**(3.7) — A~E 다섯 덩어리(알림·발송 기록·상태 머신·heartbeat·설정)로 "무엇이 없으면 기능이 성립하지 않는지"만 적고 **스키마 설계는 DBA에게 넘겼다**. 보관 90일/2,000건 + 미해제 제외, DB 없을 때 메모리 200건.
9. **갱신 주기**(4) — 새 informer·새 주기·새 `SourceId` 없이 기존 15초 루프에 얹는 것으로 정리. SSE는 토픽 `alerts` 1개만 추가하고 `overview`에 얹지 않은 근거를 적었다.
10. **단계 구분과 수용 기준**(5) — P1(화면 센터, AC-ALERT01~18) / P2(설정 + 디스코드, AC-ALERT19~34) / P3(다음 범위). P1만으로도 쓸모가 있다는 점과 **"자리 비웠을 때 알림"은 P2에서 완성된다**는 한계를 정직하게 적었다.
11. **범위 밖**(6)·**역할별 전달 사항**(7, 5개 역할)·**열린 질문**(8, Q1~Q12)·**기존 명세와의 충돌**(9, 9건)·**요약 한 장**(10) 작성.

### 5. 주요 결정과 이유

| # | 결정 | 검토한 대안 | 선택한 이유 |
|---|---|---|---|
| D1 | **알림 단위를 영역 8개로** (`area:controlPlane`·`nodes`·`workloads`·`pods`·`events`·`db`·`cost`, `source:kube`) | 개별 리소스 단위(파드·노드마다 키) | 개별 단위면 노드 1대가 내려갈 때 그 위 파드 수만큼 알림이 나가 **알림이 그 자체로 장애**가 된다. 영역 단위는 개요 카드·사이드바와 같은 단위라 링크가 자연스럽고, 영향 객체는 이미 서버가 만드는 `areas.*.problems`(최대 3)로 본문에 담을 수 있다 |
| D2 | **`area:metrics`·`overall`을 키에서 제외** | 전부 키로 두기 | `metrics`는 kOps에서 metrics-server가 없는 것이 정상이라 **상시 `unknown`** → 상시 켜진 알림은 알림이 아니다. 사용률 임계는 이미 `area:nodes`에 들어 있다. `overall`은 영역 알림의 합이라 반드시 중복 |
| D3 | **출처 키는 `source:kube` 하나만** | 출처마다 키 / 출처 키 없음 | kube가 끊기면 영역 5개가 동시에 `unknown` → 1건으로 묶는 키가 필요. 나머지 출처(`monitoredDb`·`awsResources`·`metrics` 등)는 영향 영역이 1개뿐이라 그 영역의 사유 문구로 충분. `dashboardDb`는 끊기면 이력 저장 자체가 안 되는 순환이라 제외 |
| D4 | **컨트롤 플레인을 알림에서는 분리** | 사이드바처럼 `nodes`에 합산 | 사이드바는 "어느 화면으로 가나"(합산 타당), 알림은 "무슨 일이 일어났나"(분리 필요). 마스터 장애가 워커 소음에 묻히면 kOps 전환의 목표가 무너진다 |
| D5 | **`critical` → `warning` 하락은 새 알림을 만들지 않는다** (등급만 낮추고 이력 한 줄) | 완화 알림도 발송 | 아직 해결되지 않았다. 알림 수만 늘고 정보가 늘지 않는다. 반대로 `warning` → `critical` 격상은 **새 알림**(등급이 올라간 것은 반드시 알려야 한다) |
| D6 | **해제 알림은 발생 알림을 보낸 채널에만** | 항상 발송 | 짝 없는 "복구됨"이 채널에 뜨면 사람이 "무슨 장애가 있었지?"로 혼란해진다. 화면 이력에는 항상 남긴다 |
| D7 | **`unknown`을 별도 축으로** (심각도 순서에 넣지 않고 `sendUnknown` 토글 + 5분 지속) | `warning` 아래 등급으로 줄 세우기 | `unknown`은 "얼마나 나쁜가"가 아니라 "판단할 수 없다"는 다른 축이다. 순서로 세우면 "주의부터 보내기"를 켤 때 뜻이 다른 것이 따라온다. 5분 지속은 watch 재시작 같은 일시적 끊김을 거른다(`stale` 판정 45초의 여유 배수) |
| D8 | **재시작 시 직전 종료 상태와 비교하지 않는다** (워밍업 120초 + 요약 1건 + 정지 구간 안내, 디스코드 미발송) | 종료 시 상태를 DB에 저장해 재시작 후 비교 | 비교하면 ① 바뀐 **시각**을 알 수 없어 과거 사건을 지금 일로 알리고, ② 며칠 껐다 켜면 무더기로 쏟아지고, ③ 결국 "전부 새 장애"와 같은 문제로 돌아간다. 대신 heartbeat로 **정지 구간을 정직하게 알리는 것**이 더 유용하다 |
| D9 | **억제 창 밖에서도 재알림하지 않는다** (주기적 재알림은 기본 꺼짐) | 1시간마다 재알림 | 사용자 지시 "같은 상태가 유지되는 동안 반복 발송하면 안 된다"를 그대로 따랐다. 불안하면 켤 수 있게 설정 자리만 남겼다(Q7) |
| D10 | **영향 객체가 추가되면 억제 창 밖에서 "추가 발생" 1건** | 전이만 보고 무시 | "파드 A 죽음 → 알림 → 10분 뒤 파드 B도 죽음"에서 영역 상태는 `critical` 그대로라 전이가 없다. 이 규칙이 없으면 B는 영원히 안 알려진다. 억제 창 15분이 상한이라 도배가 안 된다 |
| D11 | **플래핑은 진입 시 1건 알리고 그 뒤 침묵** | 조용히 숨기기 / 그대로 다 알리기 | 플래핑 자체가 "불안정하다"는 정보라 한 번은 알려야 하고, 6번 더 알리면 사람이 알림 전체를 무시하게 된다 |
| D12 | **웹훅 URL: DB `settings` 별도 키 + env 우선·잠금 + 원문 절대 미노출(끝 4자 힌트)** | `.env` 전용 / 로컬 파일 / 암호화 | `.env` 전용은 "화면에서 입력" 요구를 못 채운다. 로컬 파일은 이미 있는 설정 경로를 두고 새 저장소를 만드는 것이라 낭비. **원문 미노출**이 핵심 — 대시보드에 로그인이 없어서(가정 A5) 화면을 열 수 있는 사람 = URL을 복사할 수 있는 사람이 되고, 클러스터 배포 시 그 범위가 더 넓어진다. 원문을 안 보여줘도 "지우고 다시 넣기"로 모든 운영이 된다 |
| D13 | **평문 저장(암호화 안 함)** + 한계 명시 + Q4로 올림 | 암호화 | 키를 또 `.env`에 둬야 해서 보호 수준이 결국 같아진다. 대시보드 DB 접근 = 서버 접근. 다만 DB 덤프에 섞이는 것이 걸릴 수 있어 **판단을 PM에게 올렸다** |
| D14 | **웹훅 URL은 디스코드 도메인만 허용** | 임의 URL 허용(범용 웹훅) | 임의 URL이면 대시보드가 "지정한 아무 주소로나 요청을 만들어 주는 도구"가 된다. 클러스터 안에 배포하면 내부 주소 접근(SSRF 성격) 위험. 이번 범위는 디스코드 하나(가정 N4). → Q9 |
| D15 | **테스트 발송은 저장된 주소로만** | 입력 중인 값으로 테스트 | 저장 전 값을 요청 본문으로 보내면 검증 오류 `details.fields[].value`·프록시 로그에 남을 위험이 커진다(`k8s-snapshot`에서 `content`·`path`를 오류 본문에서 뺀 것과 같은 판단). "저장 → 테스트 → 틀리면 지우고 다시"로 모든 운영이 가능 |
| D16 | **테스트 발송 = 확인 대화상자 + `confirm: true`(422) + 60초 쿨다운(429) + `[테스트]` 문구 + 이력 기록** | 버튼만 두기 | 되돌릴 수 없는 외부 효과라 "사용자가 의도한 것임이 분명"해야 한다. 기존 `SNAPSHOT_CONFIRMATION_REQUIRED` 패턴을 복제해 **새 개념을 만들지 않았다**. 채널의 다른 사람이 장애로 오인하지 않게 본문에 "[테스트] … 실제 장애가 아닙니다"를 강제 |
| D17 | **`ALERTS_DISPATCH=mock\|live`** (mock에서 아웃바운드 0건, live 모드에서도 mock으로 강제 차단 가능 = 비상 스위치 겸용) | `ALERTS_ENABLED` 킬스위치 별도 / mock에서도 그냥 발송 | PM 지시대로 `ADVISOR_BRIDGE=live` 패턴을 그대로 복제했다. 스위치 하나가 "mock 차단"과 "비상 차단"을 겸해 개념이 늘지 않는다 |
| D18 | **mock 발송 시 `[MOCK]` 접두어 강제** | 없음 | `ALERTS_DISPATCH=live` + `DATA_SOURCE=mock`으로 문구를 실제 채널에서 확인할 때, 가짜 장애가 진짜로 보이면 안 된다 |
| D19 | **알림 본문에 리소스 이름 원문** (가명 안 씀) + 안내 문구 + Q3로 올림 | 어드바이저처럼 가명 처리 | 어드바이저 가명 규칙은 **외부 LLM 전송**에 대한 것이고, 알림은 운영자 자기 채널로 가는 조치용 메시지다. 가명이면 "어느 파드인지" 알 수 없어 알림이 무의미해진다. 다만 kOps에서 노드 이름 = EC2 인스턴스 ID라 **AWS 내부 식별자가 채널에 남는다** → 판단을 PM에게 올렸다 |
| D20 | **SSE 새 토픽 `alerts` 추가** | `overview` 토픽에 얹기 | 개요는 영역 요약, 알림은 목록이라 수명·크기가 다르다. 개요 갱신마다 알림 목록이 실리면 불필요하게 커진다. 프론트는 스트림 1개에 전체 토픽을 구독하므로 추가 비용이 낮다. 새 `SourceId`는 만들지 않았다(알림은 출처가 아니라 파생) |
| D21 | **단계: P1 화면 센터 → P2 설정+디스코드** | 한 번에 / 디스코드 먼저 | 사용자 지시("화면 알림 센터만으로도 쓸모가 있어야 한다"). P1은 "지나간 일을 놓치지 않는다"(이력·배지), P2가 "자리를 비웠을 때 알려 준다"를 완성한다. **이 한계를 명세에 정직하게 적었다** |

| D23 | **"쓰기"의 3층 구분을 명세 0.2절에 표로 명시** | 언급만 | PM이 특별히 요구한 항목. ① 관측 대상 쓰기 0건, ② 대시보드 자체 DB(기존 `PATCH /api/cost/settings`와 같은 성격), ③ 밖으로 나가는 단방향 통지 — 셋을 섞어 말하지 않도록 표로 못박고, `common.md` 0 요약에 한 줄 추가를 백엔드에 요청했다 |
| D24 | **억제 창·플래핑·워밍업 값을 설정 화면에 두지 않는다** | 화면에서 편집 | 잘못 만지면 알림이 조용히 사라진다. `settings`·환경 변수로만 바꾸게 했다(`aws-cost`의 `estimation` 블록을 조회 전용으로 둔 것과 같은 결) |

### 7. 남은 이슈·한계

1. **열린 질문 12개가 미결이다.** 특히 **Q1(벨 위치)·Q2(`unknown` 기본 발송)·Q3(리소스 이름 원문)·Q6(사이드바 항목 수)**는 디자인·백엔드가 착수하기 전에 답이 필요하다. Q1·Q6은 서로 얽혀 있다(벨을 안 넣으면 사이드바 배지로 대신해야 한다).
2. **P1만으로는 "자리를 비웠을 때 알려 준다"가 안 된다.** 명세 5절에 정직하게 적었지만, 사용자가 P1 완료 시점에 "왜 알림이 안 와?"라고 느낄 수 있다. PM이 단계 설명을 함께 전달하는 편이 좋다.
3. **기준값(억제 15분·플래핑 30분/4회·워밍업 120초·`unknown` 5분)은 실측 없이 정한 값이다.** 실제 클러스터에서 한 주 돌려 보고 조정해야 한다. 전부 설정값이라 나중에 바꿀 수 있게 했다(Q5).
4. **디스코드 API의 구체 제약을 확인하지 못했다** — 메시지 길이 상한(2,000자), 임베드 필드 수·길이, 웹훅 레이트리밋의 정확한 수치. 명세에는 "본문에 담을 정보"만 적고 형식은 백엔드에 넘겼다. **백엔드가 구현 전에 확인해 `docs/api/alerts.md`에 기록해야 한다.**
5. **디스코드 웹훅 URL의 정확한 형식 패턴**(`/api/webhooks/<id>/<token>`의 id·token 길이 규칙)을 확인하지 못했다. 도메인·스킴·경로 접두어까지만 명세에 적었고, 세부 검증 정규식은 백엔드가 확인해서 정한다.
6. **클러스터 안 배포 시 아웃바운드 가능 여부(Q11)는 사용자 환경 확인이 필요하다.** 나갈 수 없어도 화면 알림은 동작하므로 기능이 죽지는 않는다.
7. **`area:cost` 키를 1개로 묶은 결과**, 예산 초과와 소모율 급증이 동시에 일어나면 알림 1건에 최악 사유만 보인다(`aws-cost` 3.7의 집계를 그대로 쓰므로). 본문에 나머지 사유도 붙일지는 백엔드/계약 단계에서 정하면 된다(`reasons[]` 배열은 이미 여러 개를 담는다).
8. **기존 문서 수정은 하지 않았다.** 9절의 충돌 9건은 각 담당이 자기 영역 문서를 고쳐야 한다(아래 8절).

### 8. 다른 담당 요청

- **`backend` 요청 (문서)**: `docs/api/common.md` 갱신 — ① 5.1 토픽 표에 `alerts` 1줄, ② 5.8 이벤트 전체 목록에 `alerts.snapshot`·`alerts.created`·`alerts.updated`·`alerts.read`, ③ 6.1 mock 그룹 `alerts`(시나리오 9개), ④ 3.3 공통 에러 표에 `ALERT_TEST_CONFIRMATION_REQUIRED`(422)·`ALERT_TEST_COOLDOWN`(429), ⑤ **0 요약 "쓰기" 행에 알림 발송 층 한 줄 추가**(명세 0.2절). 기존 엔드포인트·응답 모양은 바뀌지 않는다(추가만).
- **`backend` 요청 (계약)**: `docs/api/alerts.md`를 **구현 전에** 작성. REST(`GET /api/alerts`, `PATCH /api/alerts/read`, `GET/PATCH /api/alerts/settings`, `POST /api/alerts/test`) + SSE + 발송 상태 enum + 디스코드 메시지 형식(길이 상한 확인 포함).
- **`backend` 요청 (코드, 이번 기능 범위)**: `redactSecrets`에 디스코드 웹훅 URL 패턴 추가, 오류 응답 `details.fields[].value`에서 `webhookUrl` 제외, 비밀값 스캐너(`deploy/aws-snapshot/lib`)에 웹훅 패턴이 있는지 확인·없으면 추가, 환경 변수 3개(`ALERTS_DISPATCH`·`ALERTS_DISCORD_WEBHOOK_URL`·`ALERTS_PUBLIC_BASE_URL`) 선언, `deploy/app.example.yaml` 아웃바운드 주석.
- **`backend` 요청 (기존 명세 문구, PM 경유)**: `docs/specs/cluster-status.md` 6절 범위 밖에서 **"알림 발송(Slack/메일)"을 빼고** "알림은 `docs/specs/alerts.md`" 한 줄로 교체. "알림 규칙 편집 UI"는 범위 밖으로 **남긴다**. → 이 파일은 planner 영역이므로 **PM이 지시하면 planner가 직접 고치겠다**(이번 작업에서는 임의로 고치지 않았다).
- **`designer` 요청**: `docs/design/shell.md` **2절의 "알림 벨을 두지 않는다"를 고치고 2.1의 상단바 폭 계산 표를 다시 맞춰야 한다**(오른쪽 영역 최소 304px → 약 348px, 긴 FQDN 클러스터 이름과 경쟁). 3.1 사이드바 항목 표에 `설정`(및 Q6 결정에 따라 `알림`) 추가. 그 밖에 명세 7절 "디자인" 10개 항목.
- **`dba` 요청**: 명세 3.7의 A~E를 담는 스키마 설계 + 보관 정리(`purgeExpiredData`에 90일/2,000건·미해제 제외) + `settings` 기본값에 `alerts.*`(웹훅 URL은 **별도 키**, 기본 `null`, 시드에 예시 값 금지) + heartbeat 단일 행 upsert 형태 검토 + **Q4(평문 vs 암호화)에 대한 의견**.
- **`publisher` 요청**: 새 컴포넌트 3개(`AlertItem`·`NotificationBell`·`SecretInput`)만. 나머지는 기존 것 재사용.
- **`frontend` 요청**: `alerts` 토픽을 **기존 스트림 1개**에 추가(새 EventSource 금지), `/alerts`·`/settings` 화면, 웹훅 입력값을 상태에 오래 들고 있지 않기.
- **PM 요청**: 열린 질문 Q1~Q12를 사용자에게 확인. 특히 Q1·Q2·Q3·Q6은 디자인/백엔드 착수 전에 필요하다.

### 9. 다음 담당이 알아야 할 점

1. **이 명세는 판단 기준을 하나도 새로 만들지 않았다.** 알림의 등급은 서버가 이미 계산한 `StatusInfo.status`를 그대로 옮긴 것이다. "장애 기준이 뭐예요?"라는 질문이 나오면 `cluster-status` 3.2~3.7 / `kops-support` 3.2 / `aws-cost` 3.5~3.7을 보면 된다. **알림 쪽에서 임계값을 다시 정의하지 마라.**
2. **알림 키는 8개, 영역 단위다.** 개별 파드·노드 단위 알림은 3단계(다음 범위)다. 구현 중에 "파드마다 알림을 내면 더 친절하지 않나"라는 유혹이 생기면 명세 3.1의 근거 1을 읽어라(도배로 기능이 무너진다).
3. **가장 중요한 mock 확인 경로**: `cluster` 시나리오를 `healthy` → `critical`로 바꾸면 **실제 전이가 일어나 알림이 생성되고 배지가 올라간다**(AC-ALERT02). `alerts` 그룹의 `default`는 "미리 쌓인 이력"일 뿐이다. 이 두 가지를 섞지 마라.
4. **mock에서 디스코드로 나가는 요청은 0건이어야 한다**(AC-ALERT26). 이건 테스트로 보장해야 하는 항목이다. `ALERTS_DISPATCH=live`로 명시할 때만 나간다.
5. **웹훅 URL 원문은 어떤 API 응답에도 실리면 안 된다**(AC-ALERT20). `GET`은 `configured`·`hint`(끝 4자)·`length`·`updatedAt`만 준다. 오류 응답의 `details.fields[].value`에서도 빼야 한다.
6. **테스트 발송은 `confirm: true` 없이는 422다**(AC-ALERT23). 프론트가 확인 대화상자 없이 API를 부르면 실패하도록 서버에서 막는다 — 화면만 믿지 않는다.
7. **해제 알림은 발생 알림을 보낸 채널에만 간다**(AC-ALERT32). 발송 기록(`skipped_severity` 등)을 보고 판단해야 하므로 **발송 기록을 반드시 남겨야 한다**.
8. **재시작 폭주 방지가 이 기능의 숨은 난이도다**(3.2.5). 워밍업 120초 + heartbeat 기반 정지 구간. informer가 `syncing`인 동안 "노드 0대 = 클러스터 장애" 같은 가짜 판단이 스쳐 지나간다는 점을 잊지 마라.
9. **`unknown`은 장애가 아니다.** 문구에 "장애"를 쓰지 마라. `kube` 끊김은 영역 5건이 아니라 `source:kube` 1건으로 묶인다(3.2.4 출처 억제).
10. **충돌 9건(9절)을 확인하고 자기 영역 문서를 고쳐라.** 특히 디자인의 "알림 벨을 두지 않는다"(shell.md 2절)와 상단바 폭 계산은 Q1 결정 직후 바로 손봐야 한다.
11. **RBAC·AWS 권한은 그대로다**(AC-ALERT14). 알림 때문에 `deploy/rbac.yaml`이나 IAM 정책을 늘리는 PR이 나오면 잘못된 것이다.
12. **알림 본문에 넣을 수 있는 문자열은 서버가 만든 `reasons[].text`와 `ResourceRef`뿐이다**(3.3.2). 쿠버네티스 원본 객체의 어떤 필드도 직접 넣지 마라.

- "드리프트 알림(Slack 등)"이 범위 밖에 있는데, 알림 기능이 생겼으므로 "그럼 이제 되나?"로 읽힐 수 있다 → **그대로 범위 밖**임을 하위 항목으로 명시(`alerts` 3.1의 알림 키 8개에 스냅샷·드리프트가 없고, `snapshotStore`·`k8sSnapshotStore` 출처 알림도 `alerts` 6절에서 범위 밖). 드리프트를 메뉴 상태에 넣지 않는다는 기존 결정도 그대로.

### 7. 남은 이슈·한계

1. **`docs/specs/alerts.md`가 PM 결정과 어긋나는 곳이 남아 있다** — 8절에 올렸다. 나는 고치지 않았다(지시).
2. **`cluster-status` 가정 A7 ↔ DB 파드 로그의 쿼리 원문**은 미결이다. DBA 확인 후 PM이 정해야 하고, 결론에 따라 `logs` 3.3.2 가림 규칙에 줄이 하나 늘 수 있다.
3. 내가 고친 것은 **명세 문장뿐**이다. `docs/api/common.md`(토픽·`SourceId`·mock 그룹·에러 코드), `docs/design/shell.md`(사이드바 3개 + 폭 계산), `deploy/rbac.yaml` 주석은 **각 담당이 아직 반영해야 한다**.
4. `alerts` 9절 충돌표의 나머지 5건(`docs/design/shell.md` 2건, `docs/api/common.md` 2건, `docs/db/schema.md` 1건)과 `logs` 8절의 `docs/api/**` 5건은 **내 쓰기 영역 밖**이라 손대지 않았다.

### 9. 다음 담당이 알아야 할 점

1. **`cluster-status.md` 3절(상태 판단 기준)은 이번에 한 글자도 바뀌지 않았다.** 알림·로그 어느 쪽도 새 임계값을 만들지 않는다. 기준이 궁금하면 여전히 `cluster-status` 3절 / `kops-support` 3.2 / `aws-cost` 3.5~3.7이다.
2. **범위 밖 항목이 "사라진" 것이 아니라 "옮겨간" 것이다.** 6절을 읽을 때 `→ docs/specs/alerts.md` / `→ docs/specs/logs.md`를 따라가라. Slack·이메일·AWS Budgets·예산 편집 화면·`exec`·포트 포워딩은 **여전히 범위 밖**이다.
3. **사이드바는 늘어나지만 상태 점은 늘어나지 않는다.** `nav` 키·합산 규칙(`kops-support` 3.1)은 그대로다. 알림은 **배지 숫자만** 쓴다.
4. **알림은 컨트롤 플레인을 분리(`area:controlPlane`), 사이드바는 합산(`nav.nodes`).** 이 둘이 달라 보여도 의도한 것이다 — 근거를 `alerts` 3.1과 `kops-support` 3.1 **양쪽에** 적어 두었다.
5. **로그는 어드바이저로 나가지 않는다**(`architecture-advisor` 3.4). 가린 로그도, 로그 요약도 안 된다. 스냅샷 스키마에 로그 필드를 만들지 마라.
6. **`/settings`에 예산 편집을 붙이지 마라**(`aws-cost` 6절, AC-ALERT34). 이번엔 탭 자리만이다.

### 7. 남은 이슈·한계

1. **`docs/design/alerts.md`가 이미 만들어졌다면 벨 기준으로 그려졌을 수 있다.** PM이 designer를 차단했다고 했지만, 이미 나온 산출물이 있으면 **다시 봐야 한다**(8절 요청).
2. **`docs/api/alerts.md`(백엔드 계약)가 이미 작성 중이라면** 배지·탭 제목용 필드(미확인 수·최악 심각도)는 그대로지만, **"패널용 최근 10건" 같은 전용 엔드포인트를 만들 필요가 없어졌다**(8절 요청).
3. `cluster-status` 가정 A7(DB 파드 로그의 쿼리 원문)은 **PM 지시대로 "판단 대기" 그대로** 뒀다. DBA 확인 후 결론이 나면 `logs` 3.3.2에 규칙이 하나 늘 수 있다.
4. 아직 열린 질문: `alerts` **Q11**(월요일), `logs` **Q1·Q8**(월요일), `logs` **Q5·Q9·Q10**(PM 판단 대기). 전부 착수를 막지 않는다.
5. `logs` 3.8.1 진입점 8번이 참조하던 **"7절 alerts 요청"이 실제로는 없는 절**이었다(끊긴 참조). `alerts` 7절 프론트와 8절 충돌표를 가리키도록 고쳤다.

### 8. 다른 담당 요청

- **`designer` 요청 (가장 급함)**: **상단바를 건드리지 않는다.** `shell.md` 2절("전역 검색·알림 벨·사용자 메뉴를 두지 않는다")과 **2.1 폭 계산 표는 그대로 두면 된다.** 할 일은 **3.1 사이드바 표에 `알림`·`로그`·`설정` 3개 추가**(상태 점 없음, 숫자 배지는 `알림`만, `설정`은 그룹 밖 맨 아래)뿐이다. `docs/design/alerts.md`를 이미 벨 기준으로 그렸다면 **폐기·수정**이 필요하다. 근거: `alerts` 3.3.1·7절 디자인 1·2·9, **AC-ALERT36**.

- **`frontend` 요청**: 진입점은 **사이드바 배지 + `/alerts`** 둘뿐이다. 알림 패널(Popover·Drawer)을 만들지 않는다. **브라우저 탭 제목 `(3) Sentinel`은 P1 범위**다(AC-ALERT35). 파드 알림에는 **로그 화면 링크**를 걸되 **본문에 로그 줄을 넣지 않는다**.
- **`backend` 요청**: `docs/api/alerts.md`에 **"최근 10건 패널용" 전용 응답을 만들 필요가 없다**(패널이 없어졌다). 배지에 필요한 것은 미확인 수 + 최악 심각도뿐이다. **알림 본문·이력·SSE 어디에도 로그 줄이 들어가지 않도록** 계약에 못 박아 달라(AC-ALERT13).
- **PM 요청**: `docs/reports/alerts/README.md`·`docs/reports/logs/README.md`의 **진행 현황 표**는 PM 영역이라 건드리지 않았다. 두 명세의 상태가 "초안"에서 **"착수 가능"**으로 바뀌었으니 반영이 필요하면 갱신해 달라.

### 9. 다음 담당이 알아야 할 점

1. **상단바는 이 기능에서 건드리지 않는다.** 벨·패널·폭 재계산 전부 없다. 명세에 그런 지시가 보이면 **옛 판을 보고 있는 것**이다(9절 충돌표에 "이전 판의 지시를 취소한다"고 적어 뒀다).
2. **진입점은 둘뿐**: 사이드바 `알림` 메뉴(배지) + `/alerts` 화면. 셋째 진입점을 만들지 마라.
3. **사이드바 3개(`알림`·`로그`·`설정`)는 상태 점이 없다.** `nav`에 새 상태 키를 만들지 않는다. 숫자 배지는 `알림`에만.
4. **알림 본문에 로그 줄을 넣지 마라** — 화면이든 디스코드든, 가린 줄이든 요약이든. **링크만** 건다(AC-ALERT13).
5. **브라우저 탭 제목 `(3) Sentinel`은 P1이다**(AC-ALERT35). 브라우저 알림 권한 요청·소리는 범위 밖이다.
6. **8절(alerts)·9절(logs)은 이제 "결정" 절이다.** 거기 있는 것은 **다시 묻지 마라.** 아직 열린 것은 "월요일 확인" 또는 "PM 판단 대기"로 표시돼 있고 **착수를 막지 않는다.**
7. **AC 번호는 여전히 고정**이다. 이번에 뒤에 붙인 것은 **AC-ALERT35·36 둘뿐**이고, 문구만 고친 것은 AC-ALERT02·13이다. `logs`는 AC 변경이 **없다**.

## 2026-09-25 (3차) · `alerts.snapshot`에서 목록 제거 (backend 판단에 명세를 맞춤)

### 1. 요청 내용

PM: 계약 작성 중 나온 backend 판단이 맞으니 명세를 맞출 것. **`alerts.snapshot`(SSE)에서 "최근 N건"을 뺀다.**

- 근거(PM 전달): 상단바 패널이 없어졌고(사이드바 메뉴 결정) **목록이 필요한 화면은 `/alerts` 하나뿐**인데, `alerts` 토픽은 **모든 페이지가 구독**하므로 스냅샷에 이력을 실으면 **알림 화면을 보지도 않는 탭까지 재연결마다 목록을 받는다.**
- 스냅샷에는 `unreadCount`·`worstSeverity`·`updatedAt`만, 목록은 `/alerts`가 REST로.
- **왜 그런지 이유도 함께 적을 것**(안 적으면 "스냅샷에 목록이 있으면 편한데"로 되돌린다).
- **"스냅샷에 최근 N건이 온다"를 전제한 다른 서술이 있는지 검색**할 것. 관련 AC는 문구만 맞추고 **번호는 그대로**.
- 주의: **backend 구현 시작·publisher 작업 중** → `docs/specs/**`만. `docs/api/**`는 이미 이 결정대로 쓰여 있고 **명세를 계약에 맞추는 방향**이다.

### 2. 작업 내용

**(1) 4절 SSE — 이벤트 정의 교체 + 근거 4줄**

- `alerts.snapshot` 정의를 "**최근 N건** + 미확인 수 + 최악 심각도 + 발송 설정 요약" → **"배지에 필요한 것만 — `unreadCount`·`worstSeverity`·`updatedAt`·발송 설정 요약"**으로 바꿨다.
- 바로 아래에 **"목록을 싣지 않는다 (되돌리지 말 것)"** 항목을 만들고 근거 4줄:
  1. **`alerts` 토픽은 모든 페이지가 구독한다** — 스냅샷에 이력을 실으면 **안 보는 탭까지 재연결마다 받는다.** "비용은 있고 쓰는 곳은 없다."
  2. **목록이 필요한 화면은 `/alerts` 하나뿐** — 상단바 패널이 없어졌기 때문이다(Q1). **패널이 있었다면 필요했지만 지금은 아니다**는 인과를 적었다.
  3. 목록은 `GET /api/alerts`로. 스냅샷은 **배지 한 개를 그리는 최소값**만.
  4. **실시간성은 그대로다** — 열려 있는 동안의 변화는 `alerts.created`·`alerts.updated`로 온다. (이걸 안 적으면 "목록을 빼면 실시간이 깨지지 않나"로 되돌아온다.)
- `overview` 토픽 근거 문장에도 "토픽을 나눠 두면 **이 규칙도 깔끔하게 지켜진다**"를 덧붙였다.

**(2) 전제 서술 검색 → 3곳 정리**

`snapshot`·`최근 N건`·`최근 10건`·`목록`·`토픽`·`SSE`로 전수 검색했다. 목록을 전제하던 곳은 **3곳**이었고 전부 고쳤다.

| 위치 | 고친 내용 |
|---|---|
| **7절 프론트** | "역할 분담을 지킨다" 한 줄 신설 — 배지는 SSE 스냅샷, **목록은 `/alerts`가 REST**. **"목록을 앱 레이아웃 전역 상태에 들고 있지 않는다"**까지 명시(프론트가 실수하기 쉬운 지점이다) |

### 6. 다른 담당 요청

- **`frontend` 요청**: 배지는 SSE 스냅샷, **목록은 `/alerts`에서 REST로**. **알림 목록을 앱 레이아웃 전역 상태에 얹지 마라** — 스냅샷에서 뺀 이유가 그 자리에서 되살아난다(AC-ALERT37의 취지).
- **`dba` 요청**: 조회 ②(미확인 수 + 최악 심각도)는 **모든 탭이 재연결할 때마다** 불리는 유일한 조회가 됐다. **집계 한 방**으로 끝나는 형태를 권한다. ①(최근 N건)은 이제 `/alerts` 화면에서만 불린다.
- **`backend`**: 요청 없음. **이번에는 backend 판단이 맞았고 명세가 계약에 맞춰졌다.**

### 7. 다음 담당이 알아야 할 점

1. **`alerts.snapshot`에 목록을 넣지 마라.** 모든 탭이 구독하는 토픽이라 **안 보는 탭까지 이력을 받는다**(4절, AC-ALERT37).
2. **실시간성은 안 깨진다** — 열려 있는 동안의 변화는 `alerts.created`·`alerts.updated`로 온다.
3. 이 결정은 **Q1(상단바 패널 없음)의 파생**이다. 패널이 다시 논의되면 이 규칙도 함께 봐야 한다.
4. **AC-ALERT37은 P1 소속**이고 번호만 뒤에 있다. 01~34는 그대로다.

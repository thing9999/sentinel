  - 이번 단계에서 만들 것: 공통 기반(3D 틀·상호작용·관계 표 대체 보기·지연 로딩·접근성·성능)과 **Kubernetes 스냅샷 상세의 3D 보기 탭**(3.1). AWS 스냅샷 상세·스냅샷 목록 화면은 이번에 바뀌지 않는다.

## 0. 사용자 확정 사항과 가정

### 0.1 사용자 확정 (2026-09-20, PM 전달)
- U1. 보기 네 가지 모두 원함.
  1. **K8s 구성도 + 드리프트**: k8s 스냅샷 하나를 네임스페이스(바닥 판) → 워크로드·Service·Ingress·PVC(블록) → 연결선(Ingress→Service→워크로드 셀렉터, 워크로드→PVC/ConfigMap/Secret 참조). 드리프트는 블록에 변경/삭제/추가 표시.
  2. **AWS 인프라 구성도**: AWS 스냅샷 템플릿(CloudFormation/Terraform)에서 VPC → 서브넷(AZ별) → EKS 클러스터·노드그룹 → LB·EBS 등을 층으로.
  3. **스냅샷 시간축**: 스냅샷들을 시간 순서로 쌓아 리소스 수 변화·파일 상태(커밋 금지 등), 스냅샷 사이 생긴·없어진 리소스.
  4. **AWS+K8s 통합 한 장면**: AWS 층(VPC·노드그룹) 위에 K8s 층(네임스페이스·워크로드). 두 스냅샷을 짝짓는 규칙(시점·클러스터 일치)을 정의.
- U2. 위치: 스냅샷 상세에 **"3D 보기" 탭**. 블록 클릭 → 파일·드리프트 탭의 해당 리소스로 이동. 시간축은 **목록 화면의 보기 전환**.
- U3. 범위가 크므로 **단계적 제공(phase)**. 단계별 수용 기준 구분, 권장 순서와 이유.
- U4. 조회 전용(쓰기 없음). 비밀값 원문 표시 금지(기존 가림 규칙).
- U5. **접근성·대체 필수**: WebGL 없음·저사양·스크린리더·`prefers-reduced-motion` 환경에서 2D/표 대체 보기. 3D는 보조이고 같은 정보를 대체 보기로 얻을 수 있어야 한다.
- U6. 성능: 리소스 수백~천 개 규모. 성능 목표 숫자를 명세에 둔다(인스턴싱·LOD 등 방법은 설계 몫).
- U7. mock 모드 예시.
- U8. three.js 번들 크기·지연 로딩 요구 포함.

### 0.2 가정 (다르면 수정)
- A1. 사용자는 로컬 운영자 1명(ASM A1과 같음). 이 기능도 사실상 **로컬 실행 전용**(스냅샷 폴더가 있는 곳, ASM A5).
- A2. 3D의 원본 데이터는 **스냅샷 파일 내용(현재 파일 기준)** 과 **이미 계산된 드리프트 결과**(K8S 4절)뿐이다. 현재 클러스터 상태(파드 배치·메트릭)는 섞지 않는다(Q4 결정 A, 6절 범위 밖).
- A3. 기준 장비: 2020년 이후 노트북, 내장 GPU(예: Intel Iris Xe급), 최신 Chrome/Edge, 1920×1080, 기기 배율 1~1.5. 성능 목표(4절)는 이 장비 기준이다.
- A4. 규모: 스냅샷 하나에 리소스 **1,000개·관계선 2,000개**가 설계 기준점, **3,000개**가 상한(넘으면 묶어 보기, 3.8). 스냅샷 수는 수백 개 이하(ASM 3.1과 같음).
- A5. 한 스냅샷 파일 = 한 클러스터(K8S A6). AWS 템플릿 한 벌에 클러스터가 여러 개일 수 있다(2~4단계 전제. kOps에서 "클러스터"가 템플릿에 어떤 타입으로 나타나는지는 위 메모 참고).

## 1. 배경 / 목표

- **누가**: kOps 클러스터 운영자. AWS·k8s 스냅샷을 기록·정리하는 사람(ASM·K8S와 같은 사용자).
- **왜**
  - 지금 스냅샷 화면은 파일 목록·트리·표 중심이다. 리소스가 수백 개가 되면 "무엇이 무엇에 연결돼 있나"(Ingress가 어느 Service로, Service가 어느 워크로드로, 워크로드가 어느 PVC·Secret을 쓰나)를 파일을 하나씩 열어 봐야 안다.
  - 드리프트가 "차이 3건"이라고 알려 줘도 그 리소스가 구성 안에서 어디에 있고 무엇에 영향을 주는지 한눈에 보이지 않는다.
  - AWS 템플릿(Former2 결과)은 수천 줄 YAML/HCL이라 VPC·서브넷·AZ·노드그룹·LB 배치를 머릿속으로 그려야 한다.
  - 스냅샷이 쌓여도 "언제 무엇이 생기고 없어졌는지" 흐름을 볼 방법이 없다.
- **목표**
  1. 스냅샷 하나의 구성을 **층과 연결선**으로 보여 준다(K8s·AWS 각각, 그리고 통합).
  2. 드리프트·스캔 발견을 구성 위에 겹쳐 **어디가 달라졌고 어디를 고쳐야 하는지** 위치로 보여 주고, 클릭 한 번으로 기존 파일·드리프트 화면으로 보낸다.
  3. 스냅샷 흐름을 시간축으로 보여 준다.
  4. 3D를 쓸 수 없거나 원하지 않는 사람도 **같은 정보를 표로** 얻는다. 3D는 보조 보기다.
  5. 이 모든 것이 **읽기 전용**이다. 파일·클러스터·AWS에 쓰지 않고, 새 AWS 호출·쿠버네티스 호출·RBAC·IAM 권한이 필요 없다.

## 2. 사용자 시나리오

### S1. 드리프트가 구성의 어디에 있나 (1단계)
1. "스냅샷" → Kubernetes 탭 → 최신 스냅샷 `20260919-061000` 행의 드리프트가 "차이 3건".
2. 상세 → **3D 보기** 탭. 네임스페이스 판 5개(`batch`, `data`, `default`, `monitoring`, `prod`)가 바닥에 깔리고 그 위에 블록이 층별로 서 있다.
3. `prod` 판에서 `Deployment api` 블록에 "변경됨"(□·) 표시, `Ingress api-public`에 "삭제됨"(□−), 판 가장자리에 반투명 `Deployment payments` 블록 "추가됨"(□+).
4. `Ingress api-public` → `Service api` → `Deployment api`로 선이 이어져 있어, 삭제된 Ingress가 api 앞단 진입로였음을 본다.
5. `Deployment api` 블록을 클릭 → 오른쪽 패널에 종류·이름·파일 경로·드리프트 구분·관계 목록(들어오는 선: Service api(셀렉터), HPA api(대상) / 나가는 선: ConfigMap api-config(envFrom)). [드리프트에서 보기] → 상세 드리프트 탭 `res=apps/Deployment/prod/api`가 열려 필드 차이를 본다.

### S2. 커밋 금지 원인 찾기 (1단계)
1. 스냅샷 `20260918-230000`이 "커밋 금지". 3D 보기에서 `data` 판의 `StatefulSet postgres` 블록에 오류 표시(팔각형 + "오류 1").
2. 블록을 두 번 누르면 파일 탭이 `data/statefulsets/postgres.yaml`로 열리고 발견 줄로 이동한다.

### S3. AWS 배치 확인 (2단계)
1. AWS 탭 → 스냅샷 상세 → **3D 보기**. VPC 판 위에 AZ 세 줄(`ap-northeast-2a/b/c`), 각 줄에 public·private 서브넷 판.
2. EKS 클러스터 `prod.k8s.example.com`가 private 서브넷 세 개에 걸쳐 있고, 노드그룹 `nodes-system`은 2a·2b, `nodes-batch`(스팟)는 2c에만 있다. ALB는 public 서브넷 세 곳, EBS 볼륨 하나는 2a에 있다. (2026-09-24: 이름을 api mock의 kOps InstanceGroup 이름에 맞췄다. 이전 예시는 `ng-general`·`ng-spot`이었다.)
3. "노드그룹이 한 AZ에만 있다"는 것을 보고 블록 클릭 → [템플릿에서 보기]로 `cloudformation.yml`의 해당 줄로 이동해 확인한다(수정은 사람이 판단, 이 화면은 조언·적용을 하지 않는다).

### S4. 언제 무엇이 사라졌나 (3단계)
1. Kubernetes 탭 목록에서 보기 전환 [표 | **시간축**]. 연결된 클러스터(`prod.k8s.example.com`)의 스냅샷들이 시간 순서로 판처럼 쌓인다. 각 판의 높이·블록이 종류별 리소스 수, 판 가장자리에 파일 상태(커밋 금지 판은 팔각형 표시).
2. `20260917` → `20260918` 사이 연결부에 "+1 −2". 누르면 생긴 리소스 1개, 없어진 리소스 2개 이름 목록. 없어진 `Ingress api-public`을 누르면 **이전** 스냅샷의 그 파일로 이동.

### S5. AWS와 k8s를 한 장면에서 (4단계)
1. k8s 스냅샷 `20260919-061000` 3D 보기에서 [AWS와 함께 보기]. 서버가 클러스터 이름이 `prod.k8s.example.com`로 같은 AWS 스냅샷 중 시점이 가장 가까운 `20260919-054000`(30분 전)을 기본 짝으로 제안한다.
2. 아래층에 VPC·서브넷·노드그룹, 그 위에 `prod.k8s.example.com` 클러스터 블록 위로 네임스페이스 판이 떠 있다.
3. `Service web`(type LoadBalancer)에서 아래 NLB로, PVC `data-postgres-0`에서 2a의 EBS 볼륨으로 선이 내려간다(근거: AWS 태그).
4. 짝 후보를 `20260917-…`로 바꾸면 "시점 차이 2일 — 두 스냅샷 사이에 구성이 바뀌었을 수 있습니다" 경고가 보인다.

### S6. 3D를 쓸 수 없는 환경
1. 원격 데스크톱(WebGL 없음)에서 3D 보기 탭을 열면 "이 브라우저에서 3D를 쓸 수 없어 표로 보여 줍니다" 안내와 함께 **관계 표**가 열린다. 같은 필터·검색, 같은 행 수, 행을 누르면 같은 곳으로 이동한다.
2. 스크린리더 사용자는 3D 캔버스를 건너뛰는 "표로 보기" 링크로 바로 관계 표에 간다.

## 3. 보기별 표시 대상과 규칙

### 3.0 공통 원칙
- **서버가 판단하고 화면은 그린다**(`docs/api/common.md` 2.2): 리소스 식별값, 부모(어느 판·층에 속하나), 관계선과 그 근거, 드리프트 구분, 스캔 발견 연결, 짝 후보는 서버가 준 값을 쓴다. 화면은 이것을 다시 계산하지 않는다. 배치 좌표를 어디서 계산할지는 프론트·백엔드가 정한다.
- **같은 입력이면 같은 배치**: 같은 스냅샷(파일 버전이 같음)을 다시 열면 블록이 같은 자리에 있다. 필터는 블록을 숨기기만 하고 다시 배치하지 않는다(공간 기억 유지).
- **3D와 표는 같은 데이터**: 3D에 그리는 모든 블록·관계는 대체 보기(3.7)의 행으로도 있다. 3D에만 있는 정보를 만들지 않는다.
- **값을 보여 주지 않는다**: 3D·대체 보기·그 응답에는 식별값(종류·이름·네임스페이스·논리 ID·물리 ID)과 아래에 적은 표시 필드만 담는다. 환경 변수 값, command/args, 어노테이션 값, 레이블·셀렉터 원문, ConfigMap 내용, Secret 값, UserData, 태그 값(Name 태그와 짝 맞추기에 쓴 값 제외), ARN·계정 ID는 담지 않는다. 원문이 필요하면 기존 파일 보기로 이동한다(원문 보기는 기존 파일 화면만, ASM 3.2 E·K8S-API 6.4).
- **관계는 근거와 함께**: 모든 관계선에는 "왜 이어졌는지"(근거)와 확실성(확정/추정)을 붙인다. 못 뽑은 관계는 선을 지어내지 않고 "연결 못 찾음"으로 표시한다.
- **대상이 스냅샷에 없음**: 참조한 대상이 스냅샷에 없으면 **유령 블록**(점선 윤곽, 상태색 없음)으로 그리고 이유를 붙인다(예 "스냅샷에 없음", "Secret — 값·객체를 담지 않음, 이름만", "스냅샷 밖 AWS 리소스").

### 3.1 K8s 구성도 (1단계 — **이번 범위**)

**표시 대상**: 스냅샷 하나의 모든 리소스 문서(`files[].documents`, K8S-API 6.3). 드리프트 비교 불가 종류(ConfigMap·NetworkPolicy·CronJob 등)도 블록으로 그린다(드리프트만 "비교 불가").

**배치 층** (아래→위, 세부 모양은 디자인)

| 층 | 무엇 |
|---|---|
| 바닥 판 | 네임스페이스 판 1개씩(`<ns>/namespace.yaml` 기준, 이름순. 시스템 네임스페이스는 `시스템` 표시). 클러스터 범위 리소스(`_cluster/`)는 별도 판 "클러스터 범위". 해석 실패 파일은 별도 구역 "해석 실패"(관계선 없음) |
| 저장·설정 | PersistentVolumeClaim, ConfigMap, Secret 참조(유령 블록) |
| 워크로드 | Deployment, StatefulSet, DaemonSet, CronJob, Job |
| 서비스 | Service |
| 진입 | Ingress |
| 곁(판 가장자리) | HPA, PDB, NetworkPolicy, ServiceAccount, Role, RoleBinding, ResourceQuota, LimitRange, 사용자 지정 리소스 |

- 여러 문서(`---`)가 든 파일은 문서마다 블록 1개(같은 파일을 가리킴). 경로와 내용 불일치·중복 정의 파일은 블록에 "경로 불일치"/"중복 정의" 표시(K8S 5.1 사유와 같은 말).
- 드리프트 "추가됨" 리소스(파일이 없음)는 해당 네임스페이스 판 위 **유령 블록**으로. 스냅샷에 없던 네임스페이스면 유령 판을 만든다.

**관계 추출 규칙** (워크로드의 파드 템플릿 = Deployment/StatefulSet/DaemonSet/Job `spec.template`, CronJob `spec.jobTemplate.spec.template`)

| # | 관계 | 근거(어디서 뽑나) | 확실성 | 기본 표시 | 못 뽑을 때 |
|---|---|---|---|---|---|
| K1 | Ingress → Service | `spec.rules[].http.paths[].backend.service.name`, `spec.defaultBackend.service.name` (같은 네임스페이스) | 확정 | 켬 | 대상 Service가 스냅샷에 없음 → 유령 블록 "스냅샷에 없음" |
| K2 | Service → 워크로드 | Service `spec.selector`가 워크로드 파드 템플릿 레이블의 부분집합(같은 네임스페이스). 여러 개 맞으면 모두 | 추정(셀렉터) | 켬 | 셀렉터 없음 → Service에 "셀렉터 없음(수동 Endpoints·ExternalName)" 표시 / 맞는 워크로드 없음 → "대상 없음" 표시. 선은 그리지 않는다 |
| K3 | 워크로드 → PVC | `volumes[].persistentVolumeClaim.claimName` | 확정 | 켬 | 대상 없음 → 유령 블록 |
| K4 | StatefulSet → PVC | `volumeClaimTemplates[].metadata.name` + 이름 규칙 `<템플릿>-<sts 이름>-<순번>`인 PVC | 추정(이름 규칙) | 켬 | 맞는 PVC가 없으면 StatefulSet에 "PVC 템플릿 N개(스냅샷에 PVC 없음)" 표시 |
| K5 | 워크로드 → ConfigMap | `envFrom[].configMapRef`, `env[].valueFrom.configMapKeyRef`, `volumes[].configMap`, `volumes[].projected.sources[].configMap` | 확정 | 켬 | 대상 없음 → 유령 블록. `optional: true` 참조는 확실성 옆에 "선택 참조" |
| K6 | 워크로드·Ingress → Secret | 워크로드: `envFrom[].secretRef`, `env[].valueFrom.secretKeyRef`, `volumes[].secret`, `projected…secret`, `imagePullSecrets` / Ingress: `spec.tls[].secretName`. `secret-refs.json`과 같은 규칙(K8S-API 3.3 `via`) | 확정 | 켬 | Secret은 항상 **유령 블록**("Secret — 이름만, 값 없음"). `secret-refs.json`이 없거나 손상이어도 매니페스트에서 뽑는다 |
| K7 | HPA → 워크로드 | `spec.scaleTargetRef`(kind·name) | 확정 | 켬 | 대상 없음 → 유령 블록 |
| K8 | PDB → 워크로드 | PDB `spec.selector`가 파드 템플릿 레이블과 맞음 | 추정(셀렉터) | 끔 | 맞는 것 없음 → "대상 없음" 표시 |
| K9 | 워크로드 → ServiceAccount | `serviceAccountName`(없으면 `default`) | 확정 | 끔 | 스냅샷에 없음(자동 생성 `default`는 CLI가 뺌) → 유령 블록 "자동 생성 또는 스냅샷에 없음" |
| K10 | NetworkPolicy → 워크로드 | `spec.podSelector`(빈 셀렉터 = 네임스페이스 전체) | 추정(셀렉터) | 끔 | 맞는 것 없음 → "대상 없음" |
| K11 | RoleBinding → Role·ServiceAccount | `roleRef`, `subjects[]`(kind ServiceAccount) | 확정 | 끔 | 대상 없음 → 유령 블록(ClusterRole이면 "클러스터 범위, 스냅샷에 없을 수 있음") |

- 이 밖의 관계(ExternalName, 사용자 지정 리소스 안의 참조, 다른 네임스페이스 참조 등)는 이번 범위에서 뽑지 않는다. 선이 없다는 것이 "관계 없음"을 뜻하지 않는다는 안내를 보기 안에 상시 둔다.
- YAML을 해석하지 못한 문서는 관계를 뽑지 않는다(해석 실패 구역).
- 관계 추출은 파일 내용만 읽는다. 셀렉터·레이블 원문은 응답에 싣지 않고 결과(선)만 싣는다(3.0).

**드리프트 겹쳐 보기** (K8S 4절 결과를 그대로 씀. 3D가 드리프트를 새로 계산하지 않는다)

| 드리프트 결과 (`resources[].change`, `files[].drift`) | 블록 표시 |
|---|---|
| `changed` | "변경됨" 표식(`square-dot`) + 건수 |
| `deleted` (스냅샷에만) | "삭제됨" 표식(`square-minus`) |
| `added` (클러스터에만) | 유령 블록 + "추가됨"(`square-plus`) |
| `same` | 표식 없음(숨긴 차이만 있는 것도 표식 없음. 건수에 안 들어가는 규칙과 같음, K8S 4.4-6) |
| `uncomparable` | "비교 불가"(`eye-off`), 권한 거부면 사유 문구 |
| `skipped` | "비교 못 함(해석 실패·중복)" |

- 겹쳐 보기 켜고 끄기(기본 켬). 사용할 결과: 배지 `mode`가 `auto`/`on_demand`이거나, `last_result`이면서 `resultAvailable: true`인 것. 계산 시각을 보기 안에 항상 보인다.
- 결과가 없으면(계산 안 함): 겹쳐 보기 스위치 비활성 + "드리프트 계산 안 함" + `actions.computeDrift.allowed`이면 [드리프트 계산] 버튼(기존 `POST …/drift`와 같은 동작, 3D 보기를 열어 두는 동안 기존 임대 규칙(K8S-API 10.8)으로 유지). 계산 불가(다른 클러스터·연결 없음 등)면 기존 사유 문구(K8S-D 3.5.1). 구성도는 드리프트와 관계없이 그린다.
- 드리프트 상태 배지·문구는 기존 규칙(`status.md` 10절) 그대로. stale이면 stale 표시.

**스캔 발견 겹쳐 보기**: 파일에 현재 스캔 발견이 있으면 그 파일의 블록(들)에 등급 표식(오류: 팔각형 + "오류 N", 경고: 삼각형 + "경고 N"). `metadata.json`·`secret-refs.json`의 발견은 블록이 없으므로 보기 머리의 요약("리소스 밖 발견 N건")에.

**블록 선택 시 패널**: 종류·이름·네임스페이스, 파일 경로, Helm 관리 여부, 스캔 발견 수, 드리프트 구분(+ 필드 변경 건수), 관계 목록(들어오는/나가는, 상대·근거·확실성), 이동 버튼 [파일에서 보기] [드리프트에서 보기](해당 시). 값은 없다.

### 3.2 AWS 인프라 구성도 (2단계 — **이번 범위 아님(보류)**)

> 사용자 결정(2026-09-20)으로 이번에는 만들지 않는다. 나중에 진행할 때 쓰도록 규칙을 그대로 둔다.
>
> **아래의 `AWS::EKS::*` 타입과 `eks:` 태그 전제는 EKS 시절 내용이다(2026-09-24 kOps 전환 이후 유효하지 않다).** 보류 상태라 이번에 고치지 않는다. 이 단계를 시작할 때 ASG/Launch Template 중심으로 다시 설계한다 — 문서 머리의 메모 참고.

**원본 템플릿**: `cloudformation.yml` 우선, 없거나 해석하지 못하면 `terraform.tf`. 어느 쪽으로 그렸는지 보기 머리에 표시. 두 템플릿의 리소스 수가 다르면 정보 문구("CloudFormation 42 · Terraform 40 — CloudFormation으로 그림"). 둘 다 없거나 해석 실패면 빈 상태 + 이유.
- 리소스 수는 3D에 그린 리소스 수와 상세의 리소스 수(CLI 규칙, ASM 3.2 C)가 같아야 한다. 다르면(해석 방식 차이) 차이와 이유를 정보 문구로.

**배치 층** (아래→위, 세부는 디자인)

| 층 | 무엇 (CloudFormation 타입 기준, Terraform은 대응 타입) |
|---|---|
| 리전 바닥 | 스냅샷 `metadata.region` |
| VPC 판 | `AWS::EC2::VPC`. VPC가 여러 개면 판 여러 장 |
| AZ 줄 | VPC 판 위를 AZ별로 나눈 줄. 서브넷 `AvailabilityZone`(또는 `AvailabilityZoneId`)로 정함. AZ를 모르면 "AZ 모름" 줄 |
| 서브넷 판 | `AWS::EC2::Subnet`. 공개/비공개 구분은 `MapPublicIpOnLaunch: true` 또는 태그 `kubernetes.io/role/elb`면 "공개 추정", `kubernetes.io/role/internal-elb`면 "비공개 추정", 그 밖 "구분 모름"(라우트 테이블 해석은 이번 범위 밖) |
| 네트워크 부속 | Internet Gateway·VPC 연결(VPC 가장자리), NAT Gateway·EIP(서브넷 위), Route Table, VPC Endpoint |
| 컴퓨트 | `AWS::EKS::Cluster`(지정 서브넷 전체에 걸침), `AWS::EKS::Nodegroup`(자기 서브넷들에 걸침), `AWS::EKS::FargateProfile`, Auto Scaling Group, Launch Template, `AWS::EC2::Instance`(서브넷 위) |
| 부하분산 | `AWS::ElasticLoadBalancingV2::LoadBalancer`(서브넷들에 걸침), Target Group, Listener, Classic ELB |
| 저장·DB | `AWS::EC2::Volume`(AZ 줄 위, 서브넷 없음), EFS, RDS(DB 서브넷 그룹의 서브넷들) |
| 전역·리전 서비스 선반 | VPC 밖: IAM, S3, ECR, KMS, Route53, ACM, CloudWatch 등. 종류별로 묶음 |
| 기타 선반 | 배치 규칙이 없는 타입(종류별 수만, 펼치면 블록) |
| 보안 그룹 | 블록은 전역 선반과 같은 방식으로 따로 두고, 관계선(A6)은 기본 끔 |

**관계 해석 순서** (참조를 논리 리소스로 바꾸는 방법)
1. CloudFormation 내장 함수: `Ref`, `Fn::GetAtt`, `Fn::Sub`의 `${Name}`, `DependsOn` → 논리 ID. (확정)
2. 값이 물리 ID·ARN 문자열(`vpc-…`, `subnet-…`, `sg-…`, 인스턴스·볼륨 ID, ARN 끝의 이름)이면 `logical-id-mapping.json`(논리 ID ↔ 물리 ID)으로 논리 리소스를 찾는다. Former2 결과는 ID가 하드코딩된 경우가 많기 때문이다(README 7.1-3). (확정 — 대응표 기준)
3. Terraform: `<타입>.<이름>.<속성>` 식 참조, `depends_on` → 리소스. 문자열 ID는 2와 같이 대응표로. (확정)
4. 위로 못 찾은 물리 ID(필터로 빠진 리소스, 다른 스택 소유) → **유령 블록 "스냅샷 밖 AWS 리소스 (vpc-0abc…)"**. 물리 ID만 보이고 ARN은 끝 부분만.
- `logical-id-mapping.json`이 없으면 2를 건너뛰고 보기 머리에 "logical-id-mapping.json 없음 — 하드코딩된 ID는 연결하지 못함".

**관계 목록**

| # | 관계 | 근거 속성 (CFN) | 기본 표시 |
|---|---|---|---|
| A1 | 서브넷 ⊂ VPC | Subnet `VpcId` | 배치로 표현(판 안에 놓임) |

| A5 | LB → 서브넷, Listener → LB, Target Group → VPC, Listener → Target Group | `Subnets`/`SubnetMappings`, `LoadBalancerArn`, `VpcId`, `DefaultActions[].TargetGroupArn` | 켬 |

- **자동 생성 추정**: 태그 `eks:cluster-name`, `eks:nodegroup-name`, `kubernetes.io/cluster/<이름>`, `elbv2.k8s.aws/cluster`, `kubernetes.io/created-for/pvc/name`, `aws:autoscaling:groupName`, `aws:cloudformation:stack-name`이 있는 리소스에 "자동 생성 추정" 표식(정보, README 7.1-2 판단 기준과 같음). 상태가 아니다.
- **스캔 발견**: 현재 스캔 발견의 줄이 어떤 리소스 블록(템플릿에서 그 리소스가 차지하는 줄 범위) 안이면 그 블록에 등급 표식. 어떤 리소스에도 속하지 않는 발견은 "리소스 밖 발견 N건".

### 3.3 스냅샷 시간축 (3단계 — **이번 범위 아님(보류)**)

> 사용자 결정(2026-09-20)으로 이번에는 만들지 않는다. 목록 화면(AWS 탭·Kubernetes 탭)은 이번 단계에서 바뀌지 않는다.

**위치**: 스냅샷 목록(AWS 탭·Kubernetes 탭 각각)의 보기 전환 **[표 | 시간축]**. 기본은 표. 기존 목록 주소(`/snapshots`, `/snapshots/k8s`와 필터 쿼리)는 지금처럼 표를 연다(ASM U1·K8S 5.5 호환). 시간축 여부는 새 쿼리 값으로 둔다(이름은 프론트).

**묶음**(한 번에 한 묶음): Kubernetes는 `cluster.id`별(기본: 대시보드가 연결된 클러스터, 없으면 가장 최근 스냅샷의 클러스터. "클러스터를 확인할 수 없음" 묶음 따로), AWS는 `region`별(기본: 가장 최근 스냅샷의 리전). 목록 "직전 대비"와 같은 묶음 규칙이다. 목록 필터(상태·검색)는 시간축에도 적용한다. 휴지통 스냅샷은 넣지 않는다.

**표시**
- 스냅샷마다 판 1장, 시간 순서(오래된 것 → 최신). 간격은 순서 기준(같은 간격), 실제 시각은 판 라벨. (실제 시간 비례 간격은 선택 사항, 디자인)
- 판 위: 종류별 리소스 수(Kubernetes: 종류, AWS: 3.2의 층 분류). 높이·블록 수로 수를 표현하되 숫자 라벨 필수.
- 판 표식: 파일 상태(기존 배지 규칙, crit 문구 "커밋 금지"), 라벨, (Kubernetes) 드리프트 배지가 결과를 가진 스냅샷만(목록과 같은 값).
- **이웃 스냅샷 사이 연결부**: "+생김 −없어짐" 수. 식별값은 Kubernetes `resourceKey`(K8S-API 10.3), AWS는 `타입 + 물리 ID`(대응표), 물리 ID를 모르면 `타입 + 논리 ID`(Former2 논리 ID는 내보낼 때마다 바뀔 수 있어 정확도가 낮음 — 이 경우 연결부에 "논리 ID 기준" 표시).
- 연결부를 누르면 생긴·없어진 리소스 이름 목록. 이름을 누르면 **그 리소스가 있는 스냅샷**(생김 → 뒤 스냅샷, 없어짐 → 앞 스냅샷)의 상세 파일(k8s)·템플릿 줄(AWS)로 이동.
- 비교할 수 없는 스냅샷(내보내기 진행 중, metadata 손상으로 묶음을 알 수 없음, 템플릿 없음·해석 실패)은 판은 그리되 연결부에 "비교 못 함"과 이유.
- **내용 비교는 하지 않는다**: 같은 식별값이 양쪽에 있으면 "그대로"로만 센다. 필드 차이·템플릿 diff는 범위 밖(6절). 보기 안에 "생김·없어짐만 표시합니다. 내용 변경은 비교하지 않습니다" 상시 안내.
- 범위: 기본 최신 30개, 기간을 넓힐 수 있다(최대 묶음 전체).

### 3.4 AWS + K8s 통합 장면 (4단계 — **이번 범위 아님(보류)**)

> 사용자 결정(2026-09-20)으로 이번에는 만들지 않는다. 짝 규칙은 Q1 결정(자동 제안 + 수동 선택 허용)대로 아래에 적어 두었다.
>
> **아래 짝 규칙 1과 관계 X4·X5의 `AWS::EKS::Cluster`·`eks.amazonaws.com/nodegroup` 전제는 EKS 시절 내용이다(2026-09-24 kOps 전환 이후 유효하지 않다).** 보류 상태라 이번에 고치지 않는다. 다시 설계할 때 클러스터 짝은 태그 `kubernetes.io/cluster/<이름>`, 노드그룹 짝은 ASG 태그·라벨 `kops.k8s.io/instancegroup`을 근거로 삼는 방향을 검토한다 — 문서 머리의 메모 참고.

**들어가는 곳**: k8s 3D 보기의 [AWS와 함께 보기], AWS 3D 보기의 [Kubernetes와 함께 보기]. 고른 짝은 주소 쿼리로만 기억한다(파일·DB에 저장하지 않음).

**짝 규칙** (Q1 결정 A)
1. **클러스터 일치**: k8s 스냅샷 `metadata.cluster.name`과 같은 이름의 EKS 클러스터(`AWS::EKS::Cluster`의 `Name`, 또는 Terraform `aws_eks_cluster`의 `name`)가 템플릿에 있는 AWS 스냅샷이 후보. 비교는 대소문자 구분, 앞뒤 공백 무시.
2. **시점**: 후보 중 두 스냅샷 시각 차이가 가장 작은 것을 기본 짝으로 제안(앞·뒤 모두 허용). 차이를 항상 보인다("30분 전 AWS 스냅샷").
3. **시점 차이 경고**: 24시간(설정값) 초과면 경고 "시점 차이 N일 — 두 스냅샷 사이에 구성이 바뀌었을 수 있습니다". 짝은 허용한다.
4. **파일 상태**: 짝 스냅샷의 파일 상태(커밋 금지 등)를 함께 보인다. 상태 때문에 짝을 막지 않는다(보기 전용).
5. 사용자는 후보 목록에서 다른 AWS 스냅샷을 고를 수 있다(후보는 1의 조건을 만족하는 것만).
6. 후보가 없거나 `cluster.name`이 없으면(Q1 결정 A): 같은 리전의 AWS 스냅샷을 **사용자가 수동으로 고를 수 있고**, 장면에 "짝 확인 안 됨 — 같은 클러스터인지 확인하지 못했습니다"를 상시 표시한다.
7. 한 템플릿에 EKS 클러스터가 여러 개면 이름이 맞는 클러스터 위에만 k8s 층을 올린다.

**배치**: 아래는 3.2의 AWS 장면, 짝이 맞은 EKS 클러스터 블록 위에 3.1의 네임스페이스 판들이 떠 있다. 두 층 사이 간격은 디자인.

**층 사이 관계 (추출 규칙)**

| # | 관계 | 근거 | 확실성 | 못 뽑을 때 |

- 드리프트·스캔 겹쳐 보기는 각 층의 규칙(3.1, 3.2)을 그대로 쓴다.

### 3.7 대체 보기 (필수)

- **관계 표**: 3D의 모든 블록이 행이다. 열(최소): 종류, 이름(또는 논리 ID), 위치(네임스페이스 / VPC·AZ·서브넷), 표식(드리프트 구분, 스캔 발견 수, 유령·자동 생성·Helm), 관계 수(들어오는/나가는). 행을 펼치면 관계 목록(상대·방향·근거·확실성). 행 이동 버튼은 3D 선택 패널과 같다.
- 부모-자식(네임스페이스·VPC·AZ·서브넷)은 트리(펼치기)로 보인다.
- 필터·검색은 3D와 같고, 개수(블록 수·관계 수·유령 수·짝 못 찾음 수)도 같다.
- 대체 보기는 **관계 표 하나**다. 2D 평면도(그림)는 만들지 않는다(Q2 결정 A, 6절 범위 밖).
- (3단계) 시간축의 대체 보기: 행 = 스냅샷(시간순), 열 = 파일 상태, 라벨, 종류별 수, 직전 대비 +생김/−없어짐(누르면 목록).
- (4단계) 통합 장면의 대체 보기: 두 층의 관계 표 + "층 사이 관계" 표(X1~X5).
- **자동 전환**
  - WebGL을 쓸 수 없음(컨텍스트 생성 실패) → 대체 보기로 열고 "이 브라우저에서 3D를 쓸 수 없어 표로 보여 줍니다".
  - 3D 청크 로딩 실패 → 대체 보기 + [다시 시도].
  - WebGL 컨텍스트 손실 → 대체 보기로 바꾸고 [3D 다시 켜기].
  - 저사양 감지: 3D 조작 중 5초 동안 중앙값 20fps 미만 → 라벨을 줄이는 등 자동 간소화 + "표로 보기를 권합니다" 알림(강제 전환은 하지 않음).
- `prefers-reduced-motion: reduce` → 자동 움직임 없음(자동 회전, 카메라 비행 애니메이션, 깜박임·맥동 강조 없음). 카메라 이동은 즉시 전환. 3D 자체는 쓸 수 있다.
- 스크린리더: 3D 캔버스는 요약 설명(예 "Kubernetes 구성도, 네임스페이스 5, 리소스 128, 관계 164, 드리프트 차이 3건")과 "표로 보기" 건너뛰기 링크를 가진다. 선택 결과는 `aria-live`로 읽힌다. 모든 기능은 키보드로 쓸 수 있다.
- 사용자가 고른 보기(3D/표)는 **브라우저 저장소**에 기억한다(서버·파일에 쓰지 않음).

### 3.8 큰 규모
- 스냅샷 하나에 블록이 3,000개를 넘으면 3D는 **묶어 보기**(네임스페이스·종류별 묶음 블록 + 개수, 펼치면 그 묶음만 블록으로)로 연다. "리소스가 많아 종류별로 묶어 보입니다" 안내. 대체 보기는 전체를 보인다.
- 관계선이 많아 겹칠 때 기본 끔 관계(3.1·3.2 표)를 켜면 "선 N개 — 느려질 수 있음" 안내.

| 스캔 표식·파일 상태 | 파일 변경과 같음 | |
| 시간축 | 목록 변경(스냅샷 추가·삭제)이 30초 이내 | |
| 통합 장면 짝 후보 | 목록 변경 시 다시 판단. 보고 있는 짝이 휴지통으로 가면 "짝 스냅샷이 없어졌습니다" | |

- 실시간(초 단위) 갱신은 필요 없다. 스트림에 3D 데이터(블록·관계·이름)를 싣지 않는다. 기존 변경 알림(`aws-snapshots`, `k8s-snapshots` 토픽)을 받아 다시 조회하는 방식이면 된다(방법은 백엔드·프론트).
- 3D 보기를 떠나거나 브라우저 탭이 숨겨지면 그리기를 멈춘다. 가만히 있을 때는 계속 다시 그리지 않는다(조작·갱신이 있을 때만).

|---|---|

| 상한 초과 | 3,000 블록 초과는 묶어 보기(3.8)로 위 목표를 지킨다 |

### 4.3 번들·지연 로딩
- three.js와 3D 코드는 **3D 보기(또는 시간축 3D)를 처음 열 때만** 불러온다(동적 로딩). 그 밖의 모든 페이지 첫 로딩 JS는 이 기능 전과 비교해 **gzip 5 KB 이하**만 늘어난다.
- 3D 청크 전체(three.js + 카메라 조작 + 이 기능 코드, 글꼴·텍스처 포함) **gzip 300 KB 이하**. 넘으면 프론트 보고서에 이유와 크기를 적고 PM이 판단한다.
- 로딩 중에는 자리 표시 + 진행 표시. 로딩 실패는 대체 보기 + 다시 시도(3.7).
- 3D 탭에 마우스를 올렸을 때 미리 받기는 허용(첫 로딩 5 KB 규칙은 지킨다).
- 대체 보기(표)는 three.js 없이 동작한다.

## 5. 단계(phase)와 수용 기준

### 5.0 단계 구분과 순서 (사용자 결정 2026-09-20: **1단계만 진행**)

| 단계 | 이번 범위 | 내용 | 이유 |
|---|---|---|---|
| **1단계** | **진행** | 공통 기반(3D 틀·상호작용·대체 보기·지연 로딩·접근성·성능 측정) + **K8s 구성도 + 드리프트** (3.1) | 데이터가 이미 구조화돼 있다(리소스 1개 = 파일 1개, `files[].documents`, `resourceKey`, 드리프트 결과 API, 이동할 화면 주소 `?view=files&file=`·`?view=drift&res=`가 이미 있음). 새로 해석할 것이 관계 추출뿐이라 위험이 가장 작고, "드리프트가 어디에 있나"라는 가치가 가장 크다. 공통 기반을 가장 쉬운 데이터로 먼저 검증한다 |
| **2단계** | 보류 | **AWS 인프라 구성도** (3.2) | 템플릿 해석(CFN/TF)·참조 해석(Former2의 하드코딩 ID ↔ 대응표)이 새로 필요하고, AWS 상세에는 아직 탭·줄 이동 주소가 없어 화면 구조 변경이 따른다. 1단계 기반 위에서 한다 |
| **3단계** | 보류 | **스냅샷 시간축** (3.3) | 스냅샷별 리소스 식별값이 필요하다(k8s는 1단계, AWS는 2단계의 해석 결과를 재사용). 목록 화면 변경이고 여러 스냅샷을 한꺼번에 읽어 성능 부담이 크므로 두 해석이 안정된 뒤에 한다 |
| **4단계** | 보류 | **AWS+K8s 통합 장면** (3.4) | 1·2단계 모두에 의존하고, 짝 규칙(Q1)과 층 사이 연결(태그·스케줄 제약, Q4)이 가장 불확실하다. 실제 데이터로 1·2단계를 써 본 뒤 규칙을 다듬는 것이 안전하다 |

- **이번에 만드는 것은 1단계뿐이다**(사용자 결정 2026-09-20). 2~4단계는 보류이고 나중에 진행한다. 아래 5.3~5.5의 수용 기준은 그때 쓰도록 남겨 둔다.
- 각 단계는 **따로 배포할 수 있다**. 단계가 끝날 때마다 `CLAUDE.md` 기본 흐름(디자인 → 계약 → 구현 → 통합 → 검증)을 한 번씩 돈다.
- 2~4단계를 시작할 때는 순서를 다시 정한다. 3단계 중 **Kubernetes 시간축만** 2단계보다 먼저 할 수 있다(AWS 해석이 필요 없음).
- 공통 수용 기준(5.1)은 1단계에서 충족하고, 나중에 단계가 늘어나면 새 보기마다 다시 확인한다.

번호는 `AC-3D01`부터. K-n·A-n은 3.10의 mock 예시. **이번 범위는 AC-3D01~33**(5.1 + 5.2)이다.

### 5.1 공통 (이번 범위. 1단계에서 충족하고, 나중 단계의 새 보기마다 다시 확인)

### 결정됨 (2026-09-20, 사용자)

Q1~Q4 모두 **권장안으로 확정**했다. 본문(3.4 짝 규칙, 3.6 클릭 동작, 3.7 대체 보기, X4)은 이 결정대로 쓰여 있다. 아래는 검토한 선택지와 결정 기록이다.

- **Q1 → A (자동 제안 + 수동 선택 허용)**, **Q2 → A (관계 표만)**, **Q3 → A (한 번 클릭 = 선택 패널, 두 번 클릭·`Enter` = 이동)**, **Q4 → A (스케줄 제약이 있을 때만 점선)**.

- **Q1. 통합 장면 짝 규칙 — 클러스터 이름을 모르거나 후보가 없을 때** (4단계, 보류)
  - A. **자동 제안 + 수동 선택 허용**: 이름이 맞는 후보 중 시점이 가장 가까운 것을 기본으로 제안(24시간 초과 경고). `cluster.name`이 없거나 이름이 맞는 후보가 없으면 같은 리전·아무 AWS 스냅샷을 수동으로 고를 수 있고, 장면에 "짝 확인 안 됨 — 같은 클러스터인지 확인하지 못했습니다"를 상시 표시.
  - B. 이름이 맞는 후보만 허용(없으면 통합 장면을 열 수 없음).
  - C. 항상 수동 선택(자동 제안 없음).
  - **권장(확정): A.** k8s `cluster.name`은 kubeconfig에서 오므로 비어 있을 수 있고(K8S-API 3.2), 그때도 사용자가 알고 있는 짝을 볼 수 있어야 한다. 잘못된 짝의 오해는 상시 표시로 막는다.
- **Q2. 대체 보기의 형태** (1단계부터 적용)
  - A. **관계 표(트리 + 관계 펼침)만**. 모든 환경에서 같은 정보를 준다.
  - B. 관계 표 + 2D 평면도(위에서 본 그림, WebGL 없이 그림).
  - C. 2D 평면도만.
  - **권장(확정): A.** 표가 스크린리더·저사양·WebGL 없음 모두를 가장 확실히 해결하고 비용이 작다. 2D 평면도는 만들지 않는다(필요해지면 별도 결정).
- **Q3. 블록 클릭 동작** (1단계부터 적용. 사용자 표현은 "블록 클릭 → 해당 리소스로 이동")
  - A. **한 번 클릭 = 선택 + 패널(이동 버튼), 두 번 클릭 또는 `Enter` = 바로 이동.**
  - B. 한 번 클릭 = 바로 이동(선택 패널 없음, 가리키기 툴팁만).
  - **권장(확정): A.** 한 번 클릭으로 화면을 떠나면 구성을 둘러보다가 자꾸 탭이 바뀐다. 관계 확인(선택·이웃 강조)과 이동을 나누고, 이동은 두 번 클릭으로 한 동작에 할 수 있게 한다.
- **Q4. 통합 장면에서 k8s 워크로드와 노드그룹을 어떻게 잇나** (4단계, 보류. k8s 스냅샷에는 노드·파드가 없다)
  - A. **스케줄 제약이 있을 때만 점선**(`nodeSelector`/필수 `nodeAffinity`의 노드그룹 레이블, X4). 없으면 워크로드는 클러스터 위에 떠 있고 "파드 배치는 스냅샷에 없습니다 — 현재 배치는 클러스터 상태 화면" 안내.
  - B. 대시보드가 지금 보고 있는 파드 배치(`cluster-status` 실시간 데이터)를 겹침. 스냅샷 시점과 다른 "지금" 데이터가 섞여 오해를 부르고, 과거 스냅샷에는 맞지 않는다.
  - C. 워크로드↔노드그룹 선을 그리지 않음.
  - **권장(확정): A.** 스냅샷에 적힌 사실(스케줄 제약)만 보여 주고, 기록에 없는 배치는 지어내지 않는다. 실시간 데이터를 스냅샷 장면에 섞지 않는다(6절 범위 밖).

### 권장안으로 정하고 넘어간 사소한 결정 (다르면 알려 주세요)
- 단계 순서: K8s 구성도 → AWS 구성도 → 시간축 → 통합 장면(5.0). Kubernetes 시간축만 앞당길 수 있음.
- AWS는 CloudFormation 우선, Terraform은 대체 원본.
- 시간축 묶음: Kubernetes = 클러스터 ID, AWS = 리전(목록 "직전 대비"와 같음). 휴지통 제외, 기본 최신 30개, 간격은 순서 기준.
- 시간축 비교는 식별값 수준(생김·없어짐)만. AWS 식별값은 타입 + 물리 ID, 모르면 논리 ID(표시).
- 통합 장면 시점 차이 경고 24시간(설정값), 짝은 주소 쿼리로만 기억.
- 3,000 블록 초과 시 묶어 보기, 기본 관계선은 K1~K7·A1~A5·A7·A10만 켬.
- 3D는 드리프트를 새로 계산하지 않고 기존 결과만 겹침. 계산 버튼은 기존 요청 재사용.
- 보기 선택(3D/표)은 브라우저 저장소에 기억(서버·파일 쓰기 아님).
- 드리프트 구분 색은 기존 중립색 규칙 유지(빨강·초록 금지), 유령 블록은 상태색이 아닌 점선.
- `prefers-reduced-motion`은 3D를 끄지 않고 자동 움직임만 끔.
- 성능 기준 장비는 내장 GPU 노트북(A3).
- 서브넷 공개/비공개는 속성·태그로 "추정"만(라우트 테이블 해석 안 함).

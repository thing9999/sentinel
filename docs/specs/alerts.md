# 기능 명세: alerts (알림 — 화면 알림 센터 + 디스코드 웹훅)

- 작성: planner, 2026-09-24
- 상태: **착수 가능** (2026-09-25 갱신). Q1~Q10·Q12가 **모두 결정됐다**(8.1). 남은 것은 **Q11(클러스터 안 배포의 `discord.com:443` egress, 월요일 확인)** 하나뿐이고 P1·P2 착수를 막지 않는다.
- 관련 문서: `CLAUDE.md` "확정된 결정", `docs/specs/cluster-status.md`(상태 판단 기준), `docs/specs/kops-support.md` 3.2(컨트롤 플레인 판단), `docs/specs/aws-cost.md` 3.5~3.7(예산·급증), `docs/api/common.md`(`StatusInfo`·`SourceStatus`·`unknown`·SSE·mock 시나리오), `docs/api/cluster-status.md` 2.1(`areas`·`attention`), `docs/api/aws-cost.md` 6절(설정 API 선례), `docs/design/shell.md`(상단바·사이드바)
- **이 명세는 새 상태 판단 기준을 만들지 않는다.** 서버가 이미 계산하는 `StatusInfo.status`(정상/주의/장애/알 수 없음)를 **그대로 받아서**, "언제 누구에게 알릴지"만 정한다. 임계값(재시작 3회, 연결 90%, 쿼럼 상실 …)은 전부 기존 명세에 있고 이 문서에서 다시 정의하지 않는다.
- **조회 전용 원칙은 그대로다.** 클러스터·AWS·모니터링 대상 Postgres에 쓰기를 하지 않는다. 자세한 층 구분은 0.2절.

## 0. 전제

### 0.1 가정 (합리적 기본값. 사용자가 다르게 말하면 수정한다)

- **가정 N1**: 알림을 받는 사람은 **대시보드를 운영하는 본인(1인~소규모 팀)**이고, 디스코드 채널도 본인 것이다. 당번(on-call) 로테이션·에스컬레이션 정책은 없다.
- **가정 N2**: 대시보드에 **로그인이 없다**(`cluster-status` 가정 A5). 그래서 "확인(읽음)" 상태는 사용자별이 아니라 **서버에 하나**다. 모든 탭·브라우저가 같은 값을 본다.
- **가정 N3**: 지금은 **실제 클러스터가 없고 웹훅 주소도 없다.** 월요일쯤 IAM·접속 정보를 받는다. 그때까지 모든 확인은 `DATA_SOURCE=mock`에서 한다. **mock에서 디스코드로 실제 발송은 하지 않는다**(3.6).
- **가정 N4**: 알림 대상 채널은 **디스코드 하나**다. 이메일·Slack·SMS·PagerDuty는 범위 밖(6절).
- **가정 N5**: 대시보드 자체 DB(Prisma)가 없어도 기능은 동작한다(메모리 최근 200건). 어드바이저의 인메모리 폴백과 같은 결이다.
- **가정 N6**: 알림 본문에는 **리소스 이름을 원문 그대로** 쓴다(노드·네임스페이스·워크로드·파드). 어드바이저 스냅샷의 가명 규칙은 **외부 LLM에 보내는 스냅샷**에 대한 것이고, 알림은 운영자가 지정한 자기 채널로 가는 **조치용 메시지**다. 가명을 쓰면 "어느 파드인지"를 알 수 없어 알림의 존재 이유가 사라진다. → 다만 kOps에서 노드 이름이 EC2 인스턴스 ID(`i-0…`)라는 점(`kops-support` F10) 때문에 **AWS 계정 내부 식별자가 채널에 남는다.** 이 사실을 설정 화면에 한 줄 적는다. → **Q3 결정됨(사용자, 2026-09-25): 원문 그대로 쓴다.** 사내 채널이고 알림만 보고 바로 대응할 수 있는 것이 더 중요하다는 판단이다(8.1).

### 0.2 "쓰기"의 층 구분 (원칙. 반드시 지킨다)

대시보드는 조회 전용이다. 이번 기능이 추가하는 두 가지 동작은 **관측 대상에 대한 쓰기가 아니다.** 셋을 섞어 말하지 않는다.

| 층 | 대상 | 이번 기능 | 원칙 |
|---|---|---|---|
| **① 관측 대상 쓰기** | 쿠버네티스 클러스터, AWS, 모니터링 대상 Postgres | **없다. 하나도 늘지 않는다** | 조회 전용. RBAC·IAM 그대로 |
| **② 대시보드 자체 상태 쓰기** | 대시보드 자체 DB(Prisma) — 알림 이력, 발송 기록, `settings` | **있다.** 기존 `PATCH /api/cost/settings`와 **같은 성격** | 이미 허용된 쓰기(`docs/api/common.md` 0 요약 "쓰기" 행) |
| **③ 밖으로 나가는 통지** | 사용자가 지정한 디스코드 웹훅 | **있다(선택).** 단방향 통지이고 **관측 대상을 바꾸지 않는다** | 새로 생기는 층. 기본 꺼짐(주소 미설정), mock에서 차단, 테스트 발송은 명시 확인 필요 |

- ③은 "클러스터·AWS에 쓰기"가 **아니다.** 파드를 재시작하거나 스케일을 바꾸는 것과 완전히 다른 동작이다.
- 그래도 ③은 **되돌릴 수 없는 외부 효과**다(보낸 메시지는 회수할 수 없다). 그래서 이 명세는 ③에만 별도 안전장치(3.5 테스트 발송 확인, 3.6 mock 차단, 3.3 도메인 제한, 3.2 억제·플래핑)를 둔다.
- `docs/api/common.md` 0 요약의 "쓰기" 행에 이 구분을 한 줄 추가하도록 백엔드에 요청한다(7절).

### 0.3 RBAC·권한 (늘리지 않는다)

- 쿠버네티스 RBAC(`deploy/rbac.yaml`): **바꾸지 않는다.** 알림은 이미 보고 있는 상태(`StatusInfo`)에서 파생된다. 새 리소스·동사가 필요 없다.
- AWS IAM: **바꾸지 않는다.** 비용 알림은 이미 계산된 예산·급증 상태를 쓴다.
- 새로 생기는 바깥 접속은 **`https://discord.com` 아웃바운드 HTTPS 하나**뿐이다(선택, 주소가 설정됐을 때만).

## 1. 배경 / 목표

### 1.1 누가, 왜

- **누가**: 이 kOps 클러스터와 그 안의 Postgres를 운영하는 본인. 하루 종일 대시보드를 보고 있지 않다.
- **왜**: 지금 대시보드는 **상태를 보여주기만 하고, 나빠졌을 때 알려주지 않는다.** 화면을 열어 둔 사람만 장애를 본다. 자리를 비우거나 다른 일을 하는 동안 파드가 죽고, 마스터가 내려가고, 비용이 튀어도 **그 사실이 사람에게 도달하지 않는다.** 나중에 화면을 열었을 때도 "지금 나쁘다"만 보이고 "언제부터 나빠졌나, 그 사이에 무슨 일이 있었나"를 알 수 없다(쿠버네티스 이벤트는 1시간만 남는다 — `cluster-status` 3.5).
- **왜 지금**: kOps 전환으로 **컨트롤 플레인이 내 책임**이 됐다(`kops-support` 1.2). 마스터 1대가 죽은 것을 모르고 지나가면 다음 1대가 죽는 순간 클러스터가 멈춘다. "모르고 지나가는" 구간을 없애는 것이 이 기능의 핵심이다.

### 1.2 목표

1. 상태가 **나빠지는 순간·좋아지는 순간**을 붙잡아 이력으로 남긴다. 화면을 안 보고 있어도 나중에 "14:02에 컨트롤 플레인 주의 → 14:19 해제"를 읽을 수 있다.
2. 자리를 비운 사이의 장애가 **디스코드로 도달**한다(주소가 설정되면).
3. **도배하지 않는다.** 같은 문제로 반복 발송하지 않고, 정상↔장애를 오가는 경우를 눌러 준다.
4. **끊겨서 모르는 것**(`unknown`)과 **실제로 나쁜 것**(`critical`)을 구분해서 알린다. 연결이 끊긴 것을 장애로 오인하게 만들지 않는다.
5. **설정이 하나도 없어도** 기능이 조용히 죽지 않고 화면에서 완전히 동작한다. 웹훅은 "나중에 주소만 넣으면" 켜진다.
6. **mock에서 전부 눈으로 확인**할 수 있고, mock에서는 디스코드로 한 건도 나가지 않는다.
7. 새 상태 판단 기준·새 RBAC·새 AWS 권한을 **하나도 만들지 않는다.**

### 1.3 이 기능이 하지 않는 것 (1.2와 짝)

- 알림에서 조치하지 않는다(파드 재시작·스케일 조정 버튼 없음). 조회 전용 원칙.
- 임계값을 화면에서 편집하지 않는다. 기준은 `cluster-status`·`kops-support`·`aws-cost`에 이미 있다.
- "알림을 보고 원인을 찾는" 동선은 **기존 화면**이 담당한다. 알림은 그 화면으로 보내는 입구일 뿐이다.

## 2. 사용자 시나리오

### S1. 자리를 비운 사이 파드가 죽었다 (이 기능의 대표 시나리오)
1. 14:02, `prod/api` 파드가 `CrashLoopBackOff`에 들어간다. 서버가 파드 영역을 `critical`로 판단한다(`cluster-status` 3.4 — 기존 기준).
2. 14:02:12, 디스코드 채널에 메시지가 온다: `[장애] 파드 — CrashLoopBackOff · 최근 1시간 재시작 6회` / 영향: `Pod prod/api-7f9c8d6b5-x2kq9` / `prod.k8s.example.com` / 14:02:05.
3. 사용자가 대시보드를 연다. **사이드바 `알림` 메뉴에 빨간 배지 `1`**. 누르면 `/alerts` 화면이 열린다.
4. 알림을 누르면 **파드 목록 화면의 그 파드**로 이동한다(알림은 입구만 제공하고 상세는 기존 화면이 보여 준다).
5. 14:19 파드가 회복된다. 디스코드에 `[해제] 파드 — 정상으로 돌아왔습니다 · 지속 17분`이 온다.

### S2. 아직 디스코드 주소가 없다 (지금 상태)
1. 웹훅 주소를 설정하지 않았다.
2. 대시보드는 **평소대로 동작한다.** 알림 센터에 알림이 쌓이고 배지가 올라간다.
3. 설정 화면과 알림 센터 상단에 회색 안내 한 줄: `디스코드 미설정 — 알림이 화면에만 쌓입니다.` **오류도, 빨간 배너도 아니다.**
4. 다음 주에 주소를 받으면 설정 화면에 붙여 넣는 것만으로 디스코드 발송이 켜진다. **코드·재배포 없이.**

### S3. 웹훅 주소를 받아서 설정한다
1. 디스코드 채널 설정에서 웹훅 URL을 복사한다.
2. 대시보드 `설정 → 알림`에서 붙여 넣고 저장한다. 저장 후 입력칸은 **비고**, 옆에 `설정됨 · …****7f3a (119자)`만 보인다. 원문은 다시 볼 수 없다.
3. "테스트 발송"을 누른다. 확인 대화상자: **"디스코드 채널에 실제 메시지가 즉시 전송됩니다. 되돌릴 수 없습니다."** + 보낼 메시지 전문 미리보기.
4. 확인을 누르면 채널에 `[테스트] Sentinel 알림 설정 확인 메시지입니다. 실제 장애가 아닙니다.`가 온다.
5. `보낼 심각도`를 `장애만`으로 두고 저장한다. 주의는 화면에만 쌓이고 디스코드로는 가지 않는다.

### S4. 대시보드를 재시작했다
1. `docker compose up --build`로 api를 다시 띄운다. 그 시점에 파드 장애 2건, 노드 주의 1건이 **이미 있었다.**
2. 알림이 3건 쏟아지지 **않는다.** 시작 후 120초 동안은 알림을 만들지 않고 현재 상태를 기준선으로 잡는다.
3. 120초 뒤 알림 센터에 **요약 1건**만 생긴다: `대시보드가 시작됐습니다 · 현재 장애 2, 주의 1, 확인 불가 0` + `정지 구간 09:12 ~ 09:31 (19분) — 이 동안의 변화는 알림으로 잡히지 않았습니다.` **디스코드로는 보내지 않는다**(재시작은 사용자가 한 일이다).
4. 이후 상태가 **바뀌는** 것부터 정상적으로 알린다.

### S5. 클러스터 연결이 끊겼다
1. ServiceAccount 토큰이 만료돼 쿠버네티스 조회가 401이 된다(`kube` 출처 `unavailable` + `KUBE_AUTH_FAILED`, `docs/api/common.md` 2.3).
2. 노드·컨트롤 플레인·워크로드·파드·이벤트 다섯 영역이 동시에 `unknown`이 된다.
3. 알림은 **5건이 아니라 1건**이다: `[확인 불가] 클러스터 — 인증 실패, 토큰이 만료됐을 수 있습니다 (5분 지속)`. 문구에 "장애"라는 낱말이 없다.
4. 토큰을 갈아 끼우면 `[해제] 클러스터 — 다시 확인됩니다`가 온다. 그 사이에 실제로 파드가 죽었더라도 **"그때 죽었다"고 소급해서 알리지 않는다**(관측하지 못한 구간이므로). 대신 회복 직후의 현재 상태에서 새로 판단한다.

### S6. 마스터 1대가 죽었다
1. 마스터 3대 중 1대가 NotReady. 컨트롤 플레인 영역이 `warning`이 된다(`kops-support` 3.2.1 — 기존 기준).
2. `[주의] 컨트롤 플레인 — 마스터 2/3 Ready · 1대 더 잃으면 쿼럼 상실` / 영향: `Node i-0c3d4e5f6a7b8c9d0`.
3. 2대째가 죽으면 `[장애] 컨트롤 플레인 — 쿼럼 상실 (Ready 1/3)`. **주의 → 장애 격상은 새 알림을 만든다**(같은 문제여도 등급이 올라간 것은 알려야 한다).
4. 대시보드는 아무 조치도 하지 않는다. 무슨 일이 일어났는지만 알려 준다.

### S7. 파드가 정상↔장애를 반복한다 (플래핑)
1. 메모리 한계에 걸린 파드가 5분 간격으로 죽고 살아난다. 파드 영역이 30분 동안 `ok ↔ critical`을 6번 오간다.
2. 4번째 전이에서 알림이 **플래핑으로 묶인다**: `[주의] 파드 — 불안정(최근 30분 6회 변화) · 반복 알림을 멈춥니다`. 디스코드에는 이 1건만 가고 **그 뒤로 조용해진다.**
3. 30분 동안 전이가 1회 이하가 되면 플래핑이 풀리고, 그때의 현재 상태를 1건으로 알린다(정상이면 해제, 아니면 현재 등급).

## 3. 알림 규칙

### 3.0 공통 규칙

- **알림은 판단하지 않는다.** 서버가 이미 계산한 `StatusInfo.status`와 `reasons[0]`을 그대로 쓴다. 알림 계층이 하는 일은 ① 전이 감지, ② 억제·플래핑·워밍업, ③ 채널 전달뿐이다.
- **심각도(severity)**는 상태값을 그대로 옮긴다. 새 등급을 만들지 않는다.

| `StatusInfo.status` | 알림 심각도 | 화면 문구 | 근거 |
|---|---|---|---|
| `critical` | `critical` | 장애 | `cluster-status` 3.0 |
| `warning` | `warning` | 주의 | 〃 |
| `unknown` | `unknown` | **확인 불가** | 〃. "장애"라는 낱말을 쓰지 않는다 |
| `ok` (나쁜 상태에서 복귀) | `resolved` | 해제 | 〃 |

- **심각도 순서**는 집계 우선순위와 같다: `critical > warning > unknown > ok`(`docs/api/common.md` 2.1). 단 "어느 심각도부터 보낼지"에서 `unknown`은 순서로 줄 세우지 않고 **별도 토글**로 둔다(3.4 근거 참조).
- 모든 알림에는 **판단 이유 한 줄**(`reasons[0].text`)이 그대로 들어간다. 알림 계층이 문장을 새로 쓰지 않는다. 서버가 만든 문자열은 이미 `redactSecrets` + 길이 제한을 거친다(`docs/api/common.md` 1.4).
- `stale`(데이터 오래됨)은 **상태값이 아니다**(`docs/api/common.md` 2.3). 따라서 stale 자체로는 알림을 만들지 않는다. 출처 끊김이 오래가면 3.2의 출처 규칙으로 다룬다.

### 3.1 무엇을 알릴지 — 알림 키 8개

**알림의 단위는 "알림 키"다.** 개별 파드 하나하나가 아니라 **영역 단위**로 묶는다.

| # | 알림 키 | 무엇을 보나 | 상태의 출처 | 근거 문서 |
|---|---|---|---|---|
| 1 | `area:controlPlane` | 마스터 대수·Ready·쿼럼·구성요소(static pod) | `areas.controlPlane.status` | `kops-support` 3.2.1~3.2.3 |
| 2 | `area:nodes` | **워커 노드**의 Ready·압박·cordon·사용률 | `areas.nodes.status` | `cluster-status` 3.2 |
| 3 | `area:workloads` | Deployment·StatefulSet·DaemonSet의 ready/desired·롤아웃 | `areas.workloads.status` | `cluster-status` 3.3 |
| 4 | `area:pods` | phase·대기 사유·재시작·OOM·메모리 | `areas.pods.status` | `cluster-status` 3.4 |
| 5 | `area:events` | 최근 15분 Warning·심각 reason | `areas.events.status` | `cluster-status` 3.5 |
| 6 | `area:db` | Postgres 쿠버네티스 쪽 + 내부 지표 + PVC | `areas.db.status` | `cluster-status` 3.7 |
| 7 | `area:cost` | 예산 상태 + 소모율 급증 + 일별 확정 급증 (**셋의 최악**) | `overview.cost.status` | `aws-cost` 3.5·3.6·3.7 |
| 8 | `source:kube` | 쿠버네티스 출처 자체의 끊김·인증 실패 | `SourceStatus(kube)` | `docs/api/common.md` 2.3 |

**이 8개로 정한 근거**

1. **도배가 구조적으로 불가능하다.** 파드 50개가 동시에 죽어도 알림은 `area:pods` 1건이다. 개별 리소스를 키로 삼으면(예: `pod:prod/api-…`) 노드 하나가 내려갈 때 그 위의 파드 수만큼 알림이 나간다 — 알림 기능이 그 자체로 장애가 된다.
2. **기존 화면 구조와 1:1로 맞는다.** 8개 키는 개요 화면의 영역 카드·사이드바 상태 점과 같은 단위다(`docs/api/cluster-status.md` 2.1 `areas`, `nav`). 알림을 누르면 그 영역 화면으로 보내면 된다.
3. **영향 객체는 알림 본문에 담는다.** `areas.*.problems`(최대 3개, 이미 서버가 만든다)를 그대로 쓰고 나머지는 `외 N개`로 적는다. "어느 파드인지"는 알림에서도 보인다.
4. **`area:metrics`를 키로 두지 않는다.** 이 영역의 상태는 사실상 "metrics-server가 있나 없나"이고, kOps에서는 없는 것이 정상이라 **상시 `unknown`**이 된다(`kops-support` 3.4). 상시 켜져 있는 알림은 알림이 아니다. CPU·메모리 사용률 임계(70/90%)는 이미 `area:nodes`의 노드 판단에 들어 있다(`cluster-status` 3.2).
5. **`overall`(클러스터 전체 상태)을 키로 두지 않는다.** 영역 알림의 합이라 반드시 중복된다.
6. **`source:kube`만 출처 키로 둔다.** kube가 끊기면 1~5번 다섯 영역이 **동시에** `unknown`이 되어 알림 5건이 나간다. 이를 1건으로 묶기 위한 키다(3.2 "출처 억제"). 나머지 출처는 별도 키가 필요 없다:
   - `monitoredDb`가 끊기면 `area:db` 하나만 `unknown`이 된다 → 사유 문구(`SOURCE_UNAVAILABLE`)로 충분.
   - `awsResources`·`pricing`·`costExplorer`가 끊기면 `area:cost` 하나만 영향을 받는다.
   - `metrics`·`agentBridge`·`snapshotStore`·`k8sSnapshotStore`는 화면에 이미 표시되고 운영에 즉시 지장이 없다.
   - `dashboardDb`가 끊기면 **알림 이력 자체를 저장할 수 없다**(순환). 화면 안내로만 다룬다(3.7).
7. **컨트롤 플레인을 별도 키로 둔다.** kOps 전환의 핵심 관측 대상이고(`kops-support` 1.2), 노드 키에 묻히면 마스터 장애가 워커 소음에 가려진다. 사이드바는 `nav.nodes`에 합산하지만(`kops-support` Q2 결정, 이 명세의 Q2와 다른 것이다), **알림은 분리**한다 — 사이드바는 "어느 화면으로 가면 되나"이고 알림은 "무슨 일이 일어났나"라 단위가 다르다.

**3단계(다음 범위)**: 개별 리소스 단위 알림 키(특정 파드·특정 노드만 지켜보기). 이번에는 만들지 않는다.

### 3.2 언제 알릴지 — 상태 전이 · 억제 · 플래핑 · 재시작

#### 3.2.1 기준은 "바뀌는 순간"

서버는 이미 15초마다 상태를 재평가하고 `statusChangedAt`을 유지한다(`docs/api/common.md` 2.2). 알림은 **`status` 값이 실제로 바뀐 순간에만** 만든다. 같은 값이 유지되는 동안에는 아무것도 하지 않는다.

지속 조건(노드 NotReady 60초, Pending 10분, 사용률 연속 3회 등)은 **이미 상태 판단 안에 들어 있다**(`cluster-status` 3.0). 알림 계층에서 또 기다리지 않는다. 그래서 알림은 상태가 바뀐 뒤 **30초 안에** 채널에 도달한다.

| 이전 → 현재 | 동작 | 근거 |
|---|---|---|
| `ok` → `warning` | **발생 알림** (주의) | |
| `ok` → `critical` | **발생 알림** (장애) | |
| `warning` → `critical` | **격상 알림** (장애). 새 알림을 만들고 이전 알림과 연결한다 | 같은 문제여도 등급이 올라간 것은 반드시 알려야 한다 (S6) |
| `critical` → `warning` | **새 알림을 만들지 않는다.** 기존 알림의 등급만 낮추고 이력에 "완화 14:11" 한 줄을 붙인다 | 아직 해결되지 않았다. 새 알림은 도배만 늘린다 |
| `warning`·`critical` → `ok` | **해제 알림**. 발생 알림과 연결하고 지속 시간을 적는다 | |
| 어떤 상태 → `unknown` | **확인 불가 알림** (3.2.4) | |
| `unknown` → `ok` | **해제 알림**. 문구는 "다시 확인됩니다" | |
| `unknown` → `warning`·`critical` | **발생 알림** | |

- **해제 알림은 짝이 있을 때만 보낸다.** 발생 알림을 만들지 않았거나(억제됨·워밍업 중) 그 채널로 보내지 않은 알림(심각도 하한에 걸림)의 해제는 **그 채널로 보내지 않는다.** 앞뒤가 없는 "복구됨"만 채널에 뜨는 것을 막는다. (AC-ALERT32)
- 해제 알림은 화면 알림 센터에는 **항상** 남긴다(이력의 완결성).

#### 3.2.2 중복 억제 (같은 문제로 도배 방지)

- **억제 창: 기본 15분** (설정 `alerts.dedupeWindowMin`).
- 같은 알림 키에서 억제 창 안에 일어난 사건은 **새 알림을 만들지 않고 기존 알림에 합친다.** 화면에 `반복 4회`로 표시한다(쿠버네티스 이벤트의 `count`와 같은 방식). 디스코드로는 **추가 메시지를 보내지 않는다.**
- **억제 창이 끝나도 재알림하지 않는다.** 상태가 그대로 나쁜 채로 유지되면 알림은 1건뿐이다.
  - 근거: 사용자 요구 "같은 상태가 유지되는 동안 반복 발송하면 안 된다". 주기적 재알림(`alerts.repeatEveryMin`)은 **기본 꺼짐**으로 자리만 둔다(Q7).
- **영향 객체가 바뀌면**: 상태 등급이 그대로라도 `problems` 목록에 **새 객체가 추가**되면 사건으로 친다. 억제 창 안이면 합치고, 창 밖이면 `추가 발생` 알림 1건을 만든다(같은 등급).
  - 근거: "파드 A가 죽어서 알림 → 10분 뒤 파드 B도 죽음"에서 영역 상태는 `critical`로 그대로라 전이가 없다. 이 규칙이 없으면 B는 영원히 알려지지 않는다. 억제 창 15분이 상한이므로 도배가 되지 않는다.
  - 설정 `alerts.notifyOnNewTarget`(기본 켬)으로 끌 수 있다.

#### 3.2.3 플래핑 (정상↔장애를 빠르게 오가는 경우)

- **판정: 플래핑 창(기본 30분) 안에 같은 키의 상태 전이가 4회 이상** (설정 `alerts.flapWindowMin`, `alerts.flapTransitions`).
- 플래핑에 들어가면:
  1. 그 키를 **불안정**으로 표시하고, 화면 알림 센터에서는 **묶음 1건**으로만 보여 준다(전이마다 항목을 만들지 않는다). 항목 안에 전이 타임라인을 접어 둔다.
  2. 디스코드에는 **진입 시 1건만** 보낸다: `[주의] 파드 — 불안정(최근 30분 6회 변화) · 반복 알림을 멈춥니다`.
  3. 그 뒤로 **그 키의 발송을 멈춘다.** (화면에는 계속 쌓인다.)
  4. **플래핑 해제**: 플래핑 창 동안 전이가 1회 이하가 되면 푼다. 해제 시 **현재 상태를 1건**으로 알린다(정상이면 해제 알림, 나쁘면 현재 등급의 발생 알림).
- 플래핑 알림의 심각도는 **묶인 전이들의 최악**을 따른다. 단 디스코드 발송 판단은 진입 알림 1건에 대해서만 한다.
- 근거: 플래핑 자체가 "지금 뭔가 불안정하다"는 정보이므로 조용히 숨기지 않고 **한 번은 알린다.** 그러나 그 뒤 6번 더 알리는 것은 사람을 지치게 만들고 결국 알림 전체를 무시하게 만든다.

#### 3.2.4 `unknown`은 장애와 다르다

`unknown`은 "연결이 끊기거나 권한이 없거나 출처가 없어서 **판단할 수 없는 것**"이다(`cluster-status` 3.0). 실제로 나쁜 것이 아니다.

- 심각도 `unknown`, 화면 문구 **"확인 불가"**. 알림 본문에 **"장애"라는 낱말을 쓰지 않는다.**
- **지속 조건 5분**: `unknown`이 되자마자 알리지 않고 **연속 5분** 유지될 때 알린다(설정 `alerts.unknownAfterMin`, 기본 5).
  - 근거: watch 재시작·일시적 조회 실패로 몇 초 `unknown`이 되는 것은 흔하다(`docs/api/common.md` 2.3 stale 규칙). 5분은 "일시적 끊김"과 "정말 끊겼다"를 가르는 값이고, `stale` 판정 기준(45초)의 여유 배수다. → **Q2 결정됨(PM): 5분 유지.** 시끄러우면 설정으로 조정한다(8.1).
- **출처 억제 (중요)**: `kube` 출처가 `not_configured` / `unavailable` / **3분 이상 `stale`**이면,
  1. `source:kube` 알림 **1건**을 만들고,
  2. 그 출처에서 파생되는 영역 키(`area:controlPlane`·`nodes`·`workloads`·`pods`·`events`)의 **알림 생성을 억제한다.**
  3. 억제된 키는 화면 알림 센터에서 `source:kube` 알림 안에 `영향 영역 5개`로 묶여 보인다.
  4. 출처가 회복되면 `source:kube` 해제 알림 1건을 내고, 그 시점의 현재 상태에서 다시 판단한다.
- **끊긴 구간을 소급해서 알리지 않는다.** 대시보드가 보지 못한 동안 일어난 일은 관측하지 않은 것이다. 회복 직후 상태가 나쁘면 그때 **새 발생 알림**이 나간다(시각은 "지금"). 알림 본문에 `확인 불가 구간 14:02 ~ 14:38 (36분)`을 함께 적어 사용자가 오해하지 않게 한다.
- **디스코드 발송**: `unknown` 알림은 심각도 하한(3.4)의 순서에 넣지 않고 **별도 토글 `sendUnknown`(기본 켬)**으로 다룬다.
  - 근거: 클러스터가 통째로 안 보이는 상태를 외부로 알리지 못하면 알림 기능의 존재 이유가 흔들린다(S5). 그렇다고 `unknown`을 `warning`보다 위·아래로 줄 세우면 "주의부터 보내기"를 켤 때 의미가 다른 것이 따라온다. 그래서 축을 분리한다. → **Q2 결정됨(PM): 기본 켬.** 시끄러우면 설정으로 끈다(8.1).

#### 3.2.5 대시보드 자신이 재시작했을 때 (폭주 방지)

- **워밍업: 시작 후 120초** (설정 `alerts.warmupSec`).
  1. 워밍업 동안 **어떤 알림도 만들지 않는다.** 그동안 각 키의 현재 상태를 "시작 기준선"으로 기록한다.
     - 근거: informer 최초 동기화(`syncing`) 중에는 목록이 비어 있거나 부분적이라(`docs/api/common.md` 5.4) "노드 0대 = 클러스터 장애" 같은 가짜 판단이 스쳐 지나간다. 120초는 informer 동기화 + 15초 재평가 2~3회 + metrics/DB 첫 조회를 덮는 값이다.
  2. 워밍업이 끝나면 **요약 알림 1건**만 만든다: `대시보드가 시작됐습니다 · 현재 장애 2, 주의 1, 확인 불가 0`.
  3. **이 요약은 디스코드로 보내지 않는다.** 재시작은 사용자가 한 일이고, 외부 채널에 같은 내용을 다시 쏟는 것은 노이즈다.
  4. 이후 전이부터 정상 알림.
- **직전 종료 상태와 비교하지 않는다.**
  - 검토한 대안: 종료 시 각 키의 상태를 DB에 남겼다가 재시작 후 비교해 "그 사이에 바뀐 것"을 알린다.
  - **채택하지 않는 이유**: ① 바뀐 **시각**을 알 수 없어 과거 사건을 지금 일어난 것처럼 알리게 된다. ② 며칠 꺼 뒀다 켜면 오래된 사건이 무더기로 쏟아진다. ③ "재시작했으니 전부 새 장애"와 결국 같은 문제로 되돌아간다.
- **대신 "정지 구간"을 정직하게 알린다.** 서버는 알림 상태를 **주기적으로(기본 60초) DB에 heartbeat**로 남긴다. 재시작 후 `마지막 heartbeat ~ 지금`이 워밍업보다 길면 요약 알림에 한 줄을 붙인다:
  `정지 구간 09:12 ~ 09:31 (19분) — 이 동안의 변화는 알림으로 잡히지 않았습니다.`
  - 대시보드 DB가 없으면 정지 구간을 계산할 수 없다. 그때는 `이전 실행 기록 없음`으로 적는다.

### 3.3 어디로 알릴지 — 채널

| 채널 | 필수 여부 | 동작 |
|---|---|---|
| **화면 알림 센터** | **항상 켜짐. 끌 수 없다** | 설정과 무관하게 모든 알림(해제·확인 불가·플래핑·테스트 포함)이 쌓인다 |
| **디스코드 웹훅** | 선택 | 주소가 없으면 발송을 **시도조차 하지 않는다**. 오류가 아니다 |

#### 3.3.1 화면 알림 센터

- **위치 (확정 — 사용자 결정 Q1, 2026-09-25)**
  1. **사이드바 `알림` 메뉴 + 안 읽은 개수 배지** — 모든 화면에서 보인다. 누르면 `/alerts`로 간다.
  2. **`/alerts` 전체 화면** — 이력 목록, 필터(심각도·영역·기간·해제 포함 여부), 상세.
  - **상단바 종(벨) 아이콘은 만들지 않는다.** "배지로 알린다"는 요구는 사이드바 메뉴 배지로 채우고, "언제 무슨 일이 있었나"는 `/alerts` 화면이 맡는다. 둘이면 충분하고 진입점을 셋으로 늘리지 않는다.
  - **상단바와 `docs/design/shell.md` 2.1의 폭 계산을 건드리지 않는다.** 이것이 벨 대신 사이드바를 고른 이유다 — 벨을 넣으면 상단바 오른쪽 최소 폭이 늘어나 긴 FQDN 클러스터 이름과 경쟁하고, 1024~1279px에서 무엇을 버릴지까지 다시 정해야 한다. 사이드바는 항목 추가만으로 끝난다.
  - `docs/design/shell.md` 2절의 "전역 검색, **알림 벨**, 사용자 메뉴는 두지 않는다"는 **그대로 유효하다.** 이 기능은 그 문장을 깨지 않는다(9절).
  - 최근 10건만 빠르게 보는 패널(Popover·Drawer)은 만들지 않는다. 필요하면 `/alerts`가 그 역할을 한다.
- **배지 규칙** (사이드바 `알림` 항목에 붙는다)
  - 숫자 = **미확인 알림 수**(해제 알림은 세지 않는다 — 좋은 소식으로 배지를 올리지 않는다). 99 초과는 `99+`(`components.md` 12.1 `NavItem.count` 규칙 재사용 — **새 컴포넌트가 아니라 기존 사이드바 숫자 배지다**).
  - 색 = 미확인 알림 중 **최악 심각도**(`critical` → 빨강, `warning` → 노랑, `unknown` → 회색). 기존 `status.*` 토큰만 쓰고 새 색을 만들지 않는다.
  - "확인(읽음)"은 **서버 상태 하나**다(가정 N2). `모두 확인` 버튼과 항목별 확인.
- **알림 항목에 보이는 것**: 심각도 배지, 영역, 대표 사유 한 줄, 영향 객체(최대 3 + `외 N개`), 발생 시각(상대+절대), 지속 시간, 반복 횟수, 플래핑 표시, **발송 상태**(보냄/미설정/제외/실패/mock), `MOCK` 배지(mock에서 생긴 알림).
- **링크**: 알림을 누르면 해당 화면으로 간다. `controlPlane` → `/cluster/nodes#control-plane`(전용 화면 없음, `docs/api/cluster-status.md` 2.3 규칙과 같음), `nodes` → `/cluster/nodes`, `pods` → `/cluster/pods`, `db` → `/cluster/db`, `cost` → `/cost`, `source:kube` → 개요.
- **사이드바 `알림` 메뉴에 상태 점을 두지 않는다.** 알림은 상태의 **파생**이라 점을 달면 같은 정보가 두 번 보인다. **배지 숫자만** 쓰고 `nav`에 새 상태 키를 만들지 않는다(9절, `kops-support` 3.1).
- **브라우저 탭 제목**: 미확인 알림이 있으면 탭 제목 앞에 개수를 붙인다 — `(3) Sentinel`. 0이면 붙이지 않는다. 화면을 다른 탭에 두고 있어도 숫자가 보인다(PM 결정 Q8, P1 범위). **브라우저 알림(Notification API)·소리는 범위 밖**이다(6절).

#### 3.3.2 디스코드 웹훅

- **미설정일 때**: 발송 상태 `skipped_not_configured`. 화면에 회색 정보 한 줄 `디스코드 미설정 — 알림이 화면에만 쌓입니다.` **배너·토스트·빨간색을 쓰지 않는다.**
- **URL 제한**: 호스트가 `discord.com` 또는 `discordapp.com`이고 경로가 `/api/webhooks/…`이며 **`https`**인 것만 허용한다. 그 밖은 저장 시 400.
  - 근거: ① 임의 URL을 허용하면 대시보드가 "운영자가 지정한 아무 주소로나 HTTP 요청을 만들어 주는 도구"가 된다. 클러스터 안에 배포된 경우(`deploy/app.example.yaml`) 내부 주소로 요청을 보낼 수 있어 SSRF 성격의 위험이 생긴다. ② 이번 범위는 디스코드 하나다(가정 N4). 다른 채널이 필요해지면 그때 채널 종류를 명시적으로 늘린다. → **Q9 결정됨(PM, 2026-09-25): 디스코드 도메인만 허용**(8.1).
- **발송 내용** (형식이 아니라 **담을 정보**만 정한다. 임베드/플레인 여부는 백엔드 몫)

| 항목 | 내용 | 비고 |
|---|---|---|
| 접두어 | `[장애]` / `[주의]` / `[확인 불가]` / `[해제]` / `[테스트]` | |
| **mock 표시** | `DATA_SOURCE=mock`에서 생긴 알림은 **맨 앞에 `[MOCK]`** | 필수. 실제 장애로 오인 금지 |
| 영역 | `컨트롤 플레인` / `노드` / `파드` / … | |
| 대표 사유 | 서버가 만든 `reasons[0].text` 그대로 | 새로 쓰지 않는다 |
| 영향 객체 | 최대 3개 `Kind namespace/name` + `외 N개` | `areas.*.problems` 재사용 |
| 클러스터 | `K8S_CLUSTER_NAME`(FQDN) | |
| 시각 | 발생 시각(UTC ISO). 해제 알림은 `지속 17분` 추가 | |
| 반복 | 억제 창에 합쳐진 횟수가 2 이상이면 `반복 N회` | |
| 링크 | **`ALERTS_PUBLIC_BASE_URL`이 설정됐을 때만** 대시보드 링크 | 미설정이면 링크 없음 |

  - 링크를 조건부로 두는 근거: 기본 실행은 로컬 `http://localhost:3000`이라(`cluster-status` 가정 A5) 채널에 붙여 봐야 다른 기기에서 열리지 않는다. 클러스터 안에 배포하면 port-forward가 없으므로(PM 지시 참고) 사람이 실제 접근 주소를 알고 있다 — 그 값을 환경 변수로 넣었을 때만 링크를 붙인다.
- **절대 넣지 않는 것** (`CLAUDE.md` 어드바이저 스냅샷 규칙과 같은 기준, `docs/api/common.md` 1.4):
  - 비밀값, **웹훅 URL 자체**, 환경 변수, `command`/`args` 원문, 어노테이션·레이블 원문, ConfigMap/Secret 내용, DB 쿼리 원문, 접속 문자열, 스택 트레이스.
  - **컨테이너 로그 줄 — 가림 처리한 것도 포함** (PM 결정 2026-09-25, `docs/specs/logs.md` 6절 요청). 로그 한 줄, 로그에서 뽑은 문장·오류 메시지, "ERROR N줄" 같은 **로그 요약·통계**도 넣지 않는다. **화면 알림 센터에도 넣지 않는다** — 채널로 나가는 것만의 문제가 아니라, 알림 본문은 한 벌이어야 하고 화면·디스코드에서 같은 내용을 쓴다.
    - 근거: 디스코드는 **되돌릴 수 없는 외부 경로**다(0.2절 ③). 로그 가림은 흔한 형태만 잡고 완벽하지 않으므로(`logs` 3.3.3), 가린 줄이라도 채널에 남으면 회수할 수 없다. 로그는 **대시보드 안에서 끝나야 한다**(`logs` P5·P6).
    - 대신 **링크만 건다**: 알림 항목에서 해당 파드의 로그 화면(`logs` 3.8.1 진입점 8번)으로 보낸다. "무슨 일이 일어났나"는 알림이, "왜 그랬나"는 로그 화면이 답한다.
    - 이 링크는 **따라가기를 켜지 않는다**(`follow=1`을 붙이지 않는다, 2026-09-25 `logs` 통합 1차 PM 결정 D3 — `logs` 3.8.3·AC-LOG50). 알림 링크는 **그 시각(`at`)을 보러 가는 링크**라 따라가기를 켜면 맨 아래로 끌려가 그 지점을 잃는다. (컨트롤 플레인 매트릭스에서 가는 로그 링크는 켠다 — 성격이 다르다.)
    - **로그 내용으로 알림을 만들지도 않는다** — 로그 기반 알림 규칙은 범위 밖이다(PM 결정, 6절). 판단 기준이 `alerts`와 `logs` 두 곳에 생기면 안 된다.
  - 알림 본문에 들어가는 문자열은 **서버가 만든 `reasons[].text`와 `ResourceRef`뿐**이고, 둘 다 이미 가림 처리를 거친다.
  - 리소스 **이름**은 원문 그대로 쓴다(가정 N6, 사용자 결정 Q3).
- **발송 실패·제한**
  - 4xx(429 제외)/5xx/타임아웃: **지수 백오프 3회**(5초 → 30초 → 120초) 후 포기. 상태 `failed` + 가림 처리된 사유 한 줄을 이력에 남긴다. **알림 자체는 화면에서 사라지지 않는다.**
  - 429: `Retry-After`를 지키고 큐에 남긴다. 유실하지 않는다.
  - 발송 속도 상한: 기본 **2초에 1건**(설정 `alerts.discord.minIntervalSec`). 억제·플래핑이 있어 실제로는 거의 걸리지 않지만 안전장치로 둔다.
  - 연속 실패가 10건을 넘으면 **발송을 1시간 멈추고** 화면에 `디스코드 발송이 계속 실패합니다 — 1시간 뒤 다시 시도합니다`를 표시한다(화면 알림은 계속 쌓인다).
- **재시작 시 미발송 큐**: 자동 재발송하지 **않는다.** 상태 `skipped_restart`로 남긴다.
  - 근거: 재시작 직후에 몇 분 전 알림이 뒤늦게 채널에 뜨면 사람이 시각을 오해한다. 화면 이력에는 그대로 남으므로 정보가 사라지지 않는다.

### 3.4 설정 화면

#### 3.4.1 자리

- 경로 **`/settings`**, 사이드바 맨 아래(그룹 밖) `설정` 항목 1개. 상태 점 없음.
- **탭 구조로 만든다**: `알림`(이번 범위) / `비용`(**이번에 만들지 않는다. 자리만**).
  - 근거: 예산 편집은 API(`PATCH /api/cost/settings`)만 있고 화면이 없다(`docs/api/aws-cost.md` 6절). 나중에 같은 자리에 붙일 수 있도록 라우트·레이아웃이 탭을 받을 수 있게 설계한다. **이번 범위에 예산 편집 기능은 없다.**
- **사이드바 항목은 3개가 늘어난다 (PM 결정 Q6, 2026-09-25)**: `알림`(이 기능) · `로그`(`docs/specs/logs.md`) · `설정`(이 기능). 셋 다 **상태 점이 없고**, 숫자 배지는 `알림`에만 붙는다. `설정`은 맨 아래 그룹 밖이다. 상단바는 건드리지 않는다.

#### 3.4.2 설정 항목 (화면에 보이는 것)

| 항목 | 기본값 | 설명 |
|---|---|---|
| **디스코드 알림 켜기** | 켬 | **끄면 디스코드로 보내지 않는다. 화면 알림 센터에는 계속 쌓인다.** 이 문장을 스위치 바로 아래에 적는다 |
| **웹훅 주소** | 없음 | 비밀값 취급(3.4.3). 저장·지우기 |
| **보낼 심각도** | `장애만` | `장애만` / `주의부터` |
| **확인 불가(연결 끊김)도 보내기** | 켬 | 5분 이상 지속될 때만. 심각도 순서와 별개 축(3.2.4) |
| **테스트 발송** | — | 3.5 |
| (표시만) 마지막 발송 결과 | — | 성공/실패 시각과 사유 |
| (표시만) 알림 대상 8개 목록 | — | 켜고 끄기는 **2단계**(P3) |

- **화면에 두지 않는 것**: 억제 창·플래핑 기준·워밍업 시간. 기본값을 쓰고 `settings` 테이블·환경 변수로만 바꾼다.
  - 근거: 잘못 만지면 알림이 조용히 사라진다. 운영자가 정말 필요하면 SQL/API로 바꿀 수 있게 하되 화면에서 쉽게 건드리지 않게 한다(`aws-cost` 설정의 `estimation` 블록을 조회 전용으로 둔 것과 같은 결).
- **저장 방식**: 부분 갱신(`PATCH`), 응답은 전체 설정. 환경 변수로 고정된 필드는 `lockedByEnv`로 잠근다 — **기존 `PATCH /api/cost/settings` 규칙을 그대로 따른다**(`docs/api/aws-cost.md` 6.1·6.2). 새 규칙을 만들지 않는다.
- 대시보드 DB가 없으면 설정 변경은 503 `DASHBOARD_DB_UNAVAILABLE`(기존과 동일). 조회는 된다.

#### 3.4.3 웹훅 URL의 비밀값 취급 (판단과 근거)

**전제**: 디스코드 웹훅 URL은 사실상 비밀값이다. 그 URL을 아는 사람은 **누구나 그 채널에 글을 쓸 수 있다**(인증이 URL 안에 들어 있다).

| 결정 | 내용 | 근거 |
|---|---|---|
| **저장 위치** | 대시보드 자체 DB `settings` 테이블의 **별도 키** `alerts.discord.webhookUrl` | ① 사용자 요구가 "화면에서 입력"이므로 `.env` 전용은 불가. ② 이미 설정 저장 경로(`settings` + `PATCH`)가 있고 검증된 규칙이 있다. 새 저장소를 만들 이유가 없다. ③ 별도 키로 분리하면 다른 설정 조회에 섞여 나갈 위험이 줄고, 나중에 암호화·이전이 쉽다 |
| **환경 변수 우선** | `ALERTS_DISCORD_WEBHOOK_URL`이 있으면 **그 값이 이긴다.** 화면 입력은 잠기고 `lockedByEnv: ["webhookUrl"]` | "DB에 두기 싫다"는 선택지를 남긴다. 기존 `COST_MONTHLY_BUDGET_USD` 잠금과 같은 방식이라 새 개념이 아니다 |
| **화면에 원문을 다시 보여주지 않는다** | `GET`은 `{ configured: true, hint: "…****7f3a", length: 119, updatedAt }`만 준다. **전체 URL·토큰은 어떤 API로도 나가지 않는다.** 입력칸은 저장 후 비워 두고 "다시 보기" 버튼을 두지 않는다 | **대시보드에 로그인이 없다**(가정 N2). 화면을 열 수 있는 사람 = URL을 복사할 수 있는 사람이 된다. 클러스터 안에 배포하면(`deploy/app.example.yaml`) 그 범위가 더 넓어진다. 원문을 안 보여줘도 "지우고 다시 넣기"로 모든 운영이 가능하다 |
| **가림 힌트 형식** | 끝 4자만 노출(`…****7f3a`) + 글자 수 | 끝 4자는 "내가 넣은 그 웹훅이 맞나"를 확인하기에 충분하고, 앞쪽(채널 ID)이 없으면 재구성할 수 없다 |
| **DB에 평문으로 둔다** | 암호화하지 않는다 | 암호화하려면 **키를 또 어딘가에 둬야 한다.** 그 키를 `.env`에 두면 결국 "`.env`에 비밀값"과 같은 보호 수준이고, 대시보드 DB 접근 = 서버 접근이라 실질적 이득이 작다. 대신 한계를 명세에 적고 `.env` 경로를 선택지로 남긴다. → **Q4 결정됨(PM, 2026-09-25): 평문 저장 + 원문 미노출**(8.1) |
| **로그·응답·이력에 절대 안 나간다** | 서버 공통 `redactSecrets`에 **디스코드 웹훅 URL 패턴**을 추가한다. 발송 실패 오류 메시지·`SourceStatus.error.message`·알림 본문·SSE 어디에도 없다 | `docs/api/common.md` 1.4·3.2("5xx 메시지에 접속 문자열을 넣지 않는다")의 연장 |
| **스냅샷 스캐너** | 기존 비밀값 스캐너(`deploy/aws-snapshot/lib`)가 디스코드 웹훅 URL 패턴을 잡는지 확인하고, 없으면 추가한다 | 사용자가 스냅샷 메모·템플릿에 실수로 붙여 넣는 것을 잡는다. 백엔드 요청 |
| **커밋 금지** | `.env.example`에는 이름과 형식 설명만. 실제 값은 `.env`·DB에만 | `CLAUDE.md` 공통 규칙 |

### 3.5 테스트 발송 (되돌릴 수 없는 외부 동작)

버튼을 누르면 **실제로 디스코드에 메시지가 간다.** 회수할 수 없다. 그래서 "사용자가 의도한 것임이 분명"해야 한다.

1. **저장된 주소로만 보낸다.** 저장하지 않은 입력값을 API로 보내 테스트하지 않는다.
   - 근거: 저장 전 값을 요청 본문으로 보내면 그 값이 검증 오류(`details.fields[].value`)·프록시 로그에 남을 위험이 커진다. `k8s-snapshot`에서 `content`·`path`를 오류 본문에서 빼기로 한 것과 같은 판단(`docs/api/common.md` 8절 변경 이력). 저장 → 테스트 → (틀리면) 지우고 다시 저장 순서로 모든 운영이 가능하다.
2. **버튼 활성 조건**: 주소가 저장돼 있고, 발송이 켜져 있을 때만. 아니면 비활성 + 이유 툴팁.
3. **확인 대화상자 1단계**: 제목 `디스코드로 테스트 메시지를 보냅니다`, 본문에 ① **"채널에 실제 메시지가 즉시 전송됩니다. 되돌릴 수 없습니다."** ② **보낼 메시지 전문 미리보기** ③ 대상 표시(`…****7f3a`). 버튼은 `취소` / `보내기`.
4. **API도 명시 확인을 요구한다**: `POST /api/alerts/test` 본문 `{ "confirm": true }`. 없으면 **422 `ALERT_TEST_CONFIRMATION_REQUIRED`**.
   - 기존 `SNAPSHOT_CONFIRMATION_REQUIRED`(422)와 같은 패턴이다(`docs/api/common.md` 3.3). 새 개념이 아니다.
5. **쿨다운 60초**: 그 안에 다시 부르면 **429 `ALERT_TEST_COOLDOWN`** + `Retry-After` + `details.retryAfterSec`. 화면 버튼에 남은 시간을 표시한다.
6. **메시지 본문에 테스트임이 보여야 한다**: `[테스트] Sentinel 알림 설정 확인 메시지입니다. 실제 장애가 아닙니다.` + 클러스터 이름 + 시각.
   - 근거: 채널에 다른 사람이 있을 수 있다. 장애로 오인하면 안 된다.
7. **이력에 남긴다**: `kind: test`로 알림 이력에 1건. 언제 눌렀고 결과가 무엇인지(성공/실패/사유) 남는다.
8. **mock에서는 실제로 보내지 않는다**(3.6). 버튼은 눌리고, 결과는 `실제로 보내지 않았습니다 (mock)` + 보낼 본문 전문을 화면에 보여 준다.

### 3.6 mock 모드 동작

**원칙: mock에서는 디스코드로 한 건도 나가지 않는다.** 기존 `ADVISOR_BRIDGE=live` 패턴을 그대로 따른다(`docs/reports/architecture-advisor/backend.md` "mock에서 브리지 호출은 옵트인").

| 환경 변수 | 값 | 동작 |
|---|---|---|
| `ALERTS_DISPATCH` | `mock` \| `live` (기본: `DATA_SOURCE`를 따름) | `mock`이면 **아웃바운드 요청 0건**. 발송 결과는 `skipped_mock`으로 기록하고 화면에 `실제로 보내지 않음` 배지 + **보낼 본문 전문**을 보여 준다 |
| | | `live`면 실제 발송(주소가 설정돼 있을 때). `DATA_SOURCE=mock`에서도 문구·형식을 실제 채널로 확인할 수 있다 |
| | | `DATA_SOURCE=live`에서 `ALERTS_DISPATCH=mock`으로 **강제 차단**할 수 있다(비상 스위치 역할 겸용) |

- `ALERTS_DISPATCH=live` + `DATA_SOURCE=mock`으로 보낸 메시지는 **본문 맨 앞에 `[MOCK]`**이 반드시 붙는다(3.3.2).
- 보낼 본문 전문을 화면에 그대로 보여 주는 이유: 실제 클러스터·웹훅이 없는 지금 **문구를 사람이 검토할 수 있는 유일한 방법**이다.

**mock 시나리오 그룹 `alerts` 추가** (`docs/api/common.md` 6.1 방식, `GET/PUT /api/mock/scenarios`)

| id | 재현 내용 |
|---|---|
| `default` (기본) | 최근 24시간 예시 알림 12건: 장애 3, 주의 4, 확인 불가 1, 해제 3, 플래핑 묶음 1. 미확인 3건 → **사이드바 `알림` 배지 3 + 브라우저 탭 제목 `(3) Sentinel`**(AC-ALERT35) |
| `empty` | 알림 0건 (빈 상태 문구 + "아직 알림이 없습니다") |
| `burst` | 3초마다 새 알림 1건 → **사이드바 배지 숫자와 탭 제목 숫자가 올라가는 것을 눈으로 확인** |
| `flapping` | 한 키가 30분 안에 6회 전이 → 불안정 묶음 1건, 그 뒤 조용함 |
| `restart` | 방금 재시작한 상태: 워밍업 요약 1건 + 정지 구간 19분 안내 |
| `webhook-unset` | 웹훅 미설정 (화면만 동작, 안내 한 줄) |
| `webhook-failed` | 발송 5xx 3회 실패 후 포기 |
| `webhook-ratelimited` | 429로 큐 대기 중 |
| `suppressed-by-source` | `kube` 끊김으로 영역 5개가 묶여 `source:kube` 1건만 있는 상태 |

**그룹 사이의 관계 (가장 중요한 눈 확인 경로)**

- **`cluster`·`cost` mock 시나리오를 바꾸면 상태 전이가 실제로 일어나 알림이 생성된다.** 예: `cluster`를 `healthy` → `critical`로 바꾸면 15초 안에 `area:pods`·`area:nodes` 알림이 실제로 만들어지고 배지가 올라간다. `alerts` 그룹의 `default`는 "미리 쌓인 이력"이고, **실시간 생성 확인은 cluster/cost 전환으로** 한다. (AC-ALERT02)
- `cluster` → `kube-auth-failed`로 바꾸면 `source:kube` 억제 동작을 확인할 수 있다(AC-ALERT07).
- `cost` → `budget-over` / `spike-warning`으로 비용 알림을 확인한다(AC-ALERT12).
- `POST /api/mock/reset`은 알림 이력·확인 상태·발송 기록·플래핑 카운터를 초기 상태로 되돌린다.

### 3.7 이력 보관 — **무엇을 저장해야 하는지** (설계는 DBA)

> 테이블 이름·컬럼 타입·인덱스·마이그레이션은 **DBA가 정한다.** 아래는 "이 정보가 없으면 기능이 성립하지 않는다"는 목록이다.

**A. 알림 1건**
- 식별자, 알림 키(영역/출처), 심각도, **상태 전이**(이전 → 현재), 종류(`transition` / `escalation` / `resolve` / `flapping` / `restart_summary` / `test`)
- 대표 사유 **코드**(`reasons[0].code`)와 **문구**(`reasons[0].text`, 가림 처리된 상태)
- 영향 객체 목록 최대 3개(`kind` / `namespace` / `name`)와 전체 개수
- 발생 시각, 마지막 갱신 시각, 해제 시각, 연결된 발생 알림 식별자(해제·격상용)
- 반복 횟수(억제 창 합산), 플래핑 여부
- `dataSource`(`mock` / `live`) — **mock에서 만들어진 알림이 live 이력에 섞이면 안 된다**
- 확인(읽음) 여부와 확인 시각
- (선택) 억제 사유 — 출처 억제로 묶인 알림인지

**B. 발송 기록** (알림 1건에 채널별 0~n행)
- 알림 식별자, 채널(`ui` / `discord`)
- 상태: `pending` / `sent` / `failed` / `skipped_disabled` / `skipped_not_configured` / `skipped_severity` / `skipped_unknown_off` / `skipped_mock` / `skipped_restart` / `skipped_flapping`
- 시도 횟수, 마지막 시도 시각, 응답 코드, **가림 처리된** 오류 한 줄
- **웹훅 URL 원문을 여기에 넣지 않는다.**

**C. 알림 상태 머신**
- 키별 현재 상태, 마지막 전이 시각, 억제 창 시작 시각, 억제 창에 합쳐진 사건 수
- 플래핑 판정용 **최근 전이 시각 목록**(플래핑 창 길이만큼)
- 마지막으로 알린 영향 객체 집합(3.2.2 "영향 객체 변화" 판정용)

**D. 대시보드 생존 heartbeat**
- 마지막 관측 시각(기본 60초 주기 갱신). 재시작 후 **정지 구간** 계산에 쓴다(3.2.5).

**E. 설정**
- `settings` 테이블의 `alerts.*` 키(발송 켜기, 심각도 하한, `sendUnknown`, 억제·플래핑·워밍업 기준값)와 **별도 키** `alerts.discord.webhookUrl`(3.4.3).

**보관 기간**
- **90일 또는 최근 2,000건** 중 먼저 닿는 쪽. 기본 정리 함수(`purgeExpiredData`, `docs/db/schema.md` 3절)에 얹고 `settings.retention.alertDays` / `alertMaxRows`로 바꿀 수 있게 한다.
  - 근거: `cost_rate_samples` 90일, `advisor_runs` 50건/90일과 같은 결이다. 알림은 건당 크기가 작고, "지난달에도 같은 일이 있었나"를 보려면 한 달 이상이 필요하다. → **Q12 결정됨(PM): 90일 / 2,000건**(8.1).
- **아직 해제되지 않은(진행 중) 알림은 보관 기간이 지나도 지우지 않는다.** 지우면 나중에 오는 해제 알림이 짝을 잃는다.
- **대시보드 DB가 없을 때**: 메모리에 최근 **200건**만 두고 재시작 시 사라진다. 화면에 `대시보드 DB 없음 — 알림 이력이 저장되지 않습니다` 안내. 기능은 죽지 않는다(어드바이저의 인메모리 폴백과 같은 결).

## 4. 갱신 주기

**새 조회·새 informer·새 주기 루프를 만들지 않는다.** 이미 있는 것에 얹는다.

| 대상 | 방식 | 목표 |
|---|---|---|
| 상태 전이 감지 | **기존 15초 재평가 루프**에 얹는다(`cluster-status` 4절). watch로 상태가 즉시 바뀌면 그때도 평가한다 | 전이 후 **15초 이내** 알림 생성 |
| 화면 알림 센터 반영 | **SSE 새 토픽 `alerts`** (아래) | 생성 후 **3초 이내** |
| 디스코드 발송 | 알림 생성 직후 큐 → 즉시 발송 | 전이 후 **30초 이내** 채널 도착 |
| 확인 불가(`unknown`) 지속 판정 | 같은 15초 루프에서 누적 | 5분(설정값) |
| 출처 끊김 판정 | `stream.source` 이벤트 + 15초 루프 | 3분 지속 |
| 플래핑 판정 | 전이가 일어날 때마다 | 즉시 |
| heartbeat 기록 | **60초** 주기로 대시보드 DB에 1행 갱신 | — |
| 보관 정리 | 기존 하루 1회 정리 작업에 얹는다 | — |

**SSE**: 새 토픽 **`alerts`**를 추가한다(`docs/api/common.md` 5.1 토픽 목록에 1개 추가).
- 이벤트: `alerts.snapshot`(**배지에 필요한 것만** — 미확인 수 `unreadCount`, 최악 심각도 `worstSeverity`, `updatedAt`, 발송 설정 요약 상태), `alerts.created`, `alerts.updated`(반복 횟수·해제·발송 상태 변화), `alerts.read`(확인 처리).
- **`alerts.snapshot`에 알림 목록(최근 N건)을 싣지 않는다 (2026-09-25, backend 판단을 명세에 반영. 되돌리지 말 것)**
  - **`alerts` 토픽은 모든 페이지가 구독한다.** 프론트는 앱 레이아웃에서 스트림 1개에 전체 토픽을 구독하므로(`docs/api/common.md` 5.1 권장), 스냅샷에 이력을 실으면 **알림 화면을 보지도 않는 탭까지 재연결할 때마다 목록을 받는다.** 비용은 있고 쓰는 곳은 없다.
  - **목록이 필요한 화면은 `/alerts` 하나뿐이다.** 상단바 패널이 없어졌기 때문이다(사용자 결정 Q1 — 사이드바 메뉴 + 배지). 패널이 있었다면 "모든 화면에서 최근 10건"이 필요했지만, 지금은 아니다.
  - 따라서 **목록은 `/alerts` 화면이 REST로 가져간다**(`GET /api/alerts`). 스냅샷은 **배지 한 개를 그리는 데 필요한 최소값**만 담는다.
  - 화면이 열려 있는 동안의 새 알림은 `alerts.created`·`alerts.updated`로 온다 — **목록을 스냅샷에 넣지 않아도 실시간성은 그대로다.**
- **`overview` 토픽에 얹지 않는 근거**: 개요는 영역 상태 요약이고 알림은 목록·수명이 다르다. 토픽을 나눠 두면 위 "배지만 싣는다" 규칙도 깔끔하게 지켜진다. 프론트는 앱 레이아웃에서 스트림 1개에 전체 토픽을 구독하므로(`docs/api/common.md` 5.1 권장) 토픽 추가 비용은 낮다.
- **새 `SourceId`를 만들지 않는다.** 알림은 출처가 아니라 파생 결과다.

## 5. 단계 구분과 수용 기준

**P1과 P2가 이번 범위**, P3는 다음 범위다. **P1만으로도 쓸모가 있어야 한다**(사용자 지시).

| 단계 | 이름 | 내용 | AC |
|---|---|---|---|
| **P1** | 화면 알림 센터 | 전이 감지·억제·플래핑·워밍업·출처 억제, 알림 키 8개, **사이드바 `알림` 메뉴 + 숫자 배지 + `/alerts` 화면 + 브라우저 탭 제목 `(3) Sentinel`**, 이력 저장, mock 시나리오 | AC-ALERT01~18, **35~37**(번호는 뒤에 붙였다) |
| **P2** | 설정 화면 + 디스코드 | `/settings` 알림 탭, 웹훅 저장(비밀값), 심각도 하한·켜기/끄기·확인 불가 토글, 테스트 발송, 발송 큐·재시도·실패 기록 | AC-ALERT19~34 |
| **P3** | (다음 범위) | 알림 대상 켜고 끄기(키별), 주기적 재알림 옵션, 조용한 시간, 요약 묶음(digest), 개별 리소스 알림 키, 브라우저 알림 | — |

- **P1의 가치**: 화면을 안 보고 있어도 나중에 열면 "언제부터 나빠졌고 언제 풀렸나"를 읽을 수 있다(쿠버네티스 이벤트는 1시간만 남으므로 지금은 불가능하다). 탭을 열어 두면 배지가 올라간다.
- **정직하게 적는다**: "자리를 비웠을 때 알려 준다"는 **P2에서 완성**된다. P1은 그 절반(이력·배지)이다.
- P1은 P2의 전제다. 순서를 바꾸지 않는다.

### P1. 화면 알림 센터

- [ ] **AC-ALERT01.** Given `DATA_SOURCE=mock`, kubeconfig·웹훅 없음 / When 대시보드를 연다 / Then 알림 센터가 오류 없이 열리고 예시 알림이 보이며 `MOCK 데이터` 배지가 있다. **웹훅 미설정 때문에 오류·빈 화면·빨간 배너가 생기지 않는다.**
- [ ] **AC-ALERT02.** Given mock / When `cluster` 시나리오를 `healthy` → `critical`로 바꾼다 / Then **15초 안에** 새 알림이 생기고 **사이드바 `알림` 메뉴의 배지 숫자**가 올라간다. (실제 클러스터 없이 눈으로 확인하는 기본 경로. **상단바에는 아무것도 추가되지 않는다.**)
- [ ] **AC-ALERT03.** Given 위 상태를 그대로 둔다 / When 5분이 지난다 / Then 같은 알림 키의 알림이 **추가로 생기지 않는다**(같은 상태 유지 중 반복 발송 없음).
- [ ] **AC-ALERT04.** Given 위 상태 / When `critical` → `healthy`로 되돌린다 / Then **해제 알림 1건**이 생기고 원래 알림과 연결돼 `해결됨 · 지속 N분`이 보인다.
- [ ] **AC-ALERT05.** Given 억제 창(15분) 안에 같은 키에서 사건이 4번 일어난다 / Then 알림은 **1건**이고 `반복 4회`로 표시된다.
- [ ] **AC-ALERT06.** Given `flapping` 시나리오(30분 안에 전이 6회) / Then 알림이 **불안정 묶음 1건**으로만 보이고 전이마다 항목이 생기지 않는다. 플래핑이 풀리면 현재 상태가 1건으로 나온다.
- [ ] **AC-ALERT07.** Given `cluster` 시나리오 `kube-auth-failed` / Then **`source:kube` 알림 1건**만 생기고 영역 5개(노드·컨트롤 플레인·워크로드·파드·이벤트) 알림이 따로 생기지 않는다. 심각도는 **확인 불가**이고 문구에 "장애"가 없다.
- [ ] **AC-ALERT08.** Given `kube-stale` 시나리오 / Then stale만으로는 알림이 생기지 않고, **3분 이상** 지속되면 확인 불가 알림 1건이 생긴다.
- [ ] **AC-ALERT09.** Given 이미 장애 2건·주의 1건이 있는 상태에서 API를 재시작 / Then 워밍업 120초 동안 알림이 **0건**이고, 끝나면 **요약 1건**만 생긴다. 기존 문제가 개별 알림 3건으로 쏟아지지 않는다.
- [ ] **AC-ALERT10.** Given API를 19분간 멈췄다가 켠다 / Then 요약 알림에 `정지 구간 HH:MM ~ HH:MM (19분)`과 "이 동안의 변화는 알림으로 잡히지 않았습니다"가 적혀 있다. 대시보드 DB가 없으면 `이전 실행 기록 없음`으로 적힌다.
- [ ] **AC-ALERT11.** Given `cp-node-down` / Then 컨트롤 플레인 **주의** 알림이고 문구에 쿼럼 내용이 있다. `cp-quorum-lost`면 **장애**(주의 → 장애 격상은 새 알림). `cp-not-found`면 **확인 불가**.
- [ ] **AC-ALERT12.** Given `cost` 시나리오 `budget-over` / Then 비용 **장애** 알림. `spike-warning`이면 **주의**. `no-budget`이면 예산 때문에 생기는 알림이 없다.
- [ ] **AC-ALERT13.** 알림 본문·이력·SSE 어디에도 환경 변수, `command`/`args` 원문, 어노테이션·레이블 원문, DB 쿼리 원문, 접속 문자열, 스택 트레이스, **웹훅 URL**, **컨테이너 로그 줄(가림 처리한 것 포함)과 로그 요약·통계**가 없다. 로그로는 **링크만** 건다(3.3.2).
- [ ] **AC-ALERT14.** 알림 판단은 기존 `StatusInfo`만 쓴다. **`alerts` 기능이** 새 임계값 상수를 코드에 추가하지 않았고(억제 창·플래핑·워밍업 같은 알림 계층 기준값은 예외이며 한곳에 모여 설정으로 바뀐다), `deploy/rbac.yaml`의 리소스·동사와 AWS 권한 목록에 **아무것도 추가하지 않았다.** 같은 시기에 `deploy/rbac.yaml`에 들어간 `pods/log` `get`은 **`logs` 기능의 결정**(`CLAUDE.md`, `logs` AC-LOG01)이라 이 AC의 대상이 아니다 — 이 AC는 "`alerts`가 권한·임계값을 늘리지 않는다"를 검사한다. (2026-09-25 검증에서 문구 정정)
- [ ] **AC-ALERT15.** `/alerts` 화면에서 심각도·영역·기간·해제 포함 여부로 거를 수 있고, 항목을 누르면 해당 화면으로 간다(컨트롤 플레인은 `/cluster/nodes#control-plane`).
- [ ] **AC-ALERT16.** `모두 확인` 후 배지가 0이 되고, 새 알림이 오면 다시 올라간다. 확인 상태는 새로고침·다른 탭에서도 같다(서버 상태).
- [ ] **AC-ALERT17.** Given 대시보드 DB 없음 / Then 알림 기능이 죽지 않고 메모리 최근 200건으로 동작하며, 화면에 `이력이 저장되지 않습니다` 안내가 보인다.
- [ ] **AC-ALERT18.** 보관 정리가 돌면 90일·2,000건을 넘는 알림이 지워지고, **아직 해제되지 않은 알림은 지워지지 않는다.**

> 아래 항목들은 P1에 속하지만 **기존 번호를 밀지 않으려고 뒤에 붙였다**(2026-09-25). 번호 순서가 아니라 단계 소속을 보고 읽는다.

- [ ] **AC-ALERT35.** 미확인 알림이 있으면 **브라우저 탭 제목 앞에 `(N)` 접두어가 붙고**(N = 미확인 수. 예: `(3) Sentinel`, 페이지 이름이 있는 화면은 `(4) 파드 · Sentinel`), `모두 확인` 후 접두어가 사라진다. 브라우저 알림 권한 요청·소리는 **없다**(6절). (2026-09-25 검증에서 문구 정정)
- [ ] **AC-ALERT36.** **상단바에 아무것도 추가되지 않았다.** 종(벨) 아이콘·알림 패널이 없고, `docs/design/shell.md` 2절("전역 검색·알림 벨·사용자 메뉴를 두지 않는다")과 2.1의 상단바 폭 계산이 **그대로**다. 알림 진입점은 **사이드바 `알림` 메뉴 + `/alerts` 화면** 둘뿐이고, 사이드바에 늘어난 `알림`·`로그`·`설정` 세 항목에는 **상태 점이 없다**(`알림`에만 숫자 배지).
- [ ] **AC-ALERT37.** `alerts.snapshot` 이벤트에 **알림 목록이 실리지 않는다**(미확인 수·최악 심각도·`updatedAt`·발송 설정 요약만). **`/alerts`를 열지 않은 탭**이 스트림에 재연결해도 알림 이력을 한 건도 받지 않는다(브라우저 네트워크로 확인). 목록은 `GET /api/alerts`로만 오고, 열려 있는 동안의 변화는 `alerts.created`·`alerts.updated`로 온다. `alerts.created`/`updated`가 모든 탭에 **새로 생긴 알림 1건**을 싣는 것은 **이력이 아니다** — 이 AC는 "재연결 때 이력(목록)을 받지 않는다"를 검사한다(2026-09-25 PM 판단, `docs/reports/alerts/README.md` "AC-ALERT37 — 근거 표가 짚은 어긋남"). (2026-09-25 검증에서 문구 정정)

## 6. 범위 밖

- **모든 조작**: 알림에서 파드 재시작·스케일 조정·cordon 같은 버튼을 만들지 않는다. 조회 전용 원칙(`CLAUDE.md`).
- **다른 채널**: 이메일, Slack, Teams, SMS, PagerDuty, Webhook 일반(디스코드 외 임의 URL — 3.3.2 근거, Q9).
- **임계값 편집 UI**: 재시작 3회·연결 90%·예산 90% 같은 **상태 판단 기준**을 화면에서 바꾸는 기능. 기준은 기존 명세에 있고 `settings`/환경 변수로만 바꾼다.
- **예산 편집 화면**: `PATCH /api/cost/settings`는 이미 있지만 화면은 이번에도 만들지 않는다. **자리만** 고려한다(3.4.1).
- **당번·에스컬레이션·정비 창(maintenance window)·조용한 시간**: 1인 운영 전제(가정 N1)에서 과하다.
- **브라우저 푸시 알림(Notification API)·소리**: 권한 요청 흐름·탭 상태 처리가 별도 설계다(PM 결정 Q8). **단 브라우저 탭 제목 `(3) Sentinel`은 P1에 포함**한다(비용이 거의 없다, 3.3.1·AC-ALERT35).
- **상단바 종(벨) 아이콘·알림 패널**: 만들지 않는다(사용자 결정 Q1). 진입점은 사이드바 `알림` 메뉴와 `/alerts` 화면뿐이고, `docs/design/shell.md` 2절·2.1(상단바 폭 계산)을 건드리지 않는다.
- **알림 본문에 로그 줄 넣기**(가린 줄 포함)와 **로그 기반 알림 규칙**(특정 문자열이 나오면 알림): PM 결정으로 범위 밖(3.3.2). 로그로는 **링크만** 건다. 판단 기준이 `alerts`와 `logs` 두 곳에 생기면 안 된다.
- **개별 리소스 단위 알림 키**(특정 파드만 지켜보기), **주기적 재알림**, **요약 묶음(digest)**: P3.
- **알림 문구 템플릿 편집**, 다국어.
- **사용자별 알림 설정**: 대시보드에 로그인이 없다(가정 N2).
- **알림을 근거로 한 자동 분석 실행**(어드바이저 자동 호출): Claude Code 사용량이 소모되므로 자동 트리거를 만들지 않는다.
- **`metrics`·`agentBridge`·`snapshotStore`·`k8sSnapshotStore`·`dashboardDb` 출처의 알림**: 3.1의 근거 4·6.
- **알림 이력의 외부 내보내기(CSV·API 대량 조회)**.

## 7. 역할별 전달 사항

### 디자인 (`docs/design/alerts.md`)

1. **상단바와 `docs/design/shell.md` 2.1의 폭 계산을 건드리지 않는다.** 종(벨) 아이콘을 만들지 않으므로 상단바에 추가되는 요소가 없고, 2절의 "전역 검색·알림 벨·사용자 메뉴를 두지 않는다"도 **그대로 유효하다**(사용자 결정 Q1). 상단바 오른쪽 최소 폭을 다시 계산할 일이 없다 — 이것이 벨 대신 사이드바를 고른 이유다.
2. **`/alerts` 전체 화면**(필터·목록·상세)이 알림의 유일한 화면이다. 별도 알림 패널(Popover·Drawer)은 만들지 않는다. 표·`StatusBadge`·`Dialog`는 **기존 것을 재사용**하고 새 컴포넌트를 최소화한다.
3. **심각도 표현**: `critical`/`warning`/`unknown`은 기존 `status.*` 토큰 그대로. **새로 필요한 것은 `resolved`(해제)** 하나다 — 초록 계열 `ok`를 그대로 쓸지 별도 표현을 둘지 정한다(해제는 "지금 정상"이 아니라 "정상으로 돌아왔음"이라 뜻이 조금 다르다).
4. **"확인 불가"와 "데이터 오래됨(stale)"의 구분**: 둘 다 회색이다. 알림 목록에서 헷갈리지 않게 문구·아이콘을 정한다(`kops-support` 디자인 3번과 같은 문제).
5. **플래핑 묶음**·**출처 억제 묶음**(`영향 영역 5개`)·**반복 N회**의 표현. 묶인 항목을 펼치는 방식.
6. **발송 상태 표시**: 보냄 / 미설정 / 제외(심각도) / 실패 / mock. 작은 칩 정도로 충분하다.
7. **설정 화면 `/settings`**: 탭 구조(`알림` + 나중의 `비용`), 비밀값 입력 필드(저장 후 비움 + `…****7f3a`), **테스트 발송 확인 대화상자**(경고 문구 + 본문 미리보기).
8. **미설정 안내의 톤**: 회색 정보. 경고색·배너·토스트를 쓰지 않는다(S2).
9. **사이드바**: `알림`·`로그`·`설정` **3개가 늘어난다**(PM 결정 Q6 — `로그`는 `docs/specs/logs.md`). 셋 다 **상태 점 없음**, 숫자 배지는 `알림`에만. `설정`은 맨 아래 그룹 밖. **`알림`·`로그`·`설정` 세 항목은 `designer`가 `shell.md` 3.1 표에서 한 번에 처리한다**(PM 조율).
10. **새 상태 색·배지 체계를 만들지 않는다.**
11. **브라우저 탭 제목 `(3) Sentinel`**: 디자인 산출물이 아니라 프론트 구현 사항이지만, 숫자 표기 규칙(0이면 생략, `99+` 여부)을 배지와 맞춘다.

### 퍼블리싱

- 새 컴포넌트는 **최소한**으로: ① 알림 목록 항목(`AlertItem`), ② 비밀값 입력 필드(`SecretInput` — 저장 후 마스킹 표시, 지우기) 정도. **벨 컴포넌트(`NotificationBell`)는 만들지 않는다** — 배지는 기존 사이드바 `NavItem.count`를 쓴다(사용자 결정 Q1).
- 상태 배지·카드·표·`Drawer`·`Dialog`·`Banner`·`InlineAlert`·칩은 **기존 것을 그대로 쓴다.**
- 배지 숫자 규칙은 `components.md` 12.1(`NavItem.count`, `99+`)을 재사용한다. **새 배지 컴포넌트를 만들지 않는다.**
- 색만으로 구분하지 않는다(아이콘·텍스트 병기) — 기존 원칙 유지.

### 프론트

- `alerts` SSE 토픽 구독(앱 레이아웃의 **기존 스트림 1개**에 토픽만 추가. 새 EventSource를 만들지 않는다).
- **역할 분담을 지킨다**: 배지 숫자는 **SSE `alerts.snapshot`**(미확인 수·최악 심각도)에서, **알림 목록은 `/alerts` 화면이 REST**(`GET /api/alerts`)로 가져온다. **스냅샷에 목록이 오지 않는다**(4절) — 목록을 앱 레이아웃 전역 상태에 들고 있지 않는다. 열려 있는 동안의 변화는 `alerts.created`·`alerts.updated`로 받는다.
- **사이드바 `알림` 배지**(기존 `NavItem.count`) · `/alerts` 화면 · `/settings` 화면 · **브라우저 탭 제목 `(3) Sentinel`**(AC-ALERT35). **상단바는 건드리지 않는다.**
- **상태 계산을 화면에서 하지 않는다**(기존 원칙). 심각도·억제·플래핑·정지 구간은 전부 서버 값이다.
- 알림 → 각 화면 링크(컨트롤 플레인은 `/cluster/nodes#control-plane`). **파드 알림에는 로그 화면 링크도 건다** — 본문에 로그 줄을 싣지 않고 링크로만 잇는다(3.3.2, `logs` 3.8.1 진입점 8번).
- 테스트 발송: 확인 대화상자 없이 API를 부르지 않는다. 쿨다운 남은 시간 표시.
- 웹훅 입력값을 **상태에 오래 들고 있지 않는다**(저장 성공 즉시 비운다). 브라우저 자동완성·로그에 남지 않게 주의.
- 픽스처에 알림 예시(9개 시나리오) 추가.

### 백엔드

- **상태 전이 감지를 기존 15초 재평가 루프에 얹는다.** 새 informer·새 주기 조회·새 `SourceId`를 만들지 않는다.
- 알림 키 8개(3.1), 전이 표(3.2.1), 억제(3.2.2), 플래핑(3.2.3), `unknown` 지속·**출처 억제**(3.2.4), 워밍업·정지 구간(3.2.5)을 **서버에서** 계산한다. 기준값은 한곳에 모아 `settings`/환경 변수로 바꿀 수 있게 한다.
- `docs/api/alerts.md`(계약)를 **구현 전에** 먼저 쓴다: REST(`GET /api/alerts`, `PATCH /api/alerts/read`, `GET/PATCH /api/alerts/settings`, `POST /api/alerts/test`)와 SSE(`alerts.*`).
  - **`alerts.snapshot`에는 배지에 필요한 것만 담는다**(미확인 수·최악 심각도·`updatedAt`·발송 설정 요약). **목록은 `GET /api/alerts`로만** 나간다(4절 근거). → **2026-09-25: 이미 계약이 이 결정대로 쓰여 있고, 명세를 그쪽에 맞췄다.**
- `docs/api/common.md` 갱신 요청: ① 5.1 토픽 표에 `alerts` 1줄, ② 5.8 이벤트 목록에 `alerts.*`, ③ 6.1 mock 그룹 `alerts`, ④ 3.3 에러 코드에 `ALERT_TEST_CONFIRMATION_REQUIRED`(422)·`ALERT_TEST_COOLDOWN`(429), ⑤ **0 요약 "쓰기" 행에 0.2절의 층 구분 한 줄**("밖으로 나가는 통지: 사용자가 지정한 디스코드 웹훅. 관측 대상을 바꾸지 않는다").
- **`redactSecrets`에 디스코드 웹훅 URL 패턴을 추가**하고, 오류 응답의 `details.fields[].value`에서 `webhookUrl` 필드를 제외한다(`k8s-snapshot`의 `content`·`path` 처리와 같은 방식).
- 비밀값 스캐너(`deploy/aws-snapshot/lib`)가 디스코드 웹훅 URL을 잡는지 확인하고 없으면 규칙을 추가한다.
- 디스코드 발송: URL 도메인 제한, 백오프 3회, 429 `Retry-After`, 속도 상한, 연속 실패 차단, `skipped_*` 상태 기록.
- `ALERTS_DISPATCH=mock|live`(기본 `DATA_SOURCE`를 따름) — **mock에서 아웃바운드 0건**을 테스트로 보장한다.
- 환경 변수 추가(`env.validation.ts`·`.env.example`·`docker-compose.yml`·`deploy/app.example.yaml`): `ALERTS_DISPATCH`, `ALERTS_DISCORD_WEBHOOK_URL`(선택, 설정되면 잠금), `ALERTS_PUBLIC_BASE_URL`(선택, 링크용).
- `deploy/app.example.yaml` 주석: 클러스터 안에 배포하면 **`discord.com:443` 아웃바운드가 나갈 수 있어야** 한다(NetworkPolicy·egress·프록시). 나갈 수 없으면 발송 실패로 기록되고 화면은 정상 동작한다. **RBAC는 바꾸지 않는다.**
- mock: 시나리오 9개 + `cluster`/`cost` 전환으로 **실제 전이가 일어나 알림이 생성되는** 경로(AC-ALERT02·07·12).
- 알림 본문에 리소스 이름을 **원문 그대로** 쓴다(가정 N6, **Q3 확정**). 그래도 이름을 만드는 자리는 **한곳에 모아** 두면 나중에 "노드 이름만 가리기" 같은 요구가 와도 한 군데만 고치면 된다.
- **알림 본문에 로그 줄을 넣지 않는다**(3.3.2·AC-ALERT13). 가림 처리한 줄도, 로그 요약·통계도 안 된다. 알림에서 로그로는 **링크만** 건다(`logs` 3.8.1 진입점 8번). 그 링크(`logHref`)에는 **`follow=1`을 붙이지 않는다**(2026-09-25 `logs` PM 결정 D3). 링크 규칙은 로그 쪽과 **같은 서버 규칙 한 곳**을 쓴다.

### DBA

- **3.7의 A~E를 담는 스키마 설계**(테이블·컬럼·타입·인덱스·마이그레이션). 이름·구조는 DBA가 정한다.
- 조회 패턴: ① 최근 N건 최신순(**`/alerts` 화면의 REST 전용** — SSE 스냅샷에는 목록이 실리지 않는다, 4절), ② 미확인 수와 최악 심각도(**배지용 — 매 SSE 스냅샷마다 부르므로 가장 가벼워야 한다.** 모든 페이지·모든 탭이 재연결할 때마다 불린다), ③ 심각도·영역·기간 필터, ④ 진행 중(미해제) 알림 찾기, ⑤ 키별 상태 머신 읽기·쓰기(15초마다).
  - ①과 ②의 빈도가 크게 다르다는 점을 전제로 인덱스를 잡아 달라. ②는 **집계 한 방**으로 끝나는 형태가 좋다(미확인 수 + 최악 심각도).
- **보관 정리**를 기존 `purgeExpiredData`에 추가: 90일 또는 2,000건, **미해제 알림 제외**. `settings.retention.alertDays`·`alertMaxRows`.
- `settings` 기본값(`src/database/settings-defaults.ts`)에 `alerts.*` 추가. **`alerts.discord.webhookUrl`은 별도 키로 분리**하고, 기본값은 `null`이며 시드에 예시 값을 넣지 않는다.
- **모니터링 대상 Postgres는 손대지 않는다.** 모니터링 계정·쿼리·`docs/db/health.md`에 변화 없다.
- 웹훅 URL 저장 형태는 **Q4에서 평문으로 확정**됐다(별도 키, 원문 미노출). 암호화 설계는 필요 없다. 다만 **DB 백업·덤프에 URL이 섞여 나간다**는 한계가 있으니, 덤프를 다루는 운영 문서에 한 줄 남겨 주면 좋다.
- `heartbeat` 행이 60초마다 갱신되는 것이 부담이 되지 않는 형태인지 확인(단일 행 upsert 권장).

## 10. 요약 (한 장)

- **무엇을**: 기존 상태 판단(`cluster-status`·`kops-support`·`aws-cost`)을 그대로 받아 **알림 키 8개**(컨트롤 플레인·노드·워크로드·파드·이벤트·DB·비용·쿠버네티스 출처)로 묶는다. 새 기준을 만들지 않는다.
- **언제**: 상태가 **바뀌는 순간**만. 억제 창 15분, 플래핑 30분·4회, 워밍업 120초, `unknown` 5분 지속, 출처 억제로 5건 → 1건.
- **어디로**: 화면 알림 센터(**항상**, 끌 수 없음) + 디스코드 웹훅(**선택**, 주소 없으면 화면만 — 오류 아님).
- **어디에**: **사이드바 `알림` 메뉴 + 숫자 배지**와 **`/alerts` 화면**. **상단바 종 아이콘은 만들지 않는다**(사용자 결정 Q1 — `shell.md` 2절·2.1 폭 계산을 건드리지 않는다). 미확인이 있으면 **브라우저 탭 제목 `(3) Sentinel`**. 사이드바에 늘어나는 `알림`·`로그`·`설정` 3개는 **상태 점이 없다.**
- **설정**: `/settings → 알림`. 웹훅 주소는 **비밀값**(원문 미노출, DB 별도 키, env 우선·잠금), 켜기/끄기, 심각도 하한, 확인 불가 토글.
- **테스트 발송**: 확인 대화상자 + `confirm: true` + 60초 쿨다운 + `[테스트]` 문구 + mock 차단.
- **mock**: `ALERTS_DISPATCH=mock`(기본)에서 **아웃바운드 0건**. `cluster`/`cost` 시나리오를 바꾸면 알림이 실제로 생기고 배지가 올라간다.
- **이력**: 대시보드 자체 DB, 90일 또는 2,000건, 미해제는 남김. DB 없으면 메모리 200건.
- **단계**: P1 화면 알림 센터(AC-ALERT01~18 + **35~37**) → P2 설정 + 디스코드(AC-ALERT19~34) → P3 다음 범위.
- **SSE**: `alerts` 토픽 1개 추가. **스냅샷에는 배지 값만**(미확인 수·최악 심각도) 싣고 **목록은 `/alerts`가 REST로** 가져간다 — 모든 탭이 구독하는 토픽이라 이력을 실으면 안 보는 탭까지 받는다(4절).
- **원칙**: 관측 대상 쓰기 0건, RBAC·IAM 그대로, 알림 본문에 비밀값·환경 변수·command/args 원문 없음, **컨테이너 로그 줄도 없음(링크만)**.
- **열린 것**: **Q11(클러스터 안 배포에서 `discord.com:443` egress) 하나뿐**이고 착수를 막지 않는다. 나머지 Q1~Q10·Q12는 8.1에 결정으로 정리돼 있다.

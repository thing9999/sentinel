# 기능 명세: cluster-status (쿠버네티스 서버·DB 상태 대시보드)

- 작성: planner, 2026-09-19
- 상태: 초안 (열린 질문 없음, 가정으로 진행 가능)
- 관련 문서: `CLAUDE.md` "확정된 결정", `docs/HANDOFF.md` 3절
- 후속 명세: `docs/specs/aws-cost.md`, `docs/specs/architecture-advisor.md` (이 기능의 상태 데이터를 재사용)

## 0. 가정 (합리적 기본값, 사용자가 다르게 말하면 수정)

- 가정 A1: 대상은 **EKS 클러스터 1개**. 다중 클러스터 전환은 범위 밖.
- 가정 A2: 모니터링 대상 DB는 **클러스터 안 Postgres StatefulSet 1개**(기본 Postgres 16). 어떤 StatefulSet이 DB인지는 설정값(네임스페이스 + StatefulSet 이름)으로 지정한다.
- 가정 A3: **metrics-server는 설치돼 있다**(EKS 애드온). 없으면 CPU·메모리 영역은 "알 수 없음(metrics-server 없음)"으로 표시하고 나머지 화면은 정상 동작한다.
- 가정 A4: **Prometheus는 없다고 가정**한다. 추이 그래프는 API 서버가 직접 모은 **최근 1시간** 표본으로 그린다(API 재시작 시 초기화되어도 된다). Prometheus 주소가 설정돼 있으면 그쪽을 출처로 쓰고 기간을 24시간까지 늘린다.
- 가정 A5: 대시보드는 **로컬(호스트의 docker compose)에서 운영자 본인이 보는 용도**다. 앱 내 로그인은 이번 범위 밖이며, 클러스터 배포·팀 공유를 하게 되면 인증을 별도 명세로 다룬다.
- 가정 A6: 모든 네임스페이스를 본다. 시스템 네임스페이스(`kube-system`, `kube-public`, `kube-node-lease`, `amazon-cloudwatch` 등 설정 가능)는 기본 표시하되 "시스템 숨기기" 필터를 제공한다.
- 가정 A7: DB 내부 통계는 DBA가 만드는 **모니터링 전용 읽기 계정**(예: `pg_monitor` 권한 수준)으로 조회한다. 쿼리 원문은 화면에 보여주지 않는다(개인정보 포함 가능).
- 가정 A8: DB 복제본(standby)이 없으면 복제 영역은 "해당 없음"으로 숨긴다.

## 1. 배경 / 목표

- **누가**: 이 EKS 클러스터와 그 안의 Postgres를 운영하는 개발자/운영자(1인~소규모 팀).
- **왜**: 지금은 `kubectl`과 `psql`을 번갈아 치며 상태를 확인한다. 한 화면에서 "지금 문제가 있는가, 있다면 어디인가"를 5초 안에 판단하고, 원인 파드/노드/DB 지표까지 두세 번 클릭으로 내려가고 싶다.
- **목표**
  1. 클러스터 전체·노드·워크로드·파드·DB의 상태를 **정상 / 주의 / 장애 / 알 수 없음** 네 단계로 일관되게 표시한다.
  2. 파드·노드 변화는 수 초 안에 화면에 반영한다(실시간).
  3. 조회 전용: 클러스터와 DB에 어떤 쓰기도 하지 않는다.
  4. `DATA_SOURCE=mock`에서 kubeconfig·DB 없이도 모든 화면과 모든 상태가 재현된다.

## 2. 사용자 시나리오

### S1. 아침 점검
1. 대시보드 첫 화면(개요)을 연다.
2. 상단 요약 띠에 클러스터 전체 상태(가장 나쁜 구성요소 기준)와 영역별 카드(노드, 워크로드, 파드, 이벤트, DB)가 보인다.
3. 모두 정상이면 끝. 마지막 갱신 시각이 최근인지 확인한다.

### S2. 장애 알림 → 원인 파드 찾기
1. 요약 띠가 "장애", 파드 카드에 "장애 2"가 표시된다.
2. 파드 카드를 누르면 파드 목록이 **장애 → 주의 → 정상** 순으로 정렬되어 열린다.
3. `api-7f9c...` 파드가 `CrashLoopBackOff`, 최근 1시간 재시작 6회로 표시된다.
4. 파드 상세에서 컨테이너별 상태, 대기/종료 사유(예: `OOMKilled`), 마지막 종료 시각, 관련 Warning 이벤트, 소속 워크로드, 올라가 있는 노드를 본다.
5. 노드 링크로 넘어가 해당 노드가 `MemoryPressure`인지 확인한다.

### S3. DB가 느리다는 제보
1. DB 카드가 "주의"다. 누르면 DB 상세.
2. 연결 사용률 82%, 5분 넘게 실행 중인 쿼리 3건, `idle in transaction` 12분 세션 1건이 보인다(쿼리 원문 없이 사용자·DB·상태·경과 시간만).
3. PVC 사용률, 캐시 적중률, 데드락 증가 여부를 같은 화면에서 확인한다.

### S4. 데이터 출처가 끊김
1. API가 클러스터 연결을 잃거나 SSE가 끊긴다.
2. 화면 상단에 "연결 끊김 - 마지막 갱신 14:02:10" 배너가 뜨고, 오래된 값은 회색 "데이터 오래됨"으로 바뀐다. 끊긴 것을 "장애"로 오인하지 않게 한다.

## 3. 표시할 지표와 상태 판단 기준

### 3.0 공통 규칙

| 상태 | 의미 | 색(디자인이 확정) |
|---|---|---|
| 정상 | 조치 불필요 | 초록 계열 |
| 주의 | 지켜봐야 함, 곧 문제가 될 수 있음 | 노랑 계열 |
| 장애 | 지금 서비스에 영향이 있거나 즉시 확인 필요 | 빨강 계열 |
| 알 수 없음 | 데이터 출처 없음/조회 실패/권한 없음 | 회색 |

- **집계**: 상위 항목 상태 = 하위 항목 중 가장 나쁜 상태. 우선순위 `장애 > 주의 > 알 수 없음 > 정상`.
- **데이터 오래됨**: 해당 지표의 갱신 주기 3배가 지나도록 새 값이 없으면 상태 대신 "데이터 오래됨"(회색 + 마지막 갱신 시각)으로 표시한다.
- **지속 조건**: 사용률(%) 기준은 순간 튐을 막기 위해 **연속 3회 조회(약 45초)** 동안 조건을 만족해야 상태를 올린다. 내릴 때는 1회 만족으로 즉시 내린다.
- 모든 상태 배지 옆에는 **판단 이유 한 줄**(예: "최근 1시간 재시작 6회")을 함께 보여준다.

### 3.1 클러스터 요약 (상단 띠)

| 지표 | 표시 |
|---|---|
| 클러스터 이름, 쿠버네티스 버전, 리전 | 텍스트 |
| 전체 상태 | 3.2~3.7 전체의 최악 상태 |
| 노드 수 (Ready / 전체) | 숫자 |
| 파드 수 (정상 / 주의 / 장애) | 숫자 |
| 워크로드 수 (정상 / 주의 / 장애) | 숫자 |
| 최근 15분 Warning 이벤트 수 | 숫자 |
| DB 상태 | 배지 |
| 마지막 갱신 시각, 데이터 소스(mock/live) | 텍스트, mock이면 "MOCK 데이터" 배지 상시 표시 |

### 3.2 노드

표시: 이름, 인스턴스 타입, 가용 영역, 노드그룹, 구매 옵션(온디맨드/스팟, 레이블로 알 수 있으면), kubelet 버전, 생성 후 경과 시간, Ready, 압박 조건, 스케줄 불가(cordon) 여부, 할당 가능 CPU/메모리, CPU/메모리 사용량·사용률, requests 합계/할당 가능 비율, 파드 수/최대 파드 수.

| 항목 | 정상 | 주의 | 장애 |
|---|---|---|---|
| Ready 조건 | `True` | `False`/`Unknown`이 60초 미만 | `False`/`Unknown`이 60초 이상 지속 |
| `MemoryPressure` / `DiskPressure` / `PIDPressure` | 모두 `False` | 하나라도 `True` | - (Ready가 떨어지면 위 규칙으로 장애) |
| `NetworkUnavailable` | `False` 또는 없음 | - | `True` |
| 스케줄 불가(cordon) | 아님 | cordon 상태 (표시: "스케줄 제외") | - |
| CPU 사용률 (사용량 / 할당 가능) | < 70% | 70% 이상 90% 미만 | 90% 이상 |
| 메모리 사용률 (사용량 / 할당 가능) | < 75% | 75% 이상 90% 미만 | 90% 이상 |
| CPU 또는 메모리 requests 합계 / 할당 가능 | < 85% | 85% 이상 (새 파드 스케줄 여유 부족) | - |
| 파드 수 / 최대 파드 수 | < 90% | 90% 이상 | 100% |

- 노드 카드 요약: "Ready 5/6", 장애 노드 이름 최대 3개.
- 노드 수가 0이거나 모든 노드가 NotReady면 클러스터 전체 장애.

### 3.3 워크로드 (Deployment, StatefulSet, DaemonSet)

표시: 종류, 네임스페이스, 이름, 준비/원하는 레플리카(ready/desired), 업데이트된 레플리카, 이미지(태그까지), 생성·마지막 롤아웃 시각, 소속 파드 상태 분포.

| 항목 | 정상 | 주의 | 장애 |
|---|---|---|---|
| ready / desired | ready = desired | 0 < ready < desired | desired > 0 이고 ready = 0 |
| 롤아웃 진행 (Deployment `Progressing`) | 완료 | 진행 중 | `ProgressDeadlineExceeded` |
| DaemonSet 스케줄 | numberReady = desiredNumberScheduled | 부족 1개 이상 | numberReady = 0 (desired > 0) |
| desired = 0 | "중지됨"으로 표시, 상태는 정상 | - | - |

- 단일 레플리카(desired = 1)는 이 화면에서는 정상으로 둔다. 안정성 위험 표시는 `architecture-advisor`의 규칙 기반 사전 점검에서 다룬다.

### 3.4 파드

표시: 네임스페이스, 이름, 소속 워크로드, 노드, phase, 컨테이너 준비 수(예: 1/2), 누적 재시작, **최근 1시간 재시작**, 대기 사유(waiting reason), 마지막 종료 사유(lastState terminated reason, 종료 코드, 시각), 경과 시간, CPU/메모리 사용량과 requests/limits 대비 비율, QoS 클래스.

| 항목 | 정상 | 주의 | 장애 |
|---|---|---|---|
| phase | `Running`(모든 컨테이너 ready) / `Succeeded` | `Pending` 2분 이상 10분 미만, `Running`인데 준비 안 된 컨테이너가 2분 이상 | `Pending` 10분 이상, `Failed`, `Unknown` 2분 이상 |
| 대기 사유 | 없음 또는 `ContainerCreating`/`PodInitializing` 2분 미만 | `ContainerCreating`/`PodInitializing` 2분 이상 | `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull`, `CreateContainerConfigError`, `CreateContainerError`, `InvalidImageName` |
| 최근 1시간 재시작 | 0회 | 1~2회 | 3회 이상 |
| 마지막 종료 사유 `OOMKilled` | 없음 | 최근 1시간 안에 1회 이상 | (재시작 3회 이상이면 위 규칙으로 장애) |
| 메모리 사용량 / limit | < 80% | 80% 이상 95% 미만 | 95% 이상 |
| 종료 중(`Terminating`) | - | 5분 이상 지속 | - |

- "최근 1시간 재시작"은 누적 재시작 수의 1시간 동안의 증가분이다. API가 처음 뜬 직후 1시간 동안은 "관측 N분" 표시와 함께 관측 구간 기준으로 계산한다.
- Job/CronJob이 만든 `Succeeded` 파드는 기본 목록에서 숨기고 "완료된 파드 보기" 필터로 본다. `Failed` Job 파드는 장애가 아니라 **주의**로 표시한다(재시도 설계일 수 있음).
- 파드 목록 기본 정렬: 상태(장애 → 주의 → 정상) → 최근 재시작 많은 순.

### 3.5 Warning 이벤트

표시: 최근 1시간 Warning 이벤트 목록(시각, 네임스페이스, 대상 종류/이름, reason, message, 반복 횟수). 대상 파드/노드/워크로드 상세에도 관련 이벤트를 붙인다.

| 항목 | 정상 | 주의 | 장애 |
|---|---|---|---|
| 이벤트 카드 | 최근 15분 Warning 0건 | 최근 15분 Warning 1건 이상 | 아래 "심각 reason"이 최근 15분 안에 발생 |

- 심각 reason: `FailedScheduling`(같은 대상에 5분 이상 반복), `FailedMount`, `FailedAttachVolume`, `Evicted`, `OOMKilling`(노드), `NodeNotReady`, `FailedCreatePodSandBox`, `BackOff`(같은 대상 10분 안에 5회 이상).
- 이벤트는 대상 객체 상태에도 반영한다: 대상에 심각 reason이 있으면 그 객체는 최소 주의.
- 쿠버네티스는 이벤트를 기본 1시간만 보관하므로 그 이상은 보여주지 않는다(범위 밖 참고).

### 3.6 CPU·메모리 (metrics-server)

- 클러스터 전체: CPU 사용량/할당 가능, 메모리 사용량/할당 가능, requests 합계/할당 가능, limits 합계/할당 가능.
- 상태 기준: 클러스터 전체 CPU 사용률 70%/90%, 메모리 75%/90%를 노드 기준(3.2)과 같이 적용.
- 추이 그래프: 클러스터 전체 CPU·메모리, 노드별, 선택한 파드별 (기간: 가정 A4 참조). 그래프에 주의·장애 기준선을 점선으로 표시.
- metrics-server 조회 실패: 해당 영역 "알 수 없음", 나머지 영역 판단에는 영향 없음.

### 3.7 DB 상태 (Postgres StatefulSet)

**쿠버네티스 쪽**

| 항목 | 정상 | 주의 | 장애 |
|---|---|---|---|
| DB StatefulSet ready / desired | 3.3과 동일 | | |
| DB 파드 | 3.4와 동일 | | |
| PVC phase | `Bound` | `Pending` 2분 이상 | `Lost` |
| PVC 사용률 (사용량 / 용량) | < 75% | 75% 이상 90% 미만 | 90% 이상 |

- PVC 사용량은 정확한 볼륨 사용량을 얻을 수 있으면 그것을, 없으면 `pg_database_size()` 합계를 근사치로 쓰고 "근사치" 라벨을 붙인다.

**DB 내부** (모니터링 계정)

| 항목 | 정상 | 주의 | 장애 |
|---|---|---|---|
| 접속 가능 여부 (상태 조회 쿼리) | 성공, 응답 < 500ms | 성공, 응답 500ms 이상 | 연결 실패/인증 실패/시간 초과(5초) |
| 연결 사용률 (현재 연결 수 / `max_connections`) | < 70% | 70% 이상 90% 미만 | 90% 이상 |
| 오래 실행 중인 쿼리 (`active` 상태 경과) | 5분 이상 0건 | 5분 이상 1건 이상 | 30분 이상 1건 이상 |
| `idle in transaction` 세션 경과 | 5분 이상 0건 | 5분 이상 1건 이상 | 30분 이상 1건 이상 |
| 잠금 대기 세션 (1분 이상 대기) | 0건 | 1~4건 | 5건 이상 |
| 버퍼 캐시 적중률 (직전 조회 대비 증가분 기준) | 95% 이상 | 90% 이상 95% 미만 | 90% 미만 |
| 데드락 (직전 조회 대비 증가분) | 0 | 1 이상 | - |
| 트랜잭션 ID 나이 (DB별 `datfrozenxid` 나이 최댓값) | 5억 미만 | 5억 이상 10억 미만 | 10억 이상 |
| 복제 지연 (standby가 있을 때, replay 기준) | 10초 미만 | 10초 이상 60초 미만 | 60초 이상 또는 standby 연결 끊김 |

- 추가 표시(상태 판단 없음): DB별 크기, 커밋/롤백 초당 수, 상태별 세션 수(active / idle / idle in transaction), 가장 오래된 세션 목록(사용자, DB, 상태, 경과 시간, 대기 이벤트 유형. **쿼리 원문 제외**).
- DB 카드 상태 = 쿠버네티스 쪽 + DB 내부 전체의 최악 상태. DB 파드가 떠 있는데 접속이 안 되면 장애, DB 파드가 없어서 접속이 안 되면 파드 쪽 장애가 대표 사유가 된다.
- 캐시 적중률은 조회 간격 동안 블록 읽기가 너무 적으면(가정: 1,000블록 미만) 판단하지 않고 이전 상태를 유지한다.

## 4. 갱신 주기

| 대상 | 방식 | 화면 반영 목표 |
|---|---|---|
| 노드, 파드, 워크로드, PVC, 이벤트 | 쿠버네티스 Watch로 API 서버 메모리에 유지 → SSE로 변경분 전달 | 변화 후 **3초 이내** |
| CPU·메모리 (metrics-server) | **15초** 간격 조회 → SSE | 15초 |
| DB 내부 통계 | **15초** 간격 조회 → SSE | 15초 |
| 시간 경과로 바뀌는 판단(Pending 10분 등) | API가 **15초**마다 재평가 | 15초 |
| 추이 그래프 표본 | 15초 표본, 최근 1시간 보관 (Prometheus 있으면 그 쿼리, 30초 해상도) | 15초 |

- 브라우저는 페이지 진입 시 전체 스냅샷 1회 + 이후 SSE 변경분. SSE가 끊기면 자동 재연결하고, 재연결 시 전체 스냅샷을 다시 받는다.
- 클러스터·DB를 조회하는 쪽은 API 서버 하나뿐. 브라우저 탭 수와 무관하게 조회 부하가 일정해야 한다.

## 5. 수용 기준

**공통**
- [ ] Given `DATA_SOURCE=mock`, kubeconfig·DB가 없음 / When `docker compose` 없이 api·web을 띄우고 대시보드를 연다 / Then 모든 화면(개요, 노드, 워크로드, 파드, 이벤트, DB)이 오류 없이 보이고 "MOCK 데이터" 배지가 표시된다.
- [ ] Given mock 모드 / Then 정상·주의·장애·알 수 없음·데이터 오래됨 상태가 **각 영역에서 한 번 이상** 재현된다(예: CrashLoopBackOff 파드, NotReady 노드, ready 0 Deployment, 연결 사용률 92% DB).
- [ ] Given mock 모드 / When 몇 분간 화면을 켜 둔다 / Then 값이 주기적으로 바뀌어 SSE 갱신이 동작하는 것이 보인다.
- [ ] Given `DATA_SOURCE=live`인데 kubeconfig가 없음 / When API를 시작 / Then API는 죽지 않고 클러스터 영역을 "알 수 없음(클러스터 연결 없음)"으로 표시한다.
- [ ] 모든 상태 배지 옆에 판단 이유가 한 줄로 표시된다.
- [ ] 대시보드는 쿠버네티스 API와 DB에 조회(get/list/watch, SELECT)만 한다. RBAC에 쓰기 동사와 secrets 접근이 없다.

**노드·파드·워크로드**
- [ ] Given 파드가 CrashLoopBackOff에 들어감 / When 3초가 지남 / Then 파드 목록 맨 위에 장애로 표시되고 요약 띠 전체 상태가 장애가 된다.
- [ ] Given 파드가 최근 1시간에 3회 재시작 / Then 장애, 1~2회면 주의로 표시된다.
- [ ] Given 노드 Ready가 `Unknown`이 됨 / When 60초 미만 / Then 주의, 60초 이상이면 장애.
- [ ] Given Deployment desired 3, ready 0 / Then 장애. ready 2면 주의.
- [ ] Given 노드 CPU 사용률이 한 번만 95% / Then 상태가 바뀌지 않고, 연속 3회면 장애가 된다.
- [ ] 파드 상세에서 소속 워크로드·노드·관련 Warning 이벤트로 이동할 수 있다.

**DB**
- [ ] Given 연결 사용률 92% / Then DB 카드 장애, 판단 이유 "연결 92% (max 100)".
- [ ] Given DB 접속 실패 / Then DB 장애, 다른 영역 상태에는 영향이 없다.
- [ ] 세션 목록에 쿼리 원문이 나오지 않는다.
- [ ] Given standby 없음 / Then 복제 영역이 "해당 없음"으로 표시된다.

**연결·신선도**
- [ ] Given SSE 연결이 끊김 / Then "연결 끊김 - 마지막 갱신 시각" 배너가 뜨고, 재연결되면 사라지며 전체 값이 다시 맞춰진다.
- [ ] Given DB 통계가 45초 이상 갱신되지 않음 / Then DB 지표가 "데이터 오래됨"으로 바뀐다.
- [ ] Given metrics-server 없음 / Then CPU·메모리만 "알 수 없음"이고 나머지는 정상 동작한다.

## 6. 범위 밖

- 파드 재시작, 스케일 조정, cordon/drain, 로그 스트리밍, exec 등 **모든 조작** (조회 전용 원칙)
- 컨테이너 로그 보기 (별도 명세 필요)
- 알림 발송(Slack/메일), 알림 규칙 편집 UI — 기준값은 이번에는 코드/설정값으로 고정
- 1시간을 넘는 이벤트 보관, 장기 메트릭 저장소 구축
- 다중 클러스터, 클러스터 밖 RDS 등 다른 DB
- 앱 내 로그인·권한 관리 (가정 A5)
- 비용 (→ `aws-cost`), 개선 제안 (→ `architecture-advisor`)

## 7. 역할별 전달 사항

**디자인**
- 4단계 상태 + "데이터 오래됨"의 색·아이콘·텍스트를 정한다. 색만으로 구분하지 않는다(아이콘/텍스트 병기).
- 개요 화면: 상단 요약 띠 + 영역 카드 5개(노드, 워크로드, 파드, 이벤트, DB). 카드마다 상태 배지, 개수, 대표 사유.
- 목록 화면(노드/워크로드/파드/이벤트)과 상세 화면(파드, 노드, DB). 파드 목록은 수백 개 행을 다룰 수 있어야 한다(필터: 네임스페이스, 상태, 시스템 숨기기, 검색).
- 연결 끊김 배너, MOCK 배지, "근사치" 라벨, 그래프 기준선 표기 방식.

**퍼블리싱**
- 공용 UI: 상태 배지(4단계 + 오래됨), 상태 카드, 판단 이유 텍스트, 사용률 막대(주의/장애 구간 표시), 정렬·필터 가능한 표, 배너.
- `aws-cost`, `architecture-advisor`에서도 같은 배지·카드를 재사용한다.

**프론트**
- 초기 스냅샷 + SSE 변경분 병합, 재연결 시 전체 재동기화.
- "데이터 오래됨" 판정은 서버가 준 마지막 갱신 시각 기준으로 화면에서도 표시(서버가 멈춘 경우 대비).
- 추이 그래프(가정 A4: 최근 1시간, Prometheus 있으면 24시간까지).

**백엔드**
- 상태 판단(3절의 모든 기준)은 **서버에서** 계산해 상태와 판단 이유를 함께 내려준다. 화면은 계산하지 않는다. 기준값은 한곳에 모아 설정으로 바꿀 수 있게 한다.
- 최근 1시간 재시작, 지속 조건(연속 3회, 60초, 2분/10분 등)을 위한 상태 이력을 서버가 유지한다.
- `DATA_SOURCE=mock`: 5절의 모든 상태를 재현하는 mock 데이터와, 시간에 따라 값이 바뀌는 시뮬레이션.
- 읽기 전용 RBAC(`deploy/rbac.yaml`): HANDOFF 3절 목록 + 후속 기능(`aws-cost`, `architecture-advisor`)이 요구하는 services, ingresses, poddisruptionbudgets, horizontalpodautoscalers의 get/list/watch. secrets·configmaps 제외.
- DB 설정값: 대상 StatefulSet(네임스페이스/이름), 접속 정보(모니터링 계정은 `.env`), Prometheus 주소(선택).
- API 계약(`docs/api/cluster-status.md`)에 SSE 이벤트 종류와 "데이터 오래됨"을 위한 지표별 마지막 갱신 시각을 포함.

**DBA**
- 모니터링 전용 읽기 계정 생성 스크립트(최소 권한, 쓰기 불가)와 `.env.example` 항목.
- 3.7의 지표를 얻는 조회 쿼리. 조회가 대상 DB에 부담을 주지 않아야 한다(15초 주기, 각 쿼리 타임아웃).
- 세션 정보에서 쿼리 원문을 가져오지 않거나 API 밖으로 나가지 않게 한다.
- PVC 사용량의 정확한 출처가 없을 때 쓸 근사치 방법 확인.
